# SSRF: сценарии (URL от пользователя, метаданные облака), защита

> **TL;DR:** SSRF (Server-Side Request Forgery) — сервер, по указанию пользователя, делает HTTP-запрос туда, куда пользователь сам напрямую попасть не может: во внутреннюю сеть за файрволом, к localhost-сервисам самого сервера, или к эндпоинту метаданных облачного провайдера, откуда можно вытащить учётные данные инстанса. Сервер в этом сценарии выступает **прокси для атакующего** в сеть, к которой у него нет прямого доступа — используя доверие, которым сервер обладает как участник внутренней инфраструктуры.

## Типичный уязвимый сценарий — превью ссылок

```ts
// пользователь присылает URL, сервер его фетчит, чтобы показать превью (og:title, og:image)
@Post('link-preview')
async getPreview(@Body() dto: { url: string }) {
  const response = await fetch(dto.url); // <- сервер фетчит ЛЮБОЙ URL, который прислал пользователь
  return parseOpenGraphTags(await response.text());
}
```

```
Легитимное использование: { "url": "https://example.com/article" }
Атака: { "url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name" }
       -> AWS EC2 metadata endpoint, доступный БЕЗ аутентификации с самого инстанса
       -> ответ содержит временные IAM-учётные данные инстанса
Атака: { "url": "http://localhost:6379/" }
       -> Redis на том же хосте/внутренней сети, недоступный снаружи напрямую
Атака: { "url": "http://internal-admin-panel.corp.local/users" }
       -> внутренний сервис, защищённый только тем, что "недоступен из интернета" (security through obscurity)
```

Метаданные облака (`169.254.169.254` — link-local адрес, единый для AWS/GCP/Azure/большинства облаков) — самая опасная и частая цель: этот эндпоинт исторически не требовал аутентификации именно потому, что "доступен только с самого инстанса" считалось достаточной защитой — SSRF полностью обходит это допущение, потому что запрос физически **исходит** с самого инстанса (от имени сервера, а не пользователя), просто по указанию атакующего.

## Почему это не "просто фетч чужого URL"

Разница с обычным клиентским запросом — сетевая позиция. Браузер пользователя не может напрямую достучаться до `169.254.169.254` **вашего** облачного инстанса или до внутреннего Redis за файрволом — эти адреса просто не маршрутизируются к нему из интернета. Сервер, выполняющий запрос **от своего имени** внутри той же приватной сети/облачного окружения, — может, и SSRF использует именно эту разницу в сетевой позиции: заставить доверенный компонент системы (backend-сервис) выполнить запрос, недоступный самому атакующему напрямую.

## Защита — многослойная, ни один слой не достаточен сам по себе

**1. Allowlist схем и хостов**, если это применимо к бизнес-задаче (например, известный набор доверенных доменов для интеграции) — самая надёжная защита, но не всегда применима (превью произвольных ссылок пользователя по определению не имеет фиксированного allowlist).

**2. Резолв DNS и проверка IP на приватные диапазоны — с учётом DNS rebinding:**

```ts
import { isIP } from 'net';
import dns from 'dns/promises';

const PRIVATE_RANGES = [/^127\./, /^10\./, /^172\.(1[6-9]|2\d|3[01])\./, /^192\.168\./, /^169\.254\./, /^::1$/];

async function isUrlSafe(rawUrl: string): Promise<boolean> {
  const url = new URL(rawUrl);
  if (!['http:', 'https:'].includes(url.protocol)) return false; // блокируем file://, gopher:// и т.п.

  const addresses = await dns.resolve4(url.hostname).catch(() => []);
  return addresses.every((ip) => !PRIVATE_RANGES.some((range) => range.test(ip)));
}
```

Наивная проверка "резолвим DNS один раз, проверяем IP, потом делаем `fetch(url)` по исходному hostname" уязвима к **DNS rebinding**: атакующий контролирует DNS-запись `evil-domain.com` и настраивает её так, чтобы при первом резолве (в момент проверки) она указывала на публичный безопасный IP, а при повторном резолве (когда HTTP-библиотека сама делает DNS lookup непосредственно перед соединением) — на `169.254.169.254`. Между проверкой и фактическим запросом — TOCTOU (time-of-check to time-of-use) окно. Правильная защита — резолвить IP один раз явно, и делать HTTP-запрос **по уже резолвленному IP** (с `Host`-заголовком, выставленным вручную под исходный hostname, если нужна поддержка виртуального хостинга/TLS SNI), а не полагаться на то, что библиотека резолвит тот же адрес повторно в момент соединения.

**3. Запрет или строгая перепроверка редиректов:**

```ts
const response = await fetch(url, { redirect: 'manual' }); // не следовать редиректам автоматически
if (response.status >= 300 && response.status < 400) {
  // редирект на новый URL — заново прогнать через ВСЮ проверку (включая DNS rebinding), не довериться слепо
}
```

Даже если исходный URL прошёл проверку, сервер по этому URL может ответить `302 Redirect` на внутренний адрес — если библиотека следует редиректам автоматически без повторной проверки каждого хопа, вся защита на входе обходится одним лишним прыжком.

**4. Сетевая изоляция (egress-контроль) как последний рубеж** — сервис, которому по бизнес-логике нужно фетчить произвольные внешние URL (превью ссылок, вебхуки), по возможности вынести в отдельный под/контейнер с ограниченными сетевыми правилами (не имеющий сетевого доступа к внутренней инфраструктуре — БД, Redis, admin-панелям, метаданным облака) — так, чтобы даже полностью успешный SSRF из этого сервиса не давал доступа никуда, кроме внешнего интернета, для которого он и предназначен.

## Что спрашивают на собеседовании

1. **Пользователь передаёт URL, сервер его фетчит (превью ссылок) — какие атаки и защита?** — SSRF к метаданным облака (`169.254.169.254`), внутренним сервисам за файрволом, localhost-портам; защита — allowlist где применимо, резолв DNS + проверка IP на приватные диапазоны с учётом DNS rebinding, запрет/перепроверка редиректов, сетевая изоляция сервиса как последний рубеж.
2. **Почему нельзя просто проверить IP по DNS один раз и потом сделать обычный `fetch` по hostname?** — DNS rebinding: между моментом проверки и моментом фактического соединения DNS-запись может измениться на другой IP (контролируемый атакующим) — TOCTOU-окно; нужно резолвить один раз и подключаться именно по этому IP.
3. **Почему метаданные облака (169.254.169.254) — такая частая цель SSRF?** — исторически не требуют аутентификации, потому что предполагалось, что доступны только с самого инстанса — SSRF полностью обходит это допущение, заставляя сам инстанс сделать запрос по указанию атакующего.
4. **Как редиректы могут обойти защиту от SSRF?** — исходный URL проходит все проверки, но ответ по нему — редирект на внутренний адрес; если библиотека следует редиректам автоматически без повторной проверки каждого хопа, защита на входе обходится.
5. **Что делать, если бизнес-задача требует фетчить произвольные внешние URL и allowlist в принципе неприменим?** — многослойная защита (проверка приватных диапазонов с учётом rebinding, запрет редиректов) плюс сетевая изоляция самого сервиса — вынести в окружение без доступа к внутренней инфраструктуре, чтобы SSRF не мог никуда, кроме открытого интернета.
