# Пароли: bcrypt/argon2, cost factor, соль, тайминг-safe сравнение

> **TL;DR:** `SHA-256(password)` — не хеш для паролей, а криптографическая ошибка: SHA-256 спроектирован быть **быстрым** (это нужно для проверки целостности файлов, не для защиты паролей) — на современном GPU можно перебрать миллиарды SHA-256-хешей в секунду, что делает brute-force по словарю/маскам практичным даже с солью. bcrypt/argon2 спроектированы быть **медленными и настраиваемо дорогими** — специально, чтобы перебор был вычислительно неприемлем, даже если атакующий получил всю базу хешей.

## Почему "SHA-256 с солью" — недостаточно

```
SHA-256(password + salt) — соль защищает от rainbow-table (предвычисленных таблиц),
                             но НЕ защищает от прямого перебора конкретного хеша,
                             потому что SHA-256 вычисляется за наносекунды
```

Соль (уникальная случайная строка на каждый пароль) решает одну конкретную проблему — атакующий не может использовать одну предвычисленную rainbow-table для взлома сразу всей базы (у каждого пароля эффективно свой "алфавит" из-за уникальной соли). Она не решает другую: если у атакующего есть хеш конкретного пользователя (утечка БД), скорость SHA-256 (миллиарды вычислений в секунду на современном GPU/ASIC) делает перебор по словарю с мутациями/масками реалистичной атакой за разумное время для паролей средней сложности. Соль — необходимое, но недостаточное условие; специализированный медленный алгоритм — то, что реально ограничивает скорость перебора.

## bcrypt — cost factor

```ts
import bcrypt from 'bcrypt';

const hash = await bcrypt.hash(password, 12); // cost factor = 12
// внутри: 2^12 = 4096 раундов Blowfish-based хеширования — соль генерируется автоматически, встроена в результат
// $2b$12$N9qo8uLOickgx2ZMRZoMye... — сам хеш содержит алгоритм, cost, соль и результат одной строкой

const isValid = await bcrypt.compare(password, hash); // сравнение — тоже через bcrypt, тайминг-safe по конструкции
```

Cost factor — степень двойки (`2^cost` раундов) — увеличение на 1 **удваивает** время вычисления одного хеша. Выбор конкретного значения — компромисс между "достаточно медленно для защиты" и "достаточно быстро, чтобы не создавать заметную задержку легитимному логину" — практический ориентир: подбирать cost так, чтобы хеширование одного пароля занимало **около 100-250мс** на реальном продакшен-железе (не на слабой dev-машине), пересматривая значение по мере роста вычислительной мощности атакующих со временем (то, что было безопасным cost в 2015, сегодня недостаточно — параметр должен периодически пересматриваться вверх). Соль в bcrypt генерируется автоматически и встроена прямо в итоговую строку хеша — не нужно хранить её отдельным полем.

## Argon2 — почему считается сильнее bcrypt

```ts
import argon2 from 'argon2';

const hash = await argon2.hash(password, {
  type: argon2.argon2id, // гибрид: устойчив и к GPU/ASIC-перебору, и к side-channel атакам
  memoryCost: 19456, // ~19MB памяти на одно вычисление
  timeCost: 2,        // число итераций
  parallelism: 1,
});
```

Argon2 — победитель [Password Hashing Competition](https://www.password-hashing.net/) (2015) — спроектирован **memory-hard**: требует значительного объёма памяти (не только времени CPU) на каждое вычисление хеша. Это принципиальное отличие от bcrypt, который CPU-intensive, но не memory-intensive — GPU и специализированные ASIC-чипы для перебора хешей исторически оптимизированы под параллельные вычисления с минимальным использованием памяти на поток; algorithm, требующий заметного объёма памяти **на каждую** попытку, резко снижает выгоду от массового параллелизма такого оборудования (памяти на чипе физически не хватает, чтобы держать тысячи параллельных попыток одновременно, как это возможно для чисто CPU-bound bcrypt). Три варианта Argon2 — `argon2d` (максимальная устойчивость к GPU-перебору, но уязвим к side-channel через время доступа к памяти), `argon2i` (устойчив к side-channel, но чуть слабее против чистого GPU-перебора), `argon2id` (гибрид, рекомендуемый по умолчанию — используется большинством современных руководств, включая OWASP).

## Тайминг-safe сравнение

```ts
// bcrypt.compare / argon2.verify УЖЕ реализуют это внутри — сравнение результата с исходным хешем
// НЕ через простое ===, что создавало бы теоретическую timing-attack поверхность
```

Библиотеки `bcrypt`/`argon2` инкапсулируют не только хеширование, но и безопасное сравнение — разработчику не нужно вручную писать `timingSafeEqual` поверх них (в отличие от, например, сравнения HMAC-подписи webhook вручную, см. [Webhooks: подпись, retries, идемпотентность на приёмнике](../05-api-communication/11-webhooks.md), где именно разработчик отвечает за constant-time сравнение). Единственное, за чем стоит следить, — не пытаться "оптимизировать" проверку пароля собственноручным сравнением байт хешей через `===`/`Buffer.equals` в обход `compare`/`verify` функций библиотеки.

## Что спрашивают на собеседовании

1. **Почему нельзя хранить пароли как `SHA-256(password + salt)`?** — SHA-256 спроектирован быть быстрым — соль защищает от rainbow-table, но не от прямого перебора конкретного хеша на GPU/ASIC на практически приемлемой скорости; нужен намеренно медленный/дорогой алгоритм.
2. **Что такое cost factor в bcrypt и как его выбирать?** — степень двойки, определяющая число раундов хеширования (`2^cost`); выбирается так, чтобы одно вычисление занимало ~100-250мс на реальном продакшен-железе, периодически пересматривается вверх по мере роста вычислительных мощностей атакующих.
3. **Чем argon2 лучше bcrypt?** — memory-hard конструкция: требует заметного объёма памяти на вычисление, что резко снижает выгоду от массового параллелизма GPU/ASIC-перебора, оптимизированного под минимальное использование памяти на поток — bcrypt CPU-intensive, но не memory-intensive.
4. **Зачем нужна соль, если алгоритм и так медленный?** — соль защищает от предвычисленных rainbow-таблиц на всю базу сразу — без неё одинаковые пароли у разных пользователей дают одинаковый хеш, и одна таблица атакует всех сразу; медленность алгоритма отдельно защищает от прямого перебора конкретного хеша.
5. **`argon2id` vs `argon2d` vs `argon2i` — какой выбрать и почему?** — `argon2id` — рекомендуемый гибрид: устойчив и к GPU-перебору (как `argon2d`), и к side-channel атакам через паттерны доступа к памяти (как `argon2i`).
