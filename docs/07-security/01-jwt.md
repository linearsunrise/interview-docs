# JWT: структура, подпись (HS256 vs RS256), хранение, почему нельзя «отозвать»

> **TL;DR:** JWT — не зашифрован, а **подписан**: `header.payload.signature`, где `payload` — обычный base64url (не base64, отличие в алфавите — без `+`/`/`, без padding), который читает кто угодно без ключа — секретность данных подпись не даёт, только целостность (payload не подделан). Главное структурное следствие — сервер не хранит состояние сессии, поэтому у обычного JWT нет способа "отозвать" его до истечения TTL, кроме поддержания отдельного стейта (denylist), что частично убивает саму идею stateless-токена.

## Структура

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJyb2xlIjoiYWRtaW4ifQ.4f8s...
└── header (base64url) ─┘└── payload (base64url) ─────────┘└ signature ┘

header:  { "alg": "HS256", "typ": "JWT" }
payload: { "sub": "123", "role": "admin", "exp": 1234567890 }
```

```js
JSON.parse(atob(token.split('.')[1])); // прочитает любой, ключ не нужен — это не шифрование
```

Частая ошибка кандидата — "JWT зашифрован" (см. чек-лист красных флагов в [index.md](./index.md)): payload доступен для чтения без знания секрета, поэтому в него **нельзя** класть чувствительные данные (пароли, номера карт, PII без необходимости) — только то, что не страшно раскрыть клиенту/перехватчику. Подпись защищает от **подделки** (изменить `role: user` на `role: admin` без знания секрета невозможно — пересчитанная подпись не совпадёт), не от чтения.

## HS256 vs RS256 — кто может проверять, кто может подписывать

```
HS256 (HMAC + SHA-256): один общий секрет
  signature = HMAC-SHA256(header + "." + payload, secret)
  Тот, кто может ПРОВЕРИТЬ подпись — знает secret — а значит, может и ПОДПИСАТЬ новый токен

RS256 (RSA + SHA-256): пара приватный/публичный ключ
  signature = RSA-SIGN(header + "." + payload, privateKey)
  Проверка — публичным ключом (verify), подписание — только приватным (sign)
  Знание публичного ключа НЕ даёт возможности подписать новый токен
```

Практическое следствие для микросервисной архитектуры: если токен выдаёт auth-сервис, а проверяют его десятки других сервисов — с HS256 каждый проверяющий сервис обязан знать тот же секрет, что и auth-сервис, а значит теоретически способен сам подписывать (подделывать) токены — расширение зоны доверия на все сервисы, которым это физически не нужно. RS256 решает это разделением ролей: auth-сервис держит приватный ключ и подписывает, остальные сервисы получают только публичный ключ и могут проверять, но не подписывать — компрометация одного из проверяющих сервисов не даёт атакующему возможности выпускать поддельные токены.

## `alg: none` — классическая уязвимость валидации

```json
{ "alg": "none", "typ": "JWT" }
```

Часть библиотек в ранних версиях позволяла указать `alg: none` в заголовке — сервер, не проверяющий явно ожидаемый алгоритм на своей стороне (а просто "доверяющий" значению из самого токена), принимал токен без подписи вообще. Правильная защита — не полагаться на `alg` из токена, а **явно** указывать библиотеке верификации ожидаемый алгоритм (`jwt.verify(token, key, { algorithms: ['RS256'] })`) — если атакующий пришлёт токен с `alg: none` или подменит RS256 на HS256 (используя публичный RSA-ключ как HMAC-секрет — ещё одна классическая атака "algorithm confusion"), верификация с явно закреплённым списком допустимых алгоритмов отклонит его.

## Где хранить на клиенте

| Хранилище | XSS-риск | CSRF-риск | Комментарий |
|---|---|---|---|
| `localStorage`/`sessionStorage` | доступен любому JS на странице — украдён при XSS | нет (не прикладывается браузером автоматически) | простая интеграция, но полная незащищённость от XSS |
| `httpOnly` cookie | недоступен JS — не украдён напрямую при XSS | да, если нет защиты (SameSite/CSRF-токен) | защищает от чтения через XSS, требует защиты от CSRF отдельно |
| in-memory (переменная в рантайме SPA) | недоступен для чтения через инъекцию innerHTML и т.п. напрямую, но доступен через выполнение произвольного JS в контексте страницы | нет | теряется при обновлении страницы (нужен refresh flow) |

Подробный разбор компромисса XSS vs CSRF в зависимости от места хранения — в [03-sessions-vs-jwt.md](./03-sessions-vs-jwt.md) и [09-csrf.md](./09-csrf.md).

## Почему JWT нельзя просто «отозвать»

Сервер, проверяющий JWT, делает это **без похода в БД** — вся необходимая информация (валидность подписи + `exp`) содержится в самом токене. Это и есть весь смысл statless-аутентификации (не нужно хранилище сессий, любой инстанс сервиса проверяет токен локально). Но именно поэтому "отозвать" конкретный токен раньше `exp` невозможно без нарушения этого свойства — единственные практические варианты:
- **Короткий TTL** (минуты, не часы) + **refresh flow** — компрометация access-токена ограничена коротким окном (детали — в [02-access-refresh-tokens.md](./02-access-refresh-tokens.md));
- **Denylist отозванных токенов** (Redis, TTL = оставшееся время жизни токена) — сервер всё же делает доп. проверку "не в чёрном ли списке" на каждый запрос — частично возвращает statefulness, которую JWT должен был убрать;
- **Версионирование** — хранить `tokenVersion` у пользователя в БД, класть его же в payload токена, при логауте/смене пароля инкрементировать в БД — токены со старой версией отклоняются при следующей проверке (тоже требует похода к БД/кэшу, но дешевле полноценного denylist на каждый отдельный токен).

## Что спрашивают на собеседовании

1. **JWT зашифрован?** — нет, подписан: payload читается без ключа кем угодно (base64url — не шифрование), подпись защищает только от подделки, не от чтения.
2. **Чем HS256 отличается от RS256 и когда что выбрать?** — HS256 — общий секрет, кто проверяет, тот может и подписать; RS256 — приватный ключ подписывает, публичный только проверяет — важно для архитектур, где проверяющих сервисов много, а доверять подписание им не нужно.
3. **Что такое атака `alg: none`/algorithm confusion и как защититься?** — сервер, доверяющий алгоритму из самого токена, может быть обманут; защита — явно фиксировать ожидаемый алгоритм на стороне верификации, не брать его из токена.
4. **Почему JWT нельзя отозвать до истечения TTL?** — проверка токена stateless, без похода в БД — вся валидность закодирована в самом токене; отзыв требует либо короткого TTL + refresh, либо явного возврата state (denylist/версионирование), что частично убивает смысл stateless-подхода.
5. **Где хранить JWT на клиенте?** — trade-off XSS vs CSRF: localStorage уязвим к чтению через XSS, httpOnly cookie защищает от чтения, но требует защиты от CSRF — конкретный выбор зависит от модели угроз приложения.
