# Rate limiting: алгоритмы (token bucket, sliding window), распределённый на Redis

> **TL;DR:** Rate limiting не сводится к "посчитать запросы за минуту" — наивная реализация (fixed window через `INCR`) имеет структурную дыру на границе окна, позволяющую пропустить вдвое больше запросов, чем задумано. Token bucket и sliding window решают это по-разному: token bucket допускает контролируемые всплески (burst) поверх средней скорости, sliding window даёт более точное и равномерное ограничение ценой большей сложности реализации. В распределённой системе (несколько инстансов API) лимит обязан быть общим — считать его локально на каждом инстансе означает, что реальный лимит умножается на число инстансов.

## Fixed window — простая реализация и её граничная проблема

```ts
// наивно: INCR с TTL на окно
async function isAllowed(userId: string, limit = 100, windowSec = 60): Promise<boolean> {
  const key = `rate:${userId}:${Math.floor(Date.now() / 1000 / windowSec)}`; // ключ меняется каждую минуту
  const count = await redis.incr(key);
  if (count === 1) await redis.expire(key, windowSec);
  return count <= limit;
}
```

```
Окно 1 [00:00-00:59]: пользователь делает 100 запросов в 00:00:59 (все в последнюю секунду окна) — ВСЕ разрешены
Окно 2 [01:00-01:59]: тот же пользователь делает ещё 100 запросов в 01:00:00 (сразу после смены окна) — ВСЕ разрешены
→ фактически 200 запросов за 1 секунду реального времени (00:59-01:00), при лимите "100 в минуту"
```

Проблема — окна жёстко привязаны к границам времени (например, к началу каждой календарной минуты), а не к скользящему интервалу "последние 60 секунд от текущего момента" — граница между двумя соседними окнами позволяет пройти до 2× лимита в узком промежутке времени вокруг этой границы. Простота реализации (один `INCR` + `EXPIRE`) — единственный плюс, граничная проблема — известная и почти всегда неприемлемая цена для реальной защиты.

## Sliding window — устраняет граничную проблему

**Sliding window log** — хранить временные метки каждого запроса, считать, сколько их попадает в последние N секунд:

```ts
async function isAllowedSlidingLog(userId: string, limit = 100, windowSec = 60): Promise<boolean> {
  const key = `rate:${userId}`;
  const now = Date.now();
  const windowStart = now - windowSec * 1000;

  const multi = redis.multi();
  multi.zremrangebyscore(key, 0, windowStart); // выкинуть записи старше окна
  multi.zadd(key, now, `${now}-${Math.random()}`); // добавить текущий запрос (уникальный member)
  multi.zcard(key); // посчитать оставшиеся в окне
  multi.expire(key, windowSec);
  const [, , count] = await multi.exec();

  return (count as number) <= limit;
}
```

Точен (реальное "последние 60 секунд", без граничных эффектов fixed window), но хранит запись на **каждый** запрос — память растёт пропорционально трафику, а не константна, как в fixed window. Компромисс — **sliding window counter**: не хранить каждый запрос отдельно, а взвешенно комбинировать счётчик текущего fixed-window-интервала со счётчиком предыдущего, пропорционально тому, какая доля предыдущего окна ещё "видна" из скользящего окна текущего момента — приближение sliding log с константной памятью (два счётчика вместо лога), которое использует, например, Cloudflare в описанном ими алгоритме.

## Token bucket — контролируемые всплески

```ts
// концептуально: "ведро" на N токенов, пополняется с фиксированной скоростью, каждый запрос тратит 1 токен
async function isAllowedTokenBucket(userId: string, capacity = 20, refillPerSec = 1): Promise<boolean> {
  const key = `bucket:${userId}`;
  const now = Date.now() / 1000;
  const bucket = await redis.hgetall(key); // { tokens, lastRefill }

  const elapsed = now - (Number(bucket.lastRefill) || now);
  const tokens = Math.min(capacity, (Number(bucket.tokens) || capacity) + elapsed * refillPerSec);

  if (tokens < 1) return false;
  await redis.hset(key, { tokens: tokens - 1, lastRefill: now });
  return true;
}
```

Ведро пополняется непрерывно (например, 1 токен в секунду) до ёмкости `capacity` — если пользователь не делал запросов какое-то время, ведро "накопило" токены, и он может сделать **всплеск** запросов (до `capacity` штук) сразу, после чего ограничен средней скоростью пополнения. Это отличает token bucket от sliding window: token bucket сознательно допускает burst поверх средней скорости (что часто ближе к реальному паттерну использования API — не равномерный поток, а пачками), sliding window ограничивает более жёстко и равномерно, без права на всплеск.

## Распределённый rate limiter — почему `INCR` per-instance не работает

```
3 инстанса API за балансировщиком, каждый считает лимит В СВОЕЙ ПАМЯТИ
→ реальный лимит для пользователя = заявленный лимит × 3 (по одному "полному" лимиту на каждый инстанс, который он может достичь)
```

Если каждый инстанс приложения хранит счётчик локально (в памяти процесса), пользователь, чьи запросы балансировщик раскидывает по разным инстансам, эффективно обходит лимит кратно числу инстансов — при масштабировании нагрузка на защищаемый ресурс растёт пропорционально числу реплик API, что прямо противоречит цели rate limiting. Решение — единый общий счётчик в Redis (как в примерах выше), доступный всем инстансам одинаково — лимит остаётся верным независимо от того, на какой инстанс балансировщик направил конкретный запрос.

**Атомарность через Lua-скрипт** — отдельная операция `GET` + `INCR` (или `HGETALL` + вычисление + `HSET`, как в примере token bucket выше) из нескольких команд не атомарна сама по себе: между чтением и записью другой параллельный запрос того же пользователя может вклиниться (race condition, недосчёт лимита под высокой параллельной нагрузкой). `redis.multi()`/pipeline снижает часть риска, но для сложной логики (token bucket с вычислением) правильная практика — выполнить всю проверку-и-обновление одним Lua-скриптом через `EVAL` — Redis гарантированно выполняет весь скрипт атомарно, без возможности гонки между чтением текущего состояния и его обновлением.

## Что спрашивают на собеседовании

1. **Как устроен распределённый rate limiter на Redis? Почему наивный `INCR` имеет граничную проблему?** — общий счётчик в Redis, доступный всем инстансам приложения; fixed window через `INCR`+`EXPIRE` позволяет до 2× лимита запросов в узком промежутке вокруг границы соседних окон, потому что окна жёстко привязаны к календарным интервалам, а не скользят.
2. **Token bucket vs sliding window — какие trade-offs?** — token bucket сознательно допускает контролируемые всплески поверх средней скорости (ближе к реальному паттерну использования API); sliding window даёт более равномерное и точное ограничение без права на burst, ценой большей сложности реализации.
3. **Почему нельзя просто считать лимит в памяти каждого инстанса приложения?** — реальный лимит для пользователя умножается на число инстансов, между которыми балансировщик распределяет его запросы — при масштабировании защита слабеет пропорционально росту числа реплик.
4. **Зачем нужен Lua-скрипт для rate limiter в Redis, если можно использовать `MULTI`/pipeline?** — сложная логика (например, token bucket с вычислением пополнения) требует чтения текущего состояния и его обновления как единой неделимой операции — `EVAL` со скриптом гарантирует атомарность выполнения всего скрипта, устраняя гонку между параллельными запросами, которую pipeline сам по себе не устраняет для многошаговой логики.
5. **Sliding window log vs sliding window counter — в чём разница?** — log хранит временную метку каждого запроса (точно, но память растёт с трафиком); counter комбинирует счётчики текущего и предыдущего fixed-окна пропорционально видимой доле предыдущего — приближение с константной памятью.
