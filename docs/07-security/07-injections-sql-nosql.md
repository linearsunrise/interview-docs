# SQL-инъекции и параметризация; NoSQL-инъекции

> **TL;DR:** Инъекция — всегда одна и та же ошибка: данные, пришедшие от пользователя, интерпретируются как **код/структура запроса**, а не как **значение**. Параметризованные запросы решают это структурно (не "экранированием строк", а тем, что движок БД физически получает данные отдельным каналом от текста запроса) — SQL-инъекция при правильном использовании параметризации становится архитектурно невозможной, а не просто маловероятной. NoSQL-инъекция — та же идея, но через операторы запроса (`$where`, `$ne`), а не через синтаксис SQL.

## SQL-инъекция — классика через конкатенацию

```ts
// уязвимо: пользовательский ввод становится частью текста SQL
const users = await dataSource.query(
  `SELECT * FROM users WHERE email = '${dto.email}'`
);
// dto.email = "' OR '1'='1" -> WHERE email = '' OR '1'='1' -> возвращает ВСЕХ пользователей
// dto.email = "'; DROP TABLE users; --" -> при поддержке multi-statement — уничтожение таблицы
```

```ts
// безопасно: параметризованный запрос — значение передаётся ОТДЕЛЬНО от текста запроса
const users = await dataSource.query(
  `SELECT * FROM users WHERE email = $1`, [dto.email]
);
```

Разница не в "экранировании кавычек" (хотя это тоже снижает риск для наивных случаев) — при параметризации СУБД получает текст запроса и значения параметров как **раздельные** данные по протоколу, разбирает и планирует запрос **до** подстановки значений — значение физически не может изменить структуру запроса, вне зависимости от того, что в нём написано (хоть `'; DROP TABLE users; --` целиком). ORM (TypeORM, Prisma) параметризуют запросы автоматически для стандартных методов (`find`, `save`, query builder с `.where('email = :email', { email })`) — инъекция обычно проникает именно там, где разработчик сознательно уходит от ORM-абстракции в сырой SQL через `query()`/`$queryRawUnsafe` и конкатенирует строки вручную.

```ts
// Prisma: $queryRaw с template literal — безопасно (Prisma параметризует автоматически)
await prisma.$queryRaw`SELECT * FROM users WHERE email = ${dto.email}`;
// Prisma: $queryRawUnsafe — НЕ параметризовано, буквальная конкатенация строки, как имя намекает
await prisma.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${dto.email}'`); // уязвимо
```

## NoSQL-инъекция — через операторы запроса, не синтаксис

```ts
// уязвимо: req.body напрямую используется как объект query MongoDB
app.post('/login', async (req, res) => {
  const user = await db.collection('users').findOne({
    email: req.body.email,
    password: req.body.password, // если это ОБЪЕКТ, а не строка...
  });
});
```

```json
// вместо строки клиент присылает оператор MongoDB прямо в JSON-теле запроса
{ "email": "admin@example.com", "password": { "$ne": null } }
```

MongoDB-запрос строится напрямую из объекта — если `password` в присланном JSON окажется не строкой, а объектом с оператором `$ne` (или `$gt`, `$regex` и т.п.), итоговый запрос интерпретирует это как условие "пароль не равен `null`" — что истинно почти всегда, аутентификация обходится без знания реального пароля. Это структурно та же проблема, что SQL-инъекция (данные пользователя меняют **смысл** запроса), просто механизм другой — через встроенные операторы объектного языка запросов, а не через текстовый синтаксис.

**Защита:**
```ts
// 1. Валидация типа/схемы ДО использования в запросе — DTO с class-validator (см. NestJS Pipes)
class LoginDto {
  @IsEmail() email: string;
  @IsString() @MinLength(8) password: string; // ЯВНО ожидаем строку — объект-оператор провалит валидацию
}

// 2. Явное экранирование операторов в библиотеках типа mongo-sanitize
import sanitize from 'mongo-sanitize';
const clean = sanitize(req.body); // удаляет ключи, начинающиеся с '$' и содержащие '.'
```

Валидация DTO через `class-validator`/`ValidationPipe` (см. [Pipes и валидация](../03-nestjs/07-pipes.md)) — первая и самая надёжная линия защиты: если поле объявлено как `@IsString()`, объект `{ "$ne": null }` вместо строки не пройдёт валидацию и запрос будет отклонён на этапе pipe, до того как вообще дойдёт до слоя работы с БД.

## Общий принцип защиты — не полагаться на один слой

- **Всегда параметризованные запросы** для SQL — никакого построения текста запроса конкатенацией пользовательского ввода, даже "только для внутреннего скрипта" (внутренние инструменты тоже становятся вектором, если получают данные из внешнего источника — файл, API, форма).
- **Валидация типов на границе** (DTO validation) — для NoSQL это особенно критично, потому что сама инъекция происходит через "неправильный тип", а не "неправильный текст".
- **Наименьшие привилегии для учётной записи БД, используемой приложением** — даже если инъекция каким-то образом обойдёт защиты, аккаунт без прав `DROP TABLE`/на чужие схемы ограничивает ущерб.
- **ORM/query builder как норма**, сырой SQL/`$queryRawUnsafe` — осознанное исключение с отдельным ревью, не дефолтный путь написания запроса.

## Что спрашивают на собеседовании

1. **Почему параметризация защищает от SQL-инъекции лучше, чем экранирование кавычек?** — параметр передаётся СУБД отдельно от текста запроса на уровне протокола — запрос разбирается и планируется до подстановки значения, значение физически не может изменить структуру запроса, что делает класс атаки архитектурно невозможным, а не просто менее вероятным.
2. **Покажите пример NoSQL-инъекции в MongoDB.** — присланный в теле запроса объект вместо строки (`{"password": {"$ne": null}}`) интерпретируется как оператор запроса, а не как значение для сравнения — обход аутентификации без знания реального пароля.
3. **Как защититься от NoSQL-инъекции, если параметризация как в SQL здесь не применима напрямую?** — строгая валидация типа поля на границе (DTO с `@IsString()` и т.п.) — объект-оператор не пройдёт валидацию строкового поля; дополнительно — явная санитизация ключей, начинающихся с `$`.
4. **Где в проекте на TypeORM/Prisma обычно "прячется" риск SQL-инъекции, если стандартные методы параметризованы автоматически?** — в местах, где разработчик сознательно уходит от ORM-абстракции в сырой SQL (`query()`, `$queryRawUnsafe`) и конкатенирует пользовательский ввод в текст запроса вручную.
5. **Достаточно ли одной параметризации/валидации, или нужны дополнительные меры?** — нет, defense in depth: наименьшие привилегии учётной записи БД приложения ограничивают ущерб даже при пропущенной инъекции где-то ещё в системе.
