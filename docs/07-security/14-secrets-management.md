# Секреты: env vs vault, ротация; helmet, валидация всех входных данных

> **TL;DR:** Переменные окружения — простой и повсеместно поддерживаемый способ передать конфигурацию/секреты процессу, но у них структурно нет ротации, аудита доступа и гранулярных прав — секрет либо есть у процесса целиком, либо его нет вообще. Vault-подобные системы (HashiCorp Vault, AWS Secrets Manager) добавляют то, чего env не даёт: секреты выдаются по запросу с ограниченным TTL, ротируются без передеплоя приложения, и каждый доступ логируется — то, что реально нужно для секретов с высокой ценой компрометации (ключи БД, платёжные API).

## env — простота ценой отсутствия контроля

```bash
DATABASE_URL=postgres://user:pass@host:5432/db
JWT_SECRET=...
STRIPE_SECRET_KEY=...
```

```ts
// NestJS ConfigModule читает .env, но САМ файл .env — не место для прод-секретов
ConfigModule.forRoot({ validationSchema: envValidationSchema });
```

Проблемы env-переменных как способа хранения секретов в проде: (1) **нет ротации без передеплоя** — смена пароля БД требует пересобрать/перезапустить процесс с новым значением переменной; (2) **риск утечки через побочные каналы** — переменные окружения попадают в дампы памяти при краше (crash dump), видны через `/proc/<pid>/environ` любому процессу с достаточными правами на той же машине, часто случайно логируются целиком при отладке (`console.log(process.env)`); (3) **нет аудита** — невозможно узнать, какой конкретно инстанс/когда обращался к секрету, в отличие от vault, где каждый запрос секрета — отдельная залогированная операция; (4) **`.env`-файл в репозитории** — классическая утечка, если файл случайно закоммичен (`.env` должен быть в `.gitignore` безусловно, а секреты для CI/CD — через secret-хранилище самого CI, не файл в репо).

## Vault / Secrets Manager — что добавляет

```ts
// концептуально: приложение запрашивает секрет по требованию, не хранит его постоянно в своём окружении
const dbCredentials = await vaultClient.read('database/creds/app-role');
// { username: 'v-app-role-xyz', password: '...', lease_duration: 3600 } — временные, авторотируемые
```

- **Динамические секреты с TTL** — вместо статичного пароля БД, зашитого в конфиг навсегда, Vault может сам создавать временную учётную запись в БД на каждый запрос с ограниченным сроком жизни — компрометация такого секрета имеет естественное окно истечения, не требующее ручной реакции.
- **Ротация без передеплоя** — смена секрета в vault сразу доступна приложению при следующем запросе (или через push-уведомление/polling), без пересборки и перезапуска процесса.
- **Аудит-лог** — каждый доступ к секрету залогирован (кто, когда, какой секрет) — необходимо для расследования инцидентов и compliance-требований (SOC2, PCI DSS и т.п.).
- **Гранулярные права доступа** — конкретный сервис получает доступ только к тем секретам, которые ему реально нужны (least privilege), а не ко всему пространству конфигурации целиком, как это часто происходит с общим `.env`-файлом, доступным всему процессу.

Цена — дополнительная инфраструктурная зависимость и сложность интеграции (клиентская библиотека, аутентификация самого приложения перед vault — обычно через отдельный механизм типа Kubernetes service account/IAM role, а не ещё один секрет, который снова нужно откуда-то взять). Практический ориентир: env-переменные приемлемы для конфигурации низкого риска (URL сервисов, feature-флаги) и небольших/ранних проектов; vault — оправдан, когда цена компрометации секрета высока (продовые ключи платёжных систем, доступ к PII) и организация готова нести цену дополнительной инфраструктуры.

## Валидация всех входных данных — граница доверия

```ts
class CreateOrderDto {
  @IsUUID() userId: string;
  @IsArray() @ValidateNested({ each: true }) @Type(() => OrderItemDto) items: OrderItemDto[];
  @IsOptional() @IsString() @MaxLength(500) notes?: string;
}
app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }));
```

Каждая точка входа данных извне (HTTP body/query/params, сообщения из очереди, вебхуки, файлы) — граница доверия, где предположения о форме и содержимом данных должны быть явно проверены, а не молчаливо приняты (см. подробный разбор `ValidationPipe` в [03-nestjs/07-pipes.md](../03-nestjs/07-pipes.md)). `whitelist: true` отбрасывает поля, не описанные в DTO (защита от "лишних" полей, которые могли бы случайно попасть в дальнейшую обработку — например, в SQL/NoSQL инъекцию через неожиданный тип поля, см. [07-injections-sql-nosql.md](./07-injections-sql-nosql.md)); `forbidNonWhitelisted: true` явно отклоняет запрос при наличии таких полей, а не тихо их игнорирует, что помогает раньше заметить клиентские баги/попытки зондирования API.

## `helmet` — базовый набор защитных заголовков одной строкой

```ts
import helmet from 'helmet';
app.use(helmet());
```

Устанавливает разумный набор HTTP-заголовков по умолчанию (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, базовый `Content-Security-Policy`, отключение `X-Powered-By`, раскрывающего конкретный фреймворк/версию потенциальному атакующему для таргетированного поиска известных уязвимостей) — минимальный барьер, не заменяющий остальные меры (валидацию, авторизацию, параметризацию запросов), но снижающий число тривиально устранимых недочётов конфигурации (см. категорию A05 Security Misconfiguration в [06-owasp-top10-node.md](./06-owasp-top10-node.md)).

## Что спрашивают на собеседовании

1. **Чем vault лучше env-переменных для хранения секретов?** — динамические секреты с ограниченным TTL, ротация без передеплоя приложения, аудит-лог каждого доступа, гранулярные права — ничего из этого структурно недоступно при хранении секрета как статичной переменной окружения.
2. **Какие риски у хранения секретов в `.env`-файле?** — случайный коммит файла в репозиторий, отсутствие ротации без пересборки процесса, видимость через `/proc/<pid>/environ` и crash dump другим процессам/пользователям с доступом к машине.
3. **Почему `whitelist: true` в ValidationPipe — важная защитная мера, а не просто удобство?** — отбрасывает поля, не описанные в DTO, до того как они попадут в дальнейшую обработку — снижает поверхность для NoSQL-инъекции через неожиданные поля/типы и случайного сохранения непредусмотренных данных.
4. **Что даёт `helmet()` и достаточно ли его для безопасности приложения?** — набор защитных HTTP-заголовков по умолчанию (CSP, отключение раскрывающих фреймворк заголовков, защита от MIME-sniffing и clickjacking) — необходимый, но далеко не достаточный минимум, не заменяющий валидацию входных данных, авторизацию и защиту от инъекций.
5. **Когда оправдана сложность внедрения vault, а когда env-переменных достаточно?** — зависит от цены компрометации конкретного секрета и требований compliance — высокорисковые продовые секреты (платежи, PII) оправдывают инфраструктурные затраты vault; низкорисковая конфигурация небольшого/раннего проекта — обычно нет.
