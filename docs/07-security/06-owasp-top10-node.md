# OWASP Top 10 применительно к Node.js: инъекции, broken access control, SSRF

> **TL;DR:** OWASP Top 10 — не список "экзотических атак", а ранжированный по реальной частоте/impact список категорий уязвимостей веб-приложений. На собеседовании ценнее не пересказать список наизусть, а для каждой категории уметь назвать **конкретное** место в типичном Node/Nest-сервисе, где она обычно возникает, и как выглядит фикс. Остальные темы этого раздела ([07](./07-injections-sql-nosql.md)–[15](./15-prototype-pollution-redos.md)) разбирают отдельные категории детально — здесь карта целиком.

## Карта категорий (редакция 2021, актуальная на момент подготовки) на Node/Nest

| # | Категория | Типичное проявление в Node/Nest | Где разобрано подробнее |
|---|---|---|---|
| A01 | Broken Access Control | IDOR — роль проверена guard'ом, владение ресурсом — нет | [05-rbac-abac.md](./05-rbac-abac.md) |
| A02 | Cryptographic Failures | пароли на SHA-256 вместо bcrypt/argon2; секреты в git; HTTP вместо HTTPS для чувствительных данных | [13-password-hashing.md](./13-password-hashing.md), [14-secrets-management.md](./14-secrets-management.md) |
| A03 | Injection | конкатенация строк в SQL-запрос через TypeORM `query()`; `$where`/операторы MongoDB из `req.body` напрямую в запрос | [07-injections-sql-nosql.md](./07-injections-sql-nosql.md) |
| A04 | Insecure Design | отсутствие rate limiting на эндпоинте логина/сброса пароля — архитектурный пробел, не баг конкретной строчки кода | [12-rate-limiting.md](./12-rate-limiting.md) |
| A05 | Security Misconfiguration | `helmet()` не подключён; CORS с `origin: '*'` вместе с `credentials: true` (что браузеры вообще запрещают, но настройка сама по себе — красный флаг); подробные stack trace в проде | [14-secrets-management.md](./14-secrets-management.md) |
| A06 | Vulnerable and Outdated Components | устаревшие зависимости с известными CVE; `npm audit`/Snyk не в CI | — |
| A07 | Identification and Authentication Failures | JWT без проверки `exp`/`alg`; отсутствие rate limiting на попытках логина (брутфорс); слабая политика паролей | [01-jwt.md](./01-jwt.md), [02-access-refresh-tokens.md](./02-access-refresh-tokens.md) |
| A08 | Software and Data Integrity Failures | `npm install` из непроверенного реестра/без lock-файла; десериализация недоверенных данных без валидации; отсутствие проверки подписи в CI/CD пайплайне | — |
| A09 | Security Logging and Monitoring Failures | логи не содержат достаточно контекста для расследования инцидента (кто, когда, какой ресурс); чувствительные данные (пароли, токены) **попадают** в логи по ошибке | — |
| A10 | Server-Side Request Forgery (SSRF) | сервис фетчит URL, присланный пользователем (превью ссылок, вебхуки), без валидации против внутренней сети/метаданных облака | [11-ssrf.md](./11-ssrf.md) |

## Почему именно A01 (Broken Access Control) — самая частая категория

По статистике OWASP (доля приложений с найденной уязвимостью этой категории при тестировании) — Broken Access Control устойчиво на первом месте, и это логично для типичного backend на Node/Nest: авторизация — не встроенный в фреймворк примитив (в отличие, например, от параметризации SQL-запросов, которая "просто работает", если пользоваться ORM правильно) — она **всегда** пишется руками, специфично для каждой бизнес-сущности ("этот пользователь может редактировать этот конкретный документ?"). Guard, проверяющий только роль (см. [05-rbac-abac.md](./05-rbac-abac.md)), — самая частая недоработка именно потому, что "технически заработало" (401/403 отрабатывают для явно неавторизованных) создаёт ложное чувство защищённости, маскируя отсутствие resource-level проверки.

## A06 — специфика Node-экосистемы

```bash
npm audit                    # быстрая проверка известных уязвимостей в зависимостях
npm audit fix                # автоисправление там, где возможно без breaking change
```

Node-проекты типично имеют глубокое дерево транзитивных зависимостей (`node_modules` на тысячи пакетов даже для небольшого сервиса) — уязвимость может прийти не из прямой зависимости, а из зависимости зависимости, о существовании которой разработчик даже не подозревает. `npm audit`/аналоги (Snyk, Dependabot) в CI — минимальный необходимый барьер, не решающий проблему полностью (флажки могут быть false positive для кода, который реально не исполняется, или не иметь готового патча месяцами), но превращающий "мы вообще не знаем, что уязвимо" в "мы знаем и осознанно принимаем/чиним конкретные риски".

## A08 — supply chain как Node-специфичный риск

Инцидент типа `event-stream` (2018) или подобные атаки через компрометацию популярного npm-пакета — не гипотетический риск, а реализовывавшийся на практике: злоумышленник получает доступ к публикации версии широко используемого пакета и вставляет вредоносный код, который автоматически подтягивается через `npm install` у тысяч проектов. Практические меры: lock-файлы (`package-lock.json`) обязательны в репозитории (фиксируют точные версии транзитивных зависимостей, не только диапазоны из `package.json`), `npm ci` вместо `npm install` в CI/CD (строго по lock-файлу, без пересчёта дерева), рассмотрение provenance-механизмов (`npm audit signatures` начиная с npm 9+) для критичных зависимостей.

## Что спрашивают на собеседовании

1. **Назовите топ категорий OWASP и как каждая проявляется конкретно в Node/Nest-сервисе.** — не пересказ формулировок, а конкретные примеры: IDOR через guard без resource-check (A01), конкатенация в SQL через `query()` вместо параметров (A03), отсутствие `helmet()`/подробные stack trace в проде (A05).
2. **Почему Broken Access Control — самая частая категория на практике?** — авторизация уровня ресурса не встроена во фреймворк "из коробки" в отличие от, например, параметризации запросов через ORM — пишется руками под каждую бизнес-сущность, и её легко забыть/недооценить.
3. **Как минимизировать риск уязвимых зависимостей в Node-проекте?** — `npm audit`/Snyk/Dependabot в CI как барьер, lock-файлы в репозитории, `npm ci` вместо `npm install` в пайплайнах — ни один инструмент не даёт стопроцентной гарантии, но превращает неизвестный риск в отслеживаемый.
4. **Что такое supply chain атака и почему Node-экосистема к ней особенно восприимчива?** — компрометация популярного пакета в реестре автоматически распространяется на тысячи проектов через `npm install`; глубокие деревья транзитивных зависимостей делают полный аудит вручную нереалистичным.
5. **Найдите уязвимости в сниппете кода** (типовое практическое задание) — уметь на лету распознать конкатенацию в SQL, отсутствие проверки владельца ресурса, `eval`/`Function` над пользовательским вводом, слабый/захардкоженный JWT-секрет, отсутствие валидации входных данных.
