# CORS: что реально делает, preflight, credentials — и что это не защита сервера

> **TL;DR:** CORS — это правило, которое **браузер** соблюдает, чтобы решить, отдавать ли JS-коду страницы результат кросс-доменного запроса. Сервер, настроивший CORS, не становится защищённым от чего-либо — CORS не мешает `curl`, Postman, серверу другого сервиса или атакующему, обращающемуся не из браузера, вообще ничего не получить: сам запрос **выполняется** в любом случае, CORS лишь решает, разрешит ли браузер **JS-коду страницы прочитать ответ**. Это одно из самых частых заблуждений на собеседовании (см. чек-лист «CORS защищает моё API» в [index.md](./index.md)).

## Same-Origin Policy — то, от чего CORS — управляемое исключение

Браузер по умолчанию не позволяет JS-коду одной страницы (`app.example.com`) читать ответ на запрос к другому источнику (`api.other.com`) — origin определяется тройкой схема+хост+порт. CORS — механизм, которым **сервер** явно сообщает браузеру "разрешаю такому-то origin читать ответы от меня" через заголовки ответа — не про то, выполняется ли запрос (он выполняется всегда, если сеть и сервер это позволяют), а про то, разрешено ли скрипту на странице увидеть результат.

```
Клиент (JS на app.example.com) шлёт запрос к api.other.com
Сервер api.other.com отвечает: Access-Control-Allow-Origin: https://app.example.com
Браузер: раз сервер разрешил ЭТОТ конкретный origin — отдаю ответ JS-коду страницы
```

Без правильного заголовка сервер всё равно **получил и обработал** запрос (если это, например, `POST`, изменяющий данные, изменение уже произошло) — браузер лишь не покажет JS-коду тело ответа. Это ключевое для понимания "CORS — не защита сервера": сервер, единственная защита которого — отсутствие CORS-заголовков, всё ещё полностью открыт для запросов от любого не-браузерного клиента (скрипт, curl, другой сервер) — там нет браузера, соблюдающего CORS, некому применять это правило.

## Preflight — `OPTIONS` перед "небезопасными" запросами

```
OPTIONS /orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST, GET
Access-Control-Allow-Headers: Content-Type, Authorization
```

Браузер автоматически отправляет предварительный `OPTIONS`-запрос перед "непростыми" запросами (методы кроме `GET`/`HEAD`/`POST` с простым `Content-Type`, кастомные заголовки типа `Authorization`) — спрашивает сервер "а разрешено ли мне вообще так делать?", прежде чем отправить реальный запрос с данными. Если сервер не ответил разрешающими заголовками на preflight — браузер **не отправляет** сам основной запрос вообще (в отличие от простых запросов, где запрос выполняется, а блокируется только чтение ответа) — это единственный случай, где CORS реально предотвращает выполнение запроса, а не только сокрытие ответа, и то работает только для "непростых" запросов и только в браузере.

## `credentials` — куки в кросс-доменных запросах

```ts
// клиент явно просит слать куки при кросс-доменном запросе
fetch('https://api.example.com/orders', { credentials: 'include' });
```

```
Access-Control-Allow-Origin: https://app.example.com   -- НЕ может быть '*' вместе с credentials
Access-Control-Allow-Credentials: true
```

По умолчанию браузер не прикладывает куки к кросс-доменным запросам вообще — `credentials: 'include'` на клиенте явно запрашивает их отправку, а сервер обязан явно подтвердить `Access-Control-Allow-Credentials: true` **и** указать конкретный origin (не wildcard `*`) — спецификация прямо запрещает комбинацию `Allow-Origin: *` с `Allow-Credentials: true`, потому что это фактически разрешило бы любому сайту в интернете делать аутентифицированные (с куками пользователя) запросы к API и читать ответы — ровно то, от чего CORS должен защищать.

## Почему "CORS защищает моё API" — неверно

```ts
// разработчик думает: "настрою CORS на конкретный origin — API защищён"
app.enableCors({ origin: 'https://app.example.com' });
// но: curl https://api.example.com/admin/users -H "Authorization: Bearer stolen-token" — сработает без проблем
```

CORS ничего не проверяет про **личность** или **право** отправителя запроса — только про то, разрешит ли браузер JS-коду конкретной веб-страницы прочитать ответ. Любой не-браузерный клиент (что составляет практически весь легитимный межсервисный трафик, а также большинство инструментов атакующего) не подчиняется CORS вообще — заголовок `Access-Control-Allow-Origin` для него не имеет никакого значения, потому что его не проверяет никто, кроме браузера самого пользователя. Настоящая защита ресурса — аутентификация (кто ты) и авторизация (что тебе можно) на каждом запросе, разобранные в [01-jwt.md](./01-jwt.md)–[05-rbac-abac.md](./05-rbac-abac.md) — CORS — это политика для браузеров о доверенных фронтендах, полностью ортогональная вопросу "имеет ли этот запрос право на этот ресурс".

## Что спрашивают на собеседовании

1. **Что реально делает CORS?** — управляет тем, разрешит ли браузер JS-коду страницы прочитать ответ на кросс-доменный запрос; сам запрос при этом обычно всё равно выполняется сервером (кроме preflight-блокировки для "непростых" запросов).
2. **Почему "настроил CORS — API защищено" — неверное утверждение?** — CORS соблюдается только браузером и только применительно к JS-коду веб-страницы; любой не-браузерный клиент (curl, скрипт, другой сервер, инструмент атакующего) полностью игнорирует CORS-заголовки — реальная защита ресурса — аутентификация и авторизация на сервере.
3. **Что такое preflight-запрос и когда он отправляется?** — автоматический `OPTIONS`-запрос браузера перед "непростыми" запросами (кастомные заголовки, методы кроме GET/HEAD/простого POST) — спрашивает разрешения у сервера до отправки основного запроса с данными.
4. **Почему нельзя одновременно использовать `Access-Control-Allow-Origin: *` и `Access-Control-Allow-Credentials: true`?** — эта комбинация позволила бы любому сайту в интернете делать аутентифицированные запросы (с куками пользователя) к API и читать ответы — спецификация явно запрещает такое сочетание.
5. **Если CORS не настроен вообще, значит ли это, что запрос не дойдёт до сервера?** — нет для "простых" запросов — они выполняются, браузер лишь не покажет ответ JS-коду страницы; для "непростых" запросов preflight действительно предотвращает отправку основного запроса, если сервер не подтвердил разрешение.
