# Access + refresh токены: ротация, reuse detection, хранение

> **TL;DR:** Access-токен — короткоживущий (минуты), предъявляется на каждый запрос, компрометация ограничена коротким окном. Refresh-токен — долгоживущий (дни/недели), используется **только** для получения новой пары токенов, хранится отдельно и защищённее. **Ротация** — каждый refresh одноразовый: использовал — получил новую пару, старый инвалидирован. **Reuse detection** — если один и тот же (уже использованный) refresh-токен пришёл повторно, это прямой сигнал компрометации: кто-то украл токен и пытается использовать его параллельно с легитимным владельцем — реакция должна быть немедленной инвалидацией всей цепочки.

## Зачем два токена, а не один долгоживущий

Один долгоживущий токен, предъявляемый на каждый запрос, максимизирует поверхность атаки — он летает по сети/логам/JS-контексту при каждом вызове API, и если утечёт (XSS, лог с секретом, MITM без TLS) — скомпрометирован на весь оставшийся срок жизни. Разделение снижает риск: access-токен живёт настолько коротко, что даже перехваченный, он бесполезен через несколько минут; refresh-токен используется редко (раз в TTL access-токена) и может храниться более защищённо (httpOnly cookie, отдельный secure-эндпоинт), снижая частоту его появления в потенциально уязвимых местах.

## Ротация — каждый refresh одноразовый

```ts
async function refreshTokens(oldRefreshToken: string) {
  const stored = await refreshTokenRepo.findByToken(hash(oldRefreshToken));
  if (!stored || stored.revoked) {
    // токена нет ИЛИ он уже был использован/отозван — см. reuse detection ниже
    throw new UnauthorizedException();
  }

  await refreshTokenRepo.revoke(stored.id); // старый — немедленно инвалидирован

  const newAccessToken = signAccessToken(stored.userId);
  const newRefreshToken = generateRefreshToken();
  await refreshTokenRepo.save({
    userId: stored.userId,
    tokenHash: hash(newRefreshToken),
    familyId: stored.familyId, // та же "семья" — цепочка ротаций одной исходной сессии
    parentId: stored.id,
  });

  return { accessToken: newAccessToken, refreshToken: newRefreshToken };
}
```

Хранить в БД имеет смысл **хэш** refresh-токена (тот же принцип, что и для паролей, см. [Пароли: bcrypt/argon2, cost factor, соль](./13-password-hashing.md)), не сам токен в открытом виде — утечка БД не должна сразу давать рабочие токены атакующему. Каждая ротация создаёт новую запись, связанную с предыдущей через `familyId`/`parentId` — эта цепочка и есть то, что позволяет распознать reuse.

## Reuse detection — как ловится кража

```ts
async function refreshTokens(oldRefreshToken: string) {
  const stored = await refreshTokenRepo.findByToken(hash(oldRefreshToken));
  if (stored?.revoked) {
    // токен УЖЕ был использован ранее (revoked при своей единственной легитимной ротации)
    // повторное предъявление = кто-то параллельно владеет тем же токеном → компрометация
    await refreshTokenRepo.revokeFamily(stored.familyId); // инвалидировать ВСЮ цепочку, не только этот токен
    await notifySecurityEvent(stored.userId, 'refresh_token_reuse_detected');
    throw new UnauthorizedException();
  }
  // ... обычная ротация
}
```

Сценарий: атакующий украл refresh-токен (например, через XSS до момента, пока пользователь его не использовал сам). Оба — атакующий и легитимный пользователь — в какой-то момент используют один и тот же токен для ротации. Первый из них "выигрывает" (получает новую пару, старый токен помечается `revoked`), второй получает уже отозванный токен — и именно это расхождение (кто-то предъявил уже использованный/отозванный refresh) — детектируемый признак, что токен был скомпрометирован **до** этого момента, потому что легитимный клиент никогда не должен предъявлять токен, который сам же уже обменял на новый. Реакция — не просто отклонить этот конкретный запрос, а инвалидировать **всю семью** токенов (всю цепочку ротаций начиная с исходного логина) — оба участника (атакующий и легитимный пользователь) будут вынуждены логиниться заново, что приемлемая цена за нейтрализацию кражи.

## Access token скомпрометирован — что делать

Поскольку access-токен обычно stateless JWT (см. [JWT: структура, HS256 vs RS256, отзыв](./01-jwt.md)) — его нельзя отозвать напрямую без дополнительной инфраструктуры (denylist/версионирование). Основная защита — короткий TTL, ограничивающий окно эксплуатации автоматически, без ручного вмешательства. Если требуется немедленная реакция (пользователь сам сообщил о краже, обнаружена подозрительная активность) — инвалидация всей refresh-семьи не отзовёт уже выданный access-токен немедленно, но не даст скомпрометированной сессии продлиться после истечения его короткого TTL — а для действительно срочных случаев (заблокировать прямо сейчас) нужен denylist конкретно для access-токенов или переход на серверную сессию для этого пользователя.

## Хранение refresh-токена на клиенте

Refresh-токен — более чувствительный секрет, чем access (он живёт дольше и даёт возможность получать новые access-токены неограниченно, пока не истёк или не отозван) — обычно храниться в `httpOnly` secure cookie с ограниченным `Path` (например, только `/auth/refresh`, чтобы не прикладывался к каждому запросу без необходимости) — снижает поверхность XSS-кражи по сравнению с хранением в JS-доступном месте. Trade-off с CSRF при этом подходе разобран в [CSRF: когда актуален и когда нет](./09-csrf.md) — cookie-хранение требует отдельной защиты от CSRF на самом эндпоинте `/auth/refresh`.

## Что спрашивают на собеседовании

1. **Access token скомпрометирован — что делать? Почему короткий TTL + refresh rotation?** — короткий TTL естественно ограничивает окно эксплуатации без ручного вмешательства; refresh rotation гарантирует, что даже украденный refresh-токен как максимум даёт атакующему возможность попасться на reuse detection при следующей попытке легитимного пользователя обновить сессию.
2. **Как поймать reuse украденного refresh-токена?** — каждый refresh одноразовый и помечается `revoked` после использования; повторное предъявление уже отозванного токена — прямой сигнал компрометации, реакция — инвалидация всей цепочки (`familyId`), не только конкретного токена.
3. **Почему при обнаружении reuse инвалидируется вся семья токенов, а не только использованный повторно?** — весь смысл reuse detection в том, что компрометация могла произойти на любом более раннем шаге цепочки — частичная инвалидация оставляет атакующему возможность продолжить с более старого валидного токена в этой же цепочке.
4. **Что хранить в БД — сам refresh-токен или его хэш?** — хэш, тем же принципом, что и пароли: утечка БД не должна сразу давать атакующему рабочие токены.
5. **Где хранить refresh-токен на клиенте и почему не там же, где access?** — обычно httpOnly cookie с ограниченным `Path` (например, только к эндпоинту обновления) — снижает частоту появления более чувствительного долгоживущего секрета в потенциально уязвимых местах по сравнению с access-токеном, летающим на каждый запрос.
