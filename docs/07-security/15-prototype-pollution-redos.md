# Prototype pollution, ReDoS — специфика Node/JavaScript

> **TL;DR:** Обе уязвимости — прямое следствие особенностей самого языка, не общих веб-паттернов из OWASP Top 10. Prototype pollution эксплуатирует то, что у JS-объектов есть общий разделяемый `[[Prototype]]` (см. [Прототипы и class](../01-javascript-typescript/03-prototypes-and-classes.md)) — если пользовательский ввод неконтролируемо мержится в объект, можно дотянуться до `Object.prototype` и повлиять на **все** объекты в процессе. ReDoS эксплуатирует то, что JS-движок использует backtracking-регулярку — определённые паттерны на специально сконструированном вводе выполняются экспоненциальное время от длины строки, блокируя единственный поток event loop.

## Prototype pollution — механика атаки

```js
function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === 'object') {
      target[key] = merge(target[key] || {}, source[key]); // наивный глубокий merge
    } else {
      target[key] = source[key];
    }
  }
  return target;
}

merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
// после этого ЛЮБОЙ новый объект в процессе имеет isAdmin === true через прототипную цепочку:
({}).isAdmin; // true — даже у объекта, который никогда не участвовал в merge!
```

`__proto__` — legacy-геттер/сеттер, ссылающийся на внутренний слот `[[Prototype]]` объекта (подробности — в [Прототипы и class](../01-javascript-typescript/03-prototypes-and-classes.md)). Наивная рекурсивная функция merge/clone, не фильтрующая специальные ключи (`__proto__`, `constructor.prototype`), позволяет атакующему через обычный JSON в теле запроса дописать свойство прямо в `Object.prototype` — который наследуют **все** обычные объекты в процессе. Дальше эксплуатация зависит от того, что именно приложение делает с этим "загрязнённым" свойством — классический сценарий: приложение где-то проверяет `if (user.isAdmin)` без явного `hasOwnProperty`, и это условие внезапно истинно для объекта, у которого такого собственного свойства никогда не было — просто потому, что оно "просочилось" через прототип.

## Где на практике возникает уязвимость

- **Небезопасный глубокий merge/clone** пользовательского JSON в конфиг/state объект (кастомные реализации `_.merge`-подобной функции без явной защиты — известные уязвимости находили и в самой lodash до патчей).
- **`JSON.parse` с последующим неконтролируемым присваиванием** ключей из результата напрямую в существующий объект без валидации набора допустимых ключей.
- **query-string парсеры**, поддерживающие вложенные структуры (`qs`-подобные), исторически содержали уязвимости, позволяющие через query-параметр `?__proto__[isAdmin]=true` достичь того же эффекта.

## Защита от prototype pollution

```js
// 1. Object.create(null) — объект БЕЗ прототипа вообще, __proto__ на нём не спецсимвол
const safeMap = Object.create(null);

// 2. Явная проверка опасных ключей при merge
function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue; // пропустить
    // ... остальная логика merge
  }
}

// 3. Object.freeze(Object.prototype) — сделать прототип неизменяемым (защита "в лоб", возможны побочные эффекты)

// 4. Использовать Map вместо plain object для пользовательских данных с произвольными ключами
const store = new Map(); // ключи Map никогда не взаимодействуют с прототипной цепочкой объектов
```

Явная фильтрация опасных ключей (`__proto__`, `constructor`, `prototype`) в любом коде, принимающем произвольные ключи от пользователя и присваивающем их в объект, — минимально необходимая мера. `Map` вместо plain object — структурно более надёжная защита там, где данные — это просто "ключ → значение" от пользователя без необходимости в прототипном поведении объектов вообще (см. разбор WeakMap/Map в [WeakMap / WeakSet / WeakRef](../01-javascript-typescript/08-weakmap-weakset-weakref.md) — тот же принцип "не plain object для пользовательских ключей" применим и здесь, не только для утечек памяти).

## ReDoS — catastrophic backtracking

```js
const regex = /^(a+)+$/; // классический уязвимый паттерн: вложенные квантификаторы
regex.test('aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!'); // зависает на десятки секунд+
```

Регулярное выражение с вложенными или перекрывающимися квантификаторами (`(a+)+`, `(a|a)+`, `(a*)*`) на определённых входах заставляет backtracking-движок регулярных выражений (используемый в V8, как и в большинстве других языков — в отличие от, например, RE2, гарантированно линейного, но не поддерживающего некоторые фичи regex) перебирать **экспоненциальное** число вариантов разбиения строки на группы, прежде чем окончательно решить, что совпадения нет. Строка `"aaaa...a!"` (много `a`, затем символ, не подходящий под паттерн) — специально сконструирована так, чтобы движку пришлось перепробовать все комбинации разбиения на группы `(a+)+`, прежде чем окончательно провалить совпадение на последнем символе. Поскольку Node однопоточен для JS-кода (см. [Архитектура V8 + libuv](../02-nodejs-core/01-architecture.md)) — зависшее регэксп-вычисление блокирует **весь** event loop, не только запрос текущего пользователя — единственный вредоносный вход в поле "email"/"username" формы может положить весь сервис для всех пользователей одновременно.

## Защита от ReDoS

- **Избегать вложенных квантификаторов** над одним и тем же классом символов (`(a+)+`, `(\d+)*` и подобные) — почти всегда переписываемы в эквивалентную небэктрекающуюся форму (`a+` вместо `(a+)+`, если внутренняя группировка не несёт самостоятельного смысла).
- **`safe-regex`/аналогичные линтеры** — статический анализ регулярки на потенциально опасные паттерны до того, как она попадёт в код, обрабатывающий пользовательский ввод.
- **Не строить регулярку из пользовательского ввода напрямую** — если пользователь может повлиять на сам паттерн (например, "поиск по маске"), экранировать спецсимволы (`escape-string-regexp`) или использовать не-regex алгоритм поиска.
- **Таймаут на выполнение регэкспа** — Node сам по себе не даёт встроенного таймаута для `RegExp.test`/`exec` (в отличие от некоторых других языков), поэтому либо выносить потенциально опасную обработку в `worker_threads` с возможностью прервать воркер по таймауту (см. [worker_threads / child_process / cluster](../02-nodejs-core/05-workers-cluster.md)), либо использовать библиотеки с гарантированно линейными по сложности алгоритмами вместо стандартного backtracking-движка для потенциально опасных пользовательских паттернов.

## Что спрашивают на собеседовании

1. **Что такое prototype pollution и почему это специфично для JS?** — загрязнение общего `Object.prototype` через неконтролируемый merge пользовательского ввода с ключами вроде `__proto__` — эксплуатирует то, что все обычные объекты JS разделяют общую прототипную цепочку, чего нет в языках без прототипного наследования.
2. **Как защититься от prototype pollution?** — явная фильтрация опасных ключей (`__proto__`, `constructor`, `prototype`) при merge пользовательских данных, `Object.create(null)` для объектов без прототипа, `Map` вместо plain object для произвольных пользовательских ключей.
3. **Приведите пример уязвимой регулярки для ReDoS.** — `/^(a+)+$/` и подобные с вложенными квантификаторами над одним классом символов — на специально сконструированном вводе вызывают экспоненциальный по времени backtracking.
4. **Почему ReDoS особенно опасен именно в Node?** — однопоточная модель исполнения JS-кода: зависшее вычисление регулярки блокирует весь event loop, а не только текущий запрос — один вредоносный вход кладёт сервис целиком для всех пользователей одновременно.
5. **Как защититься от ReDoS, если Node не даёт встроенного таймаута на выполнение регэкспа?** — избегать уязвимых паттернов (линтеры вроде `safe-regex`), не строить регулярку напрямую из пользовательского ввода, для действительно рискованной обработки — выносить в `worker_threads` с возможностью прервать по таймауту.
