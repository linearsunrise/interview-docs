# Сессии vs JWT — trade-offs

> **TL;DR:** Сессия — сервер хранит state (обычно в Redis), клиент носит только непрозрачный ID; отзыв — мгновенный `DEL` по ключу. JWT — сервер ничего не хранит, вся валидность закодирована в токене; отзыв структурно затруднён (см. [01-jwt.md](./01-jwt.md)). Выбор — не "что современнее", а конкретный компромисс между контролем (revocation, единственность сессии) и масштабируемостью/простотой (stateless-проверка без похода в общее хранилище).

## Механика

```
Сессия:
  Клиент: Cookie: sessionId=abc123 (непрозрачный, ничего не значащий сам по себе)
  Сервер: Redis GET session:abc123 → { userId: 42, roles: [...], loginAt: ... }
  Logout: Redis DEL session:abc123 → сессия мгновенно недействительна везде

JWT:
  Клиент: Authorization: Bearer eyJhbGc...
  Сервер: verify(token, publicKey) → { sub: 42, roles: [...], exp: ... } — без похода в хранилище
  Logout: токен остаётся валидным до exp, если нет отдельного denylist
```

## Сравнение

| | Сессии (server-side state) | JWT (stateless) |
|---|---|---|
| Мгновенный logout/бан конкретного пользователя | тривиально — `DEL` по ключу | сложно — требует denylist или короткий TTL (см. [01-jwt.md](./01-jwt.md)) |
| Масштабирование проверки токена | требует похода в общее хранилище (Redis) на каждый запрос — сетевой round-trip | локальная проверка подписи, без сетевого похода — быстрее и не создаёт нагрузку на общий стор |
| Межсервисная проверка (микросервисы) | каждый сервис должен иметь доступ к тому же хранилищу сессий | любой сервис с публичным ключом (RS256) проверяет независимо, без общей БД |
| Размер данных на запрос | минимальный (только ID) | больше (весь payload передаётся каждый раз, даже если сервису нужно только `userId`) |
| Ограничение "один активный клиент"/список активных сессий | естественно — есть явный список активных ключей в Redis | требует отдельного стора активных токенов — то есть части stateless-подхода уже нет |
| Точка отказа | Redis недоступен → аутентификация всей системы недоступна | сервис, проверяющий подпись, работает независимо от доступности любого стора |

## Когда сессии в Redis лучше JWT

- **Нужен мгновенный logout/бан** — банковское приложение, админ-панель с требованием "заблокировать пользователя прямо сейчас, а не через 15 минут по истечении TTL токена".
- **Нужен контроль "один активный клиент"** (или ограниченное число одновременных сессий) — легко проверить через список активных session ID в Redis, для JWT это требует того же denylist-подобного механизма поверх stateless-модели, то есть фактической потери её преимуществ.
- **Монолит или небольшое число сервисов с общим доступом к Redis** — сетевой поход за сессией не становится узким местом архитектуры, а плюсы (простой revocation, компактный cookie) перевешивают.
- **Нужен явный список активных сессий пользователю** ("устройства, где вы залогинены" — типичная функция настроек аккаунта) — естественно вытекает из хранения состояния на сервере.

## Когда JWT лучше сессий

- **Множество независимых сервисов**, которым нужно проверять аутентификацию без похода в общий стор на каждый запрос — особенно если сервисы физически распределены (разные дата-центры/облака), где сетевой round-trip к централизованному хранилищу сессий добавляет заметную латентность.
- **Мобильные/SPA клиенты, работающие в основном через API** — компактность и самодостаточность токена удобны для клиент-серверной модели без сессионных кук браузера.
- **Делегированная аутентификация между организациями** (OAuth2/OIDC, см. [04-oauth2-oidc.md](./04-oauth2-oidc.md)) — JWT как формат id_token/access_token — стандарт де-факто для межорганизационного доверия, где сервер, выпустивший токен, и сервер, его проверяющий, — разные компании без общей БД.
- **Готовность мириться с задержкой отзыва** — TTL в единицы минут для access-токена делает "нельзя мгновенно отозвать" не такой острой проблемой на практике.

## Гибрид — частый прод-паттерн

```
Access token: короткоживущий JWT (5-15 минут) — быстрая stateless-проверка на каждый запрос
Refresh token: непрозрачный ID, ХРАНИМЫЙ в БД/Redis (не JWT!) — отзыв, ротация, reuse detection
```

Access-токен получает выгоды stateless-проверки (быстро, не грузит общий стор на каждый запрос) там, где короткий TTL делает задержку отзыва приемлемой. Refresh-токен, наоборот, делают **не** JWT, а непрозрачным идентификатором с полноценным server-side state (см. [02-access-refresh-tokens.md](./02-access-refresh-tokens.md)) — потому что именно на нём нужен полный контроль (ротация, reuse detection, немедленный отзыв всей цепочки при компрометации), а используется он редко (раз в TTL access-токена), так что накладные расходы похода в БД/Redis на эту операцию не критичны. Это типичный способ взять сильные стороны обеих моделей там, где они наиболее уместны, а не выбирать одну на всё приложение целиком.

## Что спрашивают на собеседовании

1. **Когда сессии в Redis лучше JWT?** — нужен мгновенный logout/бан или контроль числа одновременных активных сессий на пользователя — то, что естественно для server-side state и требует дополнительной инфраструктуры поверх stateless JWT.
2. **Почему JWT масштабируется лучше сессий в микросервисной архитектуре?** — проверка подписи локальна, не требует похода в общее хранилище на каждый запрос от каждого сервиса — устраняет сетевой round-trip и единую точку отказа в виде центрального стора сессий.
3. **Какой гибридный подход обычно используют в проде?** — короткоживущий JWT для access (быстрая stateless-проверка) + непрозрачный refresh-токен с полноценным server-side state (ротация, reuse detection, мгновенный отзыв).
4. **Что теряется, если пытаться реализовать "список активных сессий пользователя" на чистом JWT?** — де-факто приходится вести отдельный server-side реестр выданных токенов — то есть терять именно то stateless-свойство, ради которого JWT изначально выбирался.
5. **Какая точка отказа у каждого подхода?** — у сессий — недоступность централизованного хранилища (Redis) блокирует всю аутентификацию системы; у JWT — точки отказа как таковой на проверке нет (локальная проверка подписи), но зато нет и лёгкого способа что-то отозвать мгновенно.
