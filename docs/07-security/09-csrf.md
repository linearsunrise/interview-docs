# CSRF: когда актуален (cookie-сессии) и когда нет (Bearer)

> **TL;DR:** CSRF работает благодаря одному конкретному поведению браузера — он **автоматически** прикладывает куки к запросу на домен, которому они принадлежат, независимо от того, откуда инициирован запрос (даже с постороннего сайта, куда жертву заманили). Bearer-токен из `Authorization`-заголовка браузер сам никогда не приложит — его должен явно прочитать и вставить JS-код на легитимной странице, значит, для CSRF атакующему просто нечего "подставить" автоматически. Отсюда точный критерий: **cookie-based аутентификация — под угрозой CSRF, Bearer-token-based (обычно из памяти/localStorage) — нет**, но приобретает свою уязвимость — XSS (см. [08-xss-csp.md](./08-xss-csp.md)).

## Как работает атака

```html
<!-- эта форма размещена на evil.com, куда заманили жертву, залогиненную на bank.com -->
<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker-account" />
  <input type="hidden" name="amount" value="10000" />
</form>
<script>document.forms[0].submit();</script>
```

Жертва открывает `evil.com` в браузере, где у неё уже есть активная сессия на `bank.com` (cookie с session ID). Скрипт на `evil.com` автоматически отправляет форму на `bank.com/transfer` — браузер, ничего не подозревая, **сам прикладывает** cookie `bank.com` к этому запросу, потому что запрос идёт именно на домен `bank.com`, независимо от того, что инициировал его совершенно посторонний сайт. Сервер `bank.com`, видя валидную сессионную куку, обрабатывает перевод как легитимный запрос от аутентифицированного пользователя — он структурно не может отличить "пользователь сам нажал кнопку на моём сайте" от "чужой сайт отправил запрос от имени пользователя браузером".

## Почему Bearer-токен из памяти не подвержен CSRF

```js
// легитимный клиент явно читает токен и кладёт его в заголовок
fetch('https://api.example.com/transfer', {
  headers: { Authorization: `Bearer ${accessToken}` }, // accessToken — переменная в JS-памяти легитимной страницы
});
```

Заголовок `Authorization` — не то, что браузер прикладывает автоматически, как куки — его обязан явно выставить JS-код, исполняющийся на странице, отправляющей запрос. Скрипт на `evil.com` физически **не имеет доступа** к `accessToken`, который хранится в памяти/localStorage легитимной страницы `bank.com` (same-origin policy браузера не даёт JS одного домена читать данные другого) — он может сформировать запрос на `bank.com/transfer`, но не может приложить к нему правильный `Authorization`-заголовок, а без него сервер (правильно спроектированный — не принимающий cookie как единственный способ аутентификации для такого запроса) его отклонит.

## Защиты для cookie-based аутентификации

```
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

- **`SameSite` атрибут cookie** — `Strict` (кука вообще не прикладывается к запросам с чужого домена, включая обычные переходы по ссылке — иногда неудобно для UX, например, "открыть письмо со ссылкой на сайт, где уже залогинен, и остаться залогиненным"), `Lax` (кука не прикладывается к "фоновым" межсайтовым запросам вроде отправки форм/fetch с других доменов, но прикладывается к обычной навигации по ссылке — разумный дефолт большинства браузеров), `None` (прикладывается всегда, требует `Secure` — фактически отключение защиты, нужно для легитимных кросс-доменных интеграций). `SameSite=Lax` уже сам по себе блокирует классический сценарий CSRF через автоматическую отправку формы с чужого домена.
- **CSRF-токен** (синхронизатор) — сервер генерирует уникальный токен на сессию, кладёт его в скрытое поле формы/заголовок, ожидает обратно при мутирующих запросах (`POST`/`PUT`/`DELETE`) — токен недоступен постороннему сайту (в отличие от куки, которая прикладывается автоматически, токен нужно явно прочитать со страницы того же домена и переслать) — сравнение сервером ожидаемого и присланного значения защищает независимо от `SameSite`.
- **Проверка `Origin`/`Referer` заголовка** — дополнительный (не основной) рубеж: сервер отклоняет мутирующие запросы, чей `Origin` не совпадает с ожидаемым — полезно как defense in depth, но не как единственная защита (эти заголовки в редких случаях могут отсутствовать по легитимным причинам конфигурации прокси/приватности).

## Когда CSRF неактуален — не путать "неактуален" с "не нужно думать вообще"

Если аутентификация полностью построена на Bearer-токене, который никогда не хранится в куке (а в памяти/localStorage) и явно прикладывается JS-кодом клиента — классический CSRF-вектор через автоматическую отправку куки браузером не работает. Это **не** означает "безопасность решена сама по себе": как разобрано в [01-jwt.md](./01-jwt.md), хранение в localStorage открывает XSS-вектор — то есть проблема не исчезает, а **меняет форму**: вместо "чужой сайт подделывает запрос от имени залогиненного пользователя" риск становится "вредоносный скрипт на самом сайте похищает токен и делает с ним что угодно, включая CSRF-подобные действия уже без ограничений same-origin". Это то, о чём чек-лист раздела говорит явно ([index.md](./index.md)): пара вопросов "JWT в localStorage vs httpOnly cookie" — не про "что безопаснее в вакууме", а про то, какой конкретный вектор атаки принимается взамен другого.

## Что спрашивают на собеседовании

1. **Почему CSRF работает именно через куки, а не через Bearer-токен?** — браузер автоматически прикладывает куки к запросу на домен, которому они принадлежат, независимо от инициатора запроса; `Authorization`-заголовок так не работает — его должен явно выставить JS, а same-origin policy не даёт постороннему сайту прочитать токен легитимной страницы.
2. **Как защититься от CSRF при cookie-based аутентификации?** — `SameSite=Lax`/`Strict` на куке как базовая защита, CSRF-токен (синхронизатор) как основной механизм для мутирующих запросов, проверка `Origin`/`Referer` как дополнительный рубеж.
3. **JWT в localStorage vs httpOnly cookie — trade-offs?** — localStorage не подвержен CSRF, но уязвим к XSS (JS-доступен); httpOnly cookie защищён от чтения через XSS, но подвержен CSRF без отдельной защиты (SameSite/CSRF-токен) — выбор — это выбор, каким конкретно вектором атаки готовы управлять.
4. **`SameSite=Lax` полностью решает проблему CSRF?** — существенно снижает риск для типичных сценариев (блокирует автоматическую отправку форм/fetch с чужого домена), но не панацея — легитимные кросс-доменные интеграции (`SameSite=None`) требуют дополнительной защиты (CSRF-токен) поверх.
5. **Актуален ли CSRF для чисто mobile-приложения, общающегося с API через Bearer-токен?** — нет в классическом виде — мобильное приложение не подвержено механизму "браузер автоматически прикладывает куки с чужого сайта", поскольку это вообще не браузерный контекст с автоматической отправкой кук.
