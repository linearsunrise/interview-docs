# OAuth2 flows: authorization code + PKCE, client credentials; OIDC поверх OAuth2

> **TL;DR:** OAuth2 — протокол **авторизации** (делегированный доступ: "приложению X разрешено делать Y от имени пользователя"), не аутентификации — сам по себе он не отвечает на вопрос "кто этот пользователь". OIDC (OpenID Connect) — тонкий слой **аутентификации** поверх OAuth2, добавляющий стандартизированный `id_token` (JWT с личностью пользователя) к тому же протоколу. Authorization Code + PKCE — сегодняшний универсальный дефолт для любого клиента (веб, мобильный, SPA), Client Credentials — отдельный flow для machine-to-machine без участия пользователя вообще.

## Authorization Code Flow — базовая механика

```
1. Клиент (веб-приложение) редиректит пользователя на сервер авторизации:
   GET https://auth.example.com/authorize?response_type=code&client_id=...&redirect_uri=...&scope=...

2. Пользователь логинится и подтверждает доступ НА сервере авторизации (не на клиенте!)

3. Сервер авторизации редиректит обратно с одноразовым кодом:
   GET https://app.example.com/callback?code=SPLXLOBEZQQYBYS6WXSD

4. Клиент (обычно backend, не браузер) обменивает код на токены СЕРВЕР-СЕРВЕР запросом:
   POST https://auth.example.com/token
   { grant_type: 'authorization_code', code: '...', client_id: '...', client_secret: '...' }

5. Сервер авторизации возвращает access_token (+ id_token, если OIDC, + refresh_token)
```

Ключевая идея — пароль пользователя никогда не попадает к клиентскому приложению, только к серверу авторизации, которому пользователь и так доверяет свою личность (Google, GitHub и т.п.). Код из шага 3 одноразовый и короткоживущий — сам по себе бесполезен без `client_secret`, которым владеет только backend клиентского приложения (шаг 4) — это и защищает от перехвата кода в редиректе браузера самого по себе.

## PKCE — зачем нужен, если и так есть `client_secret`

Проблема: `client_secret` можно безопасно хранить только на backend'е — SPA (весь код которого исполняется в браузере пользователя) или мобильное приложение (декомпилируемый бинарник на устройстве пользователя) физически не могут хранить секрет так, чтобы он не был извлекаем — это **public client**, а не confidential. Без дополнительной защиты, если атакующий перехватит код авторизации (шаг 3 — например, через вредоносное приложение, перехватывающее custom URL scheme на мобильном устройстве), он сможет обменять его на токены сам, потому что для public client `client_secret` либо отсутствует, либо бесполезен как секрет (он публично известен).

```
1. Клиент генерирует случайный code_verifier (высокоэнтропийная строка) и держит его у себя
2. Клиент вычисляет code_challenge = BASE64URL(SHA256(code_verifier)) и отправляет его в /authorize
3. Сервер авторизации запоминает code_challenge, привязанный к выданному коду
4. При обмене кода на токен клиент присылает ИСХОДНЫЙ code_verifier
5. Сервер авторизации сам вычисляет SHA256(code_verifier) и сверяет с ранее сохранённым code_challenge
   → совпадает — значит, обменивающий код на токен — тот же клиент, что инициировал flow
```

PKCE (Proof Key for Code Exchange) заменяет `client_secret` доказательством "я — тот же клиент, что запросил этот код" через одноразовую криптографическую пару, которую атакующий, перехвативший только сам код (шаг 3), не может воспроизвести — у него нет `code_verifier`, который никогда не покидал исходного клиента до шага 4. Современная рекомендация ([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), обновляющая best practices) — использовать PKCE для **всех** типов клиентов, включая confidential backend-приложения, не только для public clients, как дополнительный слой защиты от подмены/перехвата кода.

## Client Credentials Flow — machine-to-machine

```
POST https://auth.example.com/token
{ grant_type: 'client_credentials', client_id: '...', client_secret: '...', scope: 'orders:read' }
→ { access_token: '...' } // токен представляет САМ СЕРВИС, не какого-то пользователя
```

Нет пользователя, нет редиректа, нет браузера — один сервис (например, внутренний батч-джоб или бэкенд-интеграция между двумя компаниями) напрямую аутентифицируется своими `client_id`/`client_secret` и получает токен, представляющий его самого. Применим только для confidential-клиентов (секрет хранится на защищённом сервере, не выдаётся конечным пользователям) — типичный кейс для server-to-server API-интеграций, cron-джобов, межсервисной коммуникации с внешним API.

## OIDC — идентификационный слой поверх OAuth2

```
Тот же authorization code flow, но с scope=openid:
GET /authorize?response_type=code&scope=openid%20profile%20email&...

Ответ на обмен кода включает ДОПОЛНИТЕЛЬНЫЙ id_token (JWT):
{
  access_token: '...',      // для доступа к API от имени пользователя (авторизация)
  id_token: 'eyJhbGc...',   // JWT с ЛИЧНОСТЬЮ пользователя (аутентификация): sub, email, name, iss, aud, exp
  refresh_token: '...'
}
```

OAuth2 сам по себе не стандартизирует, что означает `access_token` содержательно — он просто "ключ доступа к ресурсу", формат и claims которого специфичны для конкретного сервера авторизации. OIDC добавляет стандартизированный `id_token` — именно он отвечает на вопрос "кто залогинился" (стандартные claims `sub` — уникальный ID пользователя, `email`, `email_verified`, `name` и т.п.) и `/userinfo`-эндпоинт для получения дополнительных данных профиля. Частая путаница на собеседовании — использовать `access_token` для идентификации пользователя на клиенте (его формат и claims не стандартизированы и не предназначены для этого) вместо `id_token`, который для этого специально существует.

## Что спрашивают на собеседовании

1. **Расскажите authorization code flow с PKCE — зачем PKCE?** — код авторизации обменивается на токены server-to-server через `client_secret`; PKCE защищает public clients (SPA, мобильные), которые не могут безопасно хранить `client_secret`, через одноразовую пару `code_verifier`/`code_challenge`, доказывающую, что обменивает код тот же клиент, что его запросил.
2. **Чем OAuth2 отличается от OIDC?** — OAuth2 — протокол авторизации (делегированный доступ к ресурсу), сам по себе не отвечает на "кто пользователь"; OIDC добавляет стандартизированный `id_token` и `/userinfo` для аутентификации поверх того же протокола.
3. **Когда использовать Client Credentials flow вместо Authorization Code?** — когда нет пользователя вообще — machine-to-machine коммуникация, где токен представляет сам сервис-клиент, а не человека, действующего через браузер.
4. **Почему PKCE рекомендуют даже для confidential-клиентов с `client_secret`, не только для SPA/мобильных?** — дополнительный слой защиты от перехвата/подмены кода авторизации независимо от типа клиента — современный best practice (RFC 9700) не ограничивает PKCE только public clients.
5. **`access_token` vs `id_token` — для чего каждый?** — `access_token` — для доступа к защищённому ресурсу/API от имени пользователя (авторизация), формат не стандартизирован; `id_token` — JWT со стандартизированными claims личности пользователя (аутентификация), не предназначен для передачи как ключ доступа к произвольному API.
