# Кеширование: cache-aside, write-through, write-behind; TTL vs явная инвалидация

> **TL;DR:** Три паттерна отвечают на разные вопросы: cache-aside — "кто отвечает за загрузку в кеш" (приложение, лениво, по промаху), write-through — "когда кеш узнаёт об изменении" (синхронно, в момент записи), write-behind — "когда изменение долетает до источника истины" (асинхронно, после записи в кеш). Выбор — не "какой лучше", а какой consistency/latency trade-off приемлем для конкретных данных. TTL и явная инвалидация — не взаимоисключающие, а взаимодополняющие механизмы: TTL — страховка на случай, если инвалидация не сработала (баг, пропущенное событие), а не основной способ поддерживать свежесть.

## Cache-aside (lazy loading) — самый частый паттерн

```ts
async function getUser(id: string): Promise<User> {
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached); // hit — не идём в БД вообще

  const user = await userRepo.findById(id); // miss — идём в источник истины
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300);
  return user;
}

async function updateUser(id: string, dto: UpdateUserDto) {
  const user = await userRepo.update(id, dto); // пишем в БД
  await redis.del(`user:${id}`); // инвалидируем кеш, НЕ обновляем его напрямую
  return user;
}
```

Приложение само управляет и чтением (промах → подгрузить → положить в кеш), и инвалидацией при записи. Простой для понимания и устойчивый к падению кеша (Redis недоступен — приложение просто ходит в БД напрямую, деградация производительности, не отказ функциональности). При инвалидации намеренно **удаляют** ключ, а не обновляют его новым значением — обновление создаёт собственную гонку (если два конкурентных `updateUser` пишут в кеш в неверном порядке, кеш может застрять со старым значением поверх нового) — `del` + следующий читатель сам перезагрузит актуальное значение проще и безопаснее.

## Write-through — кеш и источник истины меняются синхронно

```ts
async function updateUser(id: string, dto: UpdateUserDto) {
  const user = await userRepo.update(id, dto);
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300); // кеш обновлён СРАЗУ, в той же операции
  return user;
}
```

Кеш всегда синхронизирован с источником истины сразу после записи (не бывает промежуточного "invalidated" состояния, как в cache-aside между `del` и следующим чтением) — за счёт того, что каждая запись платит дополнительной задержкой похода в кеш синхронно. Хорошо подходит, когда данные, скорее всего, будут прочитаны сразу после записи (read-after-write — если бы кеш просто инвалидировался, первое чтение после записи было бы промахом и лишним походом в БД).

## Write-behind (write-back) — запись в кеш немедленно, в источник истины — асинхронно

```ts
async function incrementViewCount(postId: string) {
  await redis.incr(`views:${postId}`); // немедленно, быстро
  // отдельный фоновый процесс периодически сбрасывает накопленные счётчики в БД батчем
}
```

Запись подтверждается клиенту сразу после попадания в кеш — реальная персистентность в БД происходит позже, батчем (снижает нагрузку на БД для высокочастотных изменений вроде счётчиков просмотров/лайков, где точная синхронность не критична). Цена — риск потери данных при падении кеша до того, как накопленные изменения долетели до БД — оправдан только для данных, где такая потеря приемлема (аналитические счётчики, не финансовые операции).

## TTL vs явная инвалидация — не или/или

```ts
await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300); // TTL 5 минут
// ПЛЮС явная инвалидация при update — оба механизма одновременно
```

Явная инвалидация (при cache-aside — `del` при записи) даёт свежесть данных сразу после изменения — без неё пользователь видел бы старые данные до истечения TTL. TTL — страховка на случай, когда явная инвалидация **не сработала**: код обновления в другом месте забыл вызвать инвалидацию, событие изменения потерялось (при инвалидации через pub/sub между инстансами, см. [03-multi-level-caching.md](./03-multi-level-caching.md)), баг в логике инвалидации. Полагаться только на TTL без явной инвалидации означает мириться с окном устаревших данных длиной в TTL после каждого изменения — приемлемо для данных с низкой ценой устаревания (публичный каталог товаров), неприемлемо для данных, где свежесть критична (баланс счёта, статус заказа).

## Что спрашивают на собеседовании

1. **В чём разница между cache-aside, write-through и write-behind?** — cache-aside: приложение лениво загружает в кеш при промахе и явно инвалидирует при записи; write-through: кеш обновляется синхронно в момент записи в источник истины; write-behind: запись подтверждается по факту попадания в кеш, персистентность в источник истины происходит асинхронно позже.
2. **Почему при инвалидации кеша лучше удалять ключ, а не обновлять его новым значением?** — обновление кеша создаёт собственную гонку при конкурентных записях (порядок применения может привести к застрявшему старому значению поверх нового); удаление проще — следующий читатель сам загрузит актуальное состояние.
3. **Зачем нужен TTL, если есть явная инвалидация при каждом изменении?** — страховка на случай, если явная инвалидация не сработала (забытый вызов, потерянное событие, баг) — TTL гарантирует, что устаревшие данные не проживут дольше определённого времени, даже если основной механизм инвалидации подвёл.
4. **Когда write-behind оправдан, а когда опасен?** — оправдан для высокочастотных некритичных данных (счётчики просмотров), где потеря последних изменений при падении кеша приемлема; опасен для данных, где каждое изменение обязано быть надёжно зафиксировано (финансовые операции, статус заказа).
5. **Что произойдёт с приложением при cache-aside, если Redis станет недоступен?** — приложение продолжит работать, читая и (при необходимости) обновляя данные напрямую в БД — деградация производительности (выше латентность, выше нагрузка на БД), но не отказ функциональности, в отличие от write-through/write-behind, где кеш — часть критического пути записи.
