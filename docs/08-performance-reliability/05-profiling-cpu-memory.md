# Профилирование: CPU-профиль (flame graph, clinic.js, `--prof`), memory

> **TL;DR:** «Мне кажется, тут медленно» — не диагноз, а гипотеза, которую профилировщик либо подтверждает, либо опровергает конкретными числами (это прямо названо красным флагом в чек-листе раздела: «оптимизация без измерений»). CPU-профиль отвечает на вопрос «где именно процессор тратит время», flame graph — визуализация того же профиля, где ширина блока = доля времени, а не про «что вызывает что» само по себе. Memory-профиль (heap snapshot) — отдельный инструмент для отдельного класса проблем (утечки), уже подробно разобранного в [02-nodejs-core/08-memory-leaks.md](../02-nodejs-core/08-memory-leaks.md) — здесь фокус на CPU.

## `--prof` — встроенный сэмплирующий профилировщик V8

```bash
node --prof dist/main.js
# ... нагрузка на приложение (autocannon/k6, см. 10-load-testing-percentiles.md) ...
node --prof-process isolate-0x*.log > processed.txt
```

V8 периодически (сэмплированием, не построчной инструментацией — поэтому оверхед сравнительно небольшой) снимает текущий стек вызовов JS-кода и записывает в лог. `--prof-process` превращает сырой лог в читаемую сводку: сколько сэмплов пришлось на каждую функцию (`Summary` — доля времени в C++ builtins, JS, GC), топ "тяжёлых" функций по количеству попаданий. Плюс — встроен в Node, не требует установки; минус — сырой текстовый вывод менее нагляден, чем flame graph, и требует post-processing вручную.

## Flame graph — наглядная визуализация того же профиля

```bash
npm install -g clinic
clinic flame -- node dist/main.js
# нагрузка на приложение во время работы clinic...
# Ctrl+C → clinic автоматически открывает HTML-отчёт с flame graph
```

```
Читать flame graph:
- Ось X: НЕ время выполнения по порядку — сортировка по алфавиту/ширине, ширина блока = ДОЛЯ сэмплов в этой функции
- Ось Y: глубина стека вызовов (внизу — точка входа, вверху — самые вложенные вызовы)
- Широкий блок наверху стека = именно ЭТА функция потребляет много CPU-времени сама (не через дочерние вызовы)
- Широкий блок с широкими детьми = время уходит НИЖЕ по стеку, в дочерних вызовах
```

Частая ошибка чтения flame graph — искать "самый длинный путь слева направо" как хронологию, хотя X-ось не время — искать нужно **самые широкие блоки**, особенно "plateau" (широкий блок без широких детей сверху) — это функция, которая сама, в своём собственном коде (не через то, что она вызывает), съедает заметную долю CPU-времени — обычно первая цель для оптимизации.

## clinic.js — набор инструментов под конкретные вопросы

```bash
clinic doctor -- node dist/main.js   # общая диагностика: что за тип проблемы (CPU/event loop/I/O), рекомендация куда копать дальше
clinic flame -- node dist/main.js    # CPU flame graph — если doctor указал на CPU-bound проблему
clinic bubbleprof -- node dist/main.js  # визуализация асинхронных операций и задержек между ними — для I/O-bound проблем
clinic heapprofiler -- node dist/main.js  # похожий на flame graph, но для аллокаций памяти, а не CPU-времени
```

`clinic doctor` — обычно первый шаг: не даёт детального профиля, но классифицирует симптом (высокая загрузка CPU vs event loop lag без загрузки CPU vs проблемы с I/O/GC) и подсказывает, какой из более специализированных инструментов (`flame`, `bubbleprof`, `heapprofiler`) использовать дальше — экономит время по сравнению с тем, чтобы сразу гадать, в какую сторону копать.

## 0x — альтернативный генератор flame graph

```bash
npx 0x -- node dist/main.js
```

Похож по назначению на `clinic flame`, отдельный инструмент с собственными плюсами (иногда более точная символизация нативных фреймов, другой UI отчёта) — на практике выбор между `clinic flame` и `0x` часто дело вкуса команды/привычки, оба решают одну и ту же задачу через один и тот же встроенный V8 CPU-профилировщик под капотом.

## `--cpu-prof` — встроенная альтернатива без установки пакетов

```bash
node --cpu-prof --cpu-prof-dir=./profiles dist/main.js
# генерирует .cpuprofile файл, который можно открыть в Chrome DevTools (вкладка Performance/Profiler) напрямую
```

Формат `.cpuprofile` — стандартный формат Chrome DevTools, поэтому файл, снятый прямо на сервере без единого дополнительного npm-пакета, можно перетащить в DevTools локально и получить тот же flame graph и интерактивный анализ, что и для профилирования кода в браузере — удобно, когда нельзя/не хочется ставить дополнительные зависимости на прод-машину ради разового профилирования инцидента.

## Memory-профилирование — отдельная тема, отдельный инструмент

Профилирование CPU (где тратится процессорное время) и профилирование памяти (что и почему занимает heap, откуда утечка) — разные вопросы с разными инструментами, хотя `clinic`/Chrome DevTools покрывают оба через разные режимы. Полный разбор heap snapshot, retainers, `--heapsnapshot-near-heap-limit` и методики поиска утечек — в [02-nodejs-core/08-memory-leaks.md](../02-nodejs-core/08-memory-leaks.md), не дублируется здесь.

## Практический алгоритм — от симптома к профилю

1. **Подтвердить симптом метрикой**, не полагаться на ощущение — p99 latency вырос по графику, event loop lag вырос по `monitorEventLoopDelay` (см. [06-cpu-bound-event-loop-lag.md](./06-cpu-bound-event-loop-lag.md)), CPU-загрузка инстанса выросла по системным метрикам.
2. **Воспроизвести под нагрузкой** — профилирование "на глазок" в проде без контролируемой нагрузки даёт зашумлённые данные; `clinic`/`0x` под autocannon/k6-нагрузкой (см. [10-load-testing-percentiles.md](./10-load-testing-percentiles.md)) на staging — воспроизводимый результат.
3. **`clinic doctor` для классификации** — прежде чем открывать flame graph, понять, действительно ли проблема CPU-bound, а не I/O-задержка/GC-паузы, которые выглядят как "медленно", но лечатся иначе.
4. **Flame graph → найти самый широкий "plateau"** — конкретная функция, где реально тратится время, а не общие подозрения "наверное, вот этот участок кода".
5. **Оптимизировать, перепрофилировать, сравнить** — снять новый профиль/бенчмарк после изменения, убедиться, что улучшение реальное, а не воображаемое (тот же принцип, что и красный флаг «оптимизация без измерений» — измерения нужны и до, и после).

## Что спрашивают на собеседовании

1. **Как найти, какая функция потребляет больше всего CPU в Node-приложении?** — снять CPU-профиль под нагрузкой (`clinic flame`, `0x`, встроенный `--cpu-prof`), построить flame graph, искать самые широкие блоки без широких "детей" сверху — это функции, тратящие время в своём собственном коде.
2. **Как правильно читать flame graph — что означает ширина блока?** — долю сэмплов профилировщика, попавших в эту функцию, не хронологию выполнения; X-ось не время, важна ширина, а не позиция слева направо.
3. **Зачем нужен `clinic doctor`, если можно сразу снять flame graph?** — классифицирует симптом (CPU-bound vs event loop lag без загрузки CPU vs I/O/GC) до детального профилирования — экономит время, направляя сразу к подходящему инструменту вместо угадывания.
4. **Как снять CPU-профиль без установки дополнительных npm-пакетов?** — встроенный флаг `--cpu-prof`, генерирующий `.cpuprofile`, открываемый напрямую в Chrome DevTools.
5. **Почему профилирование в проде без контролируемой нагрузки даёт менее полезный результат, чем на staging под нагрузочным тестом?** — реальный прод-трафик зашумлён (разная смесь запросов, разная нагрузка в разные моменты) — контролируемая воспроизводимая нагрузка на staging даёт чистый, сравнимый до/после результат.
