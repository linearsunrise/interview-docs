# Retry budget; таймауты повсюду — клиентские, серверные, на пул БД

> **TL;DR:** Механика backoff+jitter и circuit breaker подробно разобрана в [Circuit Breaker, retry с backoff+jitter, timeout budget](../06-architecture-patterns/11-circuit-breaker-retry.md) — здесь два практических аспекта, которые дополняют ту механику: **retry budget** (сколько ретраев система в принципе может себе позволить как процент общего трафика, а не сколько раз ретраить один конкретный запрос) и **таймауты на каждом слое отдельно** (клиент, сервер, пул соединений к БД — каждый со своей ролью, отсутствие любого из них — дыра, через которую проблема одного компонента расползается на всю систему).

## Retry budget — ограничение не на запрос, а на систему целиком

```ts
class RetryBudget {
  private tokens = 100; // стартовый запас
  private readonly maxTokens = 100;
  private readonly refillPerSuccess = 1; // за каждый УСПЕШНЫЙ запрос — немного токенов обратно

  canRetry(): boolean {
    if (this.tokens < 1) return false; // бюджет исчерпан — НЕ ретраить, вернуть ошибку сразу
    this.tokens -= 10; // ретрай стоит дороже, чем даёт один успех — бюджет тает, если ретраев много
    return true;
  }
  onSuccess() { this.tokens = Math.min(this.maxTokens, this.tokens + this.refillPerSuccess); }
}
```

Ограничение "не больше 3 попыток на один запрос" (см. механику в circuit-breaker-retry.md) защищает от бесконечного зацикливания одного клиента, но не защищает систему **в целом**: если 30% всех запросов начинают падать одновременно (частичная деградация нижестоящего сервиса), и каждый ретраится до 3 раз — это уже не +30% нагрузки, а кратно больше, что само по себе может добить и без того проблемный сервис (тот же retry storm, но на уровне агрегированного трафика, а не синхронизации по времени, которую решает jitter). Retry budget — отдельный ограничитель поверх per-request retry-логики: система в целом не тратит на ретраи больше фиксированной доли своего трафика (типичный ориентир — не более 10-20% от общего числа запросов), независимо от того, сколько ретраев "разрешено" каждому отдельному запросу — при исчерпании бюджета новые ретраи просто не выполняются, запрос сразу возвращает ошибку.

## Таймауты — на каждом слое своя роль

```
Клиент → [клиентский timeout] → Load Balancer → [серверный timeout] → API → [DB pool timeout] → PostgreSQL
```

**Клиентский таймаут** — сколько времени клиент (браузер, мобильное приложение, другой сервис) готов ждать ответ, прежде чем сдаться и показать ошибку/ретраить сам. Без него — зависшая сетевая операция держит ресурсы клиента (открытый сокет, ожидающий поток/промис) неограниченно долго.

**Серверный таймаут** — сколько времени сервер готов тратить на обработку одного запроса, прежде чем принудительно оборвать его и освободить ресурсы (worker, соединение) для других запросов:

```ts
import timeout from 'connect-timeout';
app.use(timeout('5s')); // если хендлер не ответил за 5 секунд — прервать, вернуть 503
```

Без серверного таймаута один медленный запрос (например, зависший на ожидании недоступного внешнего API) может держать обработчик занятым сколь угодно долго — под нагрузкой это исчерпывает пул воркеров/соединений быстрее, чем система успевает восстановиться (см. bulkhead в [Bulkhead, load shedding, graceful degradation](./08-bulkhead-load-shedding-degradation.md) — таймаут и bulkhead решают смежные, но разные грани одной проблемы: таймаут ограничивает **время**, bulkhead — **долю ресурсов**).

**Таймаут на пул соединений к БД** — отдельная, часто забываемая настройка:

```ts
// TypeORM/pg pool
new Pool({
  connectionTimeoutMillis: 3000, // сколько ждать СВОБОДНОЕ соединение из пула, прежде чем сдаться
  statement_timeout: 5000,       // сколько ждать выполнения ОДНОГО SQL-запроса на стороне PostgreSQL
  idle_in_transaction_session_timeout: 10000, // защита от зависшей "in transaction" сессии
});
```

`connectionTimeoutMillis` — если все соединения пула заняты (см. [Connection pooling](../04-databases/08-connection-pooling.md)), новый запрос не должен ждать свободное соединение вечно — без этого таймаута очередь запросов, ожидающих соединение, растёт неограниченно при малейшей просадке производительности БД, каскадно превращая временную проблему БД в полный отказ всего сервиса (все воркеры API зависли в ожидании соединения, которое никогда не освободится, потому что БД сама перегружена этой же очередью). `statement_timeout` — независимая защита на стороне самой БД: даже плохо спроектированный/забытый долгий запрос не держит соединение (и связанные с ним локи, см. [Deadlocks](../04-databases/06-deadlocks.md)) вечно.

## Timeout budget — таймауты должны уменьшаться вниз по цепочке

```
Пользователь ждёт максимум 3000мс
  Gateway timeout: 2800мс (небольшой запас)
    OrderService timeout к PaymentService: 1500мс
    OrderService timeout к InventoryService: 1500мс (параллельно)
```

Тот же концепт timeout budget, что разобран для распределения по цепочке вызовов в [Circuit Breaker, retry с backoff+jitter, timeout budget](../06-architecture-patterns/11-circuit-breaker-retry.md), здесь стоит подчеркнуть конкретно: если каждый сервис в цепочке ставит **одинаковый** таймаут независимо от того, сколько времени уже прошло с начала обработки исходного запроса, суммарное время по цепочке легко превышает то, что готов ждать пользователь — и хуже того, "внешний" уровень (например, gateway) уже отдал пользователю таймаут-ошибку, а внутренние сервисы **продолжают** впустую тратить ресурсы на обработку запроса, результат которого уже никому не нужен. Правильная практика — таймаут каждого следующего хопа меньше оставшегося бюджета родительского вызова, а не независимая константа "у нас везде таймаут 5 секунд".

## Что спрашивают на собеседовании

1. **Что такое retry budget и чем он отличается от ограничения "3 попытки на запрос"?** — ограничение на долю трафика системы, которую можно потратить на ретраи в целом (например, не более 10-20%), а не на число попыток одного конкретного запроса — защищает от того, что частичная деградация большого числа запросов, каждый из которых ретраится в разрешённых пределах, суммарно перегружает и без того проблемный сервис.
2. **Ретраи уронили нижестоящий сервис — что пошло не так?** — либо отсутствие backoff+jitter (синхронизированные волны, см. circuit-breaker-retry.md), либо отсутствие retry budget (агрегированный объём ретраев от множества запросов превысил то, что упавший сервис может выдержать даже при восстановлении).
3. **Зачем нужен таймаут именно на пул соединений к БД, а не только на сам запрос к БД?** — без него исчерпание пула (все соединения заняты) заставляет новые запросы ждать свободное соединение неограниченно, каскадно превращая временную просадку БД в полный отказ сервиса — все воркеры API зависают в очереди за соединением.
4. **Почему таймауты по цепочке вызовов должны уменьшаться, а не быть одинаковой константой на каждом хопе?** — иначе внешний уровень может уже вернуть таймаут-ошибку пользователю, пока внутренние сервисы продолжают впустую обрабатывать запрос, результат которого больше никому не нужен — ресурсы тратятся на заведомо бесполезную работу.
5. **Что произойдёт без серверного таймаута на обработку запроса?** — один медленный запрос (например, ожидающий недоступный внешний сервис) держит обработчик занятым неограниченно долго — под нагрузкой это быстро исчерпывает пул воркеров/соединений, доступных для остальных запросов.
