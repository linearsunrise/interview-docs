# Масштабирование: stateless-приложения, горизонтальное vs вертикальное, load balancing

> **TL;DR:** Горизонтальное масштабирование (больше инстансов) требует, чтобы приложение было **stateless** — любой инстанс должен уметь обработать любой запрос, не полагаясь на состояние, оставшееся в его собственной памяти от предыдущих запросов того же клиента. Вертикальное масштабирование (более мощная машина) не требует этого условия, но упирается в физический потолок одной машины и не даёт отказоустойчивости (одна машина — одна точка отказа). Load balancing — как балансировщик выбирает, какому из нескольких stateless-инстансов отдать конкретный запрос.

## Почему stateless — предпосылка горизонтального масштабирования

```ts
// плохо: состояние в памяти процесса — не переживает переход на другой инстанс
const sessions = new Map<string, SessionData>(); // in-memory, ЛОКАЛЬНО для этого процесса

app.post('/login', (req, res) => {
  sessions.set(sessionId, { userId }); // сохранено ТОЛЬКО в памяти ЭТОГО инстанса
});
app.get('/profile', (req, res) => {
  const session = sessions.get(sessionId); // если балансировщик направил на ДРУГОЙ инстанс — session не найдена
});
```

```ts
// хорошо: состояние вынесено во внешнее хранилище, доступное всем инстансам одинаково
app.post('/login', async (req, res) => {
  await redis.set(`session:${sessionId}`, JSON.stringify({ userId }), 'EX', 3600);
});
app.get('/profile', async (req, res) => {
  const session = await redis.get(`session:${sessionId}`); // ЛЮБОЙ инстанс видит то же самое
});
```

Если сессия/состояние хранится в памяти конкретного процесса, пользователь, чей следующий запрос балансировщик направит на **другой** инстанс, потеряет это состояние — это либо вынуждает к sticky sessions (тот же компромисс, что разобран для WebSocket в [05-api-communication/08-websockets.md](../05-api-communication/08-websockets.md) — привязка клиента к конкретному инстансу, что снижает эффективность балансировки и создаёт локальную точку отказа для этого клиента), либо просто ломает функциональность. Stateless-архитектура выносит всё разделяемое состояние во внешнее хранилище (Redis, БД) — любой инстанс, получивший запрос, самодостаточен для его обработки без знания о предыдущих запросах этого же клиента к другим инстансам.

## Горизонтальное vs вертикальное масштабирование

| | Вертикальное (scale up) | Горизонтальное (scale out) |
|---|---|---|
| Механизм | более мощная машина (больше CPU/RAM) | больше инстансов той же мощности |
| Потолок | физический предел одной машины | практически не ограничен (добавляй ещё инстансы) |
| Отказоустойчивость | нет — одна машина, один отказ валит всё | да — падение одного инстанса не останавливает систему |
| Требования к приложению | почти никаких — работает как есть | требует stateless-дизайна (или sticky sessions как компромисс) |
| Простота | максимальная — просто "включить мощнее" | требует балансировщика, координации, общего хранилища состояния |
| Стоимость на единицу мощности | часто нелинейно растёт (топовое железо непропорционально дороже) | линейнее — N обычных машин часто дешевле одной сверхмощной |

Практика — не "выбрать одно навсегда": вертикальное масштабирование остаётся разумным первым шагом для небольшой нагрузки (проще, без архитектурных изменений), горизонтальное становится необходимым, когда нужна отказоустойчивость или нагрузка превышает потолок одной машины — многие системы масштабируют вертикально каждый отдельный инстанс до разумного предела, и горизонтально — число таких инстансов.

## Алгоритмы балансировки нагрузки

```
Round robin: запрос 1 → инстанс A, запрос 2 → инстанс B, запрос 3 → инстанс C, запрос 4 → инстанс A, ...
             простой, но не учитывает текущую загрузку каждого инстанса

Least connections: направить на инстанс с НАИМЕНЬШИМ числом активных соединений прямо сейчас
             лучше учитывает реальную нагрузку — если один запрос на инстансе A выполняется 10 секунд,
             а на B и C запросы быстрые, round robin продолжит слать на A наравне с остальными,
             least connections — заметит, что на A уже "занято", и предпочтёт B/C

Weighted (round robin или least connections с весами): разные инстансы имеют разную мощность
             (например, при постепенном обновлении на более мощное железо) — более мощный
             получает пропорционально больше трафика

IP hash / consistent hashing: клиент с одним IP/ключом всегда попадает на один и тот же инстанс
             — основа sticky sessions, нужна там, где состояние всё же локально на инстансе
```

**Least connections** обычно лучше **round robin** под неравномерной по времени выполнения нагрузкой (запросы разной "тяжести" — типичный случай реального API, не синтетического бенчмарка с одинаковыми запросами) — round robin слепо распределяет по количеству запросов, не по фактической загрузке, и может перегрузить инстанс, застрявший на нескольких тяжёлых запросах, продолжая слать ему новые наравне с простаивающими.

## Health checks — балансировщик должен знать, кто жив

```
GET /health → 200 OK  -- инстанс отвечает, готов принимать трафик
GET /health → timeout/5xx -- балансировщик перестаёт направлять НОВЫЕ запросы на этот инстанс
```

Балансировщик периодически опрашивает каждый инстанс — упавший или перегруженный до отказа отвечать инстанс автоматически исключается из ротации, пока не восстановится (снова начнёт отвечать на health check). Важное различие — **liveness** (процесс вообще жив, не завис) vs **readiness** (процесс жив И готов обслуживать трафик прямо сейчас — например, ещё не прогрел соединения к БД при старте, или сознательно отказывается от нового трафика во время graceful shutdown, см. [02-nodejs-core/10-graceful-shutdown.md](../02-nodejs-core/10-graceful-shutdown.md)) — в Kubernetes это два разных типа проб именно по этой причине: неготовый, но живой под не должен получать новый трафик, но и не должен быть перезапущен как сломанный.

## Что спрашивают на собеседовании

1. **Почему горизонтальное масштабирование требует stateless-приложения?** — балансировщик может направить последовательные запросы одного клиента на разные инстансы — состояние, хранящееся только в памяти конкретного процесса, недоступно другим инстансам и теряется/рассинхронизируется без вынесения во внешнее общее хранилище.
2. **Когда вертикальное масштабирование предпочтительнее горизонтального?** — небольшая нагрузка, где простота важнее отказоустойчивости, и физический потолок одной машины ещё далеко — не требует архитектурных изменений (балансировщик, вынесение состояния).
3. **Чем least connections лучше round robin?** — учитывает текущую фактическую загрузку каждого инстанса, а не просто равномерно распределяет по числу запросов — не перегружает инстанс, застрявший на медленных запросах, продолжая слать ему новые наравне с простаивающими.
4. **Зачем балансировщику health checks и в чём разница liveness vs readiness?** — исключает недоступные/неготовые инстансы из ротации трафика автоматически; liveness — процесс жив (не завис), readiness — процесс готов обслуживать трафик прямо сейчас (может быть жив, но временно не готов — прогрев, graceful shutdown).
5. **Что такое sticky sessions и почему это компромисс, а не решение?** — привязка клиента к конкретному инстансу через IP hash/cookie — решает проблему локального состояния ценой снижения эффективности балансировки и создания локальной точки отказа именно для этого клиента при падении его закреплённого инстанса.
