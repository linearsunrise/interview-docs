# Cache stampede (dogpile), cache penetration, hot keys

> **TL;DR:** Три разных сценария, которые ломают наивный кеш под нагрузкой. Stampede — истёк один горячий ключ, тысячи запросов одновременно бросаются пересчитывать его в БД. Penetration — запрашивают то, чего вообще нет ни в кеше, ни в БД (кеш структурно не может защитить от повторных промахов на несуществующие данные). Hot key — один конкретный ключ настолько популярен, что весь трафик к нему упирается в единственный узел/шард кеша, независимо от общей ёмкости кластера.

## Cache stampede (dogpile effect)

```
Ключ "trending_products" истёк в 12:00:00.000
12:00:00.001 — 1000 параллельных запросов видят промах кеша ОДНОВРЕМЕННО
Все 1000 идут в БД пересчитывать один и тот же дорогой запрос → БД получает 1000x обычной нагрузки за миллисекунды
```

**Решение 1 — распределённый лок (single flight):**

```ts
async function getTrendingProducts(): Promise<Product[]> {
  const cached = await redis.get('trending_products');
  if (cached) return JSON.parse(cached);

  const lockAcquired = await redis.set('lock:trending_products', '1', 'NX', 'EX', 10);
  if (!lockAcquired) {
    await sleep(50); // кто-то другой уже пересчитывает — подождать и попробовать снова
    return getTrendingProducts();
  }
  try {
    const data = await computeExpensiveTrendingQuery(); // пересчитывает ТОЛЬКО тот, кто взял лок
    await redis.set('trending_products', JSON.stringify(data), 'EX', 300);
    return data;
  } finally {
    await redis.del('lock:trending_products');
  }
}
```

Только один запрос (тот, что успел `SET NX` — атомарно "установить, если не существует") реально идёт в БД пересчитывать значение; остальные либо ждут и повторно проверяют кеш, либо (в более мягком варианте) сразу отдают немного устаревшее (stale) значение вместо ожидания, если небольшая задержка свежести приемлема для конкретных данных.

**Решение 2 — jitter на TTL:**

```ts
const baseTtl = 300;
const jitter = Math.floor(Math.random() * 30); // ±30 секунд случайного разброса
await redis.set(key, value, 'EX', baseTtl + jitter);
```

Если множество ключей выставлены с одинаковым TTL и были прогреты одновременно (типично после деплоя/рестарта), они истекут **одновременно**, создав множественные stampede разом. Случайный разброс TTL размазывает истечение по времени — тот же принцип jitter, что и в retry с backoff (см. [06-architecture-patterns/11-circuit-breaker-retry.md](../06-architecture-patterns/11-circuit-breaker-retry.md) — синхронизированные события в распределённой системе почти всегда лечатся внесением случайности).

**Решение 3 — probabilistic early refresh:** каждый читатель, видя, что до истечения TTL осталось немного времени, с некоторой вероятностью (растущей по мере приближения к истечению) сам инициирует фоновое обновление **до** реального истечения — так что к моменту факта истечения кеш уже обновлён кем-то из недавних читателей, и stampede не происходит вообще, потому что промаха как такового не было.

## Cache penetration — запрос данных, которых не существует

```
GET /users/99999999 (несуществующий ID)
→ кеш: промах (ключа никогда не было)
→ БД: тоже ничего не находит
→ ответ: 404, В КЕШ НИЧЕГО НЕ ЗАПИСАНО (обычно кешируют только успешные находки)
→ следующий такой же запрос ПОВТОРЯЕТ весь путь заново — кеш вообще не защищает БД от этого паттерна
```

Атакующий (или просто баг клиента, перебирающего несуществующие ID) может завалить БД потоком запросов на заведомо отсутствующие записи — кеш, спроектированный только кешировать найденные значения, тут структурно бесполезен, потому что каждый такой запрос — гарантированный промах.

**Решение — negative caching:**

```ts
async function getUser(id: string): Promise<User | null> {
  const cached = await redis.get(`user:${id}`);
  if (cached === 'NULL') return null; // кешированное "не найдено" — не идём в БД повторно
  if (cached) return JSON.parse(cached);

  const user = await userRepo.findById(id);
  if (!user) {
    await redis.set(`user:${id}`, 'NULL', 'EX', 60); // короткий TTL для негативного результата
    return null;
  }
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300);
  return user;
}
```

Кешируется сам факт "такой записи не существует", обычно с более коротким TTL, чем для позитивных результатов (данные могут появиться раньше, чем истёк бы длинный TTL — короткий TTL ограничивает окно, где реально созданная запись всё ещё "невидима" из-за закешированного негативного результата). Дополнительная защита от массового перебора несуществующих ID — bloom filter перед кешем: вероятностная структура, дающая быстрый ответ "точно нет" без похода ни в кеш, ни в БД для заведомо отсутствующих ключей (с контролируемой вероятностью ложноположительных, но никогда ложноотрицательных срабатываний).

## Hot key — один ключ, вся нагрузка

```
100 000 запросов/сек к ключу "config:global" — все идут на ОДИН шард Redis-кластера,
хотя остальные N-1 шардов кластера полностью простаивают
```

Шардирование Redis-кластера распределяет **разные** ключи по разным узлам, но не помогает, если весь трафик сфокусирован на одном конкретном ключе — единственный узел, отвечающий за этот ключ, становится узким местом независимо от общей ёмкости кластера. Типичные кейсы: глобальный конфиг, читаемый каждым запросом, счётчик/флаг вирусного контента, сессия знаменитости с аномальным трафиком.

**Решения:**
- **Локальное кеширование в памяти процесса** (in-memory LRU перед Redis, см. [03-multi-level-caching.md](./03-multi-level-caching.md)) — для по-настоящему горячих ключей поход в Redis вообще не нужен на каждый запрос, достаточно короткого TTL в локальной памяти каждого инстанса приложения.
- **Репликация горячего ключа под разными именами** (`config:global:0`..`config:global:9`, читающий код выбирает случайный суффикс) — размазывает нагрузку на конкретный ключ по нескольким физическим ключам, которые кластер может распределить по разным узлам.
- **Client-side caching** (Redis 6+ поддерживает инвалидацию на стороне клиента через RESP3-протокол) — клиент держит локальную копию, сервер уведомляет об изменении, что снимает нагрузку с сервера почти полностью для read-heavy горячих ключей.

## Что спрашивают на собеседовании

1. **Кеш популярной записи истёк, 1000 запросов одновременно пошли в БД — что это и как чинить?** — cache stampede; решения — распределённый лок (single flight, пересчитывает только один запрос), jitter на TTL (размазать истечение по времени), probabilistic early refresh (обновлять до истечения, не дожидаясь промаха).
2. **Почему обычный кеш не защищает от повторных запросов несуществующих данных?** — cache penetration: если кешируются только найденные значения, каждый запрос на отсутствующую запись — гарантированный промах, кеш структурно не участвует в защите; решение — negative caching (кешировать сам факт отсутствия с коротким TTL) и/или bloom filter.
3. **Что такое hot key и почему шардирование кластера от него не защищает?** — весь трафик к одному конкретному ключу физически идёт на один узел, отвечающий за этот ключ, независимо от общего числа узлов кластера — шардирование распределяет разные ключи, но не разные запросы к одному ключу.
4. **Как решить проблему hot key на практике?** — локальный in-memory кеш перед Redis для действительно горячих ключей, репликация ключа под несколькими именами со случайным выбором на чтение, client-side caching с server-side инвалидацией.
5. **Почему jitter на TTL помогает не только от stampede на одном ключе, но и в целом?** — множество ключей с одинаковым TTL, прогретых одновременно, истекают синхронно — создавая множественные stampede разом; случайный разброс размазывает истечение по времени, снижая пиковую нагрузку.
