# CPU-bound в Node: выявление через event loop lag, оффлоад в worker threads

> **TL;DR:** Node — один поток на весь JS-код (см. [Архитектура V8 + libuv](../02-nodejs-core/01-architecture.md)). Синхронный CPU-тяжёлый код (ресайз изображения, сложный парсинг, криптография без использования thread pool) блокирует этот единственный поток — пока он занят, event loop физически не может обработать вообще ничего другое: ни новые HTTP-запросы, ни таймеры, ни колбэки уже идущих I/O-операций. **Event loop lag** — прямая метрика этой блокировки: насколько запаздывает таймер, который должен был сработать немедленно.

## Симптом — один тяжёлый эндпоинт тормозит всё приложение

```ts
// уязвимо: синхронный CPU-bound код прямо в обработчике запроса
app.post('/resize', async (req, res) => {
  const resized = sharp(req.body.image).resize(800, 600).toBufferSync(); // блокирует event loop на время обработки
  res.send(resized);
});
```

Пока идёт ресайз одного изображения, **все остальные** запросы к серверу (даже к никак не связанным эндпоинтам — `/health`, `/users`) зависают в очереди, потому что единственный поток, исполняющий JS, занят этим одним вычислением. Внешне это выглядит как "сервер стал медленным целиком", хотя реально проблема — в одном конкретном тяжёлом эндпоинте, просто его блокировка касается вообще всех.

## Event loop lag — как измерить

```ts
import { monitorEventLoopDelay } from 'perf_hooks';

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

setInterval(() => {
  console.log({
    p50: histogram.percentile(50) / 1e6, // наносекунды -> миллисекунды
    p99: histogram.percentile(99) / 1e6,
    max: histogram.max / 1e6,
  });
  histogram.reset();
}, 5000);
```

`monitorEventLoopDelay` (тот же API, что упомянут в [Фазы event loop](../02-nodejs-core/02-event-loop-phases.md) как ключевая метрика здоровья) периодически ставит таймер и замеряет, насколько позже реального ожидаемого момента он сработал — задержка есть прямое отражение того, сколько времени event loop был занят чем-то другим (синхронным кодом) вместо своевременной обработки. Здоровый сервис — единицы миллисекунд p99 lag; рост до десятков-сотен миллисекунд — прямой сигнал, что где-то в коде исполняется тяжёлая синхронная работа.

**На какие цифры алертить:** конкретные пороги зависят от требований к latency сервиса, но практический ориентир — алертить, если p99 event loop lag устойчиво превышает несколько десятков миллисекунд (например, 50-100мс) — на этом уровне lag уже заметно добавляется к latency каждого запроса, обрабатываемого в этот момент, независимо от того, насколько сам запрос "лёгкий". Разовые всплески (GC-пауза, редкий тяжёлый запрос) отличимы от устойчивой деградации по тренду на графике, а не по единичному замеру.

## Диагностика — от симптома к причине

1. **Подтвердить через `monitorEventLoopDelay`** — растёт ли лаг синхронно с деградацией latency (см. алгоритм диагностики "медленного запроса" через профилирование в [Профилирование: CPU flame graph, clinic.js, --prof, memory](./05-profiling-cpu-memory.md)).
2. **`clinic doctor`** — подтвердит, что проблема именно CPU-bound (высокая занятость единственного JS-потока), а не I/O-задержка/ожидание внешнего сервиса, которые внешне тоже "медленно", но лечатся иначе (см. [Retry budget и таймауты повсюду](./07-retry-budget-timeouts.md) про таймауты для I/O-проблем).
3. **Flame graph под нагрузкой** — найти конкретную функцию/эндпоинт, съедающую CPU-время синхронно.

## Решение — оффлоад в worker threads

```ts
// main thread: делегирует тяжёлую работу воркеру, event loop main-потока остаётся свободным
import { Worker } from 'worker_threads';

app.post('/resize', (req, res) => {
  const worker = new Worker('./resize-worker.js', { workerData: req.body.image });
  worker.on('message', (resized) => res.send(resized));
  worker.on('error', (err) => res.status(500).send(err.message));
});

// resize-worker.js — выполняется в ОТДЕЛЬНОМ потоке с собственным event loop
const { workerData, parentPort } = require('worker_threads');
const resized = sharp(workerData).resize(800, 600).toBufferSync(); // блокирует ТОЛЬКО поток воркера
parentPort.postMessage(resized);
```

`worker_threads` даёт отдельный поток с собственным V8-инстансом и собственным event loop — тяжёлое синхронное вычисление там блокирует только этот конкретный воркер, не влияя на main-поток, который продолжает принимать и обрабатывать остальные запросы как обычно. Подробный разбор `worker_threads` vs `child_process` vs `cluster` (память, коммуникация между потоками, когда что уместно) — в [worker_threads / child_process / cluster](../02-nodejs-core/05-workers-cluster.md), здесь — именно применение к диагностированной CPU-bound проблеме.

**Альтернатива — вынести в отдельный сервис.** Если CPU-тяжёлая операция (обработка изображений, PDF-генерация, сложные вычисления) достаточно объёмна и изолирована по смыслу, часто разумнее вынести её в отдельный микросервис/фоновую очередь (см. [Очереди для сглаживания нагрузки: BullMQ](./09-queues-bullmq.md)), а не только в worker thread внутри того же процесса — это даёт независимое масштабирование именно этой тяжёлой части нагрузки, не заставляя реплицировать весь основной API-сервис ради одной прожорливой операции (тот же аргумент, что разобран для критериев выделения микросервиса в [Монолит vs модульный монолит vs микросервисы](../06-architecture-patterns/07-monolith-vs-microservices.md)).

## Что спрашивают на собеседовании

1. **Эндпоинт делает ресайз изображений и тормозит всё приложение — диагностика и решение.** — диагностика: рост event loop lag (`monitorEventLoopDelay`), `clinic doctor` подтверждает CPU-bound, flame graph находит конкретную функцию; решение — вынести тяжёлое вычисление в `worker_threads` (или отдельный сервис/очередь при достаточном объёме), чтобы не блокировать main-поток для всех остальных запросов.
2. **Как измерить event loop lag и на какие цифры алертить?** — `perf_hooks.monitorEventLoopDelay()`, метрика p99 в постоянном мониторинге; алертить на устойчивое превышение нескольких десятков миллисекунд, отличая тренд деградации от разовых всплесков (GC-пауза).
3. **Почему один тяжёлый CPU-bound эндпоинт тормозит вообще все остальные запросы, даже к другим эндпоинтам?** — единственный поток исполняет весь JS-код приложения; пока он занят синхронным вычислением, event loop не может обработать ничего другого, включая запросы к никак не связанным маршрутам.
4. **Как worker_threads решает эту проблему?** — отдельный поток с собственным V8-инстансом и event loop — тяжёлое вычисление блокирует только этот поток, main-поток продолжает обслуживать остальные запросы параллельно.
5. **Когда выносить CPU-тяжёлую работу в отдельный сервис вместо worker thread внутри того же процесса?** — когда объём и характер нагрузки оправдывают независимое масштабирование именно этой части (не реплицировать весь основной сервис ради одной прожорливой операции) — тот же критерий выделения сервиса, что и в целом для микросервисной архитектуры.
