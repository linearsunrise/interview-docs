# Нагрузочное тестирование: autocannon/k6, что мерить, coordinated omission

> **TL;DR:** Среднее время ответа — плохая метрика, потому что оно легко скрывает хвост распределения: 99 запросов по 10мс и один по 10 секунд дают среднее ~110мс — звучит нормально, но 1% пользователей реально ждал 10 секунд. Перцентили (p50, p95, p99) показывают, что происходит с конкретной долей запросов, а не усреднённую фикцию. При достаточном числе запросов на пользовательскую сессию (страница со множеством API-вызовов) p99 затрагивает почти каждого пользователя хотя бы раз — это не "редкий edge case", а статистически почти гарантированный опыт при накоплении вызовов.

## Почему среднее обманывает

```
Запросы (мс): 10, 10, 10, 10, 10, 10, 10, 10, 10, 10000  (10 запросов, один аномально медленный)
Среднее: (9×10 + 10000) / 10 = 1009мс — выглядит "средне плохо"
p50 (медиана): 10мс — половина запросов реально быстрые
p90: 10мс — тоже быстрые
p99: 10000мс — та самая аномалия видна явно
```

Среднее "размазывает" единичный выброс по всей выборке, делая typical experience (то, что видит большинство) неотличимым по метрике от того, что видит меньшинство с плохим опытом. Перцентиль pN — значение, ниже которого попадает N% измерений: p50 — медиана (типичный опыт), p95/p99 — что происходит с "плохим хвостом" запросов, которые обычно и определяют жалобы пользователей и репутацию сервиса, даже если их формально мало в процентном отношении.

## Почему p99 — это почти каждый пользователь, а не редкий edge case

Если одна страница делает 100 независимых API-вызовов (типично для сложного дашборда/SPA с множеством виджетов), и у каждого отдельного вызова p99 latency означает "1 из 100 запросов попадает в этот медленный хвост" — вероятность, что **хотя бы один** из 100 вызовов этой конкретной страницы попадёт в p99, при независимых вызовах приближается к `1 - (0.99)^100 ≈ 63%`. То есть "редкий" 1%-й хвост при накоплении вызовов на сессию превращается в опыт большинства пользователей, а не исчезающе малой доли — именно поэтому p99 нельзя игнорировать как "статистическую погрешность".

## `autocannon` — простой HTTP-нагрузочный инструмент для Node-экосистемы

```bash
npx autocannon -c 100 -d 30 -p 10 http://localhost:3000/api/orders
# -c 100: 100 одновременных соединений
# -d 30: длительность 30 секунд
# -p 10: до 10 pipelined-запросов на соединение
```

```
Stat    2.5%   50%    97.5%  99%   Avg     Stdev   Max
Latency 8ms    45ms   210ms  480ms 62ms    ...
Req/Sec ...
```

Простой в использовании инструмент (одна npm-команда, без отдельного скриптования сценария) — подходит для быстрой проверки "выдерживает ли этот конкретный эндпоинт N RPS" и грубого сравнения до/после оптимизации (тот же принцип измерения до и после, что и в профилировании, см. [05-profiling-cpu-memory.md](./05-profiling-cpu-memory.md)). Ограничение — тестирует один эндпоинт с фиксированным паттерном запроса, не реалистичные многошаговые пользовательские сценарии.

## `k6` — сценарное нагрузочное тестирование

```js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 50 },  // плавный разгон до 50 VU (virtual users)
    { duration: '1m', target: 50 },   // удержание нагрузки
    { duration: '10s', target: 0 },   // плавный спад
  ],
  thresholds: {
    'http_req_duration': ['p(99)<500'], // тест ПРОВАЛЕН, если p99 latency превышает 500мс
    'http_req_failed': ['rate<0.01'],   // и если error rate выше 1%
  },
};

export default function () {
  const res = http.get('http://localhost:3000/api/orders');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);
}
```

k6 позволяет описать реалистичный многошаговый сценарий (логин → просмотр каталога → добавление в корзину → оформление заказа — не один изолированный эндпоинт), задать профиль нагрузки во времени (постепенный разгон, устойчивая нагрузка, спайк, плавный спад — а не мгновенный "залп" запросов) и явные пороги (`thresholds`), при нарушении которых тест считается провалившимся — удобно встраивать в CI как формальный gate перед релизом, не полагаясь на ручной просмотр графиков.

## Что мерить

- **Латентность по перцентилям (p50/p95/p99)**, не только среднее — см. выше, почему.
- **RPS (requests per second)** — реальная пропускная способность при заданной latency, не абстрактный "максимум", а именно RPS **при** приемлемых p95/p99 (система может держать высокий RPS ценой деградации latency — важно знать, при каком RPS latency ещё в допустимых рамках, не просто "сколько запросов в секунду выдержит, пока не упадёт совсем").
- **Error rate** — доля неуспешных ответов (5xx, таймауты) под нагрузкой — растущий error rate при росте нагрузки часто более ранний и явный сигнал проблемы, чем плавная деградация latency.
- **Насыщение ресурсов параллельно с нагрузкой** — CPU, память, event loop lag (см. [06-cpu-bound-event-loop-lag.md](./06-cpu-bound-event-loop-lag.md)), число соединений в пуле к БД — latency/RPS/error rate показывают **что** происходит, метрики ресурсов — **почему**.

## Coordinated omission — скрытая ловушка измерения latency

```
Наивный нагрузочный инструмент: отправить запрос → ДОЖДАТЬСЯ ответа → отправить следующий
Если сервер завис на 5 секунд — инструмент просто НЕ ОТПРАВЛЯЕТ запросы эти 5 секунд,
вместо того чтобы зафиксировать 5 секунд ожидания для КАЖДОГО запроса, который "должен был" уйти в этот момент
→ latency-метрики выглядят ЛУЧШЕ, чем реальный опыт пользователей, потому что "пропущенные" медленные периоды
   не попадают в статистику вообще, а не искажают её как аномальные измерения
```

Термин введён Gil Tene (создатель HdrHistogram): если инструмент нагрузочного тестирования отправляет следующий запрос только после получения ответа на предыдущий (закрытая модель, closed-loop), период, когда сервер "подвис", просто **не генерирует** запросов вместо того, чтобы генерировать запросы, которые ожидали бы ответа аномально долго — сервер получает "поблажку" именно в момент, когда реальные пользователи страдали бы больше всего (в реальности пользователи продолжают приходить с постоянной интенсивностью независимо от того, успевает сервер отвечать или нет). Правильная модель — **открытый цикл** (open-loop): генерировать запросы с заданной постоянной интенсивностью **независимо** от того, ответил ли сервер на предыдущие — так, как ведёт себя реальный трафик множества независимых пользователей. `k6` и современные версии подобных инструментов поддерживают открытую модель нагрузки (constant arrival rate, не constant VU count) именно для того, чтобы не наступать на эту ловушку.

## Что спрашивают на собеседовании

1. **Почему среднее время ответа — плохая метрика?** — скрывает хвост распределения: единичные аномально медленные запросы "размазываются" по всей выборке, делая проблему невидимой, хотя перцентили (p95/p99) показывают её явно.
2. **p99 latency вырос, p50 в норме — какие гипотезы и как копать?** — типичные причины: GC-паузы (эпизодические, не влияют на медиану), исчерпание пула соединений к БД под пиковой нагрузкой, медленные запросы у конкретной подгруппы пользователей (hot key, специфичные данные), редкие тяжёлые операции — копать через event loop lag, профилирование под нагрузкой, разбивку latency по сегментам трафика.
3. **Почему p99 при 100 запросах на страницу почти гарантированно затрагивает каждого пользователя?** — при независимых вызовах вероятность, что хотя бы один из 100 попадёт в "плохой" 1%-й хвост, приближается к `1 - 0.99^100 ≈ 63%` — редкий хвост при накоплении вызовов на сессию становится опытом большинства.
4. **Что такое coordinated omission и почему это проблема нагрузочного тестирования?** — closed-loop инструмент, ждущий ответа перед отправкой следующего запроса, "пропускает" период зависания сервера вместо фиксации аномально долгого ожидания — искусственно занижает измеренную latency по сравнению с реальным опытом пользователей, приходящих с постоянной интенсивностью независимо от состояния сервера.
5. **autocannon vs k6 — когда что использовать?** — autocannon — быстрая проверка одного эндпоинта, простое сравнение до/после без написания сценария; k6 — реалистичные многошаговые пользовательские сценарии, профили нагрузки во времени, явные пороги для встраивания в CI как формальный gate.
