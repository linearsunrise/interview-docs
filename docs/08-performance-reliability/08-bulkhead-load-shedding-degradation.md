# Bulkhead, load shedding, graceful degradation

> **TL;DR:** Три паттерна о том, как система ведёт себя **под перегрузкой**, а не как избежать перегрузки (это отдельная тема retry/timeout/circuit breaker, см. [Retry budget и таймауты повсюду](./07-retry-budget-timeouts.md) и [Circuit Breaker, retry с backoff+jitter, timeout budget](../06-architecture-patterns/11-circuit-breaker-retry.md)). Bulkhead — изолировать ресурсы так, чтобы один перегруженный компонент не забрал ресурсы у остальных. Load shedding — сознательно отказывать части запросов **до** того, как система рухнет вся целиком. Graceful degradation — под нагрузкой отключать не критичную функциональность, чтобы сохранить критичную работающей, вместо отказа всего сервиса разом.

## Bulkhead — изоляция ресурсов по названию корабельных переборок

```ts
// плохо: один общий пул соединений для всех внешних вызовов
const sharedPool = new Pool({ max: 20 }); // используется и для БД, и для медленного внешнего API

// хорошо: раздельные пулы — деградация одного не исчерпывает ресурсы для остальных
const dbPool = new Pool({ max: 15 });          // критичный путь — своя изолированная ёмкость
const externalApiPool = new Pool({ max: 5 });  // ненадёжный внешний сервис — ограниченная ёмкость,
                                                 // даже если он весь зависнет, останется 15 слотов для БД
```

Название — от корабельных переборок (bulkheads), физически разделяющих корпус на отсеки: пробоина в одном отсеке не топит весь корабль, потому что вода не может перетечь в остальные. В программной системе то же самое — если один внешний зависимый сервис начинает массово подвисать (не падает явно с ошибкой, а просто медленно отвечает), и все запросы к нему используют **общий** пул потоков/соединений с остальной системой, этот один зависший компонент постепенно "съедает" всю доступную ёмкость пула, оставляя её недоступной для запросов, которые вообще не имеют отношения к проблемному сервису. Изолированные пулы (по внешней зависимости, по критичности пути, по типу операции) гарантируют, что деградация одного не может физически исчерпать ресурсы, зарезервированные для другого — это структурная защита, работающая даже если по какой-то причине не сработал таймаут/circuit breaker на самом зависшем вызове.

## Load shedding — сознательно отказать, пока не рухнуло всё

```ts
app.use((req, res, next) => {
  const currentLoad = getEventLoopLagOrQueueDepth(); // метрика текущей перегрузки, см. 06-cpu-bound-event-loop-lag.md
  if (currentLoad > THRESHOLD) {
    return res.status(503).set('Retry-After', '5').send('Service overloaded, try again shortly');
  }
  next();
});
```

Идея — не пытаться обработать **абсолютно все** входящие запросы любой ценой, когда система уже перегружена сверх своей реальной пропускной способности: попытка поставить всё в очередь и обработать по мере сил под сильной перегрузкой обычно приводит к тому, что **все** запросы (включая те, что могли бы быть обработаны быстро) деградируют по latency одновременно, вплоть до полного коллапса (система тратит всё больше ресурсов на поддержание растущей очереди, а не на реальную полезную работу). Load shedding на границе (API gateway, load balancer, или прямо в приложении) сознательно отклоняет **часть** запросов с быстрым `503` + `Retry-After`, как только метрика перегрузки (event loop lag, глубина очереди, число активных соединений) пересекает порог — оставшаяся часть трафика обрабатывается с нормальной latency, вместо того чтобы всем клиентам одинаково плохо ждать неопределённо долго.

**Когда отдавать 503 вместо постановки в очередь** — если ожидание в очереди означает, что к моменту обработки результат уже никому не нужен (пользователь давно закрыл вкладку, upstream-сервис уже сдался по своему таймауту) — быстрый явный отказ честнее и дешевле для системы, чем тихая деградация всех вместе. Постановка в очередь оправдана, когда: (а) есть разумная гарантия, что очередь рассосётся за приемлемое время, и (б) потребитель результата готов подождать (фоновая обработка, а не синхронный HTTP-запрос с ожидающим пользователем, см. [Очереди для сглаживания нагрузки: BullMQ](./09-queues-bullmq.md)).

## Graceful degradation — отключить неважное, сохранить важное

```ts
async function getProductPage(id: string) {
  const product = await productService.get(id); // критично — без этого страницы нет вообще

  let recommendations: Product[] = [];
  try {
    recommendations = await withTimeout(recommendationService.get(id), 200); // некритично
  } catch {
    recommendations = []; // деградировали конкретно эту секцию, но страница всё ещё работает
  }

  return { product, recommendations };
}
```

Под перегрузкой (или при частичном отказе конкретной нижестоящей зависимости) система явно жертвует не критичной функциональностью, чтобы сохранить работоспособность основной. Практические примеры: показать страницу товара без блока "рекомендации" вместо ошибки всей страницы; отдать чуть устаревшие (stale) данные из кеша вместо ожидания свежего пересчёта; отключить неточную, но дорогую в вычислении персонализацию в пользу более простой общей выдачи под пиковой нагрузкой. Отличие от простого try/catch с фолбэком в том, что это осознанное **архитектурное** решение — заранее определить, какая функциональность критична (без неё сервис бесполезен), а какая — приятное дополнение, которым можно пожертвовать под давлением, а не хаотично расставленные try/catch там, где разработчику показалось уместным.

## Как эти три паттерна дополняют друг друга

Bulkhead предотвращает то, чтобы деградация одной зависимости физически исчерпала ресурсы для остальной системы. Load shedding — реакция на общую перегрузку системы целиком, когда даже с bulkhead-изоляцией суммарного спроса больше, чем система может выдержать. Graceful degradation — способ сохранить хоть какую-то работоспособность именно там, где нельзя просто отказать (пользователь уже открыл страницу и ждёт хоть что-то), в отличие от load shedding, который отказывает целиком на входе. Вместе с circuit breaker/retry budget/таймаутами (см. [Retry budget и таймауты повсюду](./07-retry-budget-timeouts.md)) — это набор инструментов resilience engineering, каждый решающий свою грань одной общей задачи: система под давлением должна деградировать предсказуемо и частично, а не рушиться каскадно и полностью.

## Что спрашивают на собеседовании

1. **Что такое bulkhead и откуда название?** — изоляция ресурсов (пулов соединений/потоков) по зависимости/критичности пути — по аналогии с корабельными переборками, где пробоина в одном отсеке не топит весь корабль; деградация одной внешней зависимости не может исчерпать ресурсы, зарезервированные для остальной системы.
2. **Что такое load shedding и когда лучше отдать 503, чем поставить запрос в очередь?** — сознательный отказ части запросов при превышении порога перегрузки, чтобы оставшийся трафик обслуживался с нормальной latency вместо равномерной деградации всех; 503 предпочтительнее, когда ожидание в очереди не гарантирует, что результат к моменту готовности ещё кому-то нужен.
3. **Чем graceful degradation отличается от обычного try/catch с фолбэком?** — заранее определённое архитектурное решение о том, какая функциональность критична, а какой можно осознанно пожертвовать под нагрузкой — не хаотичная расстановка обработки ошибок, а системный подход к приоритизации.
4. **Почему общий пул соединений для критичного и ненадёжного внешнего вызова — плохая идея?** — зависший/медленный внешний сервис постепенно занимает весь общий пул, оставляя критичные запросы (даже никак не связанные с проблемным сервисом) без доступных соединений/потоков.
5. **Как эти паттерны соотносятся с circuit breaker и retry budget?** — дополняют друг друга: bulkhead ограничивает распространение локальной деградации, circuit breaker/retry budget ограничивают бесполезные попытки достучаться до уже упавшего компонента, load shedding и graceful degradation — реакция системы на общую перегрузку, когда первых двух механизмов недостаточно.
