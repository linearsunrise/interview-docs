# Многоуровневый кеш: in-memory (LRU) + Redis — консистентность между инстансами

> **TL;DR:** Локальная in-memory LRU-кеш (например, `lru-cache` в процессе Node) на порядок быстрее похода в Redis (наносекунды vs доли миллисекунды сетевого round-trip) — оправдана для действительно горячих данных. Цена — у **каждого** инстанса приложения своя, независимая копия кеша: инвалидация одного инстанса не убирает устаревшее значение из памяти остальных N-1 инстансов автоматически — это и есть главная сложность многоуровневого кеша, решаемая через pub/sub-инвалидацию или версионирование ключей.

## Схема — L1 (in-memory) перед L2 (Redis) перед источником истины

```ts
const localCache = new LRUCache<string, User>({ max: 1000, ttl: 30_000 }); // L1: в памяти процесса

async function getUser(id: string): Promise<User> {
  const local = localCache.get(id);
  if (local) return local; // L1 hit — быстрее всего, без сети вообще

  const cached = await redis.get(`user:${id}`); // L2 hit — сетевой round-trip, но всё ещё быстрее БД
  if (cached) {
    const user = JSON.parse(cached);
    localCache.set(id, user);
    return user;
  }

  const user = await userRepo.findById(id); // промах обоих уровней — источник истины
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300);
  localCache.set(id, user);
  return user;
}
```

Каждый уровень — фильтр, снижающий нагрузку на следующий: L1 отсекает большинство запросов к по-настоящему горячим ключам без сети вообще, L2 (Redis, общий на все инстансы) отсекает то, что не попало в L1, но уже было загружено кем-то из БД, а до БД доходят только реальные промахи обоих уровней.

## Проблема — инвалидация L1 на N инстансах

```
Инстанс 1: обновил user:42, удалил из своего L1 И из Redis (L2)
Инстанс 2: у него в L1 ВСЁ ЕЩЁ старая версия user:42 — никто не сказал ЕМУ инвалидировать
Инстанс 3: то же самое
→ пользователи, чьи запросы попадают на инстанс 2/3, видят устаревшие данные, пока не истечёт локальный TTL
```

Инвалидация Redis (L2) видна всем инстансам сразу, потому что это общее хранилище — следующий промах L1 на любом инстансе прочитает уже актуальное значение из L2. Но пока L1 конкретного инстанса не промахнулся сам (его локальный TTL ещё не истёк), он продолжает отдавать устаревшее значение из собственной памяти — L2-инвалидация не "дотягивается" до чужой оперативной памяти автоматически.

## Решение 1 — pub/sub инвалидация между инстансами

```ts
// при обновлении: инвалидируем L2 (Redis) И рассылаем сообщение всем инстансам
async function updateUser(id: string, dto: UpdateUserDto) {
  const user = await userRepo.update(id, dto);
  await redis.del(`user:${id}`);
  await redis.publish('cache-invalidation', JSON.stringify({ key: `user:${id}` }));
  return user;
}

// каждый инстанс подписан и чистит СВОЙ локальный L1 при получении события
redis.subscribe('cache-invalidation');
redis.on('message', (channel, message) => {
  const { key } = JSON.parse(message);
  localCache.delete(key);
});
```

Тот же механизм Redis pub/sub, что разобран для доставки сообщений между инстансами WebSocket-сервера (см. [WebSockets: handshake, масштабирование, heartbeat](../05-api-communication/08-websockets.md)) — здесь применяется к синхронизации инвалидации локальных кешей. Каждый инстанс, обновивший данные, оповещает **все остальные** через общий канал — они удаляют устаревшую запись из своей локальной памяти немедленно, а не ждут истечения собственного TTL. Ограничение — pub/sub Redis не гарантирует доставку сообщения инстансу, который был временно отключён/не успел подписаться (в отличие от Redis Streams с consumer groups, см. [Redis](../04-databases/13-redis.md)) — короткий локальный TTL остаётся необходимой страховкой поверх pub/sub-инвалидации, а не заменяется ею полностью.

## Решение 2 — версионирование ключей вместо явной инвалидации

```ts
async function getCacheVersion(): Promise<number> {
  return Number(await redis.get('cache:version')) || 0;
}

async function getUser(id: string): Promise<User> {
  const version = await getCacheVersion(); // дешёвый общий счётчик в Redis
  const cacheKey = `user:${id}:v${version}`;

  const local = localCache.get(cacheKey);
  if (local) return local;
  // ... обычная логика L1/L2/БД с cacheKey вместо простого id
}

async function invalidateAllCaches() {
  await redis.incr('cache:version'); // ОДНА операция инвалидирует ВСЁ и везде
}
```

Вместо явного удаления каждого конкретного ключа на каждом инстансе, ключи включают номер версии — инкремент общего счётчика версии в Redis мгновенно "обесценивает" все ключи со старой версией **везде**, потому что новые запросы формируют ключ уже с новым номером версии, а старые ключи просто перестают запрашиваться (и со временем вытесняются по LRU/TTL, не требуя активного удаления). Хорошо подходит для инвалидации **широких** наборов данных разом (весь кеш конкретного типа сущности) — менее гранулярно, чем точечная pub/sub-инвалидация по конкретному ключу, но проще и без необходимости в надёжной доставке сообщений между инстансами.

## Что спрашивают на собеседовании

1. **Как инвалидировать кеш при обновлении сущности на 5 инстансах с локальным LRU?** — pub/sub-канал в Redis: инстанс, выполнивший обновление, оповещает остальные, каждый чистит свою локальную копию; либо версионирование ключей — инкремент общего счётчика в Redis мгновенно обесценивает все ключи старой версии везде без точечного удаления.
2. **Зачем вообще нужен локальный L1-кеш, если есть общий Redis?** — L1 на порядок быстрее (наносекунды в памяти процесса против сетевого round-trip к Redis) — оправдан для действительно горячих данных, где даже поход в Redis становится заметным узким местом.
3. **Почему инвалидация Redis (L2) не решает проблему устаревших данных в L1 автоматически?** — L2 — общее хранилище, видное всем сразу, но L1 каждого инстанса — независимая копия в его собственной памяти; L2-инвалидация "не дотягивается" до чужой оперативной памяти без отдельного механизма оповещения.
4. **Достаточно ли pub/sub-инвалидации самой по себе, без TTL на L1?** — нет: Redis pub/sub не гарантирует доставку временно отключённому/переподключающемуся подписчику — короткий локальный TTL остаётся необходимой страховкой на случай пропущенного сообщения, тем же принципом, что TTL страхует явную инвалидацию в одноуровневом кеше.
5. **Чем версионирование ключей лучше/хуже точечной pub/sub-инвалидации?** — версионирование проще (одна операция инвалидирует всё разом) и не требует надёжной доставки сообщений, но менее гранулярно — инвалидирует широкий набор данных целиком, а не конкретный изменившийся ключ.
