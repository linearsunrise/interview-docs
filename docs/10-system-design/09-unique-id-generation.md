# Уникальные ID: UUID vs Snowflake vs sequence — trade-offs

> **TL;DR:** Три подхода отвечают на разные приоритеты: `sequence` (авто-инкремент БД) — простой и компактный, но требует централизованной координации (не масштабируется горизонтально без узкого места). UUID — генерируется где угодно без координации вообще, но случаен (не сортируем по времени, раздувает B-tree индексы, см. [04-databases/01-btree-indexes.md](../04-databases/01-btree-indexes.md)). Snowflake — компромисс: распределённая генерация без центрального координатора **и** сортируемость по времени, ценой встроенной зависимости от синхронизации часов узлов.

## Sequence (auto-increment) — простой, но требует координатора

```sql
CREATE TABLE orders (id bigserial PRIMARY KEY, ...); -- PostgreSQL sequence генерирует 1, 2, 3, ...
```

Компактный (8 байт для `bigint`), строго монотонно возрастающий, естественно сортируем по порядку создания — удобен для пагинации (см. [04-databases/10-pagination.md](../04-databases/10-pagination.md)) и для кластерного индекса (в СУБД, где он есть). Фундаментальное ограничение — генерация ID требует похода к **единственному** источнику истины (счётчик в конкретной БД) — при шардировании БД на несколько независимых инстансов (см. [04-databases/12-sharding-partitioning.md](../04-databases/12-sharding-partitioning.md)) каждый шард с собственным auto-increment начал бы генерировать **дублирующиеся** ID (шард A и шард B оба выдадут `id=1` для своей первой строки) — sequence по своей природе не работает без единой точки координации, что прямо противоречит цели горизонтального шардирования.

## UUID — генерация без координации, ценой случайности

```ts
crypto.randomUUID(); // "3f29b6a1-3e5c-4b8a-9c2d-7e8f1a2b3c4d" — UUIDv4, 128 бит, полностью случайный
```

Любой узел (клиент, любой сервис, без похода к общему координатору) может сгенерировать UUID с астрономически низкой вероятностью коллизии — идеален для полностью децентрализованной генерации. Цена — UUIDv4 **не сортируем по времени создания** и не имеет никакой внутренней структуры, коррелирующей с порядком вставки — это создаёт конкретную практическую проблему для B-tree первичного ключа/индекса (особенно в кластерных индексах, см. [04-databases/01-btree-indexes.md](../04-databases/01-btree-indexes.md) про InnoDB): вставки со случайным ключом попадают в случайные, а не последовательные позиции дерева/страниц, что фрагментирует индекс и снижает эффективность кеша страниц (последовательные вставки с растущим ключом хорошо ложатся в "горячую" последнюю страницу дерева, случайные — размазаны по всему дереву). Занимает вдвое больше места, чем `bigint` (16 байт против 8).

## UUIDv7 — решение проблемы сортируемости внутри UUID-формата

```
UUIDv7: [48 бит unix timestamp в мс][12 бит случайности][62 бита случайности]
        "018f4d2a-7c3e-7a1b-9f4e-2b6c8e1a3d5f"
        ─────┬─────
        монотонно растёт со временем — сортируем как обычный timestamp
```

UUIDv7 (стандартизирован в [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html), 2024) сохраняет размер (128 бит) и децентрализованную генерацию UUID, но кодирует timestamp в старшие биты — значения растут монотонно по времени создания (в отличие от полностью случайного UUIDv4), что почти полностью устраняет проблему фрагментации индекса, сохраняя нулевую координацию между генераторами. На практике — часто предпочтительнее UUIDv4 для новых систем именно по этой причине, если библиотека/база данных уже поддерживает генерацию v7.

## Snowflake — распределённая генерация с сортируемостью, изобретение Twitter

```
64-битное число: [1 бит знак][41 бит timestamp (мс с epoch)][10 бит machine ID][12 бит порядковый номер в этой мс]

Пример: узел #5, в момент времени T, третий ID, сгенерированный на этом узле за эту миллисекунду
```

Каждый узел (заранее назначенный уникальный `machine ID`, например, номер шарда/датацентра) генерирует ID **самостоятельно**, без похода к центральному координатору — timestamp в старших битах гарантирует примерную сортируемость по времени между **разными** узлами (ID, сгенерированные позже, численно больше, даже если сгенерированы на разных машинах), а комбинация `machine ID` + порядковый номер внутри миллисекунды гарантирует уникальность между узлами и внутри одного узла при множественной генерации в одну и ту же миллисекунду. Компактнее UUID (64 бита вместо 128, помещается в обычный `bigint`), сортируем как sequence, но без единой точки координации как UUID.

## Trade-off Snowflake — зависимость от синхронизации часов

```
Узел A: системные часы отстают на 5 секунд (не синхронизированы через NTP)
Узел A генерирует ID со "старым" timestamp → ID, созданный ПОЗЖЕ реального времени, может оказаться
                                                 ЧИСЛЕННО МЕНЬШЕ ID, созданного раньше на узле B с корректными часами
→ сортировка по ID перестаёт точно отражать реальный порядок создания между узлами
```

Snowflake полагается на то, что часы разных узлов достаточно синхронизированы (обычно через NTP) — рассинхрон часов не ломает уникальность ID (комбинация timestamp+machineID+counter всё ещё уникальна), но ломает **гарантию сортируемости** между узлами с разным временем — если приложение полагается на строгий порядок ID как источник истины о реальном порядке событий (а не просто "примерно по времени, достаточно для большинства целей"), рассинхрон часов — реальный практический риск, требующий мониторинга NTP-синхронизации инфраструктуры как часть эксплуатации системы.

## Сравнение и практический выбор

| | Sequence | UUID (v4) | UUID (v7) | Snowflake |
|---|---|---|---|---|
| Координация между узлами | требуется (единый источник) | не требуется | не требуется | не требуется |
| Размер | 8 байт | 16 байт | 16 байт | 8 байт |
| Сортируемость по времени | да (строго) | нет | да (примерно) | да (примерно) |
| Подходит для шардированной записи | нет | да | да | да |
| Зависимость от синхронизации часов | нет | нет | да (для сортируемости, не уникальности) | да (для сортируемости, не уникальности) |

Практический выбор в system design ответе — для нешардированной единой БД sequence достаточен и проще всего; как только пишущая нагрузка распределена по нескольким независимым узлам (шардированная БД, множество сервисов, генерирующих ID независимо), нужна одна из децентрализованных схем — UUIDv7, если сортируемость нужна не критично строго и библиотека/экосистема уже поддерживает v7, или собственная Snowflake-подобная схема, если нужен компактный размер и предсказуемая структура ID (что также раскрывает информацию — узел и примерное время создания, о чём стоит подумать с точки зрения того, не является ли это утечкой данных для внешне видимых ID).

## Что спрашивают на собеседовании

1. **Почему нельзя просто использовать auto-increment БД при шардировании данных?** — sequence требует единого центрального счётчика — каждый независимый шард с собственным auto-increment начнёт генерировать дублирующиеся ID, что прямо противоречит цели горизонтального шардирования.
2. **В чём практическая проблема UUIDv4 как первичного ключа с точки зрения БД?** — полная случайность значений фрагментирует B-tree индекс (вставки попадают в случайные, не последовательные позиции дерева), особенно ощутимо для кластерных индексов — снижает эффективность кеша страниц по сравнению с монотонно растущим ключом.
3. **Как устроен Snowflake ID и какие гарантии он даёт?** — комбинация timestamp + machine ID + порядковый номер внутри миллисекунды в одном 64-битном числе — децентрализованная генерация без координатора, компактность как у sequence, примерная сортируемость по времени между узлами.
4. **От чего зависит корректность сортировки Snowflake ID между разными узлами?** — от синхронизации системных часов узлов (обычно через NTP); рассинхрон не ломает уникальность, но ломает точность сортировки по времени между узлами с разным временем.
5. **Чем UUIDv7 лучше UUIDv4 для использования в качестве первичного ключа?** — кодирует timestamp в старшие биты, значения растут монотонно по времени создания — почти устраняет проблему фрагментации индекса UUIDv4, сохраняя децентрализованную генерацию без координатора и стандартный 128-битный формат.
