# Кейс: Rate limiter как сервис

> **TL;DR:** Отличие от «просто добавить rate limiting в API» (см. [10-rate-limiting-fanout-design.md](./10-rate-limiting-fanout-design.md)) — здесь rate limiter проектируется как **самостоятельный переиспользуемый сервис**, которым пользуются множество других независимых сервисов организации, каждый со своими правилами лимитов. Это смещает акцент с самого алгоритма (уже разобран в [07-security/12-rate-limiting.md](../07-security/12-rate-limiting.md)) на API-дизайн сервиса, точность vs производительность и поведение при недоступности самого лимитера.

## Требования

**Функциональные:** проверка "разрешён ли этот запрос прямо сейчас" по произвольному ключу (user ID, IP, API key) и произвольному настраиваемому правилу (N запросов за окно T), поддержка разных правил для разных клиентов/эндпоинтов, административный API для настройки правил.

**Нефункциональные:** сам rate limiter не должен стать узким местом производительности для сервисов, которые его используют (проверка лимита должна быть на порядок быстрее самой операции, которую она защищает), точность важна, но абсолютная точность (никогда ни на йоту не превысить лимит) обычно не требуется — контролируемая погрешность в обмен на производительность — осознанный trade-off, а не недоработка.

## Оценка

```
Используется ДЕСЯТКАМИ внутренних сервисов, каждый — тысячи RPS → сам rate limiter должен
выдерживать СУММАРНО десятки-сотни тысяч проверок/сек, с latency в единицы миллисекунд
(проверка лимита не должна становиться заметной долей latency защищаемой операции)
```

## High-level design

```
[Service A] ─┐
[Service B] ─┼──→ [Rate Limiter Service API] → [Redis Cluster: состояние счётчиков]
[Service C] ─┘              │
                       [Rules Config (какие лимиты для каких клиентов/эндпоинтов)]
```

```
POST /check
{ "key": "user:42:api:/orders", "limit": 100, "windowSec": 60 }
→ { "allowed": true, "remaining": 37, "resetAt": "..." }
```

Простой, максимально быстрый API — сервисы-потребители делают один вызов на каждый защищаемый запрос (или встраивают клиентскую библиотеку, локально кеширующую часть состояния — см. деталь ниже про точность vs производительность), rate limiter возвращает булево решение плюс метаданные для формирования правильных HTTP-заголовков (`X-RateLimit-Remaining`, `Retry-After`).

## Deep dive 1 — выбор алгоритма именно в контексте сервиса, не изолированно

Алгоритмы (fixed window, sliding window log/counter, token bucket) разобраны детально в [07-security/12-rate-limiting.md](../07-security/12-rate-limiting.md) — в контексте отдельного сервиса добавляется требование **единообразия**: разные потребители сервиса могут хотеть разное поведение (одному нужна строгая точность без граничного эффекта fixed window, другому — допустима погрешность ради максимальной скорости) — практическое решение — поддержать несколько алгоритмов как настраиваемый параметр правила, а не жёстко зашивать один на весь сервис. Token bucket обычно предпочтителен как дефолт для API-лимитов (допускает контролируемый всплеск — реалистичный паттерн использования API клиентами, которые могут делать пачку запросов после паузы), sliding window counter — когда точность важнее допущения всплесков.

## Deep dive 2 — точность vs производительность: локальный кеш решения

```
Вариант А (максимальная точность): КАЖДЫЙ запрос идёт в Redis Cluster за актуальным решением
                                     → сетевой round-trip на каждую проверку, добавляет latency

Вариант Б (компромисс): клиентская библиотека в самом Service A кеширует локально "разрешено до N запросов
                          в ближайшие M миллисекунд" батчами, синхронизируясь с центральным Redis реже
                          → меньше latency и нагрузки на центральный Redis, ценой контролируемой погрешности
                            (локальный кеш может немного отставать от реального состояния при резком
                             изменении темпа запросов на конкретном инстансе)
```

Это прямое применение trade-off consistency vs latency (см. [03-cap-consistency-models.md](./03-cap-consistency-models.md)) к конкретной инженерной задаче — большинство реальных rate limiter'ов (включая внутренние системы крупных компаний) сознательно жертвуют абсолютной точностью ради снижения latency и нагрузки на центральное хранилище состояния, потому что цена редкого небольшого превышения лимита обычно намного меньше цены добавления сетевого round-trip к каждому защищаемому запросу в системе.

## Deep dive 3 — поведение при недоступности самого rate limiter

```
Fail-open:  Rate Limiter Service недоступен → ПРОПУСТИТЬ запрос без проверки лимита
            (риск: временное отсутствие защиты, но сервисы-потребители продолжают работать)

Fail-closed: Rate Limiter Service недоступен → ОТКЛОНИТЬ запрос
             (риск: полный отказ ВСЕХ защищаемых сервисов из-за недоступности ОДНОГО вспомогательного сервиса —
              rate limiter становится единой точкой отказа для всей организации)
```

Это конкретное применение общего вопроса "что произойдёт, если этот компонент упадёт?" (красный флаг чек-листа system design про failure modes) к сервису, который сам по себе — не бизнес-критичная функциональность, а защитный механизм **поверх** неё. Практический ответ для большинства организаций — **fail-open**: rate limiter защищает от злоупотреблений и перегрузки, но его собственная недоступность не должна каскадно валить весь остальной трафик организации (тот же принцип bulkhead-изоляции критичного пути от вспомогательного, см. [08-performance-reliability/08-bulkhead-load-shedding-degradation.md](../08-performance-reliability/08-bulkhead-load-shedding-degradation.md)) — fail-closed оправдан только для очень специфичных сценариев, где отсутствие rate limiting эквивалентно реальной угрозе безопасности/устойчивости (например, публичный анонимный эндпоинт без всякой другой защиты от DoS).

## Узкие места и эволюция

- **Redis Cluster как центральное состояние** — сам по себе нуждается в шардировании по ключу лимита (consistent hashing, см. [06-load-balancing-sharding-consistent-hashing.md](./06-load-balancing-sharding-consistent-hashing.md)) при достаточном масштабе — иначе сам Redis становится узким местом для сервиса, чья единственная задача — не быть узким местом.
- **Multi-region** — если сервисы-потребители развёрнуты в нескольких регионах, глобально консистентный счётчик по одному ключу через регионы создаёт межконтинентальную latency (см. опорные числа в [02-back-of-envelope-estimation.md](./02-back-of-envelope-estimation.md)) — практика — региональные счётчики с приблизительной синхронизацией между регионами, а не единый глобальный счётчик.

## Что уточнить у интервьюера в начале

- Нужна ли строгая точность лимита, или приемлема контролируемая погрешность ради производительности?
- Развёрнуты ли сервисы-потребители в одном регионе или многих?
- Fail-open или fail-closed при недоступности самого rate limiter — есть ли явные требования безопасности, диктующие выбор?
