# Кейс: Загрузка и раздача файлов

> **TL;DR:** Главная архитектурная ошибка на этой задаче — проксировать загружаемый файл **через** собственный API-сервер (память/CPU сервера тратится на пересылку байтов, в которых нет никакой бизнес-логики). Правильный паттерн — presigned URL: API-сервер выдаёт клиенту временную подписанную ссылку, по которой клиент загружает файл **напрямую** в объектное хранилище (S3-подобное), полностью минуя собственный сервер.

## Требования

**Функциональные:** загрузка файлов (включая большие — видео, архивы), раздача загруженных файлов другим пользователям, возобновляемая/chunked-загрузка для больших файлов, (опционально) дедупликация одинакового контента.

**Нефункциональные:** сервер приложения не должен быть узким местом для передачи самих байтов файла (это не CPU/бизнес-логика, а чистая пропускная способность сети), раздача файлов должна быть быстрой глобально (география пользователей).

## Оценка

```
1M загрузок/день, средний размер файла 5 МБ → 5 ТБ/день входящего трафика
Если бы всё шло ЧЕРЕЗ API-сервер: 5ТБ/86400с ≈ 58 МБ/сек постоянной нагрузки на сеть/CPU
сервера ТОЛЬКО на пересылку байтов — при том, что реальная бизнес-логика (запись метаданных)
занимает миллисекунды и килобайты, а не мегабайты
```

## High-level design

```
[Client] → [API Service: запросить presigned URL] → [Object Storage (S3-подобное)]
                    │                                          ↑
                    │                          [Client загружает файл НАПРЯМУЮ, минуя API Service]
                    ↓
              [Metadata DB: file_id, owner, size, upload_status, content_hash]
                    │
              [CDN] ← [Object Storage] (раздача уже загруженных файлов)
```

## Deep dive 1 — presigned URL

```ts
// API Service: НЕ принимает файл сам, только выдаёт подписанную ссылку на прямую загрузку в S3
async function requestUploadUrl(userId: string, fileName: string) {
  const fileId = crypto.randomUUID();
  const key = `uploads/${userId}/${fileId}/${fileName}`;

  const presignedUrl = await s3.getSignedUrl('putObject', {
    Bucket: 'user-uploads', Key: key, Expires: 300, // ссылка валидна 5 минут
  });

  await db.query('INSERT INTO files (id, owner_id, key, status) VALUES ($1, $2, $3, $4)', [fileId, userId, key, 'pending']);
  return { fileId, presignedUrl };
}
```

```ts
// Client (браузер/мобильное приложение) — грузит файл НАПРЯМУЮ в S3 по presignedUrl, без похода через API Service
await fetch(presignedUrl, { method: 'PUT', body: fileBlob });
```

Presigned URL — временный, криптографически подписанный токен доступа, встроенный прямо в URL, дающий предъявителю ограниченное по времени право выполнить конкретную операцию (в данном случае — `PUT` конкретного объекта) напрямую в объектном хранилище, без необходимости для хранилища знать про пользователей/аутентификацию приложения вообще — сама подпись, сгенерированная API-сервером с использованием его учётных данных к хранилищу, служит доказательством авторизации. API-сервер участвует только в двух коротких операциях (выдать URL до загрузки, получить подтверждение после) — сама передача мегабайт/гигабайт данных идёт по прямому каналу клиент↔хранилище, для которого объектные хранилища и спроектированы (масштабируемая приёмка трафика — их основная задача, в отличие от произвольного API-сервера приложения).

## Deep dive 2 — подтверждение завершения загрузки

```
Проблема: presigned URL позволяет клиенту загрузить файл НАПРЯМУЮ — API Service не знает МГНОВЕННО,
          когда загрузка реально завершилась (в отличие от обычного запроса через свой сервер)

Решение 1: S3 Event Notification — хранилище само уведомляет (через SNS/SQS-подобный механизм) при появлении
           нового объекта → API Service подписан на эти события, обновляет status='uploaded' в Metadata DB

Решение 2: клиент, завершив upload, явно вызывает API Service "подтвердить завершение" →
           API Service делает HEAD-запрос к объекту в хранилище для верификации (не доверяет клиенту слепо)
```

Решение 1 надёжнее (не зависит от того, доложит ли клиент о завершении честно — важно, если клиент недоверенный) и естественно вписывается в event-driven архитектуру (тот же принцип, что очереди/события в [Очереди и async-обработка как инструмент дизайна](./07-queues-async-design.md)) — хранилище само становится источником события "файл появился", а не полагается на клиента. Между `status='pending'` (URL выдан) и `status='uploaded'` (подтверждено) — файл технически может существовать в хранилище, но не быть "официально" зарегистрированным как завершённая загрузка — периодическая очистка pending-записей старше разумного окна (клиент так и не завершил/бросил загрузку) предотвращает накопление мусора в Metadata DB.

## Deep dive 3 — chunked/resumable upload для больших файлов

```
Большой файл (видео, 2 ГБ) разбивается на чанки (например, по 5 МБ) на клиенте
Каждый чанк загружается ОТДЕЛЬНЫМ presigned URL (S3 Multipart Upload API)
При обрыве соединения — переотправляются ТОЛЬКО недошедшие чанки, не весь файл заново
После загрузки всех чанков — CompleteMultipartUpload объединяет их в один объект в хранилище
```

Для больших файлов однократная загрузка целиком уязвима к обрыву соединения на 99% прогресса, требующему полного перезапуска — S3-подобные хранилища нативно поддерживают multipart upload именно для этого сценария: каждый чанк — независимая операция с собственным presigned URL, отслеживание прогресса и повторная отправка только неудачных частей, что особенно критично на нестабильных мобильных сетях.

## Deep dive 4 — дедупликация по content hash

```sql
CREATE TABLE files (
  id uuid PRIMARY KEY, content_hash text, storage_key text, ref_count int DEFAULT 1
);
CREATE UNIQUE INDEX idx_content_hash ON files (content_hash);
```

Если несколько пользователей загружают идентичный файл (одно и то же изображение, документ), хеш содержимого (SHA-256) позволяет обнаружить это и **не хранить дубликат** физически — новая "загрузка" просто увеличивает `ref_count` на уже существующий объект в хранилище, экономя место и полосу. Требует вычисления хеша (на клиенте до загрузки, если возможно — тогда сервер может сразу сказать "уже есть, не грузи заново", экономя и полосу на саму передачу; либо на сервере после — тогда экономия только на хранении, не на полосе загрузки).

## Узкие места и эволюция

- **CDN для раздачи** — та же аргументация, что в [Кеширование и CDN в дизайне](./05-caching-cdn-design.md): географическая близость edge-узла к читателю снижает latency независимо от нагрузки origin (объектного хранилища).
- **Приватные файлы** — presigned URL той же природы используется и для **чтения** (`getObject` вместо `putObject`) приватных файлов с ограниченным TTL, вместо того чтобы делать бакет публичным целиком.
- **Вирусный/злонамеренный контент** — асинхронное сканирование после загрузки (антивирус/модерация контента) как отдельный consumer события "файл загружен" (тот же fan-out паттерн, что в [Очереди и async-обработка как инструмент дизайна](./07-queues-async-design.md)), не блокирующий сам факт загрузки.

## Что уточнить у интервьюера в начале

- Какой типичный размер файлов? (определяет, нужен ли chunked upload)
- Файлы приватные или публично доступные? (влияет на модель presigned URL для чтения)
- Нужна ли дедупликация контента?
