# Кейс: Лента новостей

> **TL;DR:** Центральный вопрос этой задачи — fan-out on write vs on read, уже разобранный на уровне общего паттерна в [10-rate-limiting-fanout-design.md](./10-rate-limiting-fanout-design.md). Здесь — применение к конкретной задаче с конкретными числами, плюс два дополнительных архитектурных решения: пагинация ленты (курсорная, не offset) и гибридная стратегия для аккаунтов-знаменитостей.

## Требования

**Функциональные:** пользователь подписывается на других пользователей, публикует посты, видит хронологическую ленту постов от своих подписок (сознательно сужаем scope — без алгоритмической рекомендательной ленты, это отдельная, намного более сложная задача, и стоит явно проговорить это сужение с интервьюером).

**Нефункциональные:** read-heavy (лента читается на порядки чаще, чем публикуются посты), доступность важнее строгой консистентности (AP — пользователь может увидеть новый пост подписки с задержкой в секунды, это приемлемо), низкая latency открытия ленты (пользователь ждёт на экране).

## Оценка

```
100M DAU, каждый открывает ленту ~10 раз/день → 1B запросов ленты/день ≈ 11 600 RPS среднее, пик ×3 ≈ 35000 RPS
10M постов/день → ~115 постов/сек публикаций — на 3 порядка меньше read-нагрузки
Средний пользователь: ~200 подписок; 0.1% аккаунтов ("знаменитости") — 1M+ подписчиков
```

## High-level design

```
[Client] → [LB] → [API Service] → [Feed Cache (Redis): предвычисленная лента ОБЫЧНЫХ подписок]
                        │                    ↑ fan-out on write (для обычных авторов)
                        │          [Fan-out Worker] ← [Queue] ← [Post published event]
                        │
                        └──→ [Celebrity posts: fan-out on READ, слить на лету при запросе ленты]
                        └──→ [Posts DB: источник истины для всех постов]
                        └──→ [Follow graph DB: кто на кого подписан]
```

## Deep dive 1 — гибридный fan-out (детали применения к этой задаче)

```
Публикация поста:
  if (author.followerCount < 100_000) {
    // fan-out on write: push поста в Redis-ленту КАЖДОГО подписчика асинхронно через очередь
    await feedFanoutQueue.add('fanout-post', { postId, authorId });
  }
  // else: НЕ пушим — знаменитости обрабатываются at read-time

Чтение ленты:
  const regularFeed = await redis.zrange(`feed:${userId}`, 0, 49); // уже готовые посты обычных подписок
  const celebrityAuthors = await getFollowedCelebrities(userId);   // обычно единицы-десятки
  const celebrityPosts = await postsDb.getRecentPosts(celebrityAuthors, limit=50); // на лету, но авторов немного
  const merged = mergeAndSort([...regularFeed, ...celebrityPosts], by='createdAt');
```

Порог (100k подписчиков в примере) — настраиваемый параметр, выбираемый эмпирически: должен быть достаточно высоким, чтобы fan-out on write оставался дешёвым для подавляющего большинства авторов (у которых умеренное число подписчиков), и достаточно низким, чтобы редкие но катастрофически дорогие push-операции (10M+ подписчиков за один пост) никогда не происходили. Чтение для обычного пользователя остаётся быстрым, потому что число подписанных знаменитостей у одного читателя обычно мало (единицы-десятки), даже если у каждой знаменитости миллионы подписчиков — асимметрия, которую стоит явно проговорить как обоснование, почему гибрид работает именно так.

## Deep dive 2 — курсорная пагинация ленты

```sql
-- НЕ offset (см. проблему деградации в 04-databases/10-pagination.md)
SELECT * FROM feed_items
WHERE user_id = ? AND (created_at, post_id) < (?, ?)  -- курсор: последний увиденный (created_at, post_id)
ORDER BY created_at DESC, post_id DESC LIMIT 20;
```

Бесконечный скролл ленты — эталонный кейс для cursor/keyset-пагинации (детальная механика — в [04-databases/10-pagination.md](../04-databases/10-pagination.md)): пользователь никогда не запрашивает "страницу 50", только "следующие 20 после того, что уже видел" — offset здесь не только медленнее на глубоких страницах, но и семантически неверен при постоянно растущей ленте (новые посты, появившиеся между запросами страниц, сдвигают нумерацию offset и создают дубли/пропуски, чего курсор по своей природе избегает).

## Узкие места и эволюция

- **Feed Cache как единая точка отказа для read-пути** — если Redis-кластер, хранящий предвычисленные ленты, недоступен, деградация всего read-пути системы (fan-out on read fallback на прямой сбор из follow graph + posts DB — дороже, но не полный отказ; стоит явно упомянуть эту деградацию как элемент resilience).
- **Follow graph как отдельная сущность** — при очень больших графах (миллиарды рёбер подписок) сам граф подписок может требовать отдельного специализированного хранилища/шардирования, отдельного от постов.
- **Consistency между постом и его появлением в ленте** — fan-out worker обрабатывает публикацию асинхронно (см. [07-queues-async-design.md](./07-queues-async-design.md)) — окно в несколько секунд между публикацией и появлением в лентах подписчиков — приемлемая eventual consistency для этого домена (см. [03-cap-consistency-models.md](./03-cap-consistency-models.md)).
- **Удаление поста** — должно инвалидировать/удалить его из уже предвычисленных лент всех подписчиков (обратный fan-out) — часто упускаемый кандидатами момент, стоит явно упомянуть.

## Что уточнить у интервьюера в начале

- Чисто хронологическая лента подписок, или нужна алгоритмическая релевантность/ранжирование? (сильно меняет сложность)
- Есть ли аккаунты с аномально большим числом подписчиков? (определяет, нужен ли гибридный fan-out вообще)
- Насколько критична свежесть ленты (секунды приемлемы, или нужна near-realtime доставка)?
