# Кейс: Чат

> **TL;DR:** Центральная сложность — та же, что разобрана для WebSocket-масштабирования в [WebSockets: handshake, масштабирование, heartbeat](../05-api-communication/08-websockets.md): соединение живёт на конкретном инстансе, и доставка сообщения пользователю, чей сокет открыт на **другом** инстансе, требует явного механизма маршрутизации между инстансами. Здесь — как это складывается в полную систему с хранением истории, офлайн-доставкой, статусами прочтения и шардированием по чатам.

## Требования

**Функциональные:** отправка/получение сообщений в реальном времени между двумя или более участниками, доставка сообщений офлайн-пользователю при возвращении в сеть, статусы прочтения, история сообщений чата.

**Нефункциональные:** низкая latency доставки (единицы-сотни мс для онлайн-получателя), гарантированная доставка хотя бы раз (at-least-once, см. [At-least-once / at-most-once / effectively-once; идемпотентные консьюмеры](../06-architecture-patterns/14-delivery-guarantees-idempotent-consumers.md)) — сообщение не должно теряться даже при падении сервера в момент отправки, порядок сообщений внутри одного чата должен быть согласованным.

## Оценка

```
50M DAU, каждый отправляет ~40 сообщений/день → 2B сообщений/день ≈ 23000 msg/сек среднее, пик ×3 ≈ 70000/сек
Средний размер сообщения (текст + метаданные) ≈ 200 байт → объём в день ≈ 400 ГБ
За год: ~145 ТБ — требует шардирования истории сообщений по объёму
```

## High-level design

```
[Client A] ↔ [WS Gateway 1]                              [WS Gateway 2] ↔ [Client B]
                    │                                            │
                    └──────→ [Redis Pub/Sub: доставка между инстансами] ←──────┘
                    │                                            │
                    └──→ [Message DB: история, шардирована по chat_id] ←──────┘
                    │
                    └──→ [Presence service: кто сейчас онлайн, на каком gateway]
                    └──→ [Push notification service: для офлайн-получателей]
```

## Deep dive 1 — доставка между инстансами и офлайн-получателям

```
Client A (на Gateway 1) шлёт сообщение Client B
Gateway 1: 1) СРАЗУ записывает сообщение в Message DB (durability — сообщение не потеряется,
              даже если доставка получателю прямо сейчас не удастся)
           2) публикует событие в Redis Pub/Sub канал "user:B:messages"
           3) ищет в Presence service, на каком именно Gateway сейчас сокет пользователя B

Gateway 2 (если B онлайн, подписан на канал): получает событие, доставляет B через его сокет
Если B офлайн: Presence service это знает → Push notification service шлёт push-уведомление
               (сообщение УЖЕ в Message DB — при следующем открытии приложения B просто
               подгружает историю обычным запросом, не требуется отдельная "доставка" в привычном смысле)
```

Ключевая деталь — запись в Message DB происходит **до** попытки real-time доставки, не после: реальная доставка через WebSocket — best-effort ускорение, а не единственный путь получения сообщения. Это снимает саму проблему "как гарантированно доставить офлайн-пользователю" — раз сообщение уже надёжно сохранено, офлайн-пользователь просто увидит его при следующем запросе истории, push-уведомление — только способ привлечь внимание пораньше, не транспорт самого сообщения.

## Deep dive 2 — порядок сообщений и шардирование по chat_id

```sql
CREATE TABLE messages (
  chat_id uuid, message_id bigint, sender_id uuid, content text, sent_at timestamptz,
  PRIMARY KEY (chat_id, message_id)  -- составной ключ: партиционирование естественно по chat_id
);
```

Шардирование по `chat_id` (не по `user_id` или глобально) — сообщения одного чата физически оказываются на одном шарде, что делает гарантию порядка **внутри чата** тривиальной (тот же принцип, что partition key в Kafka для упорядоченности, см. [Kafka vs RabbitMQ: log vs queue](../06-architecture-patterns/13-kafka-vs-rabbitmq.md) — гарантия порядка только внутри партиции/шарда, не глобально). `message_id` — монотонно растущий в пределах чата (не глобальный auto-increment — см. [Уникальные ID: UUID vs snowflake vs sequence](./09-unique-id-generation.md) про то, почему единый счётчик не масштабируется при шардировании; здесь достаточно счётчика на уровне чата, или Snowflake-подобного ID с достаточной точностью сортировки) — даёт естественный, дешёвый способ определить порядок и реализовать курсорную пагинацию истории (см. [Пагинация: offset vs cursor](../04-databases/10-pagination.md)).

## Статусы прочтения

```
Message DB: messages.read_by = [{userId, readAt}, ...] ИЛИ отдельная таблица read_receipts (chat_id, user_id, last_read_message_id)
```

Отдельная таблица `read_receipts` с одной строкой на пару (chat_id, user_id), хранящей `last_read_message_id`, обычно эффективнее, чем массив прочитавших внутри каждого сообщения — обновление статуса прочтения (частая операция) становится простым upsert одной строки, а не модификацией потенциально большого JSON-массива внутри записи сообщения при каждом новом прочтении каждым участником.

## Узкие места и эволюция

- **Presence service как критичная зависимость** — неверные данные о том, где сейчас сокет пользователя, приводят к недоставленным сообщениям в реальном времени (хотя не к потере — сообщение всё ещё в Message DB); presence обычно с коротким TTL/heartbeat (тот же принцип, что heartbeat в WebSocket, см. [WebSockets: handshake, масштабирование, heartbeat](../05-api-communication/08-websockets.md)).
- **Групповые чаты с большим числом участников** — доставка одного сообщения многим онлайн-участникам одновременно — тот же fan-out паттерн, что в ленте (см. [Кейс: Лента новостей](./12-case-news-feed.md)), с той же необходимостью думать о верхнем пределе размера группы.
- **История за годы на активный чат** — объём сообщений растёт неограниченно, партиционирование по времени поверх шардирования по chat_id (см. [Шардирование vs партиционирование](../04-databases/12-sharding-partitioning.md)) для эффективной очистки/архивации старых сообщений.

## Что уточнить у интервьюера в начале

- Один-на-один чат, или групповые чаты тоже в scope? (сильно меняет сложность fan-out)
- Нужна ли гарантия строгого порядка сообщений при одновременной отправке несколькими участниками, или достаточно "примерно по времени"?
- Нужно ли шифрование end-to-end? (меняет архитектуру хранения — сервер не может читать содержимое)
