# Кейс: Booking (отели/билеты)

> **TL;DR:** Центральная сложность — конкурентное резервирование ограниченного ресурса (последнее место в отеле, последний билет на рейс): два пользователя, нажавшие "забронировать" почти одновременно, не должны оба получить "успех" для одного и того же места. В отличие от [08-distributed-locks-fencing.md](./08-distributed-locks-fencing.md), где обсуждается, что distributed lock часто избыточен для такой задачи — здесь разбирается, почему.

## Требования

**Функциональные:** поиск доступных номеров/мест по критериям (даты, локация), временный холд места на время оформления заказа (TTL), подтверждение бронирования, отмена.

**Нефункциональные:** строгая консистентность именно на операции резервирования (два пользователя не должны одновременно "успешно" забронировать одно место — CP-поведение конкретно здесь, см. [03-cap-consistency-models.md](./03-cap-consistency-models.md)), поиск доступности может быть eventual consistent (устаревшая на секунды доступность в результатах поиска — приемлема, реальная проверка происходит в момент попытки бронирования).

## Оценка

```
Поиск: намного более частая операция, чем реальное бронирование (пользователи просматривают много
       вариантов, бронируют один) — read:write для поиска легко 1000:1+
Резервирование: относительно низкий RPS даже для крупной системы, но КАЖДАЯ операция резервирования
                 конкретного места/номера — потенциальная точка конфликта с другими пользователями,
                 смотрящими на ТОТ ЖЕ ресурс в то же окно времени
```

## High-level design

```
[Client] → [Search Service] → [Search Index (Elasticsearch): денормализованная доступность]
                │
                └→ [Booking Service] → [Inventory DB: source of truth по конкретным местам/номерам]
                                              │
                                        [Redis: TTL-холды на время оформления заказа]
                                              │
                                        [Payment (см. 15-case-payments.md)]
```

## Deep dive 1 — почему атомарная условная операция БД лучше distributed lock

```sql
-- Резервирование через УСЛОВНЫЙ UPDATE — атомарно на уровне самой БД, без внешнего лока
UPDATE room_inventory
SET status = 'held', held_by = $1, held_until = now() + interval '10 minutes'
WHERE room_id = $2 AND date = $3 AND status = 'available'
RETURNING *;
-- Если rowCount = 0 → место уже занято/захвачено кем-то другим → явная ошибка клиенту "уже недоступно"
-- Если rowCount = 1 → УСПЕШНО зарезервировано ИМЕННО этим запросом
```

Как разобрано в [08-distributed-locks-fencing.md](./08-distributed-locks-fencing.md), distributed lock (Redis `SET NX`) — правильный инструмент, когда критическая секция требует **нескольких** шагов координации между сервисами; здесь же вся операция "проверить доступность и захватить" сводится к **одной** атомарной условной записи, которую сама БД гарантирует выполнить как единую неделимую операцию через обычный `WHERE status = 'available'` + проверку числа затронутых строк (тот же паттерн optimistic locking, детально — [04-databases/07-locking.md](../04-databases/07-locking.md)). Использование отдельного distributed lock здесь было бы избыточным усложнением, добавляющим все ловушки из [08-distributed-locks-fencing.md](./08-distributed-locks-fencing.md) (GC-паузы, TTL-гонки) ради задачи, которую атомарный `UPDATE` решает проще и надёжнее.

## Deep dive 2 — TTL-холд как временная бронь до оплаты

```
1. UPDATE ... SET status = 'held', held_until = now() + 10 min WHERE status = 'available' (см. выше)
2. Клиент переходит к оплате (см. 15-case-payments.md)
3a. Оплата успешна за 10 минут → status = 'confirmed', held_until больше не важен
3b. Оплата НЕ произошла за 10 минут → фоновый job освобождает место:
    UPDATE room_inventory SET status = 'available' WHERE status = 'held' AND held_until < now()
```

Холд с TTL — компромисс между "заблокировать место сразу и надолго" (плохой UX для остальных — место недоступно, пока один пользователь долго раздумывает или вообще бросил оформление) и "не блокировать вообще до момента реальной оплаты" (риск, что пользователь дошёл до экрана оплаты, а место уже перехватил кто-то другой). Освобождение просроченных холдов — либо периодический batch-job (`WHERE held_until < now()`, аналог TTL-очистки), либо, если используется Redis для самого холда вместо поля в основной БД, — нативный TTL ключа (`EXPIRE`), избавляющий от необходимости отдельного планировщика вообще, ценой того, что Redis и основной Inventory DB теперь два места, которые нужно держать согласованными (compensating action при истечении Redis-ключа должна синхронно освобождать место и в БД).

## Овербукинг — сознательное архитектурное решение, не баг

```
Отели/авиакомпании иногда НАМЕРЕННО продают немного больше мест, чем физически есть
(статистически предсказуемый процент отмен/no-show компенсирует небольшой оверселл)
```

Стоит явно упомянуть на собеседовании как понимание реального бизнес-контекста задачи — это не техническая недоработка системы бронирования, а осознанная бизнес-стратегия, которую система должна **поддерживать** (настраиваемый процент овербукинга сверх физической ёмкости), а не предотвращать любой ценой — демонстрирует, что кандидат не воспринимает "100% строгую консистентность резервирования" как самоцель без контекста, а понимает, что бизнес-требования иногда осознанно допускают контролируемый excess.

## Узкие места и эволюция

- **Search Index как устаревшая на секунды проекция** — реальная доступность проверяется только в момент попытки резервирования (шаг из deep dive 1); поисковый индекс (см. [04-storage-selection.md](./04-storage-selection.md) про специализацию поисковых систем) — приближение для UX поиска, не источник истины.
- **Hot inventory item** (популярное направление в высокий сезон) — тот же hot key паттерн, что разобран в [08-performance-reliability/02-cache-problems.md](../08-performance-reliability/02-cache-problems.md) — множество пользователей одновременно пытаются захватить одни и те же несколько последних мест конкретного рейса/отеля.
- **Шардирование Inventory DB** — по географии/типу инвентаря (отели отдельно от рейсов, регион отдельно от региона) естественная граница шардирования, снижающая конкуренцию за одни и те же строки между географически несвязанными бронированиями.
