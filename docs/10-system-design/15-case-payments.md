# Кейс: Платёжная система

> **TL;DR:** Единственный кейс из этого списка, где CP-поведение (см. [CAP своими словами; consistency models](./03-cap-consistency-models.md)) для критичных операций — не опция, а требование: лучше временно отказать в операции, чем провести её с рассинхроном. Архитектурно платёжная система — это в первую очередь применение уже разобранных паттернов (idempotency, outbox, saga, append-only ledger) к домену, где цена ошибки — реальные деньги, а не просто плохой UX.

## Требования

**Функциональные:** списание/начисление средств, интеграция с внешним платёжным провайдером (Stripe-подобным), история транзакций, реконсиляция (сверка с провайдером), возвраты.

**Нефункциональные:** ни одна транзакция не должна теряться или дублироваться (строгая идемпотентность и durability важнее latency), полный аудит-лог каждой операции (регуляторные требования), устойчивость к сбоям внешнего провайдера без потери данных о попытке платежа.

## Оценка

```
1M транзакций/день ≈ 12 RPS среднее — сам по себе НЕВЫСОКИЙ RPS по сравнению с остальными кейсами,
потому что здесь корректность важнее пропускной способности — типичная ошибка кандидата на этой
задаче — оптимизировать под несуществующую проблему масштаба, вместо фокуса на консистентности
```

## High-level design

```
[Client] → [Payment API] → [BEGIN TRANSACTION]
                                  ├─ INSERT INTO ledger (append-only, см. ниже)
                                  ├─ INSERT INTO outbox (событие "PaymentInitiated")
                                  └─ COMMIT
                                        ↓
                            [Outbox Relay] → [Queue] → [Provider Integration Worker]
                                                              ↓
                                                    [Внешний провайдер (Stripe и т.п.)]
                                                              ↓
                                              [Webhook: PaymentSucceeded/Failed] → [Reconciliation]
```

## Deep dive 1 — idempotency на входе и outbox на выходе

```ts
// Idempotency key от клиента — см. полную механику в 05-api-communication/02-idempotency-keys.md
async function initiatePayment(idempotencyKey: string, dto: PaymentDto) {
  return db.transaction(async (tx) => {
    const existing = await tx.query('SELECT * FROM idempotency_keys WHERE key = $1', [idempotencyKey]);
    if (existing) return existing.response; // клиент ретраил — вернуть тот же результат, НЕ списывать снова

    await tx.query('INSERT INTO ledger (account_id, amount, type) VALUES ($1, $2, $3)', [...]);
    await tx.query('INSERT INTO outbox (event_type, payload) VALUES ($1, $2)', ['PaymentInitiated', ...]);
    await tx.query('INSERT INTO idempotency_keys (key, response) VALUES ($1, $2)', [idempotencyKey, ...]);
    // ВСЁ в ОДНОЙ транзакции — либо всё записалось, либо ничего
  });
}
```

Два разных механизма идемпотентности работают на разных границах системы: **idempotency key** (детально — [Idempotency keys для POST](../05-api-communication/02-idempotency-keys.md)) защищает от повторного клика/ретрая клиента на входе в систему; **transactional outbox** (детально — [Transactional Outbox + relay/CDC](../06-architecture-patterns/10-transactional-outbox.md)) защищает от dual-write проблемы на выходе — запись в ledger и намерение уведомить провайдера коммитятся одной локальной транзакцией, реальный вызов провайдера происходит асинхронно через relay уже после гарантированного коммита. Без этих двух механизмов вместе — двойное списание при повторном клике пользователя (нет idempotency key) или потерянное/задублированное событие о платеже при падении между записью в БД и вызовом провайдера (нет outbox) — оба сценария реально происходят в системах без этой защиты.

## Deep dive 2 — append-only ledger вместо мутируемого баланса

```sql
-- ПЛОХО: баланс как мутируемое поле — история операций теряется, аудит невозможен
UPDATE accounts SET balance = balance - 100 WHERE id = ?;

-- ХОРОШО: ledger — неизменяемый журнал движений, баланс — ВЫЧИСЛЯЕМАЯ величина
CREATE TABLE ledger (
  id bigserial PRIMARY KEY, account_id uuid, amount numeric, type text,
  created_at timestamptz DEFAULT now()
  -- НЕТ UPDATE/DELETE операций на эту таблицу вообще, только INSERT
);
-- баланс = SUM(amount) WHERE account_id = ? (или материализованный, периодически пересчитываемый снапшот)
```

Тот же принцип, что Event Sourcing (см. [Event Sourcing: суть, проекции, снапшоты](../06-architecture-patterns/06-event-sourcing.md)) — применённый именно там, где Event Sourcing действительно оправдан (домен, где сама история изменений — часть бизнес-ценности, прямо названный там пример "финансовые операции, где нужен полный аудит"). Append-only ledger даёт: неопровержимый аудит-след (регуляторные требования почти всегда требуют именно это — нельзя "исправить" ошибочную запись, только добавить компенсирующую), естественную защиту от гонок при конкурентных операциях (INSERT не блокирует другие INSERT так, как конкурентные UPDATE одной строки, см. [Блокировки: row-level, FOR UPDATE, advisory, optimistic vs pessimistic](../04-databases/07-locking.md)), возможность пересчитать баланс на любой момент прошлого для реконсиляции.

## Deep dive 3 — saga с внешним провайдером и реконсиляция

```
Payment Saga:
  1. Ledger: зарезервировать сумму (локальная транзакция)
  2. Вызов внешнего провайдера (async, через outbox → worker)
  3a. Провайдер подтвердил (webhook PaymentSucceeded) → Ledger: подтвердить резерв
  3b. Провайдер отклонил (webhook PaymentFailed) → Ledger: компенсация — отменить резерв
```

Внешний провайдер — отдельная система вне контроля, взаимодействие с ней — классическая saga с компенсацией (детали паттерна — [Saga: choreography vs orchestration, компенсации](../06-architecture-patterns/09-saga.md)), не распределённая транзакция (2PC с внешним провайдером физически невозможен — провайдер не участвует в вашем протоколе консенсуса, см. [Distributed transactions: почему 2PC избегают](../06-architecture-patterns/15-distributed-transactions-2pc.md)). **Реконсиляция** — отдельный обязательный процесс: периодическая сверка состояния платежей в собственном ledger с состоянием у провайдера (провайдер может прислать webhook, который потерялся по дороге, или прийти с задержкой) — без явной реконсиляции разошедшееся состояние между вашей системой и провайдером может остаться незамеченным неопределённо долго, что для денег неприемлемо, в отличие, например, от рассинхрона лайков в ленте.

## Узкие места и эволюция

- **Webhook от провайдера как ненадёжная доставка** — тот же принцип, что в [Webhooks: подпись, retries, идемпотентность на приёмнике](../05-api-communication/11-webhooks.md): HMAC-подпись для верификации подлинности, идемпотентная обработка (провайдер может задублировать webhook), быстрый `2xx`-ответ с асинхронной обработкой содержимого.
- **Двойная бухгалтерия (double-entry) как усиление ledger** — каждая транзакция записывается как минимум двумя движениями (дебет одного счёта, кредит другого), сумма которых всегда равна нулю — встроенная защита от программных ошибок, теряющих или дублирующих деньги (несовпадение суммы дебетов и кредитов сразу заметно).
- **Латентность подтверждения от провайдера** — пользователь может не получить мгновенное "оплата прошла" (провайдер отвечает не сразу) — UI должен явно показывать промежуточное состояние "обрабатывается", не притворяться синхронностью там, где её нет.
