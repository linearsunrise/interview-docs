# Distributed lock (Redis SET NX PX, лимиты Redlock), fencing tokens

> **TL;DR:** Distributed lock решает ту же задачу, что обычная блокировка в одном процессе (см. [Блокировки: row-level, FOR UPDATE, advisory, optimistic vs pessimistic](../04-databases/07-locking.md)) — "только один воркер может делать X одновременно" — но между процессами, которые не разделяют общую память. Ключевая ловушка, которую надо явно проговорить на собеседовании — сам по себе distributed lock **не гарантирует взаимного исключения** в общем случае распределённой системы (процесс может "думать", что держит лок, уже его не удерживая — GC-пауза, сетевая задержка) — отсюда fencing token как дополнительная защита.

## Базовый distributed lock на Redis

```ts
const lockKey = `lock:job:${jobId}`;
const lockValue = crypto.randomUUID(); // уникальный токен ЭТОЙ попытки захвата

const acquired = await redis.set(lockKey, lockValue, 'NX', 'PX', 30000); // NX: только если не существует, PX: TTL 30с
if (!acquired) {
  // кто-то другой уже держит лок — не выполнять критическую секцию
  return;
}
try {
  await doExclusiveWork();
} finally {
  // снять лок ТОЛЬКО если это всё ещё наш lockValue (через Lua-скрипт для атомарности check-and-delete)
  await redis.eval(
    `if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end`,
    1, lockKey, lockValue,
  );
}
```

`SET key value NX PX ttl` — атомарная операция "установить, только если ключа ещё нет, с автоматическим истечением через `ttl` миллисекунд" — TTL обязателен: без него упавший процесс, державший лок, оставляет его навечно захваченным, и никто другой никогда не сможет его получить (deadlock на уровне всей системы, а не просто одной БД-транзакции, см. [Deadlocks](../04-databases/06-deadlocks.md) для локального аналога). Снятие лока — обязательно через **сравнение значения** перед удалением (не просто `DEL`) — иначе процесс A, чей TTL истёк, пока он ещё думал, что держит лок, может случайно удалить лок, который **уже успел захватить** процесс B (гонка: A удаляет чужой, уже легитимный лок B).

## Почему TTL — не полная защита, GC-пауза как конкретный сценарий проблемы

```
Процесс A: захватил лок (TTL 30с), начал критическую секцию
Процесс A: попадает в длинную GC-паузу (см. 02-nodejs-core/07-memory-gc.md) на 35 секунд
           → пока A "заморожен", TTL лока истекает, Redis автоматически освобождает лок
Процесс B: захватывает ТОТ ЖЕ лок, начинает свою критическую секцию
Процесс A: "просыпается" после паузы, ПРОДОЛЖАЕТ свою критическую секцию,
           НЕ ЗНАЯ, что его лок уже истёк и захвачен процессом B
→ ДВА процесса одновременно выполняют "эксклюзивную" операцию — вся гарантия лока нарушена
```

Это не гипотетический edge case, а конкретный класс проблем: любая пауза процесса-держателя лока (GC-пауза, подкачка памяти на диск, временная перегрузка CPU, сетевая задержка при обращении к внешней зависимости) длиннее оставшегося TTL приводит именно к этому сценарию. Увеличение TTL "с запасом" не решает проблему принципиально — просто отодвигает порог, при котором она проявляется, а слишком большой TTL создаёт свою цену (упавший процесс держит лок неоправданно долго, блокируя остальных).

## Fencing token — защита не от потери лока, а от последствий этой потери

```
Redis (или отдельный монотонный счётчик) выдаёт fencing token ВМЕСТЕ с локом — монотонно растущее число
Процесс A: захватил лок, получил fencing token = 33
Процесс A: (пауза, TTL истёк)
Процесс B: захватил лок, получил fencing token = 34 (СТРОГО больше, чем у A)

Ресурс (например, файловое хранилище/БД), с которым работают через лок, ПРОВЕРЯЕТ token при каждой записи:
  Процесс A "просыпается", пытается записать с token=33 → ХРАНИЛИЩЕ ОТКЛОНЯЕТ, т.к. уже видело token=34
  Процесс B пишет с token=34 → принято
```

Fencing token не предотвращает саму ситуацию "два процесса одновременно думают, что держат лок" (это в принципе невозможно устранить полностью в асинхронной распределённой системе без дополнительных гарантий) — вместо этого он делает последствия этой ситуации безопасными: защищаемый ресурс сам отвергает операции со "старым" token'ом, даже если процесс, использующий его, искренне уверен, что всё ещё легитимно держит лок. Ключевое условие — **сам защищаемый ресурс** должен уметь проверять и отвергать по token'у (это не автоматическая возможность любого хранилища — требует явной поддержки монотонной проверки на стороне получателя записи), иначе fencing token существует только на бумаге, но ничего физически не предотвращает.

## Redlock — попытка укрепить гарантию через несколько независимых Redis-инстансов, и почему это спорно

```
Захватить лок на N/2+1 из N независимых Redis-инстансов (кворум) → считается захваченным,
если большинство подтвердили
```

Redlock (алгоритм, предложенный автором Redis) пытается повысить надёжность через избыточность — лок считается легитимным, только если захвачен на большинстве из нескольких независимых Redis-узлов. Мартин Клеппман (автор "Designing Data-Intensive Applications") публично [раскритиковал Redlock](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html) за то, что он всё ещё уязвим к тем же фундаментальным проблемам (паузы процессов, часы, дающие сбой) при определённых условиях, и не даёт настоящей гарантии взаимного исключения без fencing token поверх. Практический вывод для собеседования — упомянуть, что Redlock существует и решает **доступность** лок-сервиса (не единая точка отказа на одном Redis-инстансе), но не заменяет fencing token, если реально нужна строгая гарантия корректности, а не просто "снижение вероятности" конфликта.

## Когда distributed lock вообще нужен в system design

```
Хороший кандидат: "только один воркер должен обработать этот конкретный batch job прямо сейчас"
                   (оптимизация — избежать дублирующей работы, не строгая безопасность данных)

Требует ОСТОРОЖНОСТИ (нужен fencing token или альтернатива): любая операция, где двойное выполнение
                   реально повреждает данные (booking последнего места — см. 16-case-booking.md,
                   финансовая транзакция) — здесь часто лучше атомарная операция БД (условный UPDATE,
                   см. optimistic locking в 04-databases/07-locking.md) вместо распределённого лока вообще
```

Частая ошибка на собеседовании — сразу предлагать distributed lock для задач вроде бронирования последнего места, хотя атомарная условная операция на уровне самой БД (`UPDATE seats SET status='booked' WHERE id=? AND status='available'`, проверка `rowCount`) даёт ту же гарантию корректности проще и без всех перечисленных выше ловушек — distributed lock оправдан именно тогда, когда критическая секция не сводится к одной атомарной операции хранилища (координация нескольких шагов, внешних вызовов), а не как первый инстинктивный ответ на любую задачу с конкурентным доступом.

## Что спрашивают на собеседовании

1. **Как реализовать распределённый лок на Redis?** — `SET key value NX PX ttl` для атомарного захвата с автоматическим истечением; снятие лока — через проверку значения перед удалением (Lua-скрипт для атомарности check-and-delete), не просто безусловный `DEL`.
2. **Почему TTL сам по себе не делает distributed lock полностью безопасным?** — пауза процесса-держателя (GC-пауза, сетевая задержка) дольше оставшегося TTL приводит к тому, что лок освобождается и захватывается другим процессом, пока первый ещё "думает", что держит его — оба процесса выполняют критическую секцию одновременно.
3. **Что такое fencing token и как он решает проблему GC-паузы?** — монотонно растущее число, выдаваемое вместе с локом; защищаемый ресурс проверяет token при каждой операции и отклоняет запросы со "старым" номером — не предотвращает саму гонку за лок, но делает её последствия безопасными, если ресурс поддерживает такую проверку.
4. **Что критикуют в алгоритме Redlock?** — по мнению Мартина Клеппмана, он всё ещё уязвим к тем же фундаментальным проблемам асинхронной распределённой системы (паузы, сбои часов) при определённых условиях и не заменяет fencing token, если нужна строгая гарантия корректности, а не просто снижение вероятности конфликта.
5. **Всегда ли нужен distributed lock для конкурентного доступа к ресурсу в system design?** — нет: если критическая секция сводится к одной атомарной операции хранилища (условный `UPDATE` с проверкой затронутых строк), это часто безопаснее и проще distributed lock — лок оправдан, когда координация требует нескольких шагов/внешних вызовов, не сводимых к одной атомарной операции БД.
