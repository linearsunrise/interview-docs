# Кейс: Система нотификаций

> **TL;DR:** В отличие от чата (где сообщение — сам продукт), нотификация — почти всегда побочный эффект какого-то другого события в системе (заказ создан, кто-то лайкнул пост, наступил дедлайн) — архитектурно это в первую очередь задача на **fan-out через очередь** (см. [07-queues-async-design.md](./07-queues-async-design.md)) с несколькими каналами доставки, дедупликацией и per-user rate limiting, а не задача на real-time доставку саму по себе.

## Требования

**Функциональные:** отправка уведомлений по нескольким каналам (push, email, SMS, in-app), приоритизация (критичные — доставить немедленно, второстепенные — можно с задержкой/батчем), дедупликация похожих уведомлений, retry при неудачной доставке.

**Нефункциональные:** at-least-once доставка допустима (лучше продублировать редко, чем потерять важное уведомление), но с явной дедупликацией на клиенте/сервере, чтобы дубли не раздражали пользователя; rate limit на пользователя (не заваливать десятками уведомлений за минуту даже при всплеске событий).

## Оценка

```
500M событий/день (лайки, комментарии, заказы и т.п.), из них ~20% конвертируются в реальное уведомление
→ 100M уведомлений/день ≈ 1150/сек среднее, пик ×3 ≈ 3500/сек
Множители по каналам: часть пользователей получает уведомление сразу в 2-3 каналах (push + email)
```

## High-level design

```
[Event source: OrderService, SocialService, ...] → [Notification Queue (topic per event type)]
                                                              ↓
                                              [Notification Worker: правила, дедупликация, приоритет]
                                                              ↓
                          ┌───────────────────────────────────┼───────────────────────────────────┐
                    [Push Queue]                        [Email Queue]                        [SMS Queue]
                          ↓                                    ↓                                    ↓
                  [Push Worker → APNs/FCM]          [Email Worker → SendGrid/SES]         [SMS Worker → Twilio]
```

## Deep dive 1 — дедупликация и rate limiting на пользователя

```
Пользователь получил 50 лайков на пост за минуту → БЕЗ дедупликации: 50 отдельных push-уведомлений
                                                     С дедупликацией: одно агрегированное
                                                     "Иван и ещё 49 человек оценили ваш пост"
```

```ts
// Redis: временное окно агрегации перед реальной отправкой
async function handleLikeEvent(event: { postId: string; userId: string; likerId: string }) {
  const key = `notif:aggregate:like:${event.postId}:${event.userId}`;
  await redis.sadd(key, event.likerId);
  await redis.expire(key, 300); // окно агрегации — 5 минут
  await scheduleAggregatedNotification(key, delay = 300); // job, который через 5 минут соберёт итог и отправит ОДНО уведомление
}
```

Дедупликация здесь — не защита от повторной доставки одного и того же события (это отдельная задача, идемпотентность консьюмера, см. [06-architecture-patterns/14-delivery-guarantees-idempotent-consumers.md](../06-architecture-patterns/14-delivery-guarantees-idempotent-consumers.md)), а **агрегация** множества разных, но семантически похожих событий в одно уведомление — окно накопления (Redis с TTL) собирает связанные события, реальная отправка откладывается на конец окна. Rate limiting на пользователя (см. [10-rate-limiting-fanout-design.md](./10-rate-limiting-fanout-design.md)) — отдельный, дополняющий механизм: даже после агрегации похожих событий, если пользователь генерирует уведомления из многих разных источников одновременно (лайки + комментарии + новые подписчики), общий поток на этого пользователя ограничивается сверху явным лимитом.

## Deep dive 2 — приоритизация каналов и retry с учётом канала

```
Приоритет "критично" (например, код 2FA, предупреждение о безопасности аккаунта):
  → SMS/push НЕМЕДЛЕННО, retry агрессивный, короткий таймаут ожидания подтверждения доставки

Приоритет "обычно" (лайк, комментарий):
  → push с обычным приоритетом, retry с backoff, допустима задержка в минуты
```

```ts
await notificationQueue.add('send', payload, {
  priority: event.priority === 'critical' ? 1 : 10, // BullMQ: меньшее число = выше приоритет
  attempts: event.priority === 'critical' ? 5 : 3,
  backoff: { type: 'exponential', delay: 1000 },
});
```

Разные каналы имеют разную надёжность/латентность/стоимость доставки (push — дёшево и быстро, но менее надёжно доставляется мгновенно из-за особенностей APNs/FCM; SMS — дороже, но выше гарантия немедленной доставки) — критичные уведомления оправдывают более дорогой/надёжный канал и более агрессивный retry, второстепенные — нет. Retry для конкретного worker'а (см. механику в [08-performance-reliability/09-queues-bullmq.md](../08-performance-reliability/09-queues-bullmq.md)) должен учитывать природу ошибки — постоянный сбой (невалидный push-токен устройства, деинсталлированное приложение) не стоит ретраить бесконечно, это кандидат на DLQ и очистку невалидного токена из БД, а не на повторные попытки.

## Идемпотентность доставки

```ts
const notificationId = `${eventId}:${userId}:${channel}`; // детерминированный ID
await db.query(
  `INSERT INTO sent_notifications (id) VALUES ($1) ON CONFLICT DO NOTHING RETURNING id`,
  [notificationId],
);
```

At-least-once доставка событий из очереди (см. [06-architecture-patterns/14-delivery-guarantees-idempotent-consumers.md](../06-architecture-patterns/14-delivery-guarantees-idempotent-consumers.md)) означает, что worker может обработать одно событие дважды — без явной проверки "уже отправляли это конкретное уведомление этому пользователю по этому каналу" пользователь может получить один и тот же push дважды, что заметно хуже для UX, чем дублирование в чисто внутренних системах.

## Узкие места и эволюция

- **Notification Worker как единая точка правил** — при росте числа типов событий и каналов логика приоритизации/дедупликации может разрастись — разделение по типу события на отдельные worker pool'ы (см. общий принцип в [07-queues-async-design.md](./07-queues-async-design.md)) для независимого масштабирования.
- **Пользовательские предпочтения по каналам** ("не присылать email, только push") — требует явной таблицы настроек, проверяемой перед постановкой в канал-специфичную очередь, а не после.
- **Всплеск событий от одного источника** (вирусный пост с миллионом лайков за час) — тот же fan-out риск, что и в ленте (см. [12-case-news-feed.md](./12-case-news-feed.md)) — окно агрегации особенно критично именно в этом сценарии.

## Что уточнить у интервьюера в начале

- Какие каналы доставки нужны? (push/email/SMS/in-app — сильно меняет сложность)
- Есть ли критичные по времени уведомления (2FA, security alerts) с отдельными требованиями к надёжности?
- Нужна ли агрегация похожих уведомлений, или каждое событие — отдельное уведомление?
