# Фреймворк ответа: требования → оценки → high-level → углубление → узкие места

> **TL;DR:** Главная ошибка на system design — начать рисовать архитектуру до того, как понятны требования и масштаб (прямо названо красным флагом в чек-листе раздела). Фиксированная структура ответа — не формальность для галочки, а способ не пропустить критичный шаг под давлением 35-45-минутного таймера и продемонстрировать интервьюеру процесс мышления, а не только финальную схему.

## Пять фаз ответа — сколько времени на что

```
1. Требования и уточнения        ~5 мин
2. Оценки (back-of-envelope)     ~5 мин
3. High-level дизайн             ~10 мин
4. Deep dive (1-2 места)         ~15 мин
5. Узкие места и эволюция        ~5 мин
```

Пропорции — ориентир, не жёсткий регламент, но структура важна сама по себе: интервьюер оценивает не только итоговую схему, а то, как кандидат **приходит** к решениям — задаёт ли уточняющие вопросы прежде, чем взять на себя серьёзное архитектурное обязательство, обосновывает ли выбор конкретными цифрами вместо интуиции, замечает ли собственные узкие места без подсказки.

## Функциональные vs нефункциональные требования

```
Функциональные (ЧТО система делает):
- пользователь может сократить длинный URL
- пользователь может перейти по короткому URL и попасть на оригинальный
- (опционально) аналитика по кликам

Нефункциональные (КАК ХОРОШО система это делает):
- доступность важнее строгой консистентности (пользователь скорее простит редкую задержку
  появления новой ссылки, чем недоступность редиректа)
- latency редиректа — единицы миллисекунд (это на горячем пути пользовательского опыта)
- масштаб: 100M новых ссылок/месяц, соотношение чтение:запись ~100:1
```

Функциональные требования — обычно очевидны из формулировки задачи, но не должны приниматься как данность без уточнения (URL shortener — сокращает произвольные URL, или только для конкретного домена/типа контента? нужна ли кастомизация короткого алиаса пользователем?). Нефункциональные — то, что реально определяет архитектурные решения дальше: доступность vs консистентность (см. [CAP своими словами; consistency models](./03-cap-consistency-models.md)) для конкретной системы, требуемая latency, ожидаемый масштаб — без них любое дальнейшее архитектурное решение принимается вслепую, без критерия "зачем именно так".

## Уточняющие вопросы — не формальность, а способ управлять scope'ом

```
Кандидат: "Правильно ли я понимаю, что нам нужна лента только с постами от подписок,
           без алгоритмической рекомендательной ленты? Это сильно меняет сложность дизайна."
Интервьюер: "Да, только хронологическая лента подписок для этой задачи."
```

Задача system design интервью почти всегда сформулирована намеренно широко ("спроектируйте Twitter") — часть оценки именно в том, сузит ли кандидат scope до управляемого через явные вопросы, или попытается спроектировать всё сразу и не успеет проработать ничего глубоко за отведённое время. Хорошие уточняющие вопросы одновременно (а) сужают задачу до реализуемого за 35-45 минут объёма и (б) выявляют нефункциональные требования, определяющие последующие архитектурные развилки (нужна ли строгая консистентность именно здесь, какой ожидается масштаб, какие операции — самые частые).

## High-level design — сначала блоки и стрелки, потом детали

```
[Client] → [Load Balancer] → [API Service] → [Cache] → [Database]
                                    ↓
                              [Queue] → [Worker]
```

Первый проход — крупные блоки и потоки данных между ними (клиент → балансировщик → сервисы → хранилища → очереди, см. общий паттерн в [Kubernetes-базис: pod, deployment, service, ingress, configmap/secret, HPA](../09-infrastructure-devops/04-kubernetes-basics.md) применительно к тому, как это разворачивается физически), без погружения в конкретную схему БД или алгоритм генерации ID на этом этапе — это сознательно откладывается до deep dive. Цель первого прохода — согласовать с интервьюером общую форму решения, прежде чем тратить время на детали, которые могут оказаться не тем, что интервьюер хотел увидеть.

## Deep dive — 1-2 места, а не всё поровну

Попытка одинаково подробно проработать каждый компонент high-level схемы за оставшееся время физически нереалистична — deep dive выбирает 1-2 **самых интересных** (с точки зрения архитектурных trade-off) места: обычно то, где решение неочевидно и есть конкурирующие подходы с разными компромиссами (схема данных для горячего пути, стратегия консистентности между сервисами, конкретный алгоритм — генерация ID, шардирование, выбор структуры кеша). Выбор, что именно углублять, — часть оценки: кандидат, который выбирает deep dive в тривиальную часть системы (например, детально расписывает форму DTO для CRUD-эндпоинта) вместо реально сложного места (fan-out стратегия ленты, обработка конкурентного резервирования), демонстрирует непонимание того, что на самом деле сложно в этой системе.

## Узкие места и эволюция — что упадёт первым при росте

```
"При текущем дизайне single Postgres-инстанс для метаданных URL — SPOF и потолок по записи.
 При росте до 10x эту часть нужно будет шардировать по хешу short_code (см. 06-load-balancing-sharding...).
 Кеш-слой (Redis) для горячих редиректов уже частично решает эту проблему для read-нагрузки."
```

Финальная фаза — явно назвать, что сломается первым при кратном росте нагрузки (single point of failure, компонент без горизонтального масштабирования, БД-таблица, упирающаяся в лимиты одной машины, см. [Шардирование vs партиционирование](../04-databases/12-sharding-partitioning.md)) и обозначить направление эволюции, не обязательно реализуя его прямо сейчас. Это прямо отвечает на «а что, если этот компонент упадёт?» — красный флаг чек-листа именно про отсутствие этого разговора: кандидат, нарисовавший идеальную схему без единого слова про её пределы, не показал полного понимания системы, только её happy path.

## Что спрашивают на собеседовании

1. **С чего вы начнёте проектирование системы X?** — с уточняющих вопросов о функциональных и нефункциональных требованиях (масштаб, что важнее — консистентность или доступность, какие сценарии в scope), не с рисования архитектуры.
2. **Почему нельзя сразу перейти к деталям реализации?** — архитектурные решения (выбор хранилища, стратегия консистентности, необходимость шардирования) зависят от масштаба и нефункциональных требований — принятые вслепую, без этих данных, решения рискуют оказаться неверными или избыточными.
3. **Как вы выбираете, что именно углублять в deep dive?** — самые архитектурно интересные и неочевидные места системы (там, где есть конкурирующие подходы с разными trade-off), а не равномерно поверхностно всё или произвольно выбранная тривиальная часть.
4. **Что должно быть в разделе "узкие места", если дизайн работает и проходит все функциональные требования?** — явное признание пределов текущего решения: что упадёт первым при кратном росте нагрузки, где single point of failure, куда двигаться дальше — демонстрация понимания системы за пределами happy path.
5. **Какая самая частая ошибка кандидатов на system design интервью?** — прыгать в детали архитектуры без прояснения требований и хотя бы грубой оценки масштаба; вторая по частоте — предлагать сложную распределённую архитектуру ("везде Kafka и микросервисы") без обоснования, почему простое решение недостаточно для заявленного масштаба.
