# Кеширование и CDN в дизайне системы

> **TL;DR:** Механика самого кеша (cache-aside, TTL, stampede) уже разобрана детально в [08-performance-reliability](../08-performance-reliability/index.md) — здесь фокус на **где именно** в архитектуре системы кеш и CDN размещаются и что конкретно каждый уровень снимает с нижестоящего компонента. В system design ответе важнее показать понимание "кеш на этом уровне решает вот эту конкретную нагрузку", чем пересказать механику stampede — это deep dive, который стоит делать только если интервьюер туда ведёт.

## Уровни кеширования в типичной системе — от клиента до БД

```
[Browser cache] → [CDN] → [Load Balancer] → [App-level cache (Redis)] → [DB query cache] → [Database]
```

Каждый уровень снимает нагрузку с того, что физически дальше и дороже:
- **Browser/client cache** (`Cache-Control`, см. [05-api-communication/05-http-caching-keepalive.md](../05-api-communication/05-http-caching-keepalive.md)) — вообще не доходит до сети, самый дешёвый уровень, но полностью вне контроля сервера после выдачи заголовков.
- **CDN** — снимает нагрузку с origin-сервера для статичного/редко меняющегося контента, географически приближен к пользователю (снижает latency за счёт физического расстояния, не только за счёт кеширования).
- **App-level cache (Redis)** — снимает нагрузку с БД для часто запрашиваемых данных, вычисляемых результатов.
- **DB query cache/буферный кеш** — внутренний механизм самой БД (не то, что проектируется на уровне архитектуры приложения, но стоит знать, что он есть и частично компенсирует непопадание в вышестоящие уровни).

## CDN — не просто "кеш, но далеко" — географическая близость как отдельная выгода

```
Пользователь в Токио → запрос к origin-серверу в Virginia (US-East) — round trip ~150-200мс
Пользователь в Токио → запрос к ближайшему CDN edge-узлу в Токио — round trip ~5-10мс
```

CDN даёт два независимых выигрыша одновременно: (1) снятие нагрузки с origin-сервера (тысячи пользователей получают контент из кеша edge-узла, не долетая до origin вообще) и (2) снижение latency за счёт физической близости edge-узла к пользователю (даже если бы origin отвечал мгновенно без всякой нагрузки, скорость света через полмира — это принципиальный физический предел, который не устраняется никаким кешированием на самом origin). Второй эффект — то, что часто упускают в ответе: CDN полезен даже для контента, который технически не является "тяжёлым" для origin, просто в силу географии.

## Что кешировать в CDN — не только статика

```
Классика: изображения, видео, CSS/JS-бандлы, шрифты — не меняются между запросами разных пользователей

Менее очевидное, но валидное: API-ответы для ПУБЛИЧНОГО, ОДИНАКОВОГО для всех контента
  (например, каталог товаров без персонализации, публичные профили) — с коротким TTL и
  явной инвалидацией/версионированием при изменении (тот же принцип, что в 08-performance-reliability/01-caching-patterns.md)
```

Персонализированный контент (лента конкретного пользователя, ответ, зависящий от авторизации) — обычно **не** кешируется в CDN напрямую (кеш общий на всех пользователей edge-узла, персонализация ломает саму идею) — но части ответа, общие для всех пользователей (например, публичные метаданные товара в каталоге, даже если полная страница персонализирована), могут кешироваться отдельно и собираться на клиенте/edge через включение (edge-side includes, GraphQL-фрагменты) — продвинутая техника, обычно не требуется затрагивать в первом проходе дизайна, но полезно знать про существование.

## Где именно в архитектуре размещать app-level кеш

```
[API service] → [Redis] → [Database]
     ↑
  cache-aside: сервис сам решает, промах или попадание, сам управляет инвалидацией
  (детали механики — 08-performance-reliability/01-caching-patterns.md)
```

В system design ответе важнее обосновать **что именно** кешируется и **почему это горячие данные**, чем расписывать полную механику cache-aside/write-through (это deep dive уровень, не high-level). Хорошее обоснование связывает выбор с ранее посчитанным read:write соотношением (см. [02-back-of-envelope-estimation.md](./02-back-of-envelope-estimation.md)) — "read:write 1000:1, значит один популярный пост читается тысячи раз между изменениями — кешировать именно посты, а не пользовательские настройки, которые читаются реже и меняются относительно часто".

## Что именно кешировать — горячие данные, не всё подряд

```
Хорошие кандидаты на кеш: часто читаемые, редко меняющиеся, дорогие для вычисления/получения
  (агрегированные счётчики лайков, результат сложного join-запроса, сессия пользователя,
   маппинг короткий-код→URL в shortener)

Плохие кандидаты: часто меняющиеся данные (кеш будет постоянно инвалидироваться — накладные расходы
  без выгоды), редко запрашиваемые данные (кеш никогда не "прогреется", каждый запрос — промах),
  данные, для которых устаревание критично (баланс счёта прямо перед списанием)
```

Обоснование выбора конкретных данных для кеширования — то, что интервьюер реально хочет услышать в high-level фазе: не "давайте добавим Redis" без объяснения (прямой красный флаг чек-листа «добавим кеш без ответа про инвалидацию»), а конкретное "вот эти данные горячие и стабильные по такой-то причине, вот как решается инвалидация при их изменении".

## Fan-out через кеш — предвычисление вместо вычисления на лету

```
Вместо: при каждом запросе ленты — JOIN постов из всех подписок пользователя (дорого при большом числе подписок)
Через кеш: заранее (при публикации поста) push его в предвычисленный "кеш ленты" каждого подписчика
```

Это уже пересекается с fan-out on write, разобранным подробно в [10-rate-limiting-fanout-design.md](./10-rate-limiting-fanout-design.md) и на конкретном кейсе в [12-case-news-feed.md](./12-case-news-feed.md) — кеш в этом случае используется не просто как "ускоритель повторных одинаковых запросов", а как структура данных, специально предвычисленная под конкретный паттерн чтения, что стирает границу между "кешированием" и "материализованной read-моделью" (см. CQRS, [06-architecture-patterns/05-cqrs.md](../06-architecture-patterns/05-cqrs.md)).

## Что спрашивают на собеседовании

1. **Где в архитектуре системы разместить кеш и почему именно там?** — между слоем сервисов и БД (app-level, снимает read-нагрузку с самого дорогого компонента) и/или на уровне CDN для статичного или общего для всех пользователей контента (снимает нагрузку с origin и снижает latency за счёт географии) — выбор уровня зависит от того, что конкретно кешируется.
2. **Чем выгода CDN не сводится только к "кешу подальше"?** — географическая близость edge-узла к пользователю снижает latency независимо от загруженности origin — физический предел скорости передачи данных через большие расстояния не устраняется никаким улучшением производительности origin-сервера.
3. **Какие данные — хорошие кандидаты для кеширования, а какие — нет?** — часто читаемые, редко меняющиеся, дорогие для вычисления — хорошие; часто меняющиеся (постоянная инвалидация без выгоды) или редко запрашиваемые (кеш не прогревается) — плохие.
4. **Можно ли кешировать персонализированный контент в CDN?** — напрямую обычно нет (кеш общий на всех пользователей edge-узла) — но общие для всех части ответа можно кешировать отдельно и собирать с персонализированной частью на клиенте/edge.
5. **Как back-of-envelope расчёт read:write соотношения обосновывает решение о кешировании?** — сильно read-heavy соотношение (например, 1000:1) прямо указывает, что данные читаются на порядки чаще, чем меняются — кеширование даёт большой выигрыш почти без риска показать устаревшие данные слишком часто.
