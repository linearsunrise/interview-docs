# Кейс: URL shortener

> **TL;DR:** Классический "разминочный" кейс — кажется простым, но содержит два реально интересных архитектурных решения: как генерировать короткий код без коллизий и без единой точки координации, и почему выбор между `301` и `302` редиректом — не техническая мелочь, а прямое следствие требования "нужна ли аналитика по кликам".

## Требования

**Функциональные:** сократить длинный URL в короткий, редирект по короткому URL на оригинальный, (опционально) кастомный алиас, (опционально) аналитика по кликам, (опционально) TTL/истечение ссылки.

**Нефункциональные:** высокая доступность важнее строгой консистентности (пользователь скорее простит редкую задержку появления новой ссылки, чем недоступность редиректа — AP-склон, см. [03-cap-consistency-models.md](./03-cap-consistency-models.md)); latency редиректа — единицы миллисекунд; короткий код должен быть непредсказуем настолько, чтобы нельзя было легко перебором найти чужие ссылки (не криптографическая защита, но и не последовательный счётчик в открытом виде).

## Оценка

```
100M новых ссылок/месяц → ~40 запросов на создание/сек (среднее)
Read:write ≈ 100:1 → ~4000 редиректов/сек (среднее), пик ×3 ≈ 12000/сек
Короткий код: base62 (a-z, A-Z, 0-9) — 62^7 ≈ 3.5 × 10^12 комбинаций на 7 символов — с запасом на годы вперёд
Объём за 5 лет: 100M × 60 мес × ~600 байт ≈ 3.6 ТБ — не требует шардирования по объёму
```

## High-level design

```
[Client] → [Load Balancer] → [API Service] ──→ [Cache (Redis): short_code → long_url]
                                    │                        ↓ miss
                                    │              [Database: short_code → long_url, метаданные]
                                    └──→ [Async: click counter → Queue → Analytics DB]
```

## Deep dive 1 — генерация короткого кода

**Вариант А — hash-based (MD5/SHA256 от long_url, взять первые 7 символов base62):**

```
short_code = base62(md5(long_url))[:7]
```

Детерминирован (тот же long_url всегда даёт тот же short_code — можно использовать для дедупликации повторных сокращений одного URL), но требует обработки коллизий (два разных long_url теоретически могут дать одинаковый префикс хеша) — при коллизии нужно либо добавить соль и перехешировать, либо взять больше символов хеша.

**Вариант Б — counter-based (централизованный счётчик + base62-кодирование):**

```
id = следующее значение из sequence (см. 09-unique-id-generation.md)
short_code = base62(id)  // 1 → "b", 62 → "b0", и т.д.
```

Гарантированно без коллизий (монотонный счётчик никогда не повторяется), но требует централизованного источника ID — то же ограничение sequence, разобранное в [09-unique-id-generation.md](./09-unique-id-generation.md): при необходимости шардировать БД по объёму этот подход требует Snowflake-подобной схемы или предвыделенных диапазонов ID на каждый шард вместо единого auto-increment.

**Практический выбор:** counter-based с предвыделенными диапазонами (каждый инстанс API-сервиса резервирует блок из, скажем, 1000 последовательных ID заранее, генерирует коды локально без похода к БД на каждый запрос, берёт новый блок при исчерпании) — минимизирует и коллизии, и нагрузку на центральный источник ID одновременно.

## Deep dive 2 — 301 vs 302 редирект

```
301 Moved Permanently — браузер КЕШИРУЕТ редирект локально;
                          повторные клики по той же короткой ссылке СРАЗУ идут на long_url,
                          НЕ доходя до сервера — сервис никогда не узнаёт о повторных кликах
302 Found (temporary)  — браузер НЕ кеширует; каждый клик доходит до сервера заново
                          → можно посчитать КАЖДЫЙ клик для аналитики
```

Это не произвольный выбор — прямое следствие требования "нужна ли аналитика по кликам" из функциональных требований. `301` дешевле по нагрузке на сервер (после первого клика браузер обходится без сервера), но делает точный подсчёт кликов невозможным в принципе — не проблема реализации, а фундаментальное ограничение того, как браузеры трактуют `301` по спецификации HTTP (см. [05-api-communication/01-rest-semantics.md](../05-api-communication/01-rest-semantics.md) про семантику кодов ответа). Если аналитика — часть требований, `302` обязателен, несмотря на более высокую нагрузку на сервер, компенсируемую кешированием маппинга `short_code → long_url` в Redis (счётчик кликов инкрементируется асинхронно после отдачи редиректа, не блокируя сам редирект — тот же принцип развязки критического пути, что в [07-queues-async-design.md](./07-queues-async-design.md)).

## Узкие места и эволюция

- **Единая БД с маппингом `short_code → long_url`** — при расчётном объёме (3.6 ТБ за 5 лет) не требует шардирования по объёму, но по read-нагрузке (12000 RPS на пике) кеш-слой обязателен — прогретый Redis перед БД снимает подавляющее большинство read-трафика.
- **Кастомные алиасы** — пользовательский ввод произвольной строки вместо сгенерированного кода — требует уникального constraint в БД и явной обработки конфликта (алиас уже занят), не проходит через генератор ID вообще.
- **Rate limiting на создание ссылок** — без него сервис уязвим к массовому созданию ссылок ботом (см. [10-rate-limiting-fanout-design.md](./10-rate-limiting-fanout-design.md)), что быстро исчерпывает пространство коротких кодов и/или создаёт нагрузку без бизнес-ценности.
- **TTL/истечение ссылок** — если поддерживается, требует либо фонового job'а очистки истёкших записей, либо ленивой проверки `expires_at` при каждом редиректе (проще, не требует отдельного планировщика).

## Что уточнить у интервьюера в начале

- Нужна ли аналитика по кликам? (определяет 301 vs 302)
- Нужны ли кастомные алиасы?
- Нужен ли TTL/истечение ссылок?
- Ожидаемый масштаб (DAU создающих ссылки vs DAU переходящих по ним — обычно сильно разные аудитории)
