# Выбор хранилища: SQL / KV / документная / колоночная / поисковая / TSDB

> **TL;DR:** «Одна БД на всё» без обсуждения роста и «десять разных технологий без причин» — оба красных флага чек-листа, потому что оба пропускают один и тот же шаг: связать **паттерн доступа к данным** конкретной части системы с тем, для чего конкретный тип хранилища физически оптимизирован. Правильный ответ почти всегда — не одна БД для всей системы, а разные хранилища для разных подсистем, каждое обосновано своим паттерном использования, а не модой на технологию.

## Реляционная (SQL) — когда данные и их связи структурированы и важны

**Оптимизирована для:** сложные джойны между сущностями, транзакционная целостность (ACID, см. [Транзакции: ACID и уровни изоляции](../04-databases/04-transactions-isolation.md)), данные с чёткой, редко меняющейся схемой.

**Типичный кейс в system design:** метаданные заказов, платёжные транзакции (см. [Кейс: Платёжная система](./15-case-payments.md)), любая подсистема с инвариантами, требующими строгой консистентности между несколькими связанными таблицами (баланс счёта и история движений — см. агрегаты в [DDD: entity, value object, агрегат, bounded context](../06-architecture-patterns/04-ddd.md)).

**Плохо подходит для:** горизонтальное масштабирование записи без дополнительных усилий (шардирование реляционной БД — не тривиальная операция, см. [Шардирование vs партиционирование](../04-databases/12-sharding-partitioning.md)), очень высокая write-нагрузка на плоские неструктурированные данные.

## Key-Value — когда доступ всегда по известному ключу, без сложных запросов

**Оптимизирована для:** O(1)/O(log n) точечный доступ по ключу, экстремально высокая пропускная способность, горизонтальное масштабирование через простое хэш-партиционирование ключей (см. consistent hashing в [Балансировка, stateless-сервисы, шардирование, consistent hashing](./06-load-balancing-sharding-consistent-hashing.md)).

**Типичный кейс:** сессии пользователей, кеш-слой (Redis, см. [Кеширование и CDN в дизайне](./05-caching-cdn-design.md)), маппинг короткий-код → длинный-URL в URL shortener (см. [Кейс: URL shortener](./11-case-url-shortener.md)), rate limiter состояние (см. [Rate limiting в дизайне, fan-out on write vs on read](./10-rate-limiting-fanout-design.md)).

**Плохо подходит для:** запросы по неключевым полям ("найти все записи, где поле X > Y") — либо нужен вторичный индекс (не у всех KV-хранилищ есть), либо это требует полного скана.

## Документная — когда данные естественно вложенные, схема гибкая

**Оптимизирована для:** сущности, читаемые/пишущиеся целиком как один объект, с вложенной структурой, схема которой может отличаться между записями (см. подробнее [MongoDB: когда уместна, индексы, aggregation pipeline](../04-databases/14-mongodb.md)).

**Типичный кейс:** профиль пользователя со вложенными настройками, каталог товаров с разнородными атрибутами по категориям, контент поста в системе ленты/уведомлений (сам объект поста — JSON-подобная структура, читаемая целиком).

**Плохо подходит для:** данные с частыми сложными связями между разными коллекциями, требующими консистентных многотабличных транзакций (не то, для чего документная модель спроектирована в первую очередь).

## Колоночная — когда читают немного колонок из огромного числа строк

**Оптимизирована для:** аналитические запросы, агрегирующие одну-две колонки по миллиардам строк (например, `SUM(amount) WHERE date BETWEEN ...`) — колоночное хранение физически хранит значения одной колонки рядом на диске, читая с диска только нужные колонки, не всю строку целиком.

**Типичный кейс:** аналитические витрины, дашборды метрик бизнеса, агрегация исторических данных за длинные периоды (Cassandra, ClickHouse, ScyllaDB).

**Плохо подходит для:** OLTP-нагрузка с частыми точечными обновлениями отдельных строк — колоночная организация оптимизирована под чтение агрегатов по колонкам, не под транзакционные операции над отдельными записями.

## Поисковая — когда нужен полнотекстовый/фасетный поиск, не точный match

**Оптимизирована для:** полнотекстовый поиск с ранжированием релевантности, фасетная фильтрация (несколько независимых атрибутов одновременно), нечёткий поиск (опечатки, синонимы) — Elasticsearch/OpenSearch построены на инвертированных индексах именно под эти паттерны, чего обычный B-tree индекс реляционной БД не даёт эффективно (см. [B-tree индексы и leftmost prefix](../04-databases/01-btree-indexes.md) про то, для чего B-tree хорош, а для чего — нет).

**Типичный кейс:** поиск по каталогу товаров с фильтрами, полнотекстовый поиск по документам/постам, автодополнение.

**Практика:** поисковый индекс почти никогда не единственный источник истины для данных — это вторичная, оптимизированная под поиск проекция данных, чей источник истины — основная БД (та же идея, что read-модель в CQRS, см. [CQRS: когда оправдано, @nestjs/cqrs](../06-architecture-patterns/05-cqrs.md)), синхронизируемая асинхронно (события/CDC).

## Time-series (TSDB) — когда данные — упорядоченные по времени точки метрик

**Оптимизирована для:** запись огромного потока временных точек (метрика, значение, timestamp), эффективное хранение с учётом того, что соседние по времени значения часто похожи (компрессия), быстрые агрегации по временным окнам ("средняя загрузка CPU за последний час с разбивкой по минутам").

**Типичный кейс:** метрики мониторинга (тот же Prometheus, см. [Метрики: Prometheus, RED/USE, гистограммы](../09-infrastructure-devops/10-metrics-prometheus.md), внутри использует собственный TSDB-движок), IoT-телеметрия, финансовые тики котировок.

**Плохо подходит для:** данные без выраженной временной оси и паттерна "запись потоком, чтение агрегатами по времени" — обычные транзакционные сущности не выигрывают от специализации TSDB.

## Как решать на собеседовании — конкретный алгоритм

```
1. Какой основной паттерн доступа к ЭТОЙ КОНКРЕТНОЙ части данных?
   (точечный по ключу? сложные связи и джойны? полнотекстовый поиск? временные ряды? аналитика по колонкам?)
2. Насколько строгая консистентность нужна ИМЕННО ЗДЕСЬ? (см. 03-cap-consistency-models.md)
3. Какой ожидаемый масштаб чтения/записи? (см. 02-back-of-envelope-estimation.md)
4. → выбрать тип хранилища, оптимизированный именно под этот паттерн,
     а не один универсальный выбор для всей системы разом
```

Практически это означает, что зрелый ответ на system design почти всегда содержит **несколько разных** хранилищ для разных частей одной системы: реляционная БД для транзакционного ядра (заказы, платежи), key-value/Redis для кеша и сессий, поисковый индекс для полнотекстового поиска по тому же каталогу — каждое обосновано конкретным паттерном использования той конкретной подсистемы, которую оно обслуживает, а не единым решением "у нас Postgres на всё" или противоположной крайностью "у нас пять разных БД, потому что это модно".

## Что спрашивают на собеседовании

1. **Почему не использовать одну БД на всю систему?** — разные части системы имеют разные паттерны доступа (точечный по ключу vs сложные джойны vs полнотекстовый поиск vs агрегация по времени) — универсальное хранилище хорошо справляется с одним из них ценой худшей эффективности для остальных; специализированные хранилища оптимизированы под конкретный паттерн.
2. **Когда документная БД предпочтительнее реляционной?** — данные естественно вложенные и читаются/пишутся целиком как один объект, схема может отличаться между записями, нет частой потребности в консистентных многотабличных транзакциях между разными сущностями.
3. **Зачем нужна отдельная поисковая система, если данные уже в основной БД?** — обычный B-tree индекс не даёт эффективного полнотекстового поиска с ранжированием релевантности и фасетной фильтрацией — поисковый индекс (инвертированный, не B-tree) строится как вторичная, асинхронно синхронизируемая проекция данных под этот конкретный паттерн.
4. **Чем колоночное хранилище отличается от строкового с точки зрения производительности?** — колоночное физически хранит значения одной колонки рядом на диске — агрегатные запросы по немногим колонкам из огромного числа строк читают только нужные колонки, не всю строку целиком; плохо подходит для частых точечных обновлений отдельных записей (OLTP).
5. **Как выбрать хранилище для конкретной части проектируемой системы?** — определить основной паттерн доступа к этим конкретным данным, требуемый уровень консистентности и ожидаемый масштаб — выбрать тип хранилища, физически оптимизированный именно под этот паттерн, не по умолчанию/моде на технологию.
