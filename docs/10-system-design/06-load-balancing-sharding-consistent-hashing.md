# Балансировка, stateless-сервисы, шардирование данных, consistent hashing

> **TL;DR:** Три идеи, работающие вместе: stateless-сервисы — предпосылка, без которой балансировка нагрузки вообще не имеет смысла (см. подробный разбор в [08-performance-reliability/04-scaling-load-balancing.md](../08-performance-reliability/04-scaling-load-balancing.md)); шардирование — та же идея "распределить нагрузку между многими узлами", применённая не к сервисам, а к **данным**; consistent hashing — конкретный алгоритм, решающий, **какой** узел отвечает за **какой** ключ, минимизируя переток данных при изменении числа узлов.

## Почему naive-хеширование ломается при масштабировании

```
shard = hash(key) % N   -- N = текущее число шардов

N=4: hash(key) % 4
N=5 (добавили шард): hash(key) % 5   -- ПОЧТИ ВСЕ ключи меняют остаток от деления → почти все данные
                                          нужно переместить на другой шард, даже если добавили всего 1 узел
```

Простой modulo-хеш работает, пока число шардов `N` фиксировано — но при добавлении/удалении хотя бы одного узла результат `hash(key) % N` меняется для подавляющего большинства ключей (не только для тех, что логически должны переехать) — это означает практически полную миграцию данных при каждом изменении топологии кластера, что делает масштабирование дорогим и рискованным событием, а не рутинной операцией.

## Consistent hashing — минимизация перетока при изменении топологии

```
Кольцо хешей 0..2^32-1:
Узлы размещены на кольце по hash(node_id): Node A (позиция 100), Node B (позиция 5000), Node C (позиция 9000)
Ключ K с hash(K) = 200 → идёт на СЛЕДУЮЩИЙ по часовой стрелке узел → Node B (позиция 5000)

Добавили Node D на позицию 150:
Только ключи между 100 и 150 (те, что раньше шли на B) теперь идут на D
Остальные ключи (за пределами этого узкого диапазона) НЕ ЗАТРОНУТЫ — не нужно их перемещать
```

Узлы и ключи хешируются в одно и то же пространство (обычно представляемое как кольцо), каждый ключ принадлежит ближайшему по кольцу узлу (по часовой стрелке до первого встреченного) — при добавлении/удалении узла перераспределяется только диапазон ключей **непосредственно рядом** с изменившейся точкой кольца, а не весь диапазон ключей целиком. В среднем при добавлении N+1-го узла к N существующим перемещается доля `~1/(N+1)` ключей, а не почти все — на порядки меньше данных для миграции по сравнению с naive modulo-хешем.

## Virtual nodes — решение проблемы неравномерного распределения

```
Без virtual nodes: 3 физических узла на кольце → могут оказаться неравномерно распределены по кольцу
                    случайно (например, все близко друг к другу) → один узел получает непропорционально
                    большую долю ключей

С virtual nodes: каждый физический узел представлен МНОЖЕСТВОМ точек на кольце (например, 100-200
                  виртуальных узлов на 1 физический, каждая — hash(node_id + "-" + i) для i=0..199)
                  → усреднение по множеству случайных позиций даёт значительно более равномерное
                    распределение реальной нагрузки между физическими узлами
```

Чистый consistent hashing с малым числом физических узлов страдает от того, что случайное распределение точек по кольцу может оказаться неравномерным (закон больших чисел работает плохо на малой выборке) — virtual nodes размножают каждый физический узел на множество точек кольца, так что даже при небольшом числе реальных узлов распределение реальной нагрузки приближается к равномерному за счёт усреднения по множеству случайных позиций каждого. Дополнительный практический бонус — при добавлении нового физического узла его виртуальные точки распределены по всему кольцу равномерно, значит новый узел забирает свою долю ключей у **многих** существующих узлов понемногу, а не забирает целиком у одного соседа.

## Практическое применение — не только для распределения данных по БД-шардам

```
Redis Cluster: ключи распределены по хеш-слотам (16384 слота), сами слоты назначены узлам —
               похожая идея, хотя технически не классический consistent hashing на кольце

CDN/кеш-серверы: consistent hashing определяет, какой из N кеш-серверов отвечает за конкретный ключ —
                 добавление/удаление кеш-сервера минимально нарушает существующее распределение
                 (важно для cache hit rate — если бы весь кеш перераспределялся заново при масштабировании
                  кеш-кластера, это временно обнулило бы hit rate, создав cache stampede на источник данных)

Балансировка нагрузки по клиенту: направить все запросы конкретного клиента на один и тот же backend-инстанс
                                   (полезно для локального in-memory кеша на этом инстансе, см. 08-performance-reliability/03-multi-level-caching.md)
```

Consistent hashing — не специфичен для распределения строк в БД; это общий инструмент "распределить X между N узлов, минимизируя переток при изменении N" — применим везде, где эта задача возникает: шардирование данных, распределение ключей кеша между кеш-серверами, даже маршрутизация запросов балансировщиком, если нужна привязка конкретного клиента к конкретному backend-инстансу без полноценных sticky sessions.

## Как это связано со stateless-сервисами и обычной балансировкой

Обычная балансировка нагрузки (round robin, least connections, см. подробности в [08-performance-reliability/04-scaling-load-balancing.md](../08-performance-reliability/04-scaling-load-balancing.md)) работает, потому что **любой** stateless-инстанс сервиса может обработать **любой** запрос — балансировщику не важно, куда именно направить конкретный запрос, только общая справедливость распределения нагрузки. Consistent hashing нужен именно тогда, когда это условие **не выполняется** — конкретный узел/шард **обязан** быть тем, кто отвечает за конкретный ключ (данные физически там хранятся, кеш физически там прогрет) — это не взаимоисключающие концепции, а ответ на разные вопросы: балансировка нагрузки распределяет запросы между взаимозаменяемыми обработчиками, consistent hashing определяет, какой из потенциально невзаимозаменяемых узлов владеет конкретным ключом.

## Что спрашивают на собеседовании

1. **Что такое consistent hashing и какую проблему он решает?** — минимизирует объём данных, требующих перемещения при добавлении/удалении узла в распределённой системе — в отличие от простого `hash(key) % N`, где изменение N меняет распределение почти всех ключей разом.
2. **Зачем нужны virtual nodes поверх базового consistent hashing?** — компенсируют неравномерность распределения физических узлов по кольцу хешей при их небольшом числе — усреднение по множеству случайных позиций каждого физического узла даёт более равномерную реальную нагрузку.
3. **Как добавление нового узла влияет на существующее распределение данных при consistent hashing?** — перераспределяется только узкий диапазон ключей рядом с новой точкой на кольце (в среднем доля `~1/(N+1)` ключей), остальные ключи остаются на своих текущих узлах без необходимости миграции.
4. **Чем задача consistent hashing отличается от задачи обычной балансировки нагрузки?** — балансировка распределяет запросы между взаимозаменяемыми stateless-обработчиками (любой может обслужить любой запрос); consistent hashing нужен, когда конкретный узел физически владеет конкретными данными/состоянием — задачи дополняющие, не взаимоисключающие.
5. **Где ещё, кроме шардирования БД, применяется consistent hashing?** — распределение ключей между кеш-серверами (минимизирует cache stampede при масштабировании кеш-кластера, потому что не перераспределяет весь кеш разом), маршрутизация запросов к конкретному backend-инстансу для локального кеша.
