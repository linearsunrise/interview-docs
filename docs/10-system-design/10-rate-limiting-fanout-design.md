# Rate limiting в дизайне; fan-out on write vs on read

> **TL;DR:** Алгоритмы rate limiting (token bucket, sliding window) уже разобраны детально в [Rate limiting: алгоритмы, распределённый на Redis](../07-security/12-rate-limiting.md) — здесь про **место** rate limiter в архитектуре системы и отдельно про fan-out — фундаментальный выбор для любой системы с моделью "один producer, много читателей" (лента, уведомления, подписки): считать результат **при записи** (заранее, для каждого читателя) или **при чтении** (на лету, в момент запроса).

## Где размещать rate limiter в архитектуре

```
[Client] → [API Gateway: rate limiter здесь] → [микросервисы за ним]
```

Rate limiting чаще всего размещается на границе системы (API Gateway, см. [API Gateway, BFF, service discovery](../06-architecture-patterns/12-api-gateway-bff.md)), а не в каждом отдельном сервисе — единая точка применения лимитов ко всему входящему трафику, не дублирующая логику в каждом бэкенд-сервисе отдельно. Состояние счётчиков — в общем Redis (см. распределённый rate limiter в [Rate limiting: алгоритмы, распределённый на Redis](../07-security/12-rate-limiting.md)), доступном всем инстансам gateway одинаково — иначе, как разобрано там же, локальный счётчик на каждом инстансе даёт реальный лимит, умноженный на число инстансов.

## Fan-out on write ("push") — предвычислить для каждого читателя заранее

```
Пользователь A публикует пост
→ СРАЗУ (в момент публикации) записать пост в предвычисленную ленту КАЖДОГО из N подписчиков A
   (Redis-список/отдельная таблица "лента пользователя X")

Чтение ленты подписчика: просто READ уже готового списка — O(1) по сути, без вычислений в момент запроса
```

Вся работа по "собрать посты из всех подписок" выполняется один раз, в момент публикации, и результат складывается в структуру, готовую для быстрого чтения каждым конкретным подписчиком. Чтение — максимально быстрое (просто забрать готовый список), но запись становится дороже пропорционально числу подписчиков автора — публикация одного поста автором с 10 млн подписчиков означает 10 млн операций записи (fan-out) за один пост.

## Fan-out on read ("pull") — собрать на лету в момент запроса

```
Подписчик открывает ленту → В МОМЕНТ запроса: собрать все посты от ВСЕХ подписок этого пользователя
                              (JOIN/merge из отдельных источников, отсортировать по времени)
```

Запись — дешёвая (пост просто сохраняется один раз, независимо от числа подписчиков автора). Чтение — дороже пропорционально числу подписок читателя (нужно собрать и слить посты из потенциально сотен источников на каждый запрос ленты) — но не зависит от того, насколько популярен конкретный автор.

## Гибрид — стандартное решение для системы с celebrity-проблемой

```
Обычные пользователи (< порога подписчиков, например 100k): fan-out on write —
  их подписчиков немного, push-запись дешёвая, чтение подписчиков быстрое

Знаменитости (>= порога подписчиков): fan-out on read (или отложенный/батчевый push) —
  push на миллионы подписчиков при каждом посте был бы неприемлемо дорог

Чтение ленты подписчика: READ предвычисленной части (от обычных подписок) +
                          ДОБАВИТЬ на лету посты от знаменитостей (их немного по числу авторов,
                          даже если у каждой миллионы подписчиков — сам подписчик читает не более
                          нескольких десятков знаменитостей обычно)
```

Чистый fan-out on write ломается именно на knowledgeable-аккаунтах (миллионы подписчиков — 100M+ операций записи на один твит, физически неприемлемая нагрузка и латентность публикации). Чистый fan-out on read делает чтение дорогим для **всех** пользователей ради решения проблемы, актуальной только для небольшой доли (знаменитостей). Гибрид — специфично для этой конкретной асимметрии в реальном распределении подписчиков (степенной закон — небольшое число аккаунтов с огромным числом подписчиков, подавляющее большинство — с умеренным) — стандартный ответ, который твиттероподобные системы реально используют, и хороший deep dive кандидата, демонстрирующий понимание конкретной проблемы, а не абстрактный выбор "push или pull".

## Где ещё возникает та же дилемма push vs pull

```
Система уведомлений: push при событии (fan-out on write, каждый подписчик события получает
                       запись немедленно) vs pull при открытии приложения (клиент сам запрашивает
                       "что нового", агрегируя на лету) — см. 14-case-notifications.md

Материализованные представления в БД: обновлять view при каждой записи в исходные таблицы (write-heavy)
                       vs вычислять представление при каждом запросе (read-heavy) — тот же выбор,
                       что и CQRS read-модель, см. 06-architecture-patterns/05-cqrs.md
```

Это не специфичная для ленты проблема, а общий паттерн выбора в дизайне любой системы "один источник, много потребителей" — стоит явно назвать эту связь на собеседовании при работе над другой похожей задачей (уведомления, дашборд агрегированных метрик), а не заново изобретать терминологию.

## Что спрашивают на собеседовании

1. **Fan-out on write vs on read для новостной ленты — trade-offs?** — write: дешёвое быстрое чтение, но дорогая запись, пропорциональная числу подписчиков автора (проблема для знаменитостей); read: дешёвая запись, но дорогое чтение, пропорциональное числу подписок читателя (собрать и слить на лету).
2. **Как решить проблему знаменитости с миллионами подписчиков при fan-out on write?** — гибрид: обычные авторы — fan-out on write (дешёвый push небольшому числу подписчиков), авторы с подписчиками выше порога — fan-out on read (посты знаменитостей добавляются к ленте на лету при чтении, не пушатся всем подписчикам сразу).
3. **Где ещё в system design возникает та же дилемма, кроме ленты?** — система уведомлений (push при событии vs pull при открытии клиента), материализованные представления в БД (обновлять при записи vs вычислять при чтении) — тот же общий выбор для любой модели "один источник, много потребителей".
4. **Где в архитектуре размещать rate limiter и почему не в каждом сервисе отдельно?** — на границе системы (API Gateway) с общим состоянием счётчиков в Redis, доступным всем инстансам — единая точка применения лимитов ко всему входящему трафику вместо дублирования и рассинхрона логики по отдельным сервисам.
5. **Почему нельзя просто всегда использовать fan-out on write для простоты?** — работает, пока распределение подписчиков относительно равномерное; при наличии аккаунтов с аномально большим числом подписчиков (степенной закон распределения в реальных социальных графах) один пост порождает неприемлемое число операций записи — гибрид обязателен для реалистичного масштаба.
