# Очереди и async-обработка как инструмент дизайна

> **TL;DR:** В system design ответе очередь — не техническая деталь реализации, а архитектурный инструмент с тремя конкретными применениями: сгладить пиковую нагрузку (буфер между всплеском входящих запросов и ограниченной пропускной способностью обработчика), развязать по времени медленную/ненадёжную операцию от критического пути ответа пользователю, и разделить систему на независимо масштабируемые части. Механика самой очереди (retries, DLQ, backoff) разобрана в [Очереди для сглаживания нагрузки: BullMQ](../08-performance-reliability/09-queues-bullmq.md) — здесь про то, **когда** в high-level схеме вообще стоит рисовать очередь.

## Сглаживание пиковой нагрузки (load leveling)

```
Без очереди: 10 000 запросов/сек на "отправить уведомление" → сервис уведомлений должен
             мгновенно выдерживать 10 000 RPS, даже если это редкий кратковременный всплеск

С очередью:  10 000 запросов/сек → Queue (принимает мгновенно, почти без ограничения по throughput)
             → Worker обрабатывает в своём стабильном темпе (например, 1000/сек), очередь
               временно накапливает избыток и разбирает его за следующие секунды
```

Очередь превращает требование "выдерживать мгновенный пик X RPS" в требование "выдерживать средний RPS с временным буфером на пики" — конкретное экономическое решение: держать инфраструктуру, рассчитанную на редкий короткий пик (простаивающую большую часть времени), обычно дороже, чем держать инфраструктуру под средний RPS плюс буфер-очередь, разбирающую накопленное чуть медленнее в течение следующих секунд/минут после пика. Применимо, только если операция допускает такую задержку — не подходит для синхронного пути, где пользователь ждёт немедленного ответа (см. следующий пункт).

## Развязка по времени медленной/ненадёжной зависимости

```
POST /orders → OrderService создаёт заказ → publish "OrderCreated" в очередь → отвечает 201 клиенту СРАЗУ
                                                    ↓
                                    Worker: отправка email, обновление аналитики, вызов внешнего провайдера доставки
                                    (клиент НЕ ждёт завершения этих операций)
```

Тот же принцип, что разобран для async-коммуникации между сервисами (см. [Межсервисная коммуникация: sync vs async](../06-architecture-patterns/08-sync-vs-async-communication.md)) и конкретно для BullMQ (см. [Очереди для сглаживания нагрузки: BullMQ](../08-performance-reliability/09-queues-bullmq.md)) — применяется в system design ответе как явное архитектурное решение: операции, не критичные для немедленного ответа пользователю (отправка email, пуш-уведомление, обновление аналитики, вызов стороннего API с непредсказуемой latency) — выносятся за пределы синхронного пути запроса через очередь, latency ответа пользователю не зависит от latency/надёжности этих второстепенных операций.

## Разделение на независимо масштабируемые части

```
[API service] → [Queue: image-processing] → [Worker pool: image processing] (CPU-bound, масштабируется отдельно)
             → [Queue: notifications] → [Worker pool: notifications] (I/O-bound, другой профиль масштабирования)
```

Очередь как граница между подсистемами с принципиально разным профилем нагрузки (CPU-bound обработка изображений vs I/O-bound отправка уведомлений, см. также [CPU-bound в Node: event loop lag, worker threads](../08-performance-reliability/06-cpu-bound-event-loop-lag.md) про CPU-bound проблемы в Node) — каждый worker pool масштабируется независимо под свой конкретный паттерн нагрузки (число воркеров обработки изображений растёт с объёмом загруженных изображений, число воркеров уведомлений — с частотой событий, требующих уведомления, эти две метрики не обязаны расти пропорционально друг другу).

## Где очередь неуместна — синхронный критический путь

```
GET /orders/:id/status — пользователь явно ждёт ответ ПРЯМО СЕЙЧАС
→ НЕ через очередь: прямой синхронный запрос к сервису/БД, ответ немедленно
```

Не каждая операция выигрывает от асинхронности — если пользователь физически ждёт результат на экране (не может продолжить без него), оборачивание в очередь только добавляет латентность и сложность (нужен отдельный механизм уведомления клиента о готовности результата — polling, WebSocket, см. [SSE vs WebSocket vs long polling](../05-api-communication/09-sse-vs-websocket-vs-polling.md)) без реальной пользы. Явное упоминание этого границы в system design ответе ("вот эта операция синхронная, потому что пользователь ждёт результат немедленно, а вот эта — асинхронная, потому что...") демонстрирует, что выбор архитектуры обоснован конкретным сценарием использования, а не привычкой "добавить очередь на всякий случай" (тот же принцип, что критикуется в общем красном флаге «везде Kafka и микросервисы без обоснования»).

## Fan-out через очередь — один producer, много consumer'ов

```
"OrderCreated" event → Queue/Topic
                          ├── Consumer: InventoryService (резервирует товар)
                          ├── Consumer: NotificationService (шлёт email)
                          └── Consumer: AnalyticsService (обновляет метрики)
```

Одно событие, опубликованное один раз, может требовать реакции нескольких независимых подсистем — очередь/шина сообщений (особенно Kafka-подобная с моделью лога, позволяющей множеству независимых consumer'ов читать один и тот же поток, см. [Kafka vs RabbitMQ: log vs queue](../06-architecture-patterns/13-kafka-vs-rabbitmq.md)) даёт producer'у возможность не знать заранее, сколько и каких consumer'ов будут реагировать на его событие — новый consumer (например, добавили сервис лояльности, начисляющий баллы за заказ) подписывается на существующий поток событий, не требуя изменений в коде, который эти события публикует. Это прямая связь с хореографией в микросервисной коммуникации (см. [Межсервисная коммуникация: sync vs async](../06-architecture-patterns/08-sync-vs-async-communication.md)) — очередь в system design ответе часто и есть механизм, реализующий хореографию между спроектированными сервисами.

## Что спрашивают на собеседовании

1. **Когда в архитектуре стоит добавить очередь, а когда — нет?** — да: сглаживание пиковой нагрузки, развязка критического пути ответа от медленной/ненадёжной второстепенной операции, разделение подсистем с разным профилем масштабирования; нет: пользователь физически ждёт немедленный результат на экране — очередь здесь добавляет только сложность без выгоды.
2. **Как очередь помогает справиться с внезапным всплеском трафика без пропорционального увеличения инфраструктуры?** — принимает запросы почти мгновенно вне зависимости от текущей пропускной способности обработчика, обработчик разбирает накопленное в своём стабильном темпе — компромисс между стоимостью инфраструктуры под редкий пик и стоимостью буфера, сглаживающего пик во времени.
3. **Как одно событие может обслужить несколько независимых подсистем без прямой связи между ними?** — fan-out через очередь/шину событий: несколько независимых consumer'ов подписываются на один поток событий producer'а, новый consumer добавляется без изменений в коде, публикующем событие — реализация хореографии между сервисами.
4. **Почему нельзя просто "добавлять очередь везде на всякий случай"?** — то же самое, что и с микросервисами: очередь добавляет сложность (инфраструктура, обработка ошибок доставки, идемпотентность consumer'ов) — оправдана конкретным сценарием (пиковая нагрузка, развязка, независимое масштабирование), не универсальным дефолтом.
5. **Как масштабировать CPU-bound и I/O-bound части системы независимо друг от друга?** — разделить их разными очередями/worker pool'ами — каждый масштабируется по своей метрике нагрузки (объём CPU-тяжёлых задач vs частота I/O-событий), не связывая эти два профиля масштабирования в один общий сервис.
