# Partial, covering, функциональные индексы — и когда индекс не используется

> **TL;DR:** Три способа сделать индекс точнее и дешевле общего B-tree на всю таблицу: **partial** — индексировать только подмножество строк (`WHERE` в самом индексе), **covering** — включить в индекс дополнительные колонки, чтобы не ходить в heap за данными, **функциональный** — индексировать не колонку, а выражение над ней. Отдельно — частая на собеседовании ловушка: индекс молча не используется, если в запросе колонка обёрнута в функцию/приведение типа, а функционального индекса под неё нет.

## Partial index — индексировать не всё

```sql
CREATE INDEX idx_active_orders ON orders (created_at) WHERE status = 'active';
```

Если 95% заказов в таблице — `completed`/`cancelled`, а горячий путь — выборки только активных, обычный индекс на всю таблицу тратит место и I/O на 95% ненужных записей. Partial-индекс физически меньше (быстрее обход, дешевле поддержка при `INSERT`/`UPDATE`), но используется планировщиком только если условие запроса **логически покрывается** условием индекса (`status = 'active'` в `WHERE` запроса должно подразумевать то же самое, что и в индексе — точное совпадение предиката работает надёжнее всего).

## Covering index — избежать похода в heap

```sql
CREATE INDEX idx_orders_covering ON orders (user_id) INCLUDE (status, total);
```

Обычный индекс в PostgreSQL хранит только индексируемые колонки + `ctid` (указатель на строку в heap) — чтобы получить остальные поля (`SELECT status, total`), нужен дополнительный переход в heap ("bookmark lookup"). `INCLUDE` кладёт дополнительные колонки прямо в лист индекса — планировщик получает всё нужное из самого индекса, это называется **Index Only Scan**. Условие для реального Index Only Scan — ещё и то, чтобы страница heap была отмечена как "all visible" в visibility map (иначе всё равно придётся сходить проверить видимость строки по MVCC, см. [MVCC, VACUUM, bloat](./05-mvcc-vacuum.md)) — частая причина, почему `EXPLAIN` показывает Index Only Scan, но с "Heap Fetches" не нулевыми.

Отличие `INCLUDE`-колонок от обычных ключевых: они не участвуют в сортировке/поиске дерева, только "довозятся" в листе — то есть `INCLUDE (status)` бесполезен для `WHERE status = ?`, только для `SELECT status`.

## Функциональный индекс — индексируем выражение

```sql
CREATE INDEX idx_users_email_lower ON users (lower(email));
SELECT * FROM users WHERE lower(email) = 'a@b.com'; -- сработает
SELECT * FROM users WHERE email = 'a@b.com';         -- НЕ сработает — другое выражение
```

Индекс строится не по колонке, а по результату выражения — база обязана сохранять то же самое выражение (синтаксически, не просто семантически эквивалентное) в запросе, чтобы оптимизатор распознал совпадение с определением индекса.

## Почему индекс "не используется" — типовые причины

```sql
-- колонка обёрнута функцией без функционального индекса под неё
WHERE lower(email) = 'a@b.com'; -- обычный индекс на email не поможет

-- неявное приведение типа
WHERE phone_numeric_column = '12345'; -- строка вместо числа, привет implicit cast

-- LIKE с ведущим wildcard
WHERE name LIKE '%son'; -- B-tree не может определить границу диапазона для '%son'

-- OR между разными колонками без индекса на комбинацию
WHERE email = ? OR phone = ?; -- часто seq scan, если нет bitmap-плана/UNION

-- низкая селективность
WHERE is_deleted = false; -- если 99% строк false, seq scan может быть дешевле индекса
```

Общий принцип: планировщик использует индекс, только если может по нему однозначно построить границы поиска (диапазон/точное значение) **до** чтения данных. Как только колонка проходит через функцию/приведение типа, которых индекс не "знает", — это уже not sargable (Search ARGument ABLE) условие, и единственный способ его вычислить — построчно, то есть seq scan.

## Что спрашивают на собеседовании

1. **Когда имеет смысл partial-индекс вместо обычного?** — когда горячие запросы затрагивают предсказуемое небольшое подмножество строк (активные записи, не-`NULL`, конкретный статус) — индекс меньше и дешевле в поддержке.
2. **Что даёт `INCLUDE` в индексе?** — Index Only Scan: нужные для `SELECT` колонки берутся прямо из листа индекса без похода в heap, при условии видимости страницы по MVCC.
3. **Почему `WHERE lower(email) = ?` не использует обычный индекс на `email`?** — индекс построен по значению колонки, а не по результату функции — нужен функциональный индекс `lower(email)` либо `LIKE`/`ILIKE`-специфичные операторные классы.
4. **Почему `LIKE '%son'` не использует B-tree индекс, а `LIKE 'son%'` использует?** — B-tree отсортирован по значению целиком, ведущий wildcard не даёт зафиксировать точку старта диапазона; суффиксный поиск обычно решают тримграммным индексом (`pg_trgm`) или полнотекстовым поиском.
5. **Какие ещё причины, кроме отсутствия индекса, объясняют seq scan вместо index scan?** — низкая селективность условия, устаревшая статистика (`ANALYZE`), неявное приведение типов, слишком маленькая таблица (seq scan реально дешевле).
