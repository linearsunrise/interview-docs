# B-tree индексы: устройство и leftmost prefix

> **TL;DR:** B-tree — сбалансированное дерево, где в листьях лежат отсортированные пары (значение индексируемых колонок → ссылка на строку), а внутренние узлы — навигация. Поиск, вставка, удаление — `O(log n)`. Составной индекс `(a, b, c)` физически отсортирован сначала по `a`, потом по `b`, потом по `c` — это одна структура, а не три отдельных индекса, отсюда правило **leftmost prefix**: индекс можно использовать только начиная с левых колонок по порядку.

## Как устроено дерево

```
                    [50]
          ┌──────────┴──────────┐
        [20]                  [80]
    ┌────┴────┐          ┌──────┴──────┐
 [5,10]    [30,40]    [60,70]      [90,100]   ← листья: отсортированные значения + ссылка на heap
```

Каждый узел — страница диска (обычно 8 КБ в PostgreSQL). Высота дерева растёт логарифмически: индекс на миллиард строк — это дерево высотой 4-5 уровней, то есть 4-5 чтений страниц для точечного поиска. Листовые страницы связаны в двусвязный список — поэтому B-tree одинаково хорошо работает и для точечного поиска (`=`), и для диапазонного (`BETWEEN`, `>`, `ORDER BY`) — достаточно найти начало диапазона и идти по списку листьев.

## Leftmost prefix — ключевое правило

```sql
CREATE INDEX idx_orders ON orders (user_id, status, created_at);
```

| Запрос | Индекс работает? | Почему |
|---|---|---|
| `WHERE user_id = ?` | да | использует первую колонку |
| `WHERE user_id = ? AND status = ?` | да | префикс `(user_id, status)` |
| `WHERE user_id = ? AND status = ? AND created_at > ?` | да, полностью | весь индекс задействован |
| `WHERE status = ?` | нет | пропущена первая колонка — по сути ищем "неотсортированный" срез дерева |
| `WHERE user_id = ? AND created_at > ?` | частично | `user_id` — по индексу, `created_at` — фильтром после (т.к. `status` пропущен, дальше сортировки по `created_at` внутри группы `user_id` нет) |
| `WHERE user_id = ? ORDER BY status` | да | сортировка по второй колонке внутри отфильтрованной первой — бесплатна, индекс уже так отсортирован |

Правило простое: индекс — это отсортированный список кортежей `(a, b, c)`. Найти по `b` без фиксации `a` так же бессмысленно, как искать людей по фамилии в телефонной книге, отсортированной по имени, — данные не сгруппированы по нужному признаку.

## Порядок колонок — не только для WHERE, но и для селективности

Общее правило: колонку с точечным равенством (`=`) ставят раньше диапазонной (`BETWEEN`, `>`). Если у индекса `(a, b)` в запросе `WHERE a > ? AND b = ?`, то `a > ?` уже "рвёт" сортировку — база использует индекс до диапазона `a`, а условие на `b` внутри него проверяется построчно, не как часть структуры поиска. Меняем местами (`b, a`) — если `b` чаще идёт как равенство в запросах, это будет эффективнее.

## Кластерный vs некластерный индекс — почему это «зависит от СУБД»

В PostgreSQL все индексы — некластерные: таблица (heap) хранится отдельно от индекса, лист B-tree содержит только указатель (ctid) на строку — отсюда нужен дополнительный переход в heap за реальными данными (если только не covering-индекс, см. [Partial, covering, функциональные индексы](./02-index-types.md)). В MySQL/InnoDB первичный ключ — это **кластерный** индекс: сама таблица физически хранится как B-tree, отсортированная по PK, а вторичные индексы хранят в листе не указатель на страницу, а значение PK, по которому потом ищут в кластерном индексе. Практическое следствие: в InnoDB монотонно растущий PK (autoincrement/UUIDv7) — важно для производительности вставок, случайный PK (UUIDv4) фрагментирует страницы кластерного индекса; в Postgres это не так критично, но зато там свои трейд-оффы с MVCC (см. [MVCC, VACUUM, bloat](./05-mvcc-vacuum.md)).

## Что спрашивают на собеседовании

1. **Как устроен B-tree индекс изнутри?** — сбалансированное дерево, листья отсортированы и связаны в список, высота логарифмическая от числа строк, страницы = блоки диска.
2. **Сработает ли индекс `(a, b)` для запроса `WHERE b = ?`?** — нет, нарушен leftmost prefix: без фиксации `a` дерево нельзя эффективно обойти по `b`.
3. **В каком порядке ставить колонки в составном индексе?** — сначала колонки с точечным равенством и высокой селективностью, диапазонные условия и `ORDER BY` — правее; leftmost prefix определяет, какие запросы вообще смогут воспользоваться индексом.
4. **Почему точечный поиск по индексу — `O(log n)`, а не `O(1)` как у хэш-таблицы?** — дерево, не хэш: зато поддерживает диапазоны и сортировку, чего хэш-индекс не даёт в принципе.
5. **Чем кластерный индекс отличается от обычного?** — в кластерном (например, PK в InnoDB) сама таблица физически хранится в порядке индекса — не нужен доп. переход к данным; в Postgres такого нет — там всегда отдельный heap.
