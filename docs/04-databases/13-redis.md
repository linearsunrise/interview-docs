# Redis: структуры данных, TTL, eviction, персистентность, pub/sub vs streams

> **TL;DR:** Redis — не просто "key-value кэш", а набор структур данных с O(1)/O(log n) операциями, живущих в памяти. Главные развилки на собеседовании: **eviction policy** (что делать, когда память кончилась — по умолчанию `noeviction`, что для кэша обычно неправильная настройка), **персистентность** (RDB снапшоты vs AOF журнал — trade-off "скорость восстановления" vs "потеря данных при падении"), и **pub/sub vs streams** (pub/sub — fire-and-forget без сохранения, streams — персистентный лог с consumer groups, ближе к Kafka по духу).

## Структуры данных — не только строки

| Тип | Типичное применение |
|---|---|
| `String` | простой кэш значения, счётчики (`INCR`), битовые операции |
| `Hash` | объект целиком (профиль пользователя) — дешевле, чем JSON-строка, если нужно менять отдельные поля |
| `List` | очередь/стек (`LPUSH`/`RPOP`), последние N событий |
| `Set` | уникальные значения, пересечения/объединения (`SINTER` — общие теги/друзья) |
| `Sorted Set (ZSet)` | лидерборды, rate limiting по времени (score = timestamp), приоритетные очереди |
| `Stream` | персистентный лог событий с consumer groups |
| `HyperLogLog` | приближённый подсчёт уникальных элементов при огромном объёме (ошибка ~0.8%, фиксированная память ~12КБ независимо от кол-ва элементов) |
| `Bitmap` | компактные флаги (например, "какие пользователи заходили сегодня" — 1 бит на пользователя) |

Выбор структуры — не деталь реализации, а то, что определяет доступные операции и их сложность: `ZADD leaderboard score member` + `ZREVRANGE leaderboard 0 9` даёт топ-10 за `O(log n)`, тогда как эмуляция того же на строках/хэшах потребовала бы сортировки на стороне приложения.

## TTL и eviction — что происходит, когда память кончается

```
SET session:abc123 "..." EX 3600   -- TTL 1 час
maxmemory 2gb
maxmemory-policy allkeys-lru       -- при нехватке памяти вытеснять по LRU среди ВСЕХ ключей
```

Основные policy: `noeviction` (дефолт — при переполнении памяти новые записи получают ошибку, старые не трогаются — годится для Redis-как-хранилища, где потеря данных недопустима, но опасно для Redis-как-кэша, если забыть переключить), `allkeys-lru`/`allkeys-lfu` (вытеснение среди всех ключей по недавности/частоте использования — типичный выбор для чистого кэша), `volatile-lru`/`volatile-ttl` (вытеснять только ключи с выставленным TTL, ключи без TTL считаются "постоянными" и не трогаются). Частая ошибка на собеседовании — не знать, что дефолт `noeviction`, и предполагать, что Redis "сам как-то разберётся" при заполнении памяти.

## Персистентность — RDB vs AOF

- **RDB (snapshot)** — периодический полный дамп датасета на диск (`SAVE`/`BGSAVE`, или по расписанию `save 900 1`). Компактный файл, быстрое восстановление при рестарте, но теряются все изменения между последним снапшотом и падением.
- **AOF (Append Only File)** — журнал каждой операции записи, применяется заново при старте. Настройка `appendfsync` определяет, как часто журнал реально сбрасывается на диск: `always` (каждая команда — минимальная потеря данных, но самая низкая производительность), `everysec` (компромисс по умолчанию — до 1 секунды данных под риском), `no` (доверить сброс ОС — быстрее всего, но риск потери больше).
- **Комбинация (RDB + AOF)** — типичная прод-настройка: RDB для быстрого полного восстановления базового состояния + AOF поверх для минимизации окна потери данных.

Ключевой вопрос на собеседовании — "Redis как кэш vs Redis как хранилище": для чистого кэша персистентность часто вообще не критична (потеря — просто холодный кэш, перестроится из основной БД), для Redis как источника истины (сессии, очереди задач без дублирующего хранилища) — AOF с `everysec` минимум, часто `always` для критичных данных.

## Pub/Sub vs Streams

```
-- Pub/Sub: fire-and-forget
SUBSCRIBE notifications
PUBLISH notifications "new order"
-- подписчик, которого не было онлайн в момент публикации, сообщение никогда не увидит

-- Streams: персистентный лог с историей и consumer groups
XADD events '*' type order_created order_id 123
XREADGROUP GROUP workers consumer1 COUNT 10 STREAMS events '>'
XACK events workers <message-id>
```

Pub/Sub не хранит сообщения — только доставляет активным подписчикам в момент публикации; нет истории, нет подтверждения доставки, нет повторной обработки при падении консьюмера. Streams — структура, близкая по духу к Kafka: сообщения хранятся в логе, **consumer groups** позволяют нескольким воркерам разбирать поток без дублирования (`XREADGROUP`), с явным подтверждением обработки (`XACK`) и возможностью забрать необработанные сообщения упавшего консьюмера (`XCLAIM`/`XAUTOCLAIM`). Выбор: pub/sub — для "просто оповестить, кто сейчас слушает" (real-time уведомления в UI), streams — там, где нужна надёжная доставка хотя бы одному воркеру и история событий.

## Что спрашивают на собеседовании

1. **Какая структура данных для лидерборда и почему?** — Sorted Set: `ZADD`/`ZREVRANGE`/`ZRANK` дают ранжирование и вставку за `O(log n)` без сортировки на стороне приложения.
2. **Что произойдёт, если память Redis заполнится при дефолтных настройках?** — `maxmemory-policy noeviction` по умолчанию — новые записи начнут отклоняться с ошибкой, а не тихо вытеснять старые; для кэша это обычно нужно явно переключить на `allkeys-lru`/`allkeys-lfu`.
3. **Чем RDB отличается от AOF и когда что выбрать?** — RDB — компактные периодические снапшоты (быстрое восстановление, больше потенциальная потеря данных), AOF — журнал каждой операции (минимальная потеря, дороже по I/O); для критичных данных — комбинация обоих.
4. **Чем Streams отличается от Pub/Sub?** — Pub/Sub не хранит сообщения и не гарантирует доставку офлайн-подписчикам; Streams — персистентный лог с consumer groups, подтверждением обработки и возможностью перечитать историю.
5. **Redis как кэш vs как основное хранилище — что меняется в настройках?** — eviction policy (allow eviction для чистого кэша vs noeviction для хранилища), уровень персистентности (AOF `everysec`/`always` критичен для хранилища, необязателен для кэша), ожидания по доступности данных после рестарта.
