# Блокировки: row-level, `FOR UPDATE`, advisory locks, optimistic vs pessimistic

> **TL;DR:** PostgreSQL блокирует на уровне строк, не всей таблицы (кроме DDL и явных table-level команд) — это то, что делает MVCC практичным под конкурентной нагрузкой. `SELECT ... FOR UPDATE` — явная пессимистичная блокировка строки внутри транзакции. Optimistic locking не использует блокировки СУБД вообще — полагается на проверку версии при записи. Advisory locks — блокировки **произвольного** прикладного смысла (не привязаны к конкретной строке), удобны там, где нужно синхронизировать что-то за пределами данных (например, "только один воркер обрабатывает эту задачу").

## Row-level locking — `FOR UPDATE` / `FOR SHARE`

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE; -- блокирует строку до конца транзакции
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
COMMIT; -- блокировка снимается
```

Другая транзакция, пытающаяся `SELECT ... FOR UPDATE` ту же строку, будет ждать до `COMMIT`/`ROLLBACK` первой. Варианты силы блокировки (по возрастанию строгости): `FOR SHARE` (несколько читателей могут держать одновременно, блокирует только `UPDATE`/`DELETE` этой строки), `FOR NO KEY UPDATE`, `FOR UPDATE` (эксклюзивно — никто больше не может ни читать с блокировкой, ни писать). `FOR UPDATE SKIP LOCKED` — не ждать, а пропустить уже заблокированные строки: стандартный паттерн для очередей на таблице (несколько воркеров разбирают задачи, не толкаясь):

```sql
SELECT * FROM jobs WHERE status = 'pending'
ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
```

## Pessimistic locking — предполагаем конфликт заранее

Подход из примера выше: захватить блокировку **до** изменения, остальные ждут. Плюсы — гарантированная консистентность, простая ментальная модель. Минусы — конкурентность падает (все ждут в очередь), риск deadlock при неверном порядке захвата (см. [Deadlocks](./06-deadlocks.md)), долгая транзакция держит блокировку и блокирует остальных.

## Optimistic locking — предполагаем, что конфликтов мало

```sql
-- читаем вместе с текущей версией
SELECT id, balance, version FROM accounts WHERE id = 1; -- balance=100, version=5

-- пишем с проверкой, что версия не изменилась с момента чтения
UPDATE accounts SET balance = 90, version = version + 1
WHERE id = 1 AND version = 5;
-- 0 затронутых строк = кто-то успел изменить раньше нас → конфликт, повторить операцию с начала
```

Никаких блокировок СУБД не используется — конкурентность максимальна, но при реальном конфликте одна из сторон получает "0 rows affected" и обязана явно обработать это как ретрай (или ошибку пользователю "данные изменились, обновите страницу"). Хорошо подходит, когда конфликты редки (типичный веб-CRUD с формами редактирования), плохо — при высокой конкуренции за одну и ту же строку (там пессимистичный подход/атомарный `UPDATE` эффективнее, потому что при optimistic locking под высокой конкуренцией большинство попыток будут просто ретраиться раз за разом).

## Advisory locks — блокировка без данных

```sql
SELECT pg_advisory_lock(12345); -- блокирует по произвольному числовому ключу, сессия ждёт, пока свободно
-- ... критическая секция, не привязанная ни к одной строке таблицы ...
SELECT pg_advisory_unlock(12345);

SELECT pg_try_advisory_lock(12345); -- не блокирующий вариант: сразу true/false
```

Ключ — просто число (например, `hashtext('job:daily-report')`), самой блокируемой "строки" может вообще не существовать. Типичные кейсы: гарантировать, что миграция/cron-джоба выполняется только одним инстансом приложения одновременно, распределённый мьютекс для редких операций без отдельного Redis/Zookeeper. Есть session-level (держится до явного `unlock` или разрыва соединения) и transaction-level (`pg_advisory_xact_lock`, снимается сама при `COMMIT`/`ROLLBACK`) варианты.

## Что спрашивают на собеседовании

1. **Чем `FOR UPDATE` отличается от обычной транзакции без блокировки?** — явно блокирует конкретные строки на запись/повторную блокировку до конца транзакции — без этого READ COMMITTED допускает lost update.
2. **Optimistic vs pessimistic locking — когда что выбрать?** — pessimistic для высокой конкуренции за одну запись (банковский баланс под нагрузкой), optimistic для редких конфликтов (формы редактирования, где пользователи почти не пересекаются).
3. **Что делает `FOR UPDATE SKIP LOCKED` и зачем?** — не ждёт занятые строки, а пропускает их — основа паттерна очереди задач на таблице с несколькими конкурентными воркерами.
4. **Что такое advisory lock и чем он отличается от row-level?** — блокировка по произвольному ключу приложения, не привязанная к конкретной строке/таблице — для синхронизации логики за пределами данных (единственный инстанс крона, распределённый мьютекс).
5. **Как реализовать optimistic locking без отдельной колонки version?** — сравнить все значимые поля в `WHERE` (`UPDATE ... WHERE id = ? AND balance = ?`) — работает, но менее явно и хуже читается, чем выделенная `version`/`updated_at`.
