# Пагинация: offset vs cursor (keyset)

> **TL;DR:** `LIMIT/OFFSET` заставляет базу физически пройти и отбросить все `OFFSET` строк перед каждой страницей — на странице 5000 это буквально пролистывание 5000×`page_size` строк заново на каждый запрос, `O(offset)`. Cursor-пагинация (keyset) вместо "пропусти N" использует условие "дай строки после этой конкретной точки" — при поддержке индексом это `O(log n)` независимо от номера страницы. Плата — нет произвольного перехода "сразу на страницу 50", только вперёд/назад от текущей позиции.

## Почему offset деградирует

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```

Даже если `ORDER BY created_at` покрыт индексом, база обязана пройти по индексу первые 100000+20 строк и отбросить первые 100000 — сам `OFFSET` не "телепортирует" в нужную точку дерева, потому что нет способа заранее знать, какая именно строка окажется 100000-й, кроме как посчитать. Чем дальше страница — тем больше строк выбрасывается впустую на **каждый** запрос этой страницы, а не один раз.

## Cursor (keyset) пагинация — идея

Вместо "какая по счёту страница" запоминаем **значение** последней увиденной строки и просим "всё, что после неё":

```sql
-- первая страница
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 20;

-- следующая — используя created_at и id последней строки предыдущей страницы как курсор
SELECT * FROM orders
WHERE (created_at, id) < ($1, $2) -- $1/$2 — created_at и id последней строки прошлой страницы
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

При индексе `(created_at DESC, id DESC)` условие `(created_at, id) < ($1, $2)` — это ровно то, для чего B-tree создан: найти точку в отсортированном дереве и пойти по нему дальше, `O(log n)` на нахождение точки + `O(page_size)` на чтение страницы, независимо от того, какая это "страница" по счёту.

**Зачем два поля в курсоре, а не одно `created_at`:** `created_at` не уникален (несколько заказов могут быть созданы в одну и ту же миллисекунду) — без тайбрейка по уникальному `id` возможны дубли/пропуски строк на границе страниц. Составной курсор `(created_at, id)` с составным индексом под ним — устраняет неоднозначность.

## Сравнение

| | Offset | Cursor (keyset) |
|---|---|---|
| Сложность на дальних страницах | `O(offset)` — растёт линейно | `O(log n)` — не зависит от глубины |
| Прыжок на произвольную страницу | да, "страница 50" | нет, только относительно текущей позиции |
| Устойчивость к параллельным вставкам/удалениям | нет — вставка в начало сдвигает всю нумерацию, возможны дубли/пропуски строк между запросами страниц | да — курсор — это конкретное значение, а не порядковый номер |
| Реализация "Показать номера страниц 1..10" в UI | тривиальна | требует отдельного механизма (или отказа от номеров в пользу "далее/назад") |
| Индекс | обычный по `ORDER BY` колонке | составной по `(sort_col, unique_col)`, направление должно совпадать с сортировкой |

## Практический выбор

- **Публичный API, лента, бесконечный скролл, мобильные списки** — cursor: нагрузка растёт с активностью пользователей, не с глубиной пагинации; не ломается от параллельных вставок.
- **Админка с "перейти на страницу N", отчёты, небольшие таблицы** — offset вполне приемлем: данных мало, глубокая пагинация не нужна, а удобство произвольного перехода перевешивает.
- **Гибрид** — часто на практике: offset для первых N страниц (где он ещё дешёвый), с ограничением на максимальный `OFFSET` (типично в поисковых API — "доступны только первые 1000 результатов, уточните запрос").

## Что спрашивают на собеседовании

1. **Почему `LIMIT/OFFSET` деградирует на больших страницах?** — база обязана физически пройти и отбросить все `OFFSET` строк перед каждым запросом — линейный рост стоимости с номером страницы.
2. **Как устроена cursor-пагинация?** — запрос "дай строки после этой конкретной точки" через составное неравенство `(sort_col, id) < (last_val, last_id)`, эффективно при составном индексе в том же порядке.
3. **Зачем в курсоре два поля, а не только `created_at`?** — `created_at` не гарантированно уникален, нужен тайбрейк по уникальному `id`, иначе возможны пропуски/дубли строк на границе страниц.
4. **Какой минус у cursor-пагинации по сравнению с offset?** — нет произвольного перехода на страницу N — только "следующая"/"предыдущая" от текущей позиции.
5. **Offset-пагинация неустойчива при параллельных вставках — почему?** — новая строка, попавшая перед текущей "страницей" по сортировке, сдвигает нумерацию — пользователь может увидеть дубль или пропустить строку между двумя последовательными запросами.
