# Connection pooling: зачем, pgbouncer, размер пула

> **TL;DR:** Каждое соединение PostgreSQL — это отдельный **процесс** ОС (не поток, не легковесная структура), с собственным выделением памяти под `work_mem` и т.п. Сотни-тысячи открытых соединений напрямую — это сотни-тысячи процессов, конкурирующих за CPU/память, что деградирует базу задолго до исчерпания реальной пропускной способности запросов. Пул решает две разные проблемы: переиспользование дорогих соединений на стороне приложения и (через pgbouncer) сглаживание тысяч клиентских соединений в десятки реальных на стороне базы.

## Почему нельзя просто "открывать соединение на каждый запрос"

Установка TCP-соединения + аутентификация + форк процесса в PostgreSQL — заметные накладные расходы (единицы-десятки мс). При нагрузке в сотни RPS открытие нового соединения на каждый HTTP-запрос убивает и задержку, и саму базу количеством одновременных процессов. Пул соединений на стороне приложения (`pg-pool`, встроенный пул `TypeORM`/`Prisma`, `node-postgres` Pool) держит N уже установленных соединений и раздаёт их запросам по очереди — открытие происходит один раз, дальше — просто занять/освободить.

## Почему размер пула — не "чем больше, тем лучше"

Контринтуитивный факт: увеличение пула сверх некоторого предела **снижает** пропускную способность, а не растит её. У БД конечное число CPU-ядер; когда одновременно активных запросов больше, чем ядер, они начинают конкурировать за CPU/блокировки/буферы, контекст-свитчинг и borrowing latency растут быстрее, чем параллелизм даёт выигрыш. PostgreSQL wiki и практические бенчмарки (PgBouncer FAQ, книга "The Art of PostgreSQL") сходятся на формуле-отправной точке:

```
connections = ((core_count * 2) + effective_spindle_count)
```

То есть для базы на 8 ядрах с SSD ориентир — **около 20, не 200-500** соединений на саму СУБД. Это именно верхняя граница для физических соединений к Postgres, а не для количества клиентов приложения — отсюда необходимость pgbouncer при десятках инстансов сервиса.

## pgbouncer — мультиплексор поверх реальных соединений

```
[databases]
mydb = host=localhost port=5432 dbname=mydb

[pgbouncer]
pool_mode = transaction
max_client_conn = 1000    ; сколько клиентов может подключиться к pgbouncer
default_pool_size = 20    ; сколько РЕАЛЬНЫХ соединений к Postgres он держит
```

pgbouncer принимает тысячи клиентских соединений (дёшево — это лёгкий процесс, не форк Postgres), но держит к самой базе лишь пул из `default_pool_size` реальных соединений, раздавая их клиентам по мере надобности. Три режима:
- **session** — клиент занимает реальное соединение на весь сеанс (почти как без pgbouncer, просто разгружает handshake);
- **transaction** — соединение отдаётся клиенту только на время одной транзакции, между транзакциями возвращается в пул — самый эффективный режим по плотности, но **ломает** сессионные фичи (`PREPARE`, `SET` на сессию, advisory locks на уровне сессии, temporary tables) — их нужно либо не использовать, либо явно поддерживать через pgbouncer-specific настройки;
- **statement** — ещё агрессивнее, отдаёт соединение на один запрос; несовместим даже с обычными многошаговыми транзакциями — редко применим для прикладных сервисов.

## Пул на стороне приложения vs pgbouncer — не взаимоисключающие вещи

Пул в приложении (Node: `pg.Pool`, пул внутри TypeORM/Prisma) решает проблему в рамках одного процесса приложения — держит переиспользуемые соединения, не открывает новое на каждый запрос. pgbouncer решает проблему на уровне **всей инфраструктуры** — десятки подов/инстансов приложения, каждый со своим локальным пулом, в сумме легко дают тысячи соединений к базе; pgbouncer сужает это до разумного числа реальных соединений. Типичная прод-схема — оба слоя одновременно: у приложения свой небольшой пул (5-20 на инстанс), инстансы подключаются не напрямую к Postgres, а к pgbouncer.

## Что спрашивают на собеседовании

1. **Почему нельзя открывать новое соединение на каждый запрос?** — соединение PostgreSQL — процесс ОС с накладными расходами на установку и память; при заметной нагрузке это убивает и латентность, и саму базу количеством процессов.
2. **Почему "выставить пул в 500" — плохой ответ?** — избыточная конкуренция за CPU/буферы на стороне БД снижает пропускную способность после определённого порога; ориентир — от числа ядер БД (`2×cores + disks`), обычно десятки, не сотни.
3. **Что решает pgbouncer, чего не решает пул в приложении?** — мультиплексирует тысячи клиентских соединений (от множества инстансов приложения) в ограниченное число реальных соединений к самой БД.
4. **Чем `transaction`-режим pgbouncer отличается от `session`?** — соединение возвращается в пул сразу после `COMMIT`/`ROLLBACK`, а не держится на весь клиентский сеанс — выше плотность, но ломает сессионные фичи (temp tables, `SET`, `PREPARE`).
5. **Что произойдёт, если приложение открывает больше соединений, чем разрешает `max_connections` в Postgres?** — новые подключения получат ошибку `too many connections` (или будут ждать, в зависимости от прослойки) — ещё один аргумент за pgbouncer/ограниченный пул вместо "открывать соединения по требованию".
