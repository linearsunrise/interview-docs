# MVCC в PostgreSQL, VACUUM, bloat

> **TL;DR:** PostgreSQL не обновляет строки на месте — `UPDATE` создаёт **новую версию** строки и помечает старую как невидимую для новых транзакций, `DELETE` просто помечает строку мёртвой. Это и есть MVCC (Multiversion Concurrency Control) — читатели никогда не блокируют писателей и наоборот, каждая транзакция видит согласованный снимок. Плата за это: мёртвые версии строк никуда не деваются сами — их обязан убирать **VACUUM**, иначе таблица "раздувается" (bloat), а `SELECT` начинает пролистывать горы мусора.

## Как физически устроен UPDATE в PostgreSQL

```sql
UPDATE accounts SET balance = 90 WHERE id = 1;
```

Это не изменение байтов на месте. Postgres:
1. создаёт новую строку (tuple) с `balance = 90`, помечает её `xmin` = ID текущей транзакции;
2. у старой строки проставляет `xmax` = ID текущей транзакции (она ещё физически на месте, но "истекла" с этого момента);
3. обновляет индексы, чтобы они указывали на новую версию (если ни одна из индексируемых колонок не менялась и на странице есть место — применяется HOT-update, экономящий обновление индексов).

Видимость строки для конкретной транзакции определяется сравнением `xmin`/`xmax` с её снимком (snapshot): строка видна, если её `xmin` закоммичен и меньше snapshot-границы транзакции, а `xmax` — либо не установлен, либо ещё не закоммичен на момент снимка. Отсюда и MVCC: разные транзакции параллельно видят разные, но каждая — согласованные версии данных, без блокировок на чтение.

## VACUUM — сборщик мусора для строк

```sql
VACUUM orders;          -- помечает место мёртвых tuple как переиспользуемое, не возвращает диску
VACUUM FULL orders;     -- полностью перестраивает таблицу, реально сжимает файл, но блокирует таблицу (ACCESS EXCLUSIVE)
VACUUM ANALYZE orders;  -- заодно обновляет статистику планировщика
```

`VACUUM` (обычный) не уменьшает размер файла на диске — он помечает пространство мёртвых версий как свободное для **повторного использования** будущими `INSERT`/`UPDATE` этой же таблицы. Файл не усыхает, но и дальше не растёт бесконтрольно, пока автовакуум успевает за темпом изменений. `VACUUM FULL` реально сжимает, но требует эксклюзивной блокировки — на проде обычно недопустимо в рабочее время, для этого есть `pg_repack`/`pg_squeeze` (перестройка без долгой блокировки).

**Autovacuum** — фоновый процесс, который сам решает, когда пылесосить таблицу, по порогам `autovacuum_vacuum_threshold` + `autovacuum_vacuum_scale_factor` (по умолчанию — когда набирается ~20% мёртвых строк от размера таблицы). На таблицах с очень высокой частотой обновлений дефолтные пороги часто занижают агрессивность — настраивают per-table через `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.01)`.

## Bloat — когда VACUUM не успевает

Раздувание таблицы происходит, когда мёртвые tuple накапливаются быстрее, чем autovacuum успевает их пометить свободными — типично при:
- долгих открытых транзакциях (`idle in transaction`) — VACUUM не может очистить строки, которые потенциально ещё видны такой транзакции, пока она не завершится;
- отключённом или слишком редком autovacuum (`autovacuum = off`, заниженная частота);
- массовых `UPDATE`/`DELETE` без последующего `VACUUM`.

Симптомы: таблица занимает на диске в разы больше, чем реальные "живые" данные; `SELECT` замедляется — сканирование, даже индексное, вынуждено пролистывать мёртвые версии; индексы тоже раздуваются отдельно (для них есть `REINDEX`).

```sql
-- быстрая проверка bloat через n_dead_tup
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup::numeric / nullif(n_live_tup + n_dead_tup, 0) * 100, 1) AS dead_pct
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
```

## Wraparound — почему это не абстрактная угроза

Транзакционные ID (`xmin`/`xmax`) — 32-битное число, конечное. VACUUM не только чистит мёртвые строки, но и "замораживает" старые (`freeze`) — помечает их видимыми для всех будущих транзакций без сравнения ID. Если autovacuum долго не отрабатывает (например, из-за зависшей `idle in transaction` или отключённого autovacuum), база рискует упереться в **transaction ID wraparound** — в критическом случае PostgreSQL сам переходит в режим только для чтения, чтобы не допустить порчи данных. Это то, что должно быть в мониторинге прод-баз (`age(datfrozenxid)`), а не сюрприз "почему база встала".

## Что спрашивают на собеседовании

1. **Что происходит физически при `UPDATE` в PostgreSQL?** — не изменение на месте: новая версия строки + пометка старой как истёкшей (`xmax`), обновление индексов (кроме HOT-update).
2. **Зачем нужен VACUUM, если можно просто удалить мёртвые строки сразу?** — MVCC требует держать старые версии, пока их может видеть хоть одна ещё открытая транзакция; VACUUM убирает их только когда они точно никому не нужны.
3. **Чем `VACUUM` отличается от `VACUUM FULL`?** — обычный помечает место переиспользуемым без блокировки и без уменьшения файла; `FULL` реально сжимает, но требует эксклюзивной блокировки таблицы.
4. **Что вызывает bloat и как его диагностировать?** — отстающий autovacuum (долгие транзакции, заниженные пороги) при высокой частоте `UPDATE`/`DELETE`; смотреть `n_dead_tup` в `pg_stat_user_tables` или расширение `pgstattuple`.
5. **Что такое transaction ID wraparound и почему это критично?** — конечность 32-битного счётчика транзакций; без своевременного freeze база рискует потерять возможность различать "прошлое" и "будущее" для видимости строк — Postgres принудительно уходит в read-only, чтобы не допустить порчи данных.
