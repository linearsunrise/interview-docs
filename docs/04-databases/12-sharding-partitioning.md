# Шардирование vs партиционирование: ключи, resharding, hot shards

> **TL;DR:** Партиционирование — разбиение **одной логической таблицы на несколько физических частей внутри одной базы/инстанса**; для приложения таблица выглядит как одна (прозрачно). Шардирование — разбиение данных **между разными базами/серверами**; приложение (или прокси-слой) обязано знать, на какой шард идти. Партиционирование решает проблемы одной большой таблицы (VACUUM, индексы, backup), шардирование — проблему одной машины, которой физически не хватает ресурсов.

## Партиционирование — одна БД, несколько физических частей

```sql
CREATE TABLE events (
  id bigint, created_at timestamptz NOT NULL, payload jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

Запрос `SELECT * FROM events WHERE created_at >= '2026-02-10'` благодаря **partition pruning** читает только подходящую партицию (`events_2026_02`), не трогая остальные — планировщик исключает нерелевантные партиции ещё до выполнения. Практическая польза, помимо скорости: `VACUUM`/индексы работают на партициях меньшего размера (дешевле поддержка, см. [MVCC, VACUUM, bloat](./05-mvcc-vacuum.md)), а истёкшие данные удаляются мгновенным `DROP TABLE events_2025_01` вместо дорогого `DELETE ... WHERE created_at < ...` (который создаёт горы мёртвых строк вместо мгновенной очистки метаданных).

Виды: `RANGE` (по диапазону — типично для времени), `LIST` (по дискретному значению — например, по региону/типу), `HASH` (равномерное распределение по хэшу ключа, когда нет естественного диапазона).

## Шардирование — несколько независимых БД

Данные распределены по нескольким физически отдельным серверам БД, каждый — самостоятельный инстанс со своим CPU/диском/памятью. Приложение (или прокси/роутер) должно знать, к какому серверу идти за конкретной записью — обычно через **shard key**: `user_id`, `tenant_id` и т.п., хэшируемый или сопоставляемый диапазону для выбора шарда.

```
shard = hash(user_id) % N   -- простой вариант, проблема — при изменении N нужен полный reshard
```

## Выбор shard key — то, где решаются или создаются все будущие проблемы

Хороший shard key: высокая кардинальность (много уникальных значений — иначе часть шардов пустует), равномерное распределение нагрузки, и — главное — **совпадает с основным паттерном доступа**: если 90% запросов идут "дай все заказы пользователя X", `user_id` как shard key держит все данные одного пользователя на одном шарде — запрос не требует scatter-gather по всем шардам. Плохой выбор — что-то с низкой кардинальностью (`country`, `status`) или не совпадающее с доступом (тогда почти каждый запрос вынужден идти во все шарды и агрегировать на приложении — теряется весь смысл шардирования).

## Hot shard — когда распределение неравномерно по нагрузке, не по объёму

Даже при равномерном распределении **данных** нагрузка может быть неравномерной: один крупный клиент/знаменитость/вирусный контент создаёт диспропорциональный трафик на свой шард, пока остальные простаивают. Решения: более гранулярный shard key (составной, а не просто `user_id`, чтобы можно было выделить "горячего" пользователя отдельно), выделение конкретных больших сущностей на собственный шард вручную, или переход на consistent hashing с возможностью точечно перевесить конкретный диапазон.

## Resharding — почему это больно

Простой `hash(key) % N` при изменении `N` (добавили шард) требует пересчитать распределение **почти всех** ключей — массовая миграция данных между всеми шардами одновременно. **Consistent hashing** снижает объём перемещаемых данных при добавлении/удалении узла (в среднем перемещается доля `~1/N` ключей, а не почти всё), это то, чем стандартно отвечают на вопрос "как добавить шард без даунтайма всей системы". Практически resharding почти всегда — отдельный проект: double-write в старый и новый шард на время миграции, бэкфилл исторических данных, переключение чтения, затем отключение старого пути.

## Партиционирование vs шардирование — не взаимоисключающе

Партиционирование можно применять **внутри** каждого шарда отдельно — например, таблица событий шардирована по `tenant_id` между 10 серверами, и на каждом сервере ещё и партиционирована по времени. Первое решает "слишком много данных для одной машины", второе — "слишком много данных/мёртвых строк для одной таблицы", это ортогональные оси.

## Что спрашивают на собеседовании

1. **Чем шардирование отличается от партиционирования?** — партиционирование — деление одной таблицы на части внутри одной БД (прозрачно для приложения); шардирование — деление данных между разными серверами БД (приложение/роутер должны знать, куда идти).
2. **Как выбрать shard key?** — высокая кардинальность + равномерность + совпадение с основным паттерном доступа (запрос должен обычно попадать на один шард, не требовать scatter-gather).
3. **Что такое hot shard и как с ним бороться?** — неравномерная **нагрузка** (не обязательно объём данных) на конкретный шард из-за крупного клиента/горячих данных; решения — более гранулярный ключ, выделенный шард для конкретной сущности, consistent hashing.
4. **Почему resharding — дорогая операция и как её удешевить?** — простой modulo-хэш требует пересчёта почти всех ключей при изменении числа шардов; consistent hashing перемещает лишь малую долю ключей на узел.
5. **Зачем партиционировать таблицу, если она помещается на одном сервере?** — не про объём, а про операционные издержки: VACUUM/индексы на меньших кусках, мгновенное удаление старых данных через `DROP PARTITION` вместо `DELETE`, partition pruning ускоряет запросы с фильтром по ключу партиционирования.
