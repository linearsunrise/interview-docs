# EXPLAIN (ANALYZE): чтение плана запроса

> **TL;DR:** `EXPLAIN` показывает **предсказанный** планировщиком план и стоимость (без выполнения запроса), `EXPLAIN ANALYZE` — реально **выполняет** запрос и добавляет фактические время и число строк. Главный диагностический приём — сравнивать `rows` (предсказание) с `actual rows`: большое расхождение значит, что статистика устарела и планировщик принимает решения вслепую. Читать план нужно **изнутри наружу** (снизу вверх по отступам) — самые вложенные узлы выполняются первыми.

## Базовый разбор вывода

```sql
EXPLAIN ANALYZE
SELECT o.id, u.name FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'active';
```

```
Hash Join  (cost=15.50..450.30 rows=1200 width=40) (actual time=0.8..12.4 rows=980 loops=1)
  Hash Cond: (o.user_id = u.id)
  ->  Index Scan using idx_orders_status on orders o
        (cost=0.42..380.10 rows=1200 width=20) (actual time=0.05..8.2 rows=980 loops=1)
        Index Cond: (status = 'active')
  ->  Hash  (cost=10.00..10.00 rows=500 width=24) (actual time=0.6..0.6 rows=500 loops=1)
        ->  Seq Scan on users u  (cost=0.00..10.00 rows=500 width=24) (actual time=0.01..0.3 rows=500 loops=1)
Planning Time: 0.4 ms
Execution Time: 13.1 ms
```

Что смотреть в первую очередь:
- **`cost=A..B`** — условные единицы (не мс): `A` — стоимость получить первую строку, `B` — все строки. Абсолютные числа не значат ничего сами по себе, важны относительно других вариантов плана.
- **`rows` (предсказание) vs `actual rows`** — здесь 1200 против 980, близко, статистика свежая. Если бы было 1200 против 200000 — явный признак устаревшей статистики (`ANALYZE table` не запускался после массовой загрузки данных) или неверного предположения о селективности.
- **`loops=N`** — сколько раз выполнялся этот узел (например, во вложенном цикле на каждую строку внешней таблицы); `actual time` в выводе — это время **на одну итерацию**, для реальных затрат умножать на `loops`.
- Порядок чтения — снизу вверх: сначала `Seq Scan on users` и `Index Scan on orders`, потом их результаты соединяются в `Hash Join`.

## Три типа сканирования таблицы

| Узел плана | Что делает | Когда выбирает планировщик |
|---|---|---|
| `Seq Scan` | читает всю таблицу подряд | нет подходящего индекса, либо низкая селективность (индекс дороже, чем просто прочитать всё), либо таблица маленькая |
| `Index Scan` | идёт по B-tree, для каждого совпадения — отдельный переход в heap за строкой | высокая селективность условия, нужно немного строк |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | сначала собирает битовую карту нужных страниц heap по индексу, потом читает эти страницы последовательно | средняя селективность — слишком много строк для Index Scan (много случайных обращений в heap), но достаточно мало для Seq Scan |

`Bitmap Heap Scan` — компромисс: превращает "N случайных чтений" в "прочитать K страниц последовательно", что на вращающихся дисках (и отчасти на SSD из-за паттернов доступа) быстрее случайного I/O.

## Три стратегии джойна

| Join | Когда эффективен |
|---|---|
| `Nested Loop` | одна из сторон маленькая (или уже отфильтрована индексом) — на каждую строку внешней таблицы ищем совпадение во внутренней (лучше — по индексу) |
| `Hash Join` | обе стороны большие, нет полезного индекса для join-условия — строим хэш-таблицу по меньшей стороне, проходим по большей |
| `Merge Join` | обе стороны уже отсортированы по join-ключу (например, оба по индексу) — просто сливаем два отсортированных потока |

## `BUFFERS` — отдельно смотреть на I/O

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
-- Buffers: shared hit=120 read=430
```

`hit` — страницы нашлись в кэше PostgreSQL (shared_buffers), `read` — пришлось идти на диск/в файловый кэш ОС. Запрос с маленьким `cost`, но огромным `read`, на практике может быть медленнее, чем с большим `cost`, но всё из кэша — `BUFFERS` показывает то, что чистый `cost` не показывает.

## Практический алгоритм для "медленного запроса"

1. `EXPLAIN (ANALYZE, BUFFERS)` — не гадать, а увидеть факт.
2. Сравнить `rows` (план) с `actual rows` — большое расхождение → `ANALYZE table_name` (обновить статистику) или увеличить `default_statistics_target` для конкретной колонки.
3. Найти самый дорогой узел (обычно `Seq Scan` на большой таблице или `Nested Loop` с большим `loops`) — это и есть точка вмешательства.
4. Проверить, есть ли подходящий индекс под `WHERE`/`JOIN`/`ORDER BY` (leftmost prefix, см. [01-btree-indexes.md](./01-btree-indexes.md)) — если да, но не используется, искать причину: неявное приведение типов, функция без функционального индекса, низкая селективность.
5. Если индекс есть и используется, но всё равно медленно — смотреть `BUFFERS`: возможно, проблема в кэше/диске, а не в плане.

## Что спрашивают на собеседовании

1. **Чем `EXPLAIN` отличается от `EXPLAIN ANALYZE`?** — первый только строит план и оценку стоимости, второй реально выполняет запрос и добавляет фактическое время/число строк — осторожно с `ANALYZE` на `DELETE`/`UPDATE` без обёртки в транзакцию с `ROLLBACK`.
2. **Как понять, что статистика устарела?** — большое расхождение между предсказанными `rows` и `actual rows`; лечится `ANALYZE`.
3. **Чем `Bitmap Heap Scan` лучше `Index Scan` при большом числе совпадений?** — превращает много случайных чтений heap в последовательное чтение отсортированных по номеру страниц — дешевле по I/O.
4. **Как читать вложенный план с несколькими join?** — снизу вверх (по отступам): самые внутренние узлы выполняются первыми, их результат поднимается к родительскому узлу join/agg.
5. **Запрос быстрый по `cost`, но медленный по факту — куда смотреть?** — `EXPLAIN (ANALYZE, BUFFERS)`, соотношение `hit`/`read` — возможно, данные не в кэше PostgreSQL/ОС.
