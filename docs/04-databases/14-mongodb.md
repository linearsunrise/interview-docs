# MongoDB: когда уместна, индексы, aggregation pipeline

> **TL;DR:** MongoDB — документная БД: единица хранения — JSON-подобный документ (BSON), схема не фиксирована на уровне СУБД (но обычно фиксируется на уровне приложения/валидации). Главное решение "MongoDB vs PostgreSQL" — не "NoSQL быстрее", а вопрос формы данных и паттернов доступа: документоориентированные сущности, читаемые целиком, без сложных многотабличных транзакций — сильная сторона Mongo; данные с частыми JOIN-подобными связями и жёсткими консистентностными требованиями между сущностями — сильная сторона реляционной модели.

## Когда MongoDB уместна, а когда — нет

**Уместна:**
- сущность естественно моделируется как один документ (профиль пользователя со всеми настройками, каталог товаров с вложенными атрибутами, event-логи) — читается/пишется целиком, без необходимости join'ить с десятком других таблиц;
- schema меняется часто и по-разному для разных записей (разнородные атрибуты товаров в разных категориях);
- горизонтальное шардирование нужно "из коробки" на очень больших объёмах.

**Не уместна / требует осторожности:**
- много связей между сущностями с требованием строгой консистентности между ними (заказ-товар-склад-платёж с ACID-гарантиями через всю цепочку) — эмулировать реляционные инварианты в документной модели сложнее и хрупче;
- отчётность с произвольными ad-hoc джойнами между многими коллекциями — aggregation pipeline умеет `$lookup`, но это не заменяет оптимизатор реляционной БД для сложных многотабличных запросов;
- команда, привыкшая к строгой схеме и миграциям — гибкость документов легко превращается в "у разных документов одной коллекции разные наборы полей без единой версии схемы", если не дисциплинировать это на уровне приложения/JSON Schema validation.

Частый на практике паттерн — не "или-или", а обе БД в одной системе под разные подсистемы (PostgreSQL для транзакционного ядра, Mongo для каталога/логов/аналитики).

## Индексы

```js
db.orders.createIndex({ userId: 1, createdAt: -1 }); // составной, тот же leftmost prefix, что и в B-tree
db.orders.createIndex({ "items.sku": 1 });            // индекс по полю внутри вложенного массива (multikey index)
db.products.createIndex({ description: "text" });     // полнотекстовый
db.locations.createIndex({ geo: "2dsphere" });         // геопространственный
```

MongoDB тоже использует B-tree под капотом для стандартных индексов — leftmost prefix для составных индексов работает так же, как в реляционных БД (см. [01-btree-indexes.md](./01-btree-indexes.md)). Особенность — **multikey index**: индекс на поле внутри массива автоматически создаёт запись на каждый элемент массива, что позволяет искать "документы, где хотя бы один элемент массива соответствует условию", но накладывает ограничение — нельзя построить составной индекс с несколькими multikey-полями одновременно (комбинаторный взрыв записей). `explain("executionStats")` — аналог `EXPLAIN ANALYZE`, показывает `COLLSCAN` (аналог seq scan) vs `IXSCAN`.

## Aggregation pipeline

```js
db.orders.aggregate([
  { $match: { status: "completed", createdAt: { $gte: ISODate("2026-01-01") } } }, // фильтр, использует индекс если есть
  { $lookup: { from: "users", localField: "userId", foreignField: "_id", as: "user" } }, // join-подобная операция
  { $unwind: "$user" },
  { $group: { _id: "$user.country", total: { $sum: "$amount" }, count: { $sum: 1 } } },
  { $sort: { total: -1 } },
  { $limit: 10 },
]);
```

Пайплайн — последовательность стадий, каждая получает поток документов от предыдущей и передаёт результат дальше (концептуально похоже на цепочку `.filter().map().reduce()`, но выполняется на стороне БД, не в приложении). `$match` в начале пайплайна — критичен для производительности: если он первый, планировщик может использовать индекс для фильтрации до того, как документы вообще попадут в пайплайн; `$match` после тяжёлых стадий такой возможности не имеет. `$lookup` — левый outer join по факту, но не заменяет реляционный JOIN по производительности на больших объёмах — это отдельный запрос к другой коллекции на каждую (или пачку) входных документов, дорогая операция при плохих индексах на стороне `foreignField`.

## Документная модель — embed vs reference

```js
// embed — вложенный документ, весь объект читается одним запросом
{ _id: 1, name: "Alice", address: { city: "Berlin", zip: "10115" } }

// reference — как внешний ключ, отдельный запрос/lookup для получения связанных данных
{ _id: 1, name: "Alice", addressId: ObjectId("...") }
```

Правило выбора — по паттерну доступа и кардинальности: данные, которые почти всегда читаются вместе и не растут неограниченно (адрес пользователя, атрибуты товара) — embed, экономит round-trip. Данные с независимым жизненным циклом, растущие без ограничения (все заказы пользователя, комментарии к посту) или переиспользуемые из многих мест — reference, иначе один документ может упереться в лимит размера (16 МБ на документ в MongoDB) или дублирование данных станет неуправляемым при обновлении.

## Что спрашивают на собеседовании

1. **Когда выбрать MongoDB вместо PostgreSQL?** — данные естественно документные, читаются/пишутся целиком, схема меняется по сущностям; не годится там, где нужны строгие межсущностные ACID-гарантии и сложная многотабличная отчётность.
2. **Как устроены индексы в MongoDB — это то же самое, что в SQL-базах?** — да, тот же B-tree и leftmost prefix для составных индексов; отличие — multikey index для полей внутри массивов и ограничение на несколько multikey-полей в одном составном индексе.
3. **Как работает `$lookup` и в чём его ограничения по сравнению с SQL JOIN?** — join-подобная операция между коллекциями внутри aggregation pipeline; производительность сильно зависит от индекса на стороне `foreignField`, не заменяет оптимизированный джойн реляционной СУБД на больших объёмах.
4. **Embed vs reference — как решить?** — по паттерну доступа (вместе читается — embed) и кардинальности/росту (неограниченно растущая или переиспользуемая сущность — reference), плюс жёсткий лимит 16 МБ на документ как техническое ограничение.
5. **Почему важно ставить `$match` в начало pipeline?** — только стадии до первого "разрушающего" индексопригодность шага могут использовать индекс для фильтрации; `$match` в начале сокращает объём данных, проходящих через все последующие дорогие стадии.
