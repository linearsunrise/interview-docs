# Code review: что смотришь, как даёшь жёсткий фидбек бережно

> **TL;DR:** Слабый ответ на этот вопрос — список технических вещей, которые кандидат проверяет в PR (это ожидается по умолчанию, не выделяет senior). Сильный — понимание, что код-ревью одновременно решает две разные задачи: находит проблемы в коде **и** формирует то, как автор PR относится к самому процессу ревью — жёсткий по существу фидбек, поданный неаккуратно, отучает людей выкладывать код на ревью честно и рано.

## Что смотреть в code review — приоритизация, не просто список

```
Порядок значимости (от важного к менее важному):
1. Корректность — действительно ли код делает то, что должен, есть ли edge cases,
   которые не обработаны
2. Архитектурные последствия — не создаёт ли изменение проблему для остальной системы
   (нарушение границ модулей, см. 06-architecture-patterns/02-layered-architecture.md,
   негативное влияние на производительность горячего пути)
3. Читаемость и поддерживаемость — поймёт ли это другой человек через полгода
4. Стиль и форматирование — САМОЕ низкоприоритетное, в идеале вообще автоматизировано
   линтером/форматтером, а не предметом ручного ревью человека
```

Частая ошибка ревьюера — тратить основное внимание на пункт 4 (стиль, именование переменных, расстановка пробелов), потому что это самое простое для быстрого замечания, оставляя пункты 1-2 (реально важные) без должного разбора, потому что они требуют больше усилий на понимание контекста. Явное упоминание этой приоритизации в ответе — сигнал, что кандидат понимает, куда должно уходить реальное внимание ревьюера, а не просто перечисляет чек-лист вещей, которые проверяет.

## Жёсткий фидбек бережно — конкретные техники

```
Вопрос вместо утверждения:
  Резко: "Это неправильно, так делать нельзя"
  Бережно: "Что будет, если сюда придёт пустой массив? Мне кажется, тут может упасть"

Комментарий к коду, не к человеку:
  Резко: "Ты не подумал про конкурентный доступ"
  Бережно: "Здесь есть гонка при конкурентном доступе — вот сценарий: [конкретный пример]"

Явное разделение уровня серьёзности:
  "blocking: это сломает прод при нагрузке — см. пример ниже"
  "nit: было бы чище через .filter().map(), не обязательно менять"
```

Разделение на "blocking" (обязательно исправить перед мержем) и "nit" (необязательное предложение) — практический механизм, снимающий с автора PR необходимость гадать, что из фидбека реально критично, а что — вкусовщина ревьюера, которую можно принять или вежливо отклонить с объяснением. Формулировка через вопрос ("что будет, если...") вместо утверждения ("это неправильно") оставляет автору PR пространство объяснить контекст, который ревьюер мог не знать, вместо того чтобы сразу ставить его в оборонительную позицию.

## Почему подача фидбека — не менее важна, чем его содержание

```
Правильный по существу фидбек, поданный резко → автор PR учится защищаться/оправдываться
                                                    вместо того чтобы слышать суть, начинает
                                                    реже выкладывать код на ревью РАНО (только
                                                    когда уже "причёсан" и защищён от критики) →
                                                    ревью происходит позже в цикле разработки,
                                                    находки дороже исправлять
```

Это прямая связь с тем, что тестирует история про менторинг ([История: менторинг и влияние за пределами своих задач](./06-story-mentoring-impact.md)) — то, как senior-инженер даёт фидбек, формирует культуру команды долгосрочно: команда, где ревью воспринимается как безопасный процесс поиска проблем вместе, выкладывает код на ревью чаще и раньше (что снижает стоимость исправления найденного), чем команда, где ревью воспринимается как экзамен, который нужно пережить.

## Как реагировать, если автор PR не согласен с замечанием

```
1. Спросить контекст — возможно, у автора есть информация, которой нет у ревьюера
   ("расскажи, почему выбран именно такой подход?")
2. Если после объяснения замечание всё ещё кажется важным — привести конкретный пример
   провала (не абстрактное "мне кажется, это плохая практика")
3. Если разногласие не разрешается — эскалировать до третьего мнения (ещё один ревьюер,
   тимлид) вместо бесконечного пинг-понга комментариев в PR — та же логика disagree & commit,
   что в 04-story-conflict-disagreement.md, применённая конкретно к контексту код-ревью
```

## Что спрашивают на собеседовании

1. **Что вы смотрите в code review?** — приоритизированный список (корректность → архитектурные последствия → читаемость → стиль), с явным объяснением, почему стиль — низший приоритет и в идеале автоматизирован.
2. **Как вы даёте жёсткий фидбек, не обижая автора?** — конкретные техники: вопрос вместо утверждения, комментарий к коду не к человеку, явная маркировка серьёзности (blocking/nit).
3. **Что вы делаете, если автор PR не согласен с вашим замечанием?** — сначала уточнить контекст (возможно, у автора есть информация, которой нет у ревьюера), потом — конкретный пример, при неразрешимом разногласии — эскалация до третьего мнения, не бесконечный спор в комментариях.
4. **Расскажите про случай, когда фидбек в ревью был воспринят плохо.** — история, показывающая рефлексию над собственной подачей фидбека (пересекается с [История: фейл](./05-story-failure.md)) — что изменил в способе давать фидбек после этого случая.
5. **Как часто вы ревьюите PR и сколько времени на это тратите?** — практический вопрос про баланс между тщательностью ревью и скоростью цикла разработки — быстрый отклик на ревью (в течение часов, не дней) сам по себе часть здоровой культуры, стоит упомянуть это явно.
