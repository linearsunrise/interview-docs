# Idempotency keys для POST (платежи, создание заказов)

> **TL;DR:** Клиент генерирует уникальный ключ на **попытку операции** (не на каждый HTTP-запрос — один и тот же ключ переиспользуется при ретрае) и шлёт его в заголовке. Сервер атомарно (через unique constraint в БД) фиксирует "я начал обработку этого ключа" до выполнения побочных эффектов; повтор с тем же ключом либо возвращает сохранённый результат первой попытки, либо ждёт, пока первая попытка завершится — но никогда не выполняет операцию дважды.

## Схема на уровне БД

```sql
CREATE TABLE idempotency_keys (
  key text PRIMARY KEY,
  request_hash text NOT NULL,     -- хэш тела запроса — защита от повторного использования ключа с ДРУГИМ телом
  status text NOT NULL DEFAULT 'processing', -- processing | completed | failed
  response_body jsonb,
  response_status int,
  created_at timestamptz DEFAULT now()
);
```

```
1. Клиент: POST /payments, заголовок Idempotency-Key: abc-123
2. Сервер: INSERT INTO idempotency_keys (key, request_hash, status)
            VALUES ('abc-123', hash(body), 'processing')
   -- если INSERT упал на unique violation → ключ уже используется (см. конкурентность ниже)
3. Сервер выполняет операцию (списание, создание заказа) внутри той же транзакции/после успешного INSERT
4. Сервер: UPDATE idempotency_keys SET status='completed', response_body=..., response_status=201 WHERE key='abc-123'
5. Повторный запрос с тем же ключом: SELECT ... WHERE key='abc-123' → status='completed' → вернуть сохранённый response_body/status, НЕ выполнять операцию заново
```

`request_hash` — обязательная защита от логической ошибки клиента: если тот же ключ пришёл с другим телом запроса, это баг клиента (переиспользовал ключ для другой операции), а не легитимный ретрай — сервер должен вернуть `422`/`409`, а не тихо выполнить новую операцию под старым результатом или тихо вернуть чужой ответ.

## Конкурентные запросы с одним и тем же ключом

Реальный сценарий: пользователь дважды кликнул "оплатить" почти одновременно (или клиент ретраит после короткого таймаута, пока первый запрос ещё выполняется) — два запроса с одним `Idempotency-Key` приходят параллельно.

```sql
-- ключ к решению: INSERT с уникальным constraint как атомарный "замок"
INSERT INTO idempotency_keys (key, request_hash, status) VALUES ($1, $2, 'processing');
-- если это упало на unique_violation:
--   -> status уже 'processing' у другого запроса: вернуть 409 (retry later) ЛИБО поллить/ждать до completed
--   -> status уже 'completed': вернуть сохранённый ответ
```

Практически: второй запрос, увидев `status = 'processing'` от первого, либо отвечает `409 Conflict` с рекомендацией повторить позже, либо (если бизнес-логика позволяет короткое ожидание) поллит запись с небольшим интервалом до перехода в `completed`. Что нельзя делать — пропускать обе операции параллельно до завершения первой: тогда unique constraint на `idempotency_keys.key` — единственное, что физически не даёт выполниться операции дважды, вся защита держится на атомарности этого `INSERT`.

## TTL — ключи не живут вечно

```sql
DELETE FROM idempotency_keys WHERE created_at < now() - interval '24 hours';
```

Ключ актуален только на период, в течение которого клиент реально может ретраить (обычно от нескольких часов до нескольких дней — Stripe, например, хранит 24 часа). Бессрочное хранение — не нужно и создаёт растущую без пользы таблицу; слишком короткий TTL — клиент, ретраящий на следующий день после сетевого сбоя (редкий, но реальный кейс — отложенный ретрай из очереди), выполнит операцию повторно, потому что ключ уже вычищен.

## Где хранить — БД vs Redis

БД (как в примерах выше) — если нужна консистентность идемпотентности с самой бизнес-операцией (в одной транзакции с реальным списанием) — не бывает рассинхрона "ключ сохранён, а операция не выполнилась" или наоборот. Redis (`SET key value NX EX ttl`) — быстрее, TTL из коробки, но отдельное хранилище от основной БД — при падении между "заблокировали ключ в Redis" и "закоммитили операцию в БД" возможно рассогласование (ключ висит как processing, а транзакция не выполнилась/откатилась) — требует отдельной логики примирения (например, TTL на "processing" статус короче, чем на "completed", чтобы зависшие блокировки сами истекали и допускали повтор).

## Что спрашивают на собеседовании

1. **Как сделать `POST /payments` безопасным для повторов?** — клиент передаёт idempotency key, сервер атомарно (unique constraint) фиксирует его до выполнения операции, повтор с тем же ключом возвращает сохранённый результат вместо повторного выполнения.
2. **Клиент дважды кликнул "оплатить" почти одновременно — что происходит?** — оба запроса несут один ключ; атомарный `INSERT` с unique constraint гарантирует, что операция выполнится только для первого, второй получит либо `409`, либо (после ожидания) сохранённый результат первого.
3. **Зачем хранить хэш тела запроса вместе с ключом?** — защита от переиспользования того же ключа с другим телом — признак бага клиента, должно быть явной ошибкой, а не тихим выполнением новой операции под чужим ответом.
4. **Нужен ли TTL для idempotency-ключей и почему?** — да: операция актуальна только на реалистичное окно ретраев клиента; бессрочное хранение бесполезно раздувает таблицу, слишком короткий TTL допускает повтор операции при отложенном ретрае.
5. **БД vs Redis для хранения ключей — в чём trade-off?** — БД даёт транзакционную консистентность с самой операцией ценой скорости; Redis быстрее и даёт TTL "из коробки", но раздельное хранилище требует продумывать рассинхрон при падении между шагами.
