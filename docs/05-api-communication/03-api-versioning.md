# Версионирование API: URI vs header vs без версий (expand-contract)

> **TL;DR:** Три технических способа передать версию (URI-путь, заголовок, query-параметр) — второстепенный вопрос по сравнению со стратегией: **expand-contract** (она же parallel change) позволяет вообще избегать версионирования большую часть времени — новое поле добавляется совместимо, старое живёт до полной миграции клиентов, потом удаляется. Явные версии (`/v1`, `/v2`) нужны только для действительно breaking-изменений, которые нельзя провести через expand-contract.

## Три способа передать версию

```
URI:     GET /v2/orders/123
Header:  GET /orders/123          Accept: application/vnd.myapi.v2+json
Query:   GET /orders/123?version=2
```

| | Плюсы | Минусы |
|---|---|---|
| URI (`/v1/...`) | видно в логах/curl без заголовков, легко роутить на разные бэкенды, кэшируется прокси по URL | "нарушает" пуризм REST (один и тот же ресурс — разные URL), версия размножается по всем ссылкам в ответах (HATEOAS) |
| Header (`Accept`/кастомный) | URI ресурса остаётся стабильным, ближе к content negotiation из HTTP-спеки | не виден в браузере/логах без явного взгляда в заголовки, сложнее тестировать вручную |
| Query-параметр | просто добавить, необязателен (можно дать дефолт) | легко забыть проставить, засоряет URL, хуже кэшируется (часть прокси/CDN не учитывают query как часть кэш-ключа по умолчанию) |

На практике URI-версионирование — самый распространённый выбор в публичных API (GitHub, Stripe используют смесь: URI для мажорной версии или дата-based версия в заголовке) — прагматика перевешивает пуризм: видимость и простота дебага важнее теоретической "чистоты" REST.

## Expand-contract — как менять контракт без версии вообще

Три фазы одного изменения:

1. **Expand** — добавить новое, не трогая старое. Новое поле — опциональное, старое поле остаётся и продолжает работать так же:
   ```json
   // было
   { "user_name": "Alice" }
   // expand: добавили новое поле, старое не тронуто
   { "user_name": "Alice", "full_name": { "first": "Alice", "last": "Smith" } }
   ```
2. **Migrate** — клиенты постепенно переключаются на новое поле (метрики использования старого поля показывают прогресс), сервер поддерживает оба одновременно.
3. **Contract** — когда использование старого поля упало до нуля (или до приемлемого порога с явным уведомлением оставшихся клиентов) — старое поле удаляется.

Это работает для большинства изменений: добавление полей, добавление необязательных query-параметров, расширение enum новыми значениями (при условии, что клиенты по контракту обязаны игнорировать неизвестные значения, а не падать). Настоящая нужда в версии возникает только когда экспанд невозможен: смена типа существующего поля, удаление обязательного поля, смена семантики существующего эндпоинта.

## Что считается breaking change

| Изменение | Breaking? |
|---|---|
| Добавить новое опциональное поле в ответ | нет |
| Добавить новый эндпоинт | нет |
| Добавить новый **необязательный** параметр запроса | нет |
| Удалить поле из ответа | да |
| Переименовать поле | да (по факту — удаление + добавление) |
| Сделать необязательный параметр обязательным | да |
| Изменить тип поля (`string` → `number`) | да |
| Добавить новое значение в `enum` | да, если клиенты не обязаны толерантно обрабатывать неизвестные значения (иначе — нет) |
| Изменить бизнес-логику при том же контракте (например, поменять правило валидации) | обычно да, хоть формально "контракт" не поменялся — это тоже нужно версионировать/анонсировать |

Последний пункт — то, что часто упускают: breaking change — не только про форму JSON, но и про **поведение**. Если раньше `PATCH` разрешал частичное обновление, а стал требовать все поля — это breaking, даже если структура запроса не изменилась.

## Deprecation — стратегия по шагам

1. Анонсировать (changelog, email, `Deprecation`/`Sunset` HTTP-заголовки — [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594)) с конкретной датой отключения.
2. Дать метрики использования старого пути клиентам (дашборд/уведомление конкретным intergrators, у кого есть трафик на устаревший эндпоинт).
3. Отслеживать реальное падение использования, не только объявлять дедлайн "на бумаге".
4. Только после этого — отключение (иногда через промежуточный этап "работает, но возвращает `Warning`-заголовок" или искусственно деградированный, но не сломанный ответ).

## Что спрашивают на собеседовании

1. **Как правильно ломать обратную совместимость API?** — по возможности не ломать вообще (expand-contract), а когда неизбежно — явная версия + анонс + период сосуществования + метрики миграции клиентов перед отключением старого.
2. **URI vs header versioning — что выбрать?** — URI проще дебажить и кэшировать по URL, но "грязнее" с точки зрения REST-пуризма; header — чище семантически, но менее заметен; на практике выбор определяется удобством для потребителей API, не теорией.
3. **Что такое expand-contract и зачем оно нужно?** — стратегия совместимых изменений в три фазы (добавить новое → мигрировать клиентов → убрать старое), позволяющая избегать формального версионирования для большинства изменений.
4. **Добавление нового значения в `enum` — breaking change или нет?** — зависит от контракта: breaking, если клиенты по спецификации обязаны знать все значения заранее; не breaking, если контракт требует толерантно обрабатывать неизвестные значения (defensive parsing на стороне клиента).
5. **Как анонсировать deprecation эндпоинта, чтобы не сломать интеграции молча?** — заголовки `Deprecation`/`Sunset`, конкретная дата, метрики фактического использования перед отключением, а не просто запись в changelog.
