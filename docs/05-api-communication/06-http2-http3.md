# HTTP/2, HTTP/3: что дают

> **TL;DR:** HTTP/2 решает проблему HTTP/1.1 — головой-в-очереди-блокировку (head-of-line blocking) **на уровне приложения**: одно TCP-соединение мультиплексирует много запросов параллельно вместо одного запроса за раз (или нескольких TCP-соединений как костыля). HTTP/3 решает HOL blocking **на уровне транспорта**: сам TCP гарантирует порядок байтов в одном потоке, поэтому потеря одного пакета блокирует все мультиплексированные запросы HTTP/2 разом — HTTP/3 меняет транспорт на QUIC (поверх UDP), где потоки независимы даже на уровне доставки пакетов.

## HOL blocking в HTTP/1.1 — откуда проблема

HTTP/1.1 на одном соединении обрабатывает запросы строго последовательно: ответ на запрос N+1 не может быть доставлен, пока не завершён запрос N (pipelining существовал в спецификации, но практически не использовался и не решал проблему в браузерах). Обходной путь до HTTP/2 — открывать **несколько** параллельных TCP-соединений к одному хосту (браузеры исторически ограничивали 6 на домен) — отсюда практики вроде доменного шардинга (раздача статики с разных поддоменов, чтобы обойти лимит на соединения) и спрайтов/бандлинга (объединение множества файлов в один, чтобы сократить число запросов).

## HTTP/2 — мультиплексирование на одном соединении

Одно TCP-соединение, запросы и ответы разбиваются на **фреймы**, помеченные ID потока (stream), и перемежаются в любом порядке — сервер может начать отправлять ответ на запрос 2 раньше, чем закончит ответ на запрос 1, всё в рамках одного соединения. Практические следствия:
- домен-шардинг и спрайты/бандлинг статики становятся **вредной** практикой при HTTP/2 (лишние соединения только мешают мультиплексированию, а бандлинг мешает точечному кэшированию отдельных файлов) — специфичные оптимизации HTTP/1.1 не переносятся автоматически;
- **HPACK** — сжатие заголовков между запросами (заголовки часто повторяются почти неизменными — cookie, user-agent, авторизация — HPACK хранит их в общем "словаре" между запросами одного соединения, передавая только дельту);
- **Server Push** (сервер сам инициативно шлёт ресурсы, которые клиент ещё не запросил, предугадывая их надобность) — формально в спецификации, но de facto почти умер: Chrome убрал поддержку в 2022, оказался сложным в правильном использовании (легко "пушить" то, что уже в кэше клиента, тратя bandwidth впустую) — на собеседовании стоит знать, что это было, но не рекомендовать как актуальную практику.

## HOL blocking на уровне TCP — почему HTTP/2 не решает проблему полностью

Мультиплексирование HTTP/2 живёт поверх **одного** TCP-соединения. TCP гарантирует доставку байтов **по порядку** — если пакет с данными для потока A потерялся в сети, TCP не отдаст приложению *ничего* из последующих пакетов (включая данные потоков B, C, никак не связанных с потерянным пакетом), пока потерянный не будет доставлен повторно. То есть один потерянный пакет блокирует все параллельные HTTP/2-запросы на этом соединении разом — HOL blocking переехал с уровня приложения на уровень транспорта, не исчез.

## HTTP/3 — QUIC вместо TCP

HTTP/3 использует **QUIC** — транспорт поверх UDP (не TCP), который сам реализует независимые потоки на уровне транспорта: потеря пакета в потоке A не блокирует доставку уже пришедших пакетов потоков B/C — они доставляются приложению немедленно. Дополнительные практические выигрыши QUIC:
- **шифрование обязательно и встроено** (TLS 1.3 — часть самого протокола QUIC, а не надстройка сверху, как TLS над TCP) — меньше round-trip'ов на установление защищённого соединения;
- **0-RTT / быстрое переподключение** — при повторном соединении к уже известному серверу QUIC может отправить данные в первом же пакете, не дожидаясь полного handshake;
- **устойчивость к смене сети** — соединение QUIC идентифицируется по Connection ID, а не по паре IP+порт — переключение Wi-Fi → мобильная сеть не рвёт соединение, как это происходит с TCP.

Плата: UDP исторически хуже поддержан некоторыми корпоративными фаерволами/прокси (иногда блокируется или дросселируется), реализация QUIC сложнее (много логики, которая раньше была в ядре ОС для TCP, теперь в user-space библиотеке).

## Практический вывод для бэкенда

Для Node.js-сервиса HTTP/2 обычно включается на уровне reverse-proxy/CDN (nginx, Cloudflare, ALB) перед приложением, а не в самом Node-процессе — `node:http2` существует, но большинство прод-инсталляций терминируют TLS+HTTP/2 на балансировщике и говорят с приложением по HTTP/1.1 внутри защищённого периметра. HTTP/3 сейчас в основном на уровне CDN/edge — доводить его до самого бэкенд-сервиса пока редкая практика.

## Что спрашивают на собеседовании

1. **Что такое head-of-line blocking и как HTTP/2 его решает?** — в HTTP/1.1 ответы идут строго по очереди на одном соединении; HTTP/2 мультиплексирует независимые потоки на одном TCP-соединении через фреймы с ID потока.
2. **Почему HTTP/2 не решает HOL blocking полностью?** — мультиплексирование живёт поверх одного TCP-соединения, а TCP гарантирует порядок байтов — потеря одного пакета блокирует доставку данных всех потоков этого соединения до его повторной доставки.
3. **Что меняет HTTP/3 на уровне транспорта?** — переход с TCP на QUIC (поверх UDP), где потоки независимы даже на уровне доставки пакетов — потеря пакета одного потока не блокирует остальные.
4. **Актуальны ли домен-шардинг и бандлинг статики при HTTP/2?** — нет, это оптимизации под ограничения HTTP/1.1 (лимит соединений на домен); при HTTP/2 они скорее вредны — мешают мультиплексированию и точечному кэшированию.
5. **Что даёт быстрое переподключение (0-RTT) в QUIC и в чём его риск?** — сокращает round-trip'ы при повторном соединении к известному серверу; риск — 0-RTT данные теоретически уязвимы к replay-атакам, поэтому под них подходят только идемпотентные запросы.
