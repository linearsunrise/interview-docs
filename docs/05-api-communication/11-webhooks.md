# Webhooks: подпись, retries, идемпотентность на приёмнике

> **TL;DR:** Webhook переворачивает обычную модель клиент-сервер: **провайдер** инициирует HTTP-запрос к **получателю**, когда происходит событие. Это создаёт три задачи, которых нет в обычном API: получатель должен убедиться, что запрос реально от провайдера (подпись), провайдер должен гарантировать доставку при недоступности получателя (retries с backoff), а получатель — не обработать одно и то же событие дважды из-за этих самых retries (идемпотентность на приёмнике, at-least-once by design).

## Подпись — проверка подлинности запроса

```
POST /webhooks/payments HTTP/1.1
X-Signature: sha256=5257a869e7bfa8...
Content-Type: application/json

{"event": "payment.succeeded", "id": "evt_123", "amount": 5000}
```

```ts
import { createHmac, timingSafeEqual } from 'crypto';

function verifySignature(rawBody: Buffer, signatureHeader: string, secret: string): boolean {
  const expected = createHmac('sha256', secret).update(rawBody).digest('hex');
  const provided = signatureHeader.replace('sha256=', '');
  return timingSafeEqual(Buffer.from(expected), Buffer.from(provided));
}
```

Провайдер и получатель заранее договариваются об общем секрете; провайдер подписывает **сырое** тело запроса HMAC перед отправкой, получатель вычисляет ту же подпись независимо и сравнивает. Два важных технических нюанса: (1) подпись обязана считаться от **сырых байт** тела, не от результата `JSON.parse` — любая перепарсировка/переформатирование JSON (другой порядок ключей, другие пробелы) даст другую подпись, поэтому в Nest для этого роута нужен доступ к raw body до применения `body-parser`/`ValidationPipe` (см. [Middleware](../03-nestjs/05-middleware.md) про raw body); (2) сравнение обязано быть через `timingSafeEqual`, не через `===`/`Buffer.equals` — обычное сравнение строк завершается на первом несовпадающем байте, что теоретически позволяет через замер времени ответа побайтово подобрать правильную подпись (timing attack).

## Retries — provider-side, не полагаться на "доставили один раз"

Получатель может быть недоступен (деплой, временная перегрузка, сетевой сбой) в момент, когда провайдер пытается доставить событие. Ответственные webhook-провайдеры (Stripe, GitHub) ретраят с экспоненциальным backoff в течение продолжительного окна (часы-дни), считая доставленным только явный `2xx`-ответ получателя. Практические следствия для получателя: обработчик обязан **быстро** отвечать `2xx`, как только запрос принят (сама обработка — асинхронно, через очередь), а не держать соединение открытым на время долгой бизнес-логики — иначе провайдер может счесть это таймаутом/ошибкой и запустить ретрай поверх уже идущей обработки.

## Идемпотентность на приёмнике — обязательна, не опциональна

```ts
async function handlePaymentWebhook(event: { id: string; type: string; data: unknown }) {
  const inserted = await db.query(
    `INSERT INTO processed_webhook_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING RETURNING event_id`,
    [event.id],
  );
  if (inserted.rowCount === 0) return; // уже обработали этот event.id раньше — no-op, но всё равно 200
  await processPaymentEvent(event);
}
```

Ретраи провайдера означают, что одно и то же событие (с одним и тем же `event.id`/`event_id`) может прийти на эндпоинт получателя больше одного раза — это не баг провайдера, а нормальное поведение at-least-once доставки. Тот же паттерн, что и idempotency key на исходящих запросах (см. [Idempotency keys для POST](./02-idempotency-keys.md)), только в зеркальном направлении: `id` события используется как ключ для `unique constraint`/`ON CONFLICT DO NOTHING` — обработка бизнес-логики выполняется не более одного раза, но `2xx` отдаётся при **каждом** повторе (иначе провайдер продолжит ретраить бесконечно, посчитав, что доставка так и не удалась).

## Что нужно предусмотреть, проектируя webhook-провайдера (не только получателя)

- **Гарантия доставки**: очередь с ретраями и экспоненциальным backoff, ограниченное число попыток или окно (например, 72 часа), после чего — фиксация как failed + уведомление владельца интеграции.
- **Подпись каждого события** общим секретом (или, для более высокого уровня доверия — асимметричная подпись, которую получатель проверяет публичным ключом провайдера).
- **Уникальный `event.id`** в каждом payload — без него получатель физически не сможет реализовать идемпотентность на своей стороне.
- **Dashboard/лог доставок** для владельца интеграции — какие события отправлены, какие зафейлились, возможность ручного replay конкретного события.
- **Явный timeout на попытку доставки** (обычно несколько секунд) — не ждать медленный эндпоинт получателя долго, это чужой код, который не должен блокировать очередь провайдера.

## Что спрашивают на собеседовании

1. **Как защитить эндпоинт от поддельных webhook-запросов?** — HMAC-подпись сырого тела общим секретом, сравнение через constant-time-сравнение (`timingSafeEqual`), не обычное `===`.
2. **Почему подпись считается от сырого тела, а не от распарсенного JSON?** — любая перепарсировка/переформатирование меняет байтовое представление — подпись, посчитанная получателем после `JSON.parse`+`stringify`, не совпадёт с подписью провайдера, даже если данные логически те же.
3. **Как гарантировать доставку webhook, если получатель временно недоступен?** — ретраи с экспоненциальным backoff на стороне провайдера в течение ограниченного окна, доставленным считается только явный `2xx`-ответ.
4. **Почему обработчик webhook должен быстро отвечать `2xx`, не дожидаясь завершения бизнес-логики?** — долгий ответ может быть истолкован провайдером как сбой доставки и спровоцировать ретрай поверх уже идущей обработки; правильный паттерн — быстро принять и поставить в очередь, обработать асинхронно.
5. **Как получателю не обработать одно и то же событие дважды из-за ретраев?** — `event.id` из payload как ключ уникальности (`ON CONFLICT DO NOTHING` в БД или аналог), обработка бизнес-логики один раз, но `2xx` отдаётся на каждый повтор.
