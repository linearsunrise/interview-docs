# GraphQL: schema-first vs code-first, резолверы, N+1 и DataLoader, complexity limits

> **TL;DR:** GraphQL решает проблему over/under-fetching REST (клиент получает ровно те поля, что запросил, за один round-trip, даже если они логически из разных "ресурсов") — но платит за это тем, что каждое поле схемы потенциально отдельный резолвер, отдельный поход за данными → N+1 запросов к БД по умолчанию, если не батчить явно через **DataLoader**. Вторая цена гибкости — клиент сам решает, насколько дорогой будет его запрос (глубокая вложенность, широкие списки), поэтому без лимитов сложности GraphQL-эндпоинт — готовый вектор для DoS одним запросом.

## Schema-first vs code-first в NestJS

```graphql
# schema-first: .graphql файл — источник истины, Nest генерирует TS-типы из него
type Order {
  id: ID!
  status: String!
  user: User!
}
```

```ts
// code-first: TS-декораторы — источник истины, Nest генерирует SDL-схему из кода
@ObjectType()
class Order {
  @Field(() => ID) id: string;
  @Field() status: string;
  @Field(() => User) user: User;
}
```

Code-first (декораторы `@ObjectType`/`@Field`/`@Resolver`) — более естественен в TypeScript-проекте: типы и схема не расходятся, рефакторинг переименовывает и то, и другое разом, автокомплит работает сразу. Schema-first — схема как явный контракт, который можно версионировать/ревьюить отдельно от реализации, удобнее при command-driven разработке (сначала согласовали контракт с фронтом, потом имплементировали) или когда схема — общий артефакт между несколькими командами/языками. Nest поддерживает оба через `@nestjs/graphql`, но в TS-проектах code-first — практически дефолтный выбор.

## Резолверы — единица логики на поле, не на эндпоинт

```ts
@Resolver(() => Order)
class OrderResolver {
  @Query(() => [Order])
  orders() { return this.ordersService.findAll(); }

  @ResolveField(() => User) // отдельный резолвер для КАЖДОГО заказа в списке
  user(@Parent() order: Order) { return this.usersService.findById(order.userId); }
}
```

Ключевое отличие от REST-контроллера: `@ResolveField` вызывается **отдельно для каждого объекта** в результате родительского запроса. Список из 50 заказов → `orders()` выполнится один раз, но `user()` — 50 раз, по одному на заказ, если внутри — прямой поход в БД. Это и есть источник N+1 в GraphQL, структурно то же самое, что N+1 в ORM (см. [ORM: N+1, транзакции, миграции (TypeORM/Prisma)](../04-databases/09-orm-typeorm-prisma.md)), но встроено в саму модель выполнения запроса, а не побочный эффект неаккуратного кода.

## DataLoader — batching + per-request кэш

```ts
function createUserLoader(usersService: UsersService) {
  return new DataLoader<string, User>(async (userIds) => {
    const users = await usersService.findByIds([...userIds]); // 1 запрос на ВСЮ пачку
    const byId = new Map(users.map(u => [u.id, u]));
    return userIds.map(id => byId.get(id)); // порядок результата обязан совпадать с порядком ключей
  });
}

@ResolveField(() => User)
user(@Parent() order: Order, @Context() ctx: { userLoader: DataLoader<string, User> }) {
  return ctx.userLoader.load(order.userId); // вызовы за один "тик" события собираются в одну пачку
}
```

Механизм: `DataLoader.load(key)` не бьёт в БД сразу — откладывает вызов до конца текущего цикла event loop (микротаск), собирая все вызовы `.load()`, сделанные синхронно в этом тике, в один пакет, и передаёт их разом в batch-функцию — 50 вызовов `user()` для 50 заказов превращаются в один SQL-запрос `WHERE id IN (...)` вместо 50 отдельных. Это тот же самый батчинг, что решает N+1 в ORM вручную (собрать ID, один `IN`-запрос), просто DataLoader делает это автоматически и прозрачно на уровне резолверов.

**Почему per-request инстанс, а не синглтон:** DataLoader кэширует результаты внутри себя (повторный `.load()` того же ключа в рамках инстанса не бьёт в БД снова) — если бы инстанс был общим на всё приложение, кэш одного пользователя утёк бы к другому (авторизационная утечка данных) и никогда не инвалидировался бы естественным образом. Правильный паттерн — создавать новый `DataLoader` на каждый GraphQL-запрос (обычно в `context factory`), жить он должен ровно один request.

## Complexity/depth limits — защита от дорогих запросов

```graphql
query Evil {
  users { orders { items { product { reviews { author { orders { items { ... } } } } } } } }
}
```

Гибкость GraphQL — клиент сам строит форму запроса — означает, что клиент может построить экспоненциально дорогой запрос глубокой вложенностью связанных списков, ничем формально не нарушая схему. Защиты:
- **depth limit** — простое ограничение максимальной глубины вложенности запроса (например, не больше 7 уровней) — грубо, но дёшево реализовать;
- **complexity/cost analysis** — каждому полю резолвера присваивается "стоимость" (обычно с учётом ожидаемого количества элементов в списках), суммарная стоимость запроса считается до выполнения и отклоняется при превышении лимита — точнее, чем просто глубина, но требует разметки стоимости по всей схеме;
- **persisted queries** — клиент заранее регистрирует допустимые запросы (хэш → текст запроса на сервере), рантайм принимает только запросы по известным хэшам — исключает произвольные ad-hoc запросы вообще, ценой потери части гибкости GraphQL (обычно применяется для мобильных/веб-клиентов первой стороны, не для публичного API).

## Что спрашивают на собеседовании

1. **Как DataLoader чинит N+1 в GraphQL?** — батчинг вызовов `.load()`, сделанных в одном тике event loop, в один запрос с `IN (...)`, плюс кэш результата внутри инстанса на время запроса.
2. **Почему DataLoader должен быть per-request инстансом, а не синглтоном?** — его внутренний кэш привязан к конкретному запросу/пользователю; общий на всё приложение инстанс утёк бы данные между пользователями и не имел бы естественной инвалидации.
3. **Как защитить GraphQL от тяжёлых запросов?** — depth limit (простой потолок вложенности), complexity/cost analysis (стоимость по полям, отклонение дорогих запросов до выполнения), persisted queries (только заранее известные запросы).
4. **Schema-first vs code-first в NestJS — что выбрать?** — code-first естественнее в TS-проекте (типы и схема не расходятся, рефакторинг синхронный); schema-first — когда схема нужна как независимый контракт между командами/языками.
5. **Чем GraphQL-резолвер принципиально отличается от REST-контроллера с точки зрения N+1?** — резолвер поля выполняется отдельно на каждый объект родительского списка — N+1 встроен в саму модель выполнения, а не следствие невнимательности разработчика, как часто в ORM-коде.
