# OpenAPI/Swagger в NestJS, contract-first разработка

> **TL;DR:** В NestJS Swagger-документация обычно **code-first**: `@nestjs/swagger` читает те же декораторы, что уже описывают DTO для валидации (`class-validator`) и структуру контроллеров, и генерирует OpenAPI-схему из них — один источник истины вместо ручного поддержания `.yaml` отдельно от кода. Contract-first — обратный подход (сначала пишется `.yaml`/`.json` спецификация, потом код генерируется/сверяется с ней) — используется, когда контракт согласовывается между командами/языками **до** реализации, а не выводится из неё постфактум.

## Code-first в Nest — схема из тех же декораторов, что и валидация

```ts
class CreateOrderDto {
  @ApiProperty({ example: 'sku-123', description: 'Идентификатор товара' })
  @IsString()
  sku: string;

  @ApiProperty({ minimum: 1 })
  @IsInt() @Min(1)
  quantity: number;
}

@ApiTags('orders')
@Controller('orders')
class OrdersController {
  @Post()
  @ApiOperation({ summary: 'Создать заказ' })
  @ApiResponse({ status: 201, type: Order })
  @ApiResponse({ status: 422, description: 'Невалидные данные заказа' })
  create(@Body() dto: CreateOrderDto) { /* ... */ }
}
```

`@ApiProperty` дублирует часть информации, уже присутствующей в `class-validator`-декораторах (`@IsInt`, `@Min`) — плагин `@nestjs/swagger/plugin`, подключаемый в `nest-cli.json`, умеет вытаскивать большую часть этих метаданных автоматически через анализ AST на этапе сборки, снижая ручное дублирование до случаев, где нужно явно переопределить пример/описание. DTO — фактически двойного назначения: одновременно контракт валидации рантайма (см. [03-nestjs/07-pipes.md](../03-nestjs/07-pipes.md)) и источник OpenAPI-схемы — рассинхрон между "что реально валидируется" и "что задокументировано" структурно невозможен, потому что это один и тот же класс.

## Contract-first — когда схема ведёт, а не следует за кодом

```yaml
# openapi.yaml — пишется/согласовывается ДО реализации
paths:
  /orders:
    post:
      requestBody:
        content:
          application/json:
            schema: { $ref: '#/components/schemas/CreateOrderDto' }
      responses:
        '201': { $ref: '#/components/responses/Order' }
```

Из такой спецификации типы/DTO-заготовки генерируются инструментами (`openapi-generator`, `orval`) для сервера и для клиентов на разных языках одновременно. Имеет смысл, когда: несколько команд/сервисов на разных стеках должны согласовать контракт до начала параллельной разработки (бэкенд и фронтенд/мобильные команды стартуют одновременно по одному контракту), контракт — часть формального SLA с внешними партнёрами, или когда клиентские SDK должны генерироваться на нескольких языках без ручного дублирования типов. Цена — дополнительный шаг синхронизации: код обязан оставаться совместим со спекой, для чего нужны либо кодогенерация с последующей ручной имплементацией, либо тесты на соответствие рантайм-поведения заявленной схеме (contract testing).

## Что реально даёт автогенерируемая OpenAPI-схема в проде

- **Swagger UI** (`/api` по умолчанию) — интерактивная документация с возможностью выполнить запрос прямо из браузера, не открывая Postman.
- **Кодогенерация типизированного клиента** для фронтенда (`openapi-typescript`, `orval`) — фронт получает актуальные TS-типы запросов/ответов автоматически при каждой пересборке бэкенда, не переписывает их руками вслед за изменениями API.
- **Контрактные тесты** — сверка, что реальные ответы API соответствуют заявленной схеме (полезно как страховка от "задокументировали одно, а после рефакторинга контроллер стал отдавать другое").
- **Экспорт схемы для API-gateway/шлюзов** (валидация запросов на уровне gateway ещё до попадания в сервис, rate-limiting по операциям и т.п.).

## Риск: документация как источник правды, если не синхронизирована с кодом

Главная опасность ручного (не code-first) подхода — документация расходится с реальным поведением API постепенно, по мере рефакторинга кода без обновления `.yaml`/аннотаций. В Nest code-first-подход структурно снижает этот риск (схема выводится из тех же типов и декораторов валидации, что реально исполняются), но не устраняет полностью: описание (`@ApiOperation summary`, примеры) — всё ещё текст, который можно забыть обновить при изменении бизнес-логики, даже если структура полей (типы/обязательность) остаётся синхронной автоматически.

## Что спрашивают на собеседовании

1. **Как в NestJS получается OpenAPI-схема — пишется вручную или генерируется?** — генерируется из тех же декораторов, что описывают DTO для class-validator (плюс `@ApiProperty`/`@ApiOperation`/`@ApiResponse`) — один источник истины для валидации и документации.
2. **Чем contract-first отличается от code-first и когда он оправдан?** — спецификация пишется/согласовывается до реализации, код/клиенты генерируются из неё; оправдан при параллельной разработке нескольких команд/языков по одному контракту или формальных SLA с внешними партнёрами.
3. **Что даёт `@nestjs/swagger/plugin` кроме ручных `@ApiProperty`?** — вытаскивает часть метаданных схемы автоматически через анализ AST на сборке (типы, опциональность), сокращая дублирование декораторов.
4. **Может ли документация разойтись с реальным API даже при code-first подходе?** — да, частично: структура полей синхронна автоматически (один класс для валидации и схемы), но текстовые описания/примеры — по-прежнему ручной артефакт, который можно забыть обновить.
5. **Зачем нужна кодогенерация клиента из OpenAPI-схемы?** — фронтенд/другие сервисы получают актуальные типизированные клиенты автоматически при каждом изменении бэкенд-контракта, вместо ручного синхронного переписывания типов вслед за API.
