# SSE vs WebSocket vs long polling — критерии выбора

> **TL;DR:** Первый вопрос — направление потока данных. Если серверу нужно только **отправлять** клиенту обновления (уведомления, live-лента, прогресс задачи) — SSE проще WebSocket и работает поверх обычного HTTP. Если нужен полноценный **двунаправленный** канал с низкой задержкой в обе стороны (чат, игры, совместное редактирование) — WebSocket. Long polling — запасной вариант, когда ни то, ни другое недоступно (устаревшие прокси/фаерволы, максимальная совместимость), с явной ценой на латентность и накладные расходы.

## SSE (Server-Sent Events) — однонаправленный поток поверх HTTP

```
GET /events HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: {"type": "order_created", "orderId": 123}

data: {"type": "order_shipped", "orderId": 123}

```

```js
const es = new EventSource('/events');
es.onmessage = (e) => console.log(JSON.parse(e.data));
```

Это обычное HTTP-соединение, которое сервер держит открытым и постепенно дописывает в тело ответа — браузер (через `EventSource`) сам парсит формат `text/event-stream` и авто-переподключается при разрыве (со встроенным `Last-Event-ID` для продолжения с места обрыва — то, что в WebSocket и long polling пришлось бы реализовывать вручную). Работает через большинство прокси/CDN без специальной настройки (это просто HTTP), но клиент не может **отправлять** данные через тот же канал — только читать; для запросов от клиента нужен отдельный обычный HTTP-запрос.

## WebSocket — двунаправленный низколатентный канал

Разобран подробно в [WebSockets: handshake, масштабирование, heartbeat](./08-websockets.md): после handshake — полнодуплексный канал, обе стороны шлют сообщения в любой момент без накладных расходов HTTP-заголовков на каждое сообщение. Стоит своей сложности (масштабирование между инстансами, heartbeat, отдельный протокол вместо "просто HTTP") только когда двунаправленность и минимальная задержка реально нужны бизнес-логике — печатает ли собеседник в чате прямо сейчас, синхронизация курсора в совместном редакторе, real-time игра.

## Long polling — эмуляция push поверх обычных запросов

```
Клиент: GET /updates?since=lastEventId
Сервер: держит соединение открытым, НЕ отвечает сразу
        -> как только появилось новое событие (или таймаут ~30-60с) -> отвечает
Клиент: сразу шлёт следующий GET /updates?since=newEventId
```

Клиент делает обычный HTTP-запрос, сервер не отвечает немедленно, а ждёт, пока не появится что сказать (или не истечёт таймаут) — как только ответ пришёл, клиент тут же открывает следующий такой же запрос. Работает вообще везде, где работает HTTP (максимальная совместимость с древними прокси/корпоративными фаерволами, которые могут блокировать WebSocket upgrade), но каждый цикл — новый HTTP round-trip с полными заголовками, и есть неустранимое окно задержки между ответом на один запрос и открытием следующего. Практически это резервный вариант, когда ни SSE, ни WebSocket не проходят через конкретную инфраструктуру клиента.

## Сравнение

| | Направление | Транспорт | Автопереподключение | Сложность инфраструктуры |
|---|---|---|---|---|
| SSE | сервер → клиент | обычный HTTP | встроено в `EventSource` (с `Last-Event-ID`) | низкая — просто держим HTTP-соединение открытым |
| WebSocket | оба направления | отдельный протокол после `Upgrade` | нет, реализуется вручную | высокая — свой протокол, масштабирование между инстансами (см. [WebSockets: handshake, масштабирование, heartbeat](./08-websockets.md)) |
| Long polling | оба (эмуляция) | обычный HTTP, запрос за запросом | естественно (каждый цикл — новый запрос) | низкая, но накладные расходы на каждый цикл выше |

## Практический выбор

- **Уведомления, live-лента, статус фоновой задачи, дашборд с метриками** — SSE: однонаправленно, не нужен свой протокол, авто-реконнект бесплатно.
- **Чат, совместное редактирование, игры, торговые терминалы (котировки с обеих сторон)** — WebSocket: нужна низкая задержка в обе стороны.
- **Максимальная совместимость с непредсказуемой сетевой инфраструктурой клиента (некоторые B2B-интеграции, старые корпоративные окружения)** — long polling как fallback, часто автоматически выбираемый библиотекой (тот же `socket.io` умеет откатываться на long polling, если WebSocket upgrade не проходит).

## Что спрашивают на собеседовании

1. **Когда SSE лучше WebSocket?** — когда поток однонаправленный (сервер → клиент): SSE проще, работает поверх обычного HTTP, даёт автопереподключение бесплатно — не нужна сложность полноценного WebSocket-протокола.
2. **Почему SSE не подходит для чата?** — клиент не может отправлять сообщения через тот же канал — только читать; для отправки нужен отдельный обычный HTTP-запрос, что теряет смысл единого real-time канала для двунаправленного сценария.
3. **В чём цена long polling по сравнению с WebSocket/SSE?** — каждый цикл обновления — новый HTTP round-trip с полными заголовками, плюс неустранимое окно задержки между закрытием одного запроса и открытием следующего.
4. **Что даёт `Last-Event-ID` в SSE?** — при авто-реконнекте браузер сам отправляет ID последнего полученного события, позволяя серверу продолжить поток с места обрыва, а не начинать заново.
5. **Почему long polling всё ещё используют, если есть WebSocket и SSE?** — как fallback для инфраструктуры, не пропускающей WebSocket upgrade (корпоративные прокси/фаерволы) — универсальная совместимость важнее эффективности в этом случае.
