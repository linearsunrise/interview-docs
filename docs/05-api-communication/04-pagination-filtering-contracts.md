# Пагинация, фильтрация, сортировка: дизайн контрактов API

> **TL;DR:** Это документ про **форму контракта** (что видит клиент API) — механика cursor vs offset на уровне БД разобрана в [04-databases/10-pagination.md](../04-databases/10-pagination.md). Здесь — как это спроектировать так, чтобы контракт не пришлось ломать при смене реализации внутри, и как не открыть DoS-вектор через неограниченную фильтрацию/сортировку.

## Пагинация — контракт, скрывающий реализацию

```json
// хороший ответ: курсор непрозрачен для клиента, реализация может меняться
{
  "items": [...],
  "pageInfo": { "nextCursor": "eyJpZCI6MTIzLCJjcmVhdGVkQXQiOiIuLi4ifQ==", "hasNextPage": true }
}
```

Курсор стоит отдавать клиенту как **непрозрачную строку** (обычно base64 от внутреннего представления `{id, createdAt}`), а не как сырые значения полей сортировки в query-параметрах. Причины: (1) клиент не должен полагаться на внутреннюю структуру — сервер может сменить поле сортировки/алгоритм без слома контракта; (2) сырые значения в URL — потенциальная утечка деталей реализации и лазейка для манипуляции (подставить произвольные значения, обойти фильтры). Ответ обычно включает `hasNextPage` явно — не заставлять клиента угадывать конец списка по пустому массиву на следующий запрос.

**Offset всё ещё уместен** в контракте, если UI реально нуждается в номерах страниц ("страница 5 из 20") и глубина пагинации предсказуемо мала (админки, отчёты) — тогда `?page=5&pageSize=20` плюс `totalCount` в ответе (с оговоркой: `COUNT(*)` на большой таблице — сам по себе дорогая операция, иногда его отдают приближённо или вообще не отдают, а заменяют на `hasNextPage`).

## Фильтрация — от простого к RSQL/GraphQL-подобному

```
GET /orders?status=active&createdAfter=2026-01-01          -- простые equality/range фильтры, каждый — свой параметр
GET /orders?filter=status:active,createdAt:gt:2026-01-01   -- DSL-подобный синтаксис одним параметром
GET /orders?filter[status]=active&filter[createdAt][gt]=2026-01-01  -- JSON:API-style вложенные параметры
```

Простые именованные параметры — читаемее, проще документировать в OpenAPI (каждый параметр — отдельное поле схемы), но плохо масштабируются на сложные условия (`OR`, вложенные группы). DSL/RSQL-подобный синтаксис (`filter=status==active;createdAt=gt=2026-01-01`) — гибче, но требует парсера на сервере и хуже документируется автоматически. Практический выбор: начинать с именованных параметров под конкретные бизнес-фильтры (не "универсальный фильтр по любому полю") — большинство API не нуждаются в произвольных ad-hoc запросах, а те, что нуждаются, обычно эволюционируют к GraphQL или отдельному search-эндпоинту поверх Elasticsearch, а не к всё более сложному query-языку над REST.

## Сортировка

```
GET /orders?sort=createdAt:desc
GET /orders?sort=-createdAt          -- знак минус как признак desc, компактнее
GET /orders?sort=status,-createdAt   -- составная сортировка
```

Ключевой момент безопасности и производительности: **сортировка не может быть по произвольному полю без ограничений**. Если сервер слепо подставляет параметр `sort` в `ORDER BY` — это (а) потенциальная SQL-инъекция при небрежной реализации, (б) гарантированный способ получить полное сканирование таблицы, если клиент запросит сортировку по неиндексированному полю на многомиллионной таблице. Контракт должен явно ограничивать допустимые поля сортировки whitelist'ом, соответствующим реально существующим индексам — не "сортируй по чему хочешь".

## Лимиты — где DoS-вектор незаметен по умолчанию

```
GET /orders?pageSize=1000000   -- без верхнего предела — сервер попытается собрать миллион строк в память
GET /orders?filter=name:like:%25%25  -- LIKE '%%' без ведущего/хвостового текста — full scan
```

Контракт обязан ограничивать: максимальный `pageSize` (сервер должен клампить, а не доверять клиенту — `min(requested, MAX_PAGE_SIZE)`), допустимую глубину/сложность фильтров (особенно если разрешён DSL с `AND`/`OR` вложенностью — без лимита на глубину это тот же вектор, что и depth limit в GraphQL, см. [07-graphql.md](./07-graphql.md)), таймаут на выполнение самого запроса на стороне БД как последний рубеж защиты.

## Что спрашивают на собеседовании

1. **Почему курсор пагинации стоит отдавать клиенту как непрозрачную строку, а не как сырые значения полей?** — не привязывать контракт к текущей реализации сортировки/хранения; сырые значения — потенциальная лазейка для манипуляции запросом в обход намеренных ограничений.
2. **Как спроектировать фильтрацию, чтобы не открыть дыру в производительности?** — не давать сортировку/фильтрацию по произвольному полю без whitelist, соответствующего реально существующим индексам.
3. **Клиент присылает `pageSize=1000000` — что делает сервер?** — клампит к заранее заданному максимуму на своей стороне, никогда не доверяет лимиту от клиента напрямую.
4. **Именованные параметры фильтра vs DSL-синтаксис (`filter=a:b,c:gt:d`) — когда что?** — именованные параметры для ограниченного, предсказуемого набора бизнес-фильтров (проще документировать в OpenAPI); DSL — когда реально нужна комбинаторная гибкость, с осознанной ценой парсера и сложности документации.
5. **Нужно ли отдавать `totalCount` вместе со списком?** — зависит: `COUNT(*)` на большой таблице — сам по себе дорогой запрос; если UI не показывает номера страниц, часто достаточно `hasNextPage` без точного общего числа.
