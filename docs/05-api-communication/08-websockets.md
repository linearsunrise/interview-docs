# WebSockets: handshake, масштабирование, heartbeat

> **TL;DR:** WebSocket начинается как обычный HTTP-запрос с заголовком `Upgrade: websocket` — сервер отвечает `101 Switching Protocols`, и то же TCP-соединение дальше живёт как двунаправленный канал без HTTP-обёртки поверх каждого сообщения. Главная ловушка на собесе про масштабирование: соединение живёт на **конкретном** инстансе приложения — sticky sessions решают только то, что реконнект/handshake попадёт на тот же инстанс, но не решают доставку сообщения пользователю, чей сокет открыт на **другом** инстансе. Для этого нужен pub/sub-слой между инстансами.

## Handshake

```
Клиент:  GET /chat HTTP/1.1
         Upgrade: websocket
         Connection: Upgrade
         Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
         Sec-WebSocket-Version: 13

Сервер:  HTTP/1.1 101 Switching Protocols
         Upgrade: websocket
         Connection: Upgrade
         Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

`Sec-WebSocket-Accept` вычисляется сервером из `Sec-WebSocket-Key` детерминированной формулой (конкатенация с фиксированным GUID + SHA-1 + base64) — не секрет, а просто подтверждение, что сервер действительно понял запрос как WebSocket-апгрейд (защита от кэширующих прокси, случайно принявших произвольный ответ за успешный апгрейд). После `101` — то же TCP-соединение, но дальше это уже WebSocket-фреймы, не HTTP.

## Почему "WebSocket не масштабируется сам"

Соединение — стейтфул и живёт на одном процессе/инстансе, в отличие от stateless HTTP-запроса, который балансировщик может кинуть на любой инстанс независимо. Два инстанса за балансировщиком, три пользователя — каждый сокет физически подключен к одному конкретному инстансу. Если пользователь A (сокет на инстансе 1) отправляет сообщение пользователю B (сокет на инстансе 2), инстанс 1 не может просто "написать в сокет B" — у него физически нет доступа к чужому TCP-соединению.

```
Инстанс 1: держит сокет пользователя A
Инстанс 2: держит сокет пользователя B
A шлёт сообщение B → инстанс 1 получил его, но сокет B — не его
```

## Sticky sessions решают только про handshake/реконнект

```
# nginx: ip_hash или cookie-based sticky sessions
upstream ws_backend {
  ip_hash;
  server app1:3000;
  server app2:3000;
}
```

Sticky sessions гарантируют, что **новое** подключение (или реконнект после разрыва) одного и того же клиента попадёт на тот же инстанс, что и раньше (обычно через hash IP или cookie) — это важно для консистентности состояния в памяти конкретного инстанса (например, если сессия хранится локально, не в общем хранилище), но никак не помогает инстансу 1 доставить сообщение сокету, открытому на инстансе 2. Это разные проблемы: "куда направить новое соединение" и "как достучаться до чужого открытого соединения".

## Redis adapter — реальное решение доставки между инстансами

```ts
import { createAdapter } from '@socket.io/redis-adapter';
io.adapter(createAdapter(pubClient, subClient));
```

Каждый инстанс подписывается на общий Redis pub/sub-канал. Когда инстанс 1 хочет доставить сообщение сокету B (которого у него нет), он публикует событие в Redis; **все** инстансы получают публикацию, инстанс 2 узнаёт своих подписчиков и находит сокет B среди своих локальных соединений, отправляет напрямую. Де-факто это тот же паттерн pub/sub, что разобран в [04-databases/13-redis.md](../04-databases/13-redis.md) — здесь Redis используется не как хранилище данных, а как шина сообщений между процессами приложения. Альтернативы Redis adapter — NATS, Kafka как шина, либо (для совсем маленького масштаба) прямой broadcast между инстансами по внутренней сети — на практике Redis pub/sub чаще всего достаточно и проще всего интегрировать (`socket.io` даёт готовый адаптер из коробки).

## Heartbeat — обнаружение "мёртвых" соединений

TCP сам по себе не всегда сообщает о разрыве соединения быстро (обрыв Wi-Fi, смена сети, упавший клиент без штатного закрытия) — сервер может долго думать, что соединение живо, удерживая ресурсы под "зомби"-сокет. Heartbeat — периодический ping/pong между клиентом и сервером:

```ts
// сервер шлёт ping, ожидает pong в течение таймаута
setInterval(() => {
  if (!socket.isAlive) return socket.terminate(); // не ответил на прошлый ping — считаем мёртвым
  socket.isAlive = false;
  socket.ping();
}, 30000);
socket.on('pong', () => { socket.isAlive = true; });
```

Без heartbeat сервер копит "мёртвые" соединения в памяти неограниченно долго (утечка ресурсов, см. [02-nodejs-core/08-memory-leaks.md](../02-nodejs-core/08-memory-leaks.md) про накопление подписок/соединений) — heartbeat даёт детерминированный таймаут, после которого соединение принудительно закрывается и освобождает ресурсы, а клиент (если он ещё жив) знает, что нужно переподключиться.

## Что спрашивают на собеседовании

1. **Как происходит WebSocket handshake?** — обычный HTTP-запрос с `Upgrade: websocket`, ответ `101 Switching Protocols`, дальше то же TCP-соединение используется для WebSocket-фреймов вместо HTTP.
2. **Чат на 3 инстансах за балансировщиком — как доставить сообщение пользователю на другом инстансе?** — sticky sessions тут не помогают (решают только маршрутизацию нового подключения); нужен pub/sub слой между инстансами (Redis adapter или аналог) — каждый инстанс публикует и подписан на сообщения для своих локальных сокетов.
3. **Чем sticky sessions отличаются от Redis adapter по решаемой проблеме?** — sticky sessions про "куда направить новое/переподключаемое соединение", Redis adapter — про "как доставить сообщение уже открытому соединению на чужом инстансе".
4. **Зачем нужен heartbeat, если TCP и так должен сообщать о разрыве?** — TCP не всегда быстро/надёжно детектирует разрыв (смена сети, упавший клиент без штатного закрытия) — heartbeat даёт контролируемый таймаут для очистки "зомби"-соединений и освобождения ресурсов сервера.
5. **Почему WebSocket-соединение нельзя просто "перекинуть" на другой инстанс балансировщиком на лету?** — соединение — стейтфул TCP-канал, физически привязанный к процессу, который его принял; "перенос" эквивалентен разрыву и новому handshake, состояние (открытые подписки, буферы) не переносится автоматически.
