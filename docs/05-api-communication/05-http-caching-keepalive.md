# HTTP: keep-alive, ETag/Cache-Control, сжатие

> **TL;DR:** Keep-alive убирает накладные расходы на TCP-хендшейк для каждого запроса, переиспользуя соединение. `Cache-Control` управляет тем, **можно ли вообще** взять ответ из кэша и как долго без повторного похода к серверу; `ETag`/`If-None-Match` — что делать, когда кэш устарел: не перекачивать тело заново, а спросить "изменилось ли?" и получить `304` почти бесплатно. Это разные механизмы, решающие разные проблемы, их часто путают на собесе.

## Keep-alive — переиспользование TCP-соединения

```
Connection: keep-alive
Keep-Alive: timeout=5, max=1000
```

Без keep-alive каждый HTTP-запрос — новое TCP-соединение: SYN/SYN-ACK/ACK (плюс TLS handshake для HTTPS — ещё несколько round-trip'ов) прежде, чем уйдёт первый байт полезных данных. При частых запросах к одному хосту (типичный случай — SPA, дёргающая API) это ощутимая доля латентности впустую. С HTTP/1.1 keep-alive включён по умолчанию — соединение живёт и переиспользуется для следующих запросов, пока не истечёт `timeout` бездействия или не будет достигнут `max` запросов на соединение. На стороне Node это касается и исходящих запросов: `http.Agent({ keepAlive: true })` для клиента, иначе каждый исходящий вызов к внешнему API — новое соединение (подробнее про агенты — в [02-nodejs-core/12-http-internals.md](../02-nodejs-core/12-http-internals.md)).

## `Cache-Control` — можно ли кэшировать и на сколько

```
Cache-Control: public, max-age=3600           -- кэшируемо кем угодно (включая CDN/прокси), 1 час без повторного запроса
Cache-Control: private, max-age=60             -- кэшируемо только браузером конкретного пользователя, не общими прокси
Cache-Control: no-cache                        -- можно кэшировать, но ОБЯЗАТЕЛЬНА ревалидация перед использованием (несмотря на название!)
Cache-Control: no-store                        -- вообще не кэшировать (чувствительные данные — токены, платёжные данные)
```

`no-cache` — самое частое заблуждение: это не "не кэшировать", а "кэшируй, но перед каждым использованием спроси сервер, не устарело ли" (через `ETag`/`If-Modified-Since`) — фактически то же самое, что `max-age=0, must-revalidate`. Настоящее "не кэшировать вообще" — `no-store`.

## `ETag` / `If-None-Match` — ревалидация без перекачки тела

```
Клиент:  GET /users/123
Сервер:  200 OK, ETag: "a1b2c3", Cache-Control: no-cache

-- позже, кэш "устарел" по времени или клиент явно ревалидирует --
Клиент:  GET /users/123, If-None-Match: "a1b2c3"
Сервер:  304 Not Modified   -- ресурс не менялся, тело НЕ передаётся, только заголовки
```

`ETag` — хэш/версия содержимого ресурса. Если ресурс не изменился, сервер отвечает `304` без тела — экономия трафика при неизменном содержимом, даже когда клиент обязан ревалидировать на каждый запрос (`no-cache`/`must-revalidate`). Дешевле генерации всего ответа заново, особенно для больших payload'ов, где сама генерация (не только передача) стоит ресурсов сервера. Похожий, но более грубый механизм — `Last-Modified`/`If-Modified-Since` (сравнение по времени, а не по хэшу содержимого — менее точно: не различает два разных сохранения с одинаковым содержимым и одинаковой секундой времени).

## Комбинация в реальном ответе

```
Cache-Control: private, max-age=60, must-revalidate
ETag: "a1b2c3"
```

Первые 60 секунд клиент использует кэш без единого запроса к серверу вообще (максимальная экономия). После истечения `max-age` — обязан ревалидировать через `If-None-Match`, но если содержимое не изменилось, платит только за круговой запрос заголовков, не за полное тело. Это стандартная связка для данных, которые меняются нечасто, но не могут быть закэшированы навечно.

## Сжатие

```
Клиент:  Accept-Encoding: gzip, br
Сервер:  Content-Encoding: br, Vary: Accept-Encoding
```

`gzip` — универсальная поддержка, `br` (Brotli) — обычно эффективнее сжимает текстовый контент (JSON, HTML, JS), но чуть дороже по CPU на сжатие — на статике (уже сжатой заранее на сборке, а не на лету) это не проблема, для динамических ответов — trade-off CPU сервера vs размер передачи. `Vary: Accept-Encoding` обязателен, если ответ кэшируется прокси/CDN — иначе прокси может закэшировать сжатую версию и отдать её клиенту, не поддерживающему это кодирование (или наоборот) без учёта заголовка запроса. Сжимать имеет смысл текстовые форматы (JSON, HTML) — бинарные уже сжатые форматы (JPEG, большинство видео) от повторного gzip/brotli почти не выигрывают, а CPU тратится впустую.

## Что спрашивают на собеседовании

1. **Зачем нужен keep-alive и что произойдёт без него при высокой частоте запросов?** — избежать TCP(+TLS)-хендшейка на каждый запрос; без него латентность и нагрузка на сервер растут за счёт постоянного передоговора соединений, особенно заметно для множества мелких запросов подряд.
2. **`no-cache` vs `no-store` — в чём разница?** — `no-cache` разрешает кэшировать, но требует обязательной ревалидации перед использованием; `no-store` запрещает сохранение вообще (для чувствительных данных).
3. **Как `ETag` экономит трафик, если ревалидация всё равно происходит на каждый запрос?** — сервер отвечает `304 Not Modified` без тела, если содержимое не изменилось — платим за заголовки, не за повторную передачу (и часто не за повторную генерацию) полного ответа.
4. **Зачем нужен заголовок `Vary: Accept-Encoding` при использовании сжатия за CDN/прокси?** — без него прокси может закэшировать один вариант кодирования и отдавать его клиентам независимо от их `Accept-Encoding`, что либо ломает декодирование, либо теряет выгоду от сжатия для части клиентов.
5. **Есть ли смысл сжимать уже сжатые бинарные форматы (JPEG, видео)?** — почти нет — повторное сжатие почти не уменьшает размер, но тратит CPU впустую; сжатие эффективно на текстовых форматах.
