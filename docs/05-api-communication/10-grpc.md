# gRPC: protobuf, типы стриминга, deadlines, когда брать вместо REST

> **TL;DR:** gRPC — RPC-фреймворк поверх HTTP/2 с контрактом, описанным в Protocol Buffers (`.proto`): строго типизированная бинарная сериализация вместо JSON, кодогенерация клиента/сервера на десятках языков из одного файла контракта. Выигрывает у REST+JSON в производительности (меньше payload, меньше CPU на (де)сериализацию) и в строгости контракта (breaking change виден на этапе компиляции, не в рантайме), проигрывает в отладке "руками" (нельзя curl'ом посмотреть, что происходит) и в поддержке браузером напрямую.

## Protobuf — контракт и сериализация

```protobuf
syntax = "proto3";

message Order {
  string id = 1;
  string status = 2;
  int64 total_cents = 3;
}

service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc StreamOrderUpdates (GetOrderRequest) returns (stream Order); // server streaming
}
```

Номера полей (`= 1`, `= 2`) — не для красоты, а часть бинарного формата: сообщение сериализуется как последовательность (номер поля, тип, значение), без имён полей в самих байтах (в отличие от JSON, где ключи объекта передаются каждый раз текстом) — отсюда компактность. Переименовать поле — безопасно (номер не меняется), удалить — нельзя просто взять и удалить номер (нужно `reserved`, чтобы он не переиспользовался случайно для несовместимого типа в будущем) — совместимость контролируется на уровне номеров полей, а не имён, что и даёт настоящую forward/backward compatibility между версиями сервиса.

## Четыре типа RPC/стриминга

```protobuf
rpc GetOrder (Request) returns (Order);                    // unary — обычный запрос-ответ
rpc StreamOrders (Request) returns (stream Order);          // server streaming — один запрос, поток ответов
rpc UploadEvents (stream Event) returns (Response);          // client streaming — поток запросов, один ответ
rpc Chat (stream Message) returns (stream Message);          // bidirectional streaming — оба потока независимы
```

- **Unary** — то же, что REST-запрос по духу: один запрос, один ответ.
- **Server streaming** — клиент шлёт один запрос, сервер отвечает потоком (живые котировки на один тикер, прогресс долгой операции) — HTTP/2 позволяет это нативно, без polling/SSE-костылей.
- **Client streaming** — клиент шлёт поток (например, батч событий телеметрии), сервер отвечает один раз в конце.
- **Bidirectional streaming** — оба потока независимы друг от друга по времени (не обязана быть строгая пара запрос-ответ) — ближе всего по духу к WebSocket, но со строгой типизацией сообщений через protobuf.

## Deadlines — обязательная часть контракта вызова

```
grpc.deadline: now + 500ms
```

В отличие от REST, где таймаут — забота клиента "снаружи" протокола (обычный HTTP-клиентский timeout, о котором сервер ничего не знает), в gRPC клиент передаёт **deadline** как часть самого запроса — сервер видит, сколько времени осталось, и может передать этот же deadline **дальше** по цепочке вызовов (микросервис A вызывает B вызывает C — все с одним and тем же остающимся временем, а не с независимыми таймаутами на каждом хопе, которые в сумме могут сильно превысить ожидания вызывающей стороны). Сервер, увидевший истёкший deadline до начала тяжёлой работы, может сразу отказаться от выполнения — не тратить ресурсы на ответ, который клиент уже не будет ждать.

## Почему gRPC хорош межсервисно, а REST — наружу

| | gRPC | REST+JSON |
|---|---|---|
| Производительность | компактная бинарная сериализация, HTTP/2 мультиплексирование | текстовый JSON, обычно HTTP/1.1 (хотя HTTP/2 тоже возможен) |
| Строгость контракта | `.proto` — единый источник истины, кодогенерация, breaking change виден при компиляции | контракт обычно в документации/OpenAPI отдельно от кода, легко разойтись |
| Браузер | нет нативной поддержки (нужен grpc-web + прокси-транскодер) | нативно, `fetch` работает из коробки |
| Отладка | нужны специальные инструменты (`grpcurl`, BloomRPC) — бинарный формат не прочитать глазами в сетевой вкладке | `curl`, DevTools Network — сразу читаемо |
| Стриминг | нативно все 4 типа | эмуляция через SSE/WebSocket/chunked |

Практический паттерн: gRPC для внутренней коммуникации между микросервисами (контролируемое окружение, важна производительность и строгость контракта, отладка через специализированные внутренние инструменты приемлема), REST/GraphQL — на границе с внешним миром (браузер, мобильные клиенты, партнёрские интеграции — где нужна доступность из любого HTTP-клиента и человекочитаемая отладка). NestJS поддерживает gRPC как транспорт нативно через `@nestjs/microservices` — подробнее в [03-nestjs/14-microservices.md](../03-nestjs/14-microservices.md).

## Что спрашивают на собеседовании

1. **gRPC vs REST для внутренних сервисов — какие trade-offs?** — производительность и строгость контракта в пользу gRPC ценой сложности отладки и отсутствия нативной поддержки браузером; для внешнего API обычно REST/GraphQL остаётся практичнее.
2. **Зачем protobuf использует номера полей вместо имён в бинарном формате?** — компактность (не передавать имена ключей каждый раз) и явный контроль совместимости — переименование поля безопасно, номер не меняется, удаление требует `reserved`, чтобы не переиспользовать номер под несовместимый тип.
3. **Какие есть типы стриминга в gRPC?** — unary, server streaming, client streaming, bidirectional — все нативно поверх HTTP/2, без обходных путей вроде SSE/long polling для REST.
4. **Что такое deadline в gRPC и чем это лучше клиентского таймаута в REST?** — deadline передаётся как часть запроса и может распространяться по цепочке вызовов между сервисами — все хопы видят одно и то же оставшееся время, а не независимые таймауты, суммарно превышающие ожидания клиента.
5. **Почему gRPC плохо подходит для публичного браузерного API напрямую?** — браузеры не дают нативного доступа к HTTP/2-фреймам, нужным протоколу; требуется grpc-web + прокси-транскодер (например, Envoy) для моста между браузером и gRPC-сервисом.
