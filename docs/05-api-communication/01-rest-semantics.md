# REST: семантика методов, идемпотентность, коды ответов

> **TL;DR:** Идемпотентность — это про **сервер**, не про клиента: повторный одинаковый запрос должен приводить к тому же итоговому состоянию, что и один запрос (не обязательно тот же ответ байт-в-байт). `GET/PUT/DELETE` обязаны быть идемпотентны по спецификации HTTP, `POST` — нет, поэтому ретраи `POST` (таймаут, разрыв соединения) — источник дублей, если не защититься отдельно (см. [Idempotency keys для POST](./02-idempotency-keys.md)).

## Идемпотентность по методам

| Метод | Идемпотентен | Безопасен (safe, без побочных эффектов) | Семантика |
|---|---|---|---|
| `GET` | да | да | получить ресурс, никогда не менять состояние |
| `HEAD` | да | да | как GET, без тела ответа |
| `PUT` | да | нет | заменить ресурс целиком заданным представлением |
| `DELETE` | да | нет | удалить; повторное удаление того же ресурса — не ошибка по духу идемпотентности (хотя ответ может отличаться: 204 → 404) |
| `PATCH` | **нет**, если не спроектирован иначе | нет | частичное изменение — зависит от формата патча |
| `POST` | нет | нет | создать новый ресурс / произвольное действие |

**`PUT` идемпотентен, потому что заменяет целиком:** два одинаковых `PUT /users/5 {"name": "Alice"}` подряд оставляют ресурс в одном и том же состоянии. **`PATCH` обычно неидемпотентен:** `PATCH /accounts/5 {"op": "increment", "value": 10}` при повторе даст другое итоговое состояние (+20 вместо +10) — а вот `PATCH` в формате "установить поле в значение" (`{"balance": 110}`) уже идемпотентен по факту, хотя формально метод не обязывает. Это частый вопрос-ловушка: идемпотентность `PATCH` зависит от того, **что именно** описывает патч (декларативное состояние vs операция-дельта), а не от метода самого по себе.

## Почему идемпотентность критична при ретраях

Сетевой сбой не сообщает, дошёл ли запрос до сервера — таймаут на `POST /orders` мог означать и "запрос не долетел" (безопасно повторить), и "запрос выполнился, не долетел только ответ" (повтор создаст дубль заказа). At-least-once доставка (ретраи на любом уровне — HTTP-клиент, очередь, API-gateway) — это норма распределённых систем, а не редкий edge case. Идемпотентные операции можно ретраить бездумно; неидемпотентные (`POST`, дельта-`PATCH`) требуют либо естественной идемпотентности на уровне бизнес-логики (запрос содержит клиентский ID, повторная вставка с тем же ID — no-op через `ON CONFLICT DO NOTHING`), либо явного idempotency key.

## Коды ответов — не только "успех/ошибка"

| Код | Когда | Частая ошибка в использовании |
|---|---|---|
| `200 OK` | успех с телом ответа | использовать для всего подряд, включая создание (правильнее `201`) |
| `201 Created` | успешное создание ресурса, обычно с `Location` заголовком | забывают `Location` |
| `204 No Content` | успех без тела (например, `DELETE`) | возвращать `200` с пустым телом вместо `204` |
| `400 Bad Request` | запрос синтаксически/структурно некорректен | путают с `422` |
| `401 Unauthorized` | не аутентифицирован (несмотря на название — это про identity, не про права) | путают с `403` |
| `403 Forbidden` | аутентифицирован, но нет прав на это действие | путают с `401` |
| `404 Not Found` | ресурс не существует (или скрыт из соображений безопасности вместо `403`) | — |
| `409 Conflict` | запрос конфликтует с текущим состоянием ресурса (версия устарела, дубликат уникального поля, конкурентное изменение) | использовать `400` вместо `409` для конфликтов состояния |
| `422 Unprocessable Entity` | синтаксически корректный запрос, но семантически невалидный (провалилась бизнес-валидация) | путают с `400` |
| `429 Too Many Requests` | rate limit превышен, обычно с заголовком `Retry-After` | забывают `Retry-After`, клиент не знает, сколько ждать |

Различие `400` vs `422` — частый вопрос: `400` — сервер не смог даже распарсить/понять запрос (битый JSON, отсутствует обязательное поле по схеме), `422` — запрос понят, синтаксически валиден, но нарушает бизнес-правило (например, email занят, дата окончания раньше даты начала). `409` — отдельная категория: запрос сам по себе валиден, но конфликтует с **текущим состоянием** сервера (оптимистичная блокировка не прошла, попытка создать ресурс с уже занятым уникальным ключом).

## Что спрашивают на собеседовании

1. **`PUT` vs `PATCH` vs `POST` — в чём разница по семантике и идемпотентности?** — `PUT` заменяет ресурс целиком и идемпотентен; `PATCH` — частичное изменение, идемпотентность зависит от формата (декларативный патч — да, дельта-операция — нет); `POST` — создание/произвольное действие, не идемпотентен в общем случае.
2. **Почему идемпотентность важна именно при ретраях?** — сеть не гарантирует доставку "один раз ровно": таймаут не говорит, выполнился ли запрос — безопасный повтор возможен только для идемпотентных операций, иначе получаем дубли.
3. **Чем `409` отличается от `422`?** — `409` — конфликт с текущим состоянием ресурса на сервере (версия, уникальность, конкурентное изменение), `422` — запрос сам по себе нарушает бизнес-правило независимо от состояния других ресурсов.
4. **Всегда ли `PATCH` неидемпотентен?** — нет: зависит от формата патча — "установить значение поля" идемпотентен, "инкрементировать на N" — нет.
5. **`401` vs `403` — в чём разница и как их часто путают?** — `401` про отсутствие/невалидность аутентификации ("кто ты?"), `403` — идентификация прошла, но прав недостаточно ("тебе нельзя"); частая ошибка — возвращать `401` там, где реально пользователь опознан, но не авторизован.
