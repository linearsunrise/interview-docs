# Transactional Outbox + relay/CDC — надёжная публикация событий

> **TL;DR:** "Записал в БД, потом отправил в Kafka" — это **dual write**: две независимые системы (БД и брокер), без общей транзакции между ними. Процесс может упасть ровно между этими двумя операциями — событие или потеряется (записали в БД, упали до отправки), или задублируется (отправили, упали до фиксации, что отправлено, ретрай отправит снова). Transactional Outbox чинит это, сводя проблему обратно к одной локальной ACID-транзакции: событие пишется в таблицу `outbox` **той же транзакцией**, что и бизнес-данные, а отдельный процесс (relay) публикует его в брокер уже после гарантированного коммита.

## Проблема dual write

```ts
// плохо: два независимых write без общей транзакции
async function createOrder(dto: CreateOrderDto) {
  const order = await orderRepo.save(dto);              // 1. записали в БД
  await kafkaProducer.send('orders', { type: 'OrderCreated', orderId: order.id }); // 2. отправили в Kafka
  // если процесс упал МЕЖДУ 1 и 2 -> заказ создан, но событие никогда не отправлено
  // если упал ПОСЛЕ отправки, но до какого-то финального шага -> при ретрае всей операции событие продублируется
}
```

Ни один порядок операций (сначала БД, потом брокер, или наоборот) не устраняет проблему — она в самом факте, что это две раздельные системы без общего транзакционного контекста. "Отправить сначала в Kafka, потом записать в БД" не лучше: тогда можно получить событие о заказе, которого в базе так и не появилось.

## Outbox — сведение к одной локальной транзакции

```sql
CREATE TABLE outbox (
  id bigserial PRIMARY KEY,
  aggregate_id uuid NOT NULL,
  event_type text NOT NULL,
  payload jsonb NOT NULL,
  created_at timestamptz DEFAULT now(),
  published_at timestamptz  -- NULL, пока relay не подтвердил публикацию
);
```

```ts
async function createOrder(dto: CreateOrderDto) {
  await db.transaction(async (tx) => {
    const order = await orderRepo.save(dto, tx);
    await outboxRepo.save({
      aggregateId: order.id, eventType: 'OrderCreated', payload: { orderId: order.id, items: order.items },
    }, tx); // ОДНА транзакция с бизнес-данными — либо оба пишутся, либо ни один
  });
  // событие ЕЩЁ не в Kafka — только зафиксировано в БД, гарантированно вместе с заказом
}
```

Запись бизнес-данных и запись намерения "нужно опубликовать событие" — теперь одна и та же атомарная операция, за которую отвечает обычный ACID-механизм БД (см. [04-databases/04-transactions-isolation.md](../04-databases/04-transactions-isolation.md)) — либо закоммитятся оба изменения, либо ни одно. Проблема dual write не решена, а **перенесена**: теперь она между строкой в `outbox` и фактической публикацией в Kafka — но это уже гораздо проще, потому что relay может безопасно ретраить публикацию сколько угодно раз (см. ниже), не рискуя потерять сам факт "это нужно опубликовать".

## Relay — как строка из outbox попадает в брокер

**Вариант 1 — поллер:**

```ts
setInterval(async () => {
  const pending = await outboxRepo.findUnpublished(); // WHERE published_at IS NULL
  for (const event of pending) {
    await kafkaProducer.send('orders', event.payload);
    await outboxRepo.markPublished(event.id); // отдельный update ПОСЛЕ подтверждения от брокера
  }
}, 1000);
```

Простой в реализации, но добавляет задержку публикации (интервал поллинга) и постоянную фоновую нагрузку на БД (регулярный `SELECT` таблицы outbox). Если процесс упадёт между `send` и `markPublished` — при следующем поллинге событие будет отправлено повторно (at-least-once на этом стыке, а не exactly-once) — consumer на другой стороне обязан быть идемпотентным (см. [14-delivery-guarantees-idempotent-consumers.md](./14-delivery-guarantees-idempotent-consumers.md)), это не устраняется, а сознательно принимается как компромисс.

**Вариант 2 — CDC (Change Data Capture), например Debezium:**

```
PostgreSQL WAL → Debezium (читает поток изменений напрямую из WAL) → Kafka
```

CDC-инструмент подключается к журналу транзакций БД (WAL в PostgreSQL — тот же механизм, что используется для репликации, см. [04-databases/11-replication.md](../04-databases/11-replication.md)) и стримит изменения таблицы `outbox` в Kafka **без опроса** — почти нулевая задержка публикации, никакой дополнительной нагрузки в виде поллинг-запросов к БД, потому что чтение идёт из уже существующего физического потока изменений, который БД пишет в любом случае. Цена — дополнительная инфраструктурная единица (Debezium + Kafka Connect), которую нужно разворачивать и поддерживать отдельно от приложения.

## Итоговая гарантия — at-least-once, не exactly-once

Outbox гарантированно не **теряет** событие (оно надёжно зафиксировано в той же транзакции, что бизнес-данные) — но не гарантирует, что оно будет доставлено **ровно один раз**: и поллер, и CDC могут в редких сценариях (падение между отправкой и фиксацией "опубликовано") доставить событие повторно. Это принципиальное ограничение, не недоработка конкретной реализации — единственный способ получить итоговую консистентность без сложной распределённой транзакции — переложить дедупликацию на consumer'а (идемпотентный обработчик), а не пытаться гарантировать exactly-once на стороне отправителя.

## Что спрашивают на собеседовании

1. **Сервис A пишет в свою БД и должен уведомить сервис B. Что не так с "записал в БД, потом отправил в Kafka"?** — dual write: две раздельные системы без общей транзакции — падение между шагами теряет или дублирует событие независимо от порядка операций.
2. **Как чинит outbox?** — событие пишется в таблицу outbox той же локальной транзакцией, что бизнес-данные — атомарность гарантируется обычным ACID; отдельный relay публикует событие в брокер уже после гарантированного коммита.
3. **Outbox даёт exactly-once доставку?** — нет, at-least-once: relay может отправить событие повторно при падении между публикацией и отметкой "опубликовано" — consumer обязан быть идемпотентным.
4. **Поллер vs CDC (Debezium) как relay — в чём разница?** — поллер проще, но добавляет задержку и постоянную нагрузку регулярными запросами к БД; CDC читает поток изменений напрямую из WAL, почти без задержки и без дополнительного опроса, ценой отдельной инфраструктуры.
5. **Почему нельзя просто гарантировать exactly-once на уровне outbox-механизма?** — фундаментальное ограничение распределённых систем (два независимых действия — фиксация в БД и подтверждение от брокера — не могут быть одной атомарной операцией без 2PC, см. [15-distributed-transactions-2pc.md](./15-distributed-transactions-2pc.md)) — практичнее принять at-least-once и решить дублирование на стороне потребителя.
