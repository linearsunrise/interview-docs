# DDD: entity vs value object, агрегат и его инварианты, bounded context, ubiquitous language

> **TL;DR:** Domain-Driven Design — не про технические паттерны сами по себе, а про то, чтобы код говорил на языке бизнеса (**ubiquitous language**), а не на языке таблиц БД. Entity и value object различаются тем, что для entity важна **идентичность** (два заказа с одинаковыми полями — всё равно два разных заказа), а для value object — только **значение** (два адреса с одинаковыми полями — один и тот же адрес, взаимозаменяемы). Агрегат — граница консистентности: правило "один агрегат — одна транзакция" существует не из технической прихоти, а потому что именно агрегат — единица, чьи инварианты обязаны быть согласованы **всегда**, без исключений.

## Entity vs Value Object

```ts
// Entity — идентичность важнее содержимого
class Order {
  constructor(readonly id: OrderId, private items: OrderItem[]) {}
  equals(other: Order) { return this.id.equals(other.id); } // сравнение по ID, не по полям
}

// Value Object — содержимое И ЕСТЬ идентичность, неизменяем
class Money {
  constructor(readonly amount: number, readonly currency: string) {}
  equals(other: Money) { return this.amount === other.amount && this.currency === other.currency; }
  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error('currency mismatch');
    return new Money(this.amount + other.amount, this.currency); // новый объект, не мутация
  }
}
```

Практическое следствие: `Money(100, 'USD')`, созданный в двух разных местах кода, — это один и тот же value object по смыслу (можно свободно копировать, сравнивать по значению, кэшировать) — в отличие от `Order`, где два заказа с одинаковой суммой и товарами — всё равно разные заказы (разный `id`, разная судьба: один может быть отменён, другой — нет). Value object обычно делают **immutable** — любое "изменение" возвращает новый объект, что устраняет целый класс багов с чужим кодом, случайно держащим ссылку на объект, который кто-то изменил у себя.

## Агрегат и инварианты — почему "один агрегат — одна транзакция"

```ts
class Order { // Order — корень агрегата (aggregate root)
  private items: OrderItem[] = [];
  private status: 'draft' | 'confirmed' | 'shipped' = 'draft';

  addItem(item: OrderItem) {
    if (this.status !== 'draft') throw new Error('cannot modify confirmed order'); // инвариант
    this.items.push(item);
  }
  confirm() {
    if (this.items.length === 0) throw new Error('cannot confirm empty order'); // инвариант
    this.status = 'confirmed';
  }
}
```

Агрегат — кластер связанных объектов (здесь `Order` + `OrderItem[]`), у которого есть **корень** (aggregate root) — единственная точка входа для изменений извне. Всё, что снаружи хочет поменять `OrderItem`, обязано идти через методы `Order`, а не трогать `items` напрямую — так гарантируются инварианты ("нельзя подтвердить пустой заказ", "нельзя менять подтверждённый заказ"), которые должны выполняться **всегда**, а не только в конце какого-то бизнес-процесса.

Отсюда правило "один агрегат — одна транзакция": если сохранять изменения в `Order` и, скажем, в независимом агрегате `Inventory` в **разных** транзакциях, между ними неизбежно окно, где данные рассинхронизированы (заказ подтверждён, а склад ещё не зарезервирован) — но это **допустимо**, потому что `Order` и `Inventory` — разные агрегаты с разными инвариантами, и согласованность между ними — **eventual**, через доменные события (см. [09-saga.md](./09-saga.md)), а не через распределённую транзакцию. Внутри же одного агрегата (сам `Order` и его `items`) рассинхрон недопустим никогда — иначе теряет смысл сама граница агрегата как единицы консистентности.

## Bounded Context — одно слово, разный смысл в разных частях системы

```
Контекст "Продажи": Product { name, price, availableForSale }
Контекст "Склад":   Product { sku, warehouseLocation, quantityOnHand }
Контекст "Доставка": Product { weight, dimensions, fragile }
```

"Product" — не одна универсальная сущность на всю систему, а разное понятие в разных **bounded context** — каждый контекст моделирует только те атрибуты и поведение, которые ему нужны, даже если в реальности речь об "одном и том же" товаре. Попытка сделать единую модель `Product` на всю компанию (частая ошибка "давайте сделаем одну общую сущность, чтобы не дублировать") обычно кончается God-объектом, который знает слишком много и меняется по слишком многим причинам (снова нарушение SRP, см. [01-solid.md](./01-solid.md), но на уровне модели данных, а не класса). Границы bounded context на практике часто совпадают с границами микросервисов (если система разбивается на сервисы) — это не совпадение, а прямое следствие: разный смысл одного слова — сигнал независимой эволюции модели, а значит, и независимого владения командой.

## Ubiquitous language — язык кода = язык бизнеса

Если аналитик/продакт говорит "зарезервировать товар", а в коде это называется `updateInventoryFlag(true)` — это разрыв: перевод между бизнес-терминами и кодом происходит в голове каждого разработчика заново, накапливая расхождения. Ubiquitous language — договорённость называть вещи в коде так же, как их называет бизнес (`reserveStock()`, не `updateFlag()`) — метод переименования не косметика, а способ избежать ситуации, когда код и бизнес-обсуждение говорят про формально одно и то же, но требуют мысленного перевода туда-обратно, где и теряются нюансы.

## Что спрашивают на собеседовании

1. **Чем entity отличается от value object?** — entity различается по идентичности (ID), даже если все поля совпадают; value object различается только по значению — два объекта с одинаковыми полями взаимозаменяемы и обычно immutable.
2. **Расскажите про агрегат в DDD.** — кластер объектов с единым корнем (aggregate root), через который идут все внешние изменения — так гарантируются инварианты, которые обязаны выполняться постоянно, не только "в конце процесса".
3. **Почему "один агрегат — одна транзакция"?** — согласованность внутри агрегата обязана быть строгой всегда (иначе граница агрегата бессмысленна); согласованность между разными агрегатами допустимо делать eventual, через доменные события, а не распределённую транзакцию.
4. **Что такое bounded context и зачем он нужен?** — граница, внутри которой одно и то же слово/понятие имеет один согласованный смысл; вне границы то же слово может означать другое — попытка унифицировать одну модель на всю систему обычно ведёт к God-объекту.
5. **Что такое ubiquitous language и как оно проявляется в коде?** — соглашение называть методы/сущности так же, как их называет бизнес, а не в терминах технической реализации — устраняет расхождение между обсуждением требований и кодом.
