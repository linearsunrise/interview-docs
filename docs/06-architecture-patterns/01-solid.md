# SOLID с примерами из бэкенда

> **TL;DR:** SOLID — не пять независимых правил, а один и тот же вопрос с разных сторон: "что заставит этот код сломаться, если требования изменятся, и можно ли изолировать эту зону риска". На собеседовании абстрактный пример с фигурами (`Circle`/`Rectangle`) — сигнал, что кандидат выучил определение, но не применял на практике. Ниже — примеры на типичном бэкенд-сервисе (заказы, оплата, уведомления).

## Single Responsibility — "одна причина для изменения", не "один метод"

```ts
// плохо: сервис меняется и при смене правил скидок, и при смене формата письма, и при смене провайдера оплаты
class OrderService {
  createOrder(dto) { /* валидация + расчёт скидки + сохранение + отправка email + вызов платёжного шлюза */ }
}

// лучше: каждый класс меняется по одной причине
class OrderService { constructor(private pricing: PricingService, private payments: PaymentGateway, private notifier: OrderNotifier) {} }
class PricingService { calculateTotal(order) { /* правила скидок — меняются отдельно от остального */ } }
class OrderNotifier { notify(order) { /* формат письма/канал — меняется отдельно */ } }
```

Частая ошибка трактовки — "один метод/один класс = SRP". Реальный критерий — **кто инициирует изменение**: если правила скидок меняет одна команда/по одной бизнес-причине, а формат уведомлений — другая, смешивание их в одном классе означает, что правка одного риска ломает или требует перетеста другого, никак логически с ним не связанного.

## Open/Closed — расширение без правки существующего кода

```ts
// плохо: добавление способа оплаты требует править существующий switch
function charge(method: string, amount: number) {
  if (method === 'card') return chargeCard(amount);
  if (method === 'paypal') return chargePaypal(amount);
  // добавили crypto — снова лезем сюда и рискуем сломать card/paypal
}

// лучше: новый способ оплаты = новый класс, ничего существующего не трогаем
interface PaymentMethod { charge(amount: number): Promise<Receipt>; }
class CardPayment implements PaymentMethod { charge(amount) { /* ... */ } }
class PaypalPayment implements PaymentMethod { charge(amount) { /* ... */ } }
// добавление CryptoPayment не требует изменений в вызывающем коде
```

"Closed for modification" не значит "нельзя менять никогда" — значит, что типичное расширение функциональности (новый способ оплаты, новый тип уведомления) не требует трогать уже протестированный существующий код, а добавляется рядом через уже существующую точку расширения (интерфейс/абстракцию).

## Liskov Substitution — наследник не должен удивлять вызывающий код

```ts
// нарушение LSP: наследник ужесточает контракт базового класса
class Repository { save(entity: Entity): Promise<void> { /* ... */ } }
class ReadOnlyRepository extends Repository {
  save(): Promise<void> { throw new Error('not supported'); } // вызывающий код, работающий с Repository, этого не ожидает
}
```

Любой код, написанный против типа `Repository`, должен продолжать корректно работать, если ему подсунули `ReadOnlyRepository` — исключение вместо ожидаемого поведения нарушает это обещание. На практике LSP чаще всего ловится не через "геометрические" примеры, а через ORM-репозитории/интерфейсы сервисов, где наследник добавляет более строгие предусловия или более слабые постусловия, чем заявляет базовый тип, — и код, писавшийся против абстракции, начинает падать там, где не ожидал.

## Interface Segregation — не заставлять реализовывать лишнее

```ts
// плохо: один "толстый" интерфейс на все возможные операции с заказом
interface OrderOperations {
  create(dto): Order; refund(id): void; generateInvoicePdf(id): Buffer; exportToAccounting(id): void;
}
// сервис уведомлений вынужден реализовывать generateInvoicePdf, который ему не нужен

// лучше: узкие интерфейсы под конкретных потребителей
interface OrderCreator { create(dto): Order; }
interface OrderRefunder { refund(id): void; }
```

Толстый интерфейс заставляет каждую реализацию тащить методы, которые ей не нужны (пустые заглушки/`throw new Error('not implemented')` — тот же запах, что и в примере LSP выше), и делает любое изменение интерфейса шире, чем нужно — правка ради одного потребителя ломает компиляцию у всех остальных.

## Dependency Inversion — сервис зависит от абстракции, не от конкретной реализации

```ts
// плохо: OrderService напрямую завязан на конкретную реализацию (Stripe SDK)
class OrderService {
  private stripe = new Stripe(apiKey);
  async pay(order) { await this.stripe.charges.create({ amount: order.total }); }
}

// лучше: зависимость от абстракции, конкретная реализация подставляется снаружи (DI)
interface PaymentGateway { charge(amount: number): Promise<Receipt>; }
class OrderService {
  constructor(private gateway: PaymentGateway) {} // не знает про Stripe вообще
  async pay(order) { await this.gateway.charge(order.total); }
}
```

Это ровно то, на чём стоит DI-контейнер NestJS (см. [DI-контейнер и провайдеры](../03-nestjs/01-di-and-providers.md)): `OrderService` объявляет зависимость от абстракции (`PaymentGateway`), а какая конкретная реализация подставится (`StripeGateway`, `MockGateway` в тестах) — решает модуль конфигурации, а не сам сервис. DI-контейнер — не альтернатива DIP, а конкретный механизм, автоматизирующий "подстановку абстракции" без ручного создания зависимостей в конструкторе.

## Что спрашивают на собеседовании

1. **Приведите пример SRP не на геометрических фигурах.** — сервис заказа, разделённый на расчёт цены/уведомления/оплату по критерию "кто и почему инициирует изменение", а не по формальному подсчёту методов.
2. **Как понять, что класс нарушает OCP?** — типичное расширение функциональности (новый способ оплаты, новый канал уведомлений) требует правки существующего протестированного кода (`switch`/`if`-цепочка), а не добавления нового класса рядом.
3. **Что конкретно нарушает LSP, если не "квадрат не прямоугольник"?** — наследник, который ужесточает предусловия или ослабляет постусловия базового типа — например, репозиторий, кидающий исключение на операции, которую базовый интерфейс объявляет поддерживаемой.
4. **Зачем нужен ISP, если можно один большой интерфейс?** — потребители не должны зависеть от методов, которые им не нужны — толстый интерфейс раздувает поверхность изменений и вынуждает реализации на пустые заглушки.
5. **Как DIP связан с DI-контейнером в NestJS?** — DIP — принцип ("зависеть от абстракции, не от конкретики"), DI-контейнер — механизм, который автоматически подставляет конкретную реализацию под объявленную абстракцию, не заставляя сервис создавать зависимости самому.
