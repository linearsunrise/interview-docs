# Clean/Hexagonal Architecture: ports & adapters

> **TL;DR:** Идея одна и та же под разными названиями (Hexagonal/Ports & Adapters Алистера Кокбёрна, Clean Architecture Роберта Мартина, Onion Architecture) — домен (бизнес-логика) не зависит **ни от чего** внешнего: ни от фреймворка, ни от конкретной БД, ни от HTTP. Внешний мир взаимодействует с доменом через **порты** (интерфейсы, которые определяет сам домен), а конкретные технологии (Postgres, Express, Kafka) — это **адаптеры**, реализующие эти порты и подключаемые снаружи. В NestJS это достижимо, но не бесплатно — фреймворк сам по себе построен вокруг декораторов, которые уже "просачиваются" в код, если не изолировать их сознательно.

## Порт — интерфейс, который определяет домен, а не инфраструктура

```ts
// порт — домен объявляет, ЧТО ему нужно, в своих терминах
interface OrderRepository {
  findById(id: OrderId): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

// use case (доменный сервис) зависит ТОЛЬКО от порта — ни слова про TypeORM/Postgres
class PlaceOrderUseCase {
  constructor(private readonly orders: OrderRepository, private readonly payments: PaymentPort) {}
  async execute(cmd: PlaceOrderCommand) {
    const order = Order.create(cmd.items); // доменная логика, без единого импорта из TypeORM
    await this.payments.charge(order.total);
    await this.orders.save(order);
  }
}
```

```ts
// адаптер — конкретная реализация порта, знает про TypeORM/Postgres
@Injectable()
class TypeOrmOrderRepository implements OrderRepository {
  constructor(@InjectRepository(OrderEntity) private readonly orm: Repository<OrderEntity>) {}
  async findById(id: OrderId) { /* маппинг OrderEntity <-> доменный Order */ }
  async save(order: Order) { /* ... */ }
}
```

Направление зависимости — ключевое отличие от обычной слоистой архитектуры (см. [02-layered-architecture.md](./02-layered-architecture.md)): там репозиторий — просто нижний слой, здесь домен **не знает**, что порт вообще будет реализован через TypeORM — интерфейс объявлен в терминах домена (`OrderId`, `Order`), а не в терминах хранилища (`WHERE id = ?`). Зависимость всегда направлена **внутрь**, к домену — инфраструктура зависит от домена, а не домен от инфраструктуры (то же Dependency Inversion Principle, применённое на уровне всей архитектуры, а не отдельного класса — см. [01-solid.md](./01-solid.md)).

## Почему это не бесплатно в NestJS

```ts
// доменная сущность, "чистая" от Nest
class Order {
  private constructor(private readonly items: OrderItem[]) {}
  static create(items: OrderItem[]): Order { /* инварианты создания */ return new Order(items); }
}

// а вот PlaceOrderUseCase уже приходится оборачивать в @Injectable(), чтобы Nest DI его создавал
@Injectable()
class PlaceOrderUseCase { /* ... */ }
```

NestJS сам по себе — фреймворк, построенный вокруг декораторов и DI-контейнера (`@Injectable`, `@Module`, `reflect-metadata` — см. [03-nestjs/01-di-and-providers.md](../03-nestjs/01-di-and-providers.md)). Чтобы use case создавался через контейнер Nest (а не вручную `new`), он обычно помечается `@Injectable()` — формально это уже "знание о фреймворке" в слое, который в чистой гексагональной модели должен быть от него независим. На практике большинство Nest-проектов идут на компромисс: домен (сущности, value objects, чистая бизнес-логика) остаётся без декораторов и импортов из `@nestjs/*`, а слой use case'ов/application services допускает `@Injectable()` как приемлемую цену за использование родного DI — полная изоляция ценой отказа от Nest DI и ручной сборки графа зависимостей редко того стоит.

## Когда это оправдано, а когда — нет

**Оправдано:** сложная предметная область с правилами, которые переживут смену технологий (типичный кейс — финтех/страхование/логистика с долгой жизнью бизнес-правил и вероятной сменой инфраструктуры за годы жизни продукта); нужна тестируемость бизнес-логики без поднятия БД/HTTP (юнит-тесты домена — чистые функции над объектами, без моков фреймворка); несколько входных точек в одну и ту же логику (HTTP API + консьюмер очереди + CLI — все дергают один use case).

**Не оправдано:** типичный CRUD-сервис без сложной бизнес-логики — накладные расходы на порты/адаптеры/маппинг между доменными и ORM-сущностями превышают пользу, когда "домен" — это по сути обёртка над таблицей БД без реальных инвариантов. Оверинжиниринг здесь — реальный риск, который стоит явно называть на собеседовании: гексагональная архитектура — инструмент под конкретную сложность, не универсальный "правильный" способ строить любой сервис.

## Что спрашивают на собеседовании

1. **В чём разница между гексагональной архитектурой и обычной слоистой (controller-service-repository)?** — направление зависимости: в слоистой репозиторий — просто нижний уровень, в гексагональной домен сам объявляет порт в своих терминах, а инфраструктура реализует его снаружи — домен физически не может импортировать ничего из инфраструктурного слоя.
2. **Что такое порт и что такое адаптер?** — порт — интерфейс, определённый доменом ("что мне нужно"), адаптер — конкретная реализация этого интерфейса под конкретную технологию (Postgres, Kafka, HTTP-клиент).
3. **Почему полная гексагональность "дорога" именно в NestJS?** — сам фреймворк построен на декораторах и DI-контейнере — чтобы использовать родной DI, use case-слой обычно всё равно помечается `@Injectable()`, что формально уже связывает его с фреймворком; полная изоляция требует отказа от Nest DI в этом слое.
4. **Когда гексагональная архитектура — оверинжиниринг?** — для простого CRUD без содержательных бизнес-инвариантов: накладные расходы на порты и маппинг между доменными и ORM-сущностями не окупаются, если "домен" — тонкая обёртка над таблицей.
5. **Как гексагональная архитектура облегчает тестирование?** — юнит-тесты бизнес-логики пишутся против портов (простые in-memory реализации/моки), без поднятия реальной БД/HTTP-сервера — домен тестируется в изоляции от инфраструктуры.
