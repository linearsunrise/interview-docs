# Saga: последовательность локальных транзакций и компенсации

> **TL;DR:** Saga — способ провести бизнес-процесс, затрагивающий несколько сервисов/агрегатов, как последовательность **локальных** транзакций (каждая — ACID в рамках своего сервиса), без единой распределённой транзакции. Если шаг N падает, saga не откатывает всё магически (как `ROLLBACK` в обычной транзакции) — она явно выполняет **компенсирующие** действия для уже выполненных шагов 1..N-1, каждое из которых нужно спроектировать отдельно, семантически, а не автоматически.

## Пример: заказ → оплата → резерв склада → доставка

```
Шаг 1: OrderService создаёт заказ (локальная транзакция, свой агрегат)
Шаг 2: PaymentService списывает деньги (локальная транзакция, свой агрегат)
Шаг 3: InventoryService резервирует товар (локальная транзакция, свой агрегат)
Шаг 4: ShippingService планирует доставку (локальная транзакция, свой агрегат)
```

Если шаг 3 падает (товара не хватило), saga не может просто "откатить" шаги 1-2 — денег уже списаны реальным платёжным провайдером, заказ уже реально создан. Вместо этого запускаются **компенсации** в обратном порядке:

```
Компенсация для шага 2: PaymentService.refund(orderId)   -- вернуть деньги
Компенсация для шага 1: OrderService.cancel(orderId)     -- пометить заказ отменённым
```

Ключевое отличие от `ROLLBACK`: компенсация — не "как будто ничего не было", а новое, семантически осмысленное действие ("возврат денег" — это отдельная бизнес-операция со своим следом в системе, не магическое стирание списания). Если шаг 4 (доставка) уже начал выполняться физически (курьер выехал) — компенсация "отменить доставку" может быть невозможна буквально, только "оформить возврат после получения" — компенсирующие действия обязаны проектироваться в терминах реального мира, не в терминах отмены байтов в БД.

## Оркестрация — явный saga-координатор

```ts
class CreateOrderSaga {
  async execute(cmd: CreateOrderCommand) {
    const order = await this.orderService.create(cmd);
    try {
      await this.paymentService.charge(order.id, order.total);
      try {
        await this.inventoryService.reserve(order.id, order.items);
      } catch (e) {
        await this.paymentService.refund(order.id); // компенсация шага 2
        throw e;
      }
    } catch (e) {
      await this.orderService.cancel(order.id); // компенсация шага 1
      throw e;
    }
  }
}
```

Координатор явно знает всю последовательность шагов и соответствующие компенсации для каждого — весь бизнес-процесс читается в одном месте (подробнее про trade-off оркестрации vs хореографии — в [Межсервисная коммуникация: sync vs async](./08-sync-vs-async-communication.md)). На практике вложенные `try/catch` быстро становятся нечитаемыми при росте числа шагов — библиотеки/фреймворки оркестрации саг (например, `@nestjs/cqrs` с явными saga-обработчиками событий, или специализированные движки типа Temporal/Camunda) дают декларативный способ описать шаг + компенсацию без ручной пирамиды `try/catch`.

## Хореография — саги без единого координатора

```ts
@EventsHandler(OrderCreatedEvent)
class ChargePaymentOnOrderCreated { handle(e) { /* PaymentService реагирует сам */ } }

@EventsHandler(PaymentFailedEvent)
class CancelOrderOnPaymentFailed { handle(e) { /* OrderService реагирует сам, компенсация */ } }

@EventsHandler(InventoryReservationFailedEvent)
class RefundOnReservationFailed { handle(e) { /* PaymentService реагирует сам, компенсация */ } }
```

Каждый сервис публикует событие об успехе/неудаче своего шага, следующий по цепочке сервис сам решает реагировать. Компенсации в хореографии — тоже реакция на событие "шаг N провалился", но выполняется тем сервисом, который отвечает за соответствующее действие, а не центральным координатором. Требует особой дисциплины именования и документирования событий — единственный способ понять полный сценарий "что произойдёт при падении оплаты" — это найти все обработчики, подписанные на `PaymentFailedEvent`, по всем сервисам.

## Идемпотентность шагов — обязательное условие

Saga строится поверх async-коммуникации между сервисами (события/сообщения), которая по природе at-least-once (см. [Idempotency keys для POST](../05-api-communication/02-idempotency-keys.md) и [At-least-once / at-most-once / effectively-once; идемпотентные консьюмеры](./14-delivery-guarantees-idempotent-consumers.md)) — каждый шаг и каждая компенсация обязаны быть безопасны для повторного выполнения. `PaymentService.refund(orderId)`, вызванный дважды (например, из-за ретрая), не должен вернуть деньги дважды — обычно достигается тем же приёмом, что и idempotency keys: проверка "уже выполнено?" перед действием, атомарно с самим действием.

## Что спрашивают на собеседовании

1. **Спроектируйте сагу для процесса заказ → оплата → резерв склада → доставка. Что при падении на шаге 3?** — резервирование склада провалилось → компенсация в обратном порядке: возврат денег (компенсация шага 2), отмена заказа (компенсация шага 1); доставка (шаг 4) вообще не запускается.
2. **Чем компенсация отличается от `ROLLBACK`?** — не автоматическая отмена на уровне транзакционного движка, а явно спроектированное семантическое действие (возврат денег — отдельная бизнес-операция), которое может быть даже физически невозможно отменить буквально (например, если товар уже отгружен).
3. **Оркестрация vs хореография саги — какие trade-offs?** — оркестрация: весь процесс виден в одном месте, но координатор связан со всеми участниками; хореография: слабая связность и лёгкость добавления новых реакций, но полный сценарий не описан нигде явно целиком — собирается по подписчикам событий в разных сервисах.
4. **Почему шаги саги обязаны быть идемпотентны?** — коммуникация между сервисами в саге обычно построена на async-доставке с гарантией at-least-once — повторная доставка события/сообщения не должна приводить к повторному выполнению шага или компенсации.
5. **Можно ли всегда гарантированно компенсировать любой шаг?** — нет — некоторые действия необратимы буквально (курьер уже выехал, письмо уже отправлено) — компенсация в таких случаях — не "отмена", а следующий адекватный шаг в реальном мире (оформить возврат после доставки, выслать письмо с извинением).
