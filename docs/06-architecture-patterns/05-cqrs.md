# CQRS: когда разделение читающей/пишущей модели оправдано

> **TL;DR:** CQRS (Command Query Responsibility Segregation) — разделение модели **записи** (команды, меняющие состояние, проходят через бизнес-валидацию и инварианты) от модели **чтения** (запросы, оптимизированные под конкретный UI/отчёт, без бизнес-логики). Ключевая цена — модель чтения может **отставать** от модели записи (eventual consistency), если они физически разнесены (разные таблицы/БД, синхронизируемые через события). Это не "всегда правильная" архитектура — большинство CRUD-сервисов не выигрывают от неё, а платят сложностью синхронизации без реальной пользы.

## Проблема, которую решает разделение

Одна модель на чтение и запись начинает противоречить сама себе по мере роста системы: модель записи хочет быть нормализованной и защищать инварианты (агрегат `Order` с методами `addItem`/`confirm`, см. [DDD: entity, value object, агрегат, bounded context](./04-ddd.md)), модель чтения хочет отдавать данные в форме, удобной конкретному экрану — часто денормализованной, с джойнами из нескольких агрегатов, без валидационной логики вообще (просто спроецированные данные). Компромиссная единая модель обычно получается неудобной для обеих целей одновременно: либо read-запросы вынуждены собирать данные через сложные джойны нескольких агрегатов на лету, либо write-модель обрастает read-специфичными полями/методами, ей не нужными.

```ts
// Command — меняет состояние, идёт через доменную валидацию
class ConfirmOrderCommand { constructor(readonly orderId: string) {} }

@CommandHandler(ConfirmOrderCommand)
class ConfirmOrderHandler implements ICommandHandler<ConfirmOrderCommand> {
  constructor(private readonly repo: OrderRepository, private readonly eventBus: EventBus) {}
  async execute(cmd: ConfirmOrderCommand) {
    const order = await this.repo.findById(cmd.orderId);
    order.confirm(); // доменный инвариант проверяется здесь
    await this.repo.save(order);
    this.eventBus.publish(new OrderConfirmedEvent(order.id)); // модель чтения узнает об этом асинхронно
  }
}

// Query — читает из отдельной, денормализованной read-модели, без бизнес-логики
class GetOrderSummaryQuery { constructor(readonly orderId: string) {} }

@QueryHandler(GetOrderSummaryQuery)
class GetOrderSummaryHandler implements IQueryHandler<GetOrderSummaryQuery> {
  constructor(private readonly readDb: OrderSummaryReadRepository) {}
  execute(query: GetOrderSummaryQuery) {
    return this.readDb.findSummary(query.orderId); // просто SELECT из готовой проекции под конкретный экран
  }
}
```

## `@nestjs/cqrs` — что конкретно даёт

```ts
@Controller('orders')
class OrdersController {
  constructor(private readonly commandBus: CommandBus, private readonly queryBus: QueryBus) {}
  @Post(':id/confirm')
  confirm(@Param('id') id: string) { return this.commandBus.execute(new ConfirmOrderCommand(id)); }
  @Get(':id/summary')
  summary(@Param('id') id: string) { return this.queryBus.execute(new GetOrderSummaryQuery(id)); }
}
```

Модуль даёт инфраструктуру для маршрутизации команд/запросов к обработчикам (`CommandBus`/`QueryBus`) и публикации доменных событий (`EventBus`) — сам по себе не заставляет физически разносить БД чтения и записи. Уровни CQRS на практике — по нарастающей сложности:
1. **Логическое разделение** — разные классы/методы для команд и запросов, но одна и та же БД/таблицы — просто дисциплина кода, почти без цены, часто оправдана даже в простых сервисах.
2. **Разные модели поверх одной БД** — read-модель как денормализованные SQL-views/материализованные представления над теми же таблицами — умеренная цена (обновление view), но всё ещё строго consistent.
3. **Физически разные хранилища** — write в PostgreSQL, read в Elasticsearch/денормализованных таблицах, синхронизация через события — максимальная гибкость под конкретные read-паттерны, но полноценная eventual consistency и инфраструктура синхронизации.

## Eventual consistency между моделями — как с этим жить в UI

Если read-модель обновляется асинхронно (через события из write-модели), между `COMMIT` команды и появлением данных в read-модели существует окно — пользователь, подтвердивший заказ, может на долю секунды увидеть в списке заказов старый статус. Практические решения:
- **Оптимистичное обновление UI** — клиент сразу показывает ожидаемый результат команды, не дожидаясь re-fetch из read-модели (тот же паттерн, что и read-your-writes при чтении с реплики, см. [Репликация](../04-databases/11-replication.md) — концептуально та же проблема, другой механизм);
- **Возврат данных прямо из command-хендлера** — команда может вернуть достаточно данных для немедленного отображения результата, не дожидаясь синхронизации read-модели;
- **UI, явно показывающий "обрабатывается"** — для операций, где мгновенная консистентность некритична (аналитика, отчёты), честнее показать статус "обновляется", чем делать вид, что данные мгновенно синхронны.

## Когда CQRS оправдан, а когда — нет

**Оправдан:** read и write нагрузки сильно асимметричны (на порядки больше чтений, чем записей, и они требуют разных оптимизаций хранения — типичный кейс: дашборды/аналитика поверх транзакционных данных); модель записи содержит сложные инварианты (см. агрегаты в [DDD: entity, value object, агрегат, bounded context](./04-ddd.md)), которые дорого/неудобно было бы поддерживать, если та же модель обслуживает ещё и произвольные read-паттерны; несколько принципиально разных представлений одних данных для разных клиентов (мобильное приложение, admin-панель, публичный API — каждому своя денормализация).

**Не оправдан:** обычный CRUD-сервис без сложных инвариантов и без реальной асимметрии нагрузки — полное разделение стоит инфраструктуры синхронизации (событий, обработчиков, возможно отдельной БД) и когнитивной нагрузки (разработчику нужно всегда думать "это команда или запрос") ради выгоды, которой ещё нет. Как и в разговоре про гексагональную архитектуру ([Clean/Hexagonal: ports & adapters](./03-clean-hexagonal.md)) — это инструмент под конкретную форму сложности, не архитектурный стандарт по умолчанию.

## Что спрашивают на собеседовании

1. **Что такое CQRS и какую проблему он решает?** — расхождение требований к модели записи (нормализация, инварианты) и модели чтения (денормализация под конкретный UI) в единой модели по мере роста системы.
2. **Обязательно ли CQRS означает разные базы данных?** — нет, есть градация от простого логического разделения команд/запросов в коде до полностью физически разных хранилищ — выбор уровня зависит от реальной потребности, не "всё или ничего".
3. **Какие проблемы приносит eventual consistency между моделями чтения и записи?** — окно, где read-модель ещё не отразила только что выполненную команду; решается оптимистичным обновлением UI, возвратом данных прямо из команды, либо честным индикатором "обрабатывается".
4. **Когда CQRS не стоит применять?** — типичный CRUD без сложных инвариантов и без выраженной асимметрии read/write нагрузки — цена синхронизации превышает пользу.
5. **Что даёт `@nestjs/cqrs` конкретно?** — инфраструктуру маршрутизации (`CommandBus`/`QueryBus`) и публикации доменных событий (`EventBus`); сам по себе не обязывает физически разносить хранилища — это отдельное архитектурное решение поверх модуля.
