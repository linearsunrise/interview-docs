# API Gateway, BFF, service discovery

> **TL;DR:** API Gateway — единая точка входа перед множеством микросервисов, решающая кросс-сервисные задачи (аутентификация, rate limiting, маршрутизация) один раз вместо дублирования в каждом сервисе. BFF (Backend for Frontend) — не альтернатива gateway, а дополнительный слой **под конкретного клиента** (веб, мобильное приложение), агрегирующий и адаптирующий данные под его специфичные потребности. Service discovery — как сервисы вообще находят друг друга по сети, когда их адреса не статичны (контейнеры пересоздаются, масштабирование меняет число инстансов).

## API Gateway — что он берёт на себя

```
Клиент → API Gateway → { OrderService, PaymentService, InventoryService, ... }
```

- **Маршрутизация** — единый внешний URL, gateway решает, в какой внутренний сервис направить запрос по пути/заголовку.
- **Аутентификация/авторизация** — проверка токена один раз на входе, а не в каждом сервисе отдельно (хотя авторизация на уровне конкретного ресурса обычно всё равно остаётся внутри сервиса — gateway решает только "кто ты", не всегда "что тебе можно").
- **Rate limiting** — единая точка для ограничения нагрузки от конкретного клиента/API-ключа на всю систему, а не per-service лимиты, которые сложно координировать.
- **Агрегация запросов** (иногда) — один запрос клиента разворачивается в несколько внутренних вызовов, результаты объединяются перед ответом — но эта функция быстро приводит к тому, что gateway начинает знать бизнес-логику агрегации нескольких сервисов, что во многих архитектурах сознательно выносится в отдельный слой (BFF), чтобы gateway оставался тонким и универсальным.
- **Централизованное логирование/трейсинг входящих запросов** — точка, откуда естественно начинается distributed trace ID для всей цепочки вызовов.

Риск: gateway легко превращается в **God-объект** инфраструктуры — если в него начинают закладывать бизнес-логику конкретных доменов ("а давайте в gateway посчитаем скидку"), он становится скрытым монолитом, через который вынуждены проходить изменения любого сервиса, теряя изначальный смысл тонкого универсального слоя.

## BFF — Backend for Frontend

```
Веб-клиент  → Web BFF     → { OrderService, UserService, ... } — агрегирует под десктопный UI, полные данные
Мобильный   → Mobile BFF  → { OrderService, UserService, ... } — агрегирует под мобильный UI, урезанный payload
```

Разные клиенты (веб-SPA, мобильное приложение, публичный партнёрский API) часто нуждаются в существенно разной форме одних и тех же данных: мобильному приложению критична экономия трафика и число round-trip'ов (агрегировать несколько сервисных вызовов в один ответ BFF), десктопному веб-клиенту — полнота данных для богатого UI. Один общий "универсальный" API, пытающийся угодить всем клиентам сразу, обычно превращается либо в переразмеченный (клиент получает лишние поля, которые не использует), либо в компромиссно-неудобный для всех сразу. BFF — отдельный тонкий слой **на команду фронтенда**, которая его использует (часто разрабатывается и деплоится той же командой, что и сам клиент, а не бэкенд-командой) — агрегирует вызовы к нескольким сервисам и формирует ответ именно под нужды конкретного UI.

**BFF vs GraphQL** — похожая мотивация (клиент получает данные в удобной форме за один запрос), разный механизм: BFF — конкретный написанный код под конкретного клиента (негибкий, но простой и предсказуемый по производительности), GraphQL — универсальный язык запроса произвольной формы данных одной схемой на всех клиентов (гибче, но требует защиты от дорогих запросов — см. [GraphQL: резолверы, N+1, DataLoader, complexity limits](../05-api-communication/07-graphql.md)).

## Service discovery — как сервис находит другой сервис по сети

В монолите вызов другого модуля — вызов функции по известному имени. В микросервисах адрес конкретного инстанса сервиса непостоянен: контейнеры пересоздаются с новым IP при рестарте, масштабирование меняет число живых инстансов, деплой заменяет старые инстансы новыми — жёстко прописанный IP/hostname в конфиге ломается при первом же изменении инфраструктуры.

**Client-side discovery** — вызывающий сервис сам спрашивает реестр (Consul, etcd, Eureka) "какие сейчас живые адреса у сервиса X" и сам выбирает конкретный инстанс (часто с балансировкой на своей стороне):
```
OrderService → [спросить у Consul: где InventoryService?] → [10.0.1.5:3000, 10.0.1.9:3000] → выбрать один → вызвать напрямую
```

**Server-side discovery** — вызывающий сервис обращается к известному стабильному адресу (load balancer/service mesh), который сам знает актуальный список живых инстансов и проксирует запрос:
```
OrderService → http://inventory-service (стабильное DNS-имя) → [балансировщик/service mesh сам находит живой инстанс] → InventoryService
```

Server-side discovery проще для вызывающей стороны (не нужна логика поиска и балансировки в каждом клиенте) и типичен для Kubernetes (встроенный DNS для Service-объектов + kube-proxy делают это прозрачно — приложению не нужно знать про реестр вообще, оно просто резолвит стабильное DNS-имя). Client-side discovery даёт больше контроля балансировки на стороне клиента (например, разные стратегии для разных вызовов), но требует явной интеграции с реестром в каждом сервисе.

## Что спрашивают на собеседовании

1. **Зачем нужен API Gateway, если можно обращаться к сервисам напрямую?** — единая точка для кросс-сервисных задач (аутентификация, rate limiting, маршрутизация, логирование входящих запросов), не дублируемых в каждом сервисе отдельно.
2. **В чём разница между API Gateway и BFF?** — gateway — универсальный тонкий слой для всех клиентов и кросс-сервисных задач; BFF — специфичный слой под конкретного клиента (веб/мобильный), агрегирующий данные под его форму — они дополняют друг друга, не взаимозаменяемы.
3. **Почему не стоит закладывать бизнес-логику в API Gateway?** — превращает его в скрытый монолит, через который вынуждены проходить изменения бизнес-логики любого сервиса — теряется изначальный смысл тонкого универсального инфраструктурного слоя.
4. **Что такое service discovery и зачем оно нужно в микросервисах?** — механизм поиска актуальных сетевых адресов сервисов, чьи инстансы непостоянны (пересоздание контейнеров, масштабирование) — жёстко прописанные адреса ломаются при первом изменении инфраструктуры.
5. **Client-side vs server-side discovery — в чём разница?** — client-side: вызывающий сервис сам спрашивает реестр и балансирует; server-side: вызывающий сервис обращается к стабильному адресу (балансировщик/DNS), который сам находит живой инстанс — типично для Kubernetes.
