# Circuit Breaker, retry с exponential backoff + jitter, timeout budget

> **TL;DR:** Retry и Circuit Breaker решают разные проблемы одного семейства. Retry — "эта конкретная попытка вызова могла быть случайной неудачей (сетевой blip, временная перегрузка) — попробуем ещё раз". Circuit Breaker — "этот сервис систематически недоступен прямо сейчас — прекратим засыпать его запросами и дадим ему время восстановиться, вместо того чтобы каждый наш запрос добавлял нагрузку на и без того упавший сервис". Без backoff+jitter ретраи от множества клиентов синхронизируются и превращаются в **retry storm** — сами становятся причиной, по которой упавший сервис не может подняться.

## Retry — почему "просто попробовать ещё раз" опасно без оговорок

```ts
// опасно: мгновенный ретрай без задержки
async function callWithNaiveRetry(fn: () => Promise<unknown>, attempts = 3) {
  for (let i = 0; i < attempts; i++) {
    try { return await fn(); } catch (e) { if (i === attempts - 1) throw e; }
  }
}
```

Если сервис упал из-за перегрузки, мгновенный ретрай **всех** клиентов одновременно только усиливает нагрузку в момент, когда сервису и так плохо — вместо восстановления получаем усугубление. Дополнительно: ретраить стоит только **идемпотентные** операции (см. [05-api-communication/01-rest-semantics.md](../05-api-communication/01-rest-semantics.md)) — повтор неидемпотентного `POST` без защиты может задублировать эффект операции.

## Exponential backoff + jitter

```ts
async function retryWithBackoff<T>(fn: () => Promise<T>, maxAttempts = 5): Promise<T> {
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      return await fn();
    } catch (e) {
      if (attempt === maxAttempts - 1) throw e;
      const baseDelay = 100 * 2 ** attempt;              // экспоненциальный рост: 100, 200, 400, 800...
      const jitter = Math.random() * baseDelay;           // случайная добавка — разводит клиентов по времени
      await new Promise((r) => setTimeout(r, baseDelay / 2 + jitter));
    }
  }
  throw new Error('unreachable');
}
```

**Exponential backoff** — задержка между попытками растёт экспоненциально (не линейно) — если проблема временная, короткая начальная задержка достаточна; если проблема продолжительная, ретраи быстро "разрежаются", не долбя недоступный сервис постоянным потоком. **Jitter** — случайная составляющая в задержке — без неё сотни клиентов, упавших в один момент (например, все получили таймаут от одного и того же перегруженного сервиса), будут ретраить синхронно **все разом** на 2-й, 4-й, 8-й секунде — сами эти синхронизированные волны и есть retry storm, они создают периодические пики нагрузки, которые мешают сервису восстановиться, даже если каждый отдельный клиент "вежливо" ждёт между попытками. Jitter размазывает ретраи по времени, превращая пики в равномерный поток.

## Circuit Breaker — три состояния

```
CLOSED (норма) → [N ошибок подряд/за окно] → OPEN (все запросы мгновенно fail, без похода к сервису)
OPEN → [прошёл timeout] → HALF-OPEN (пропускаем ОДИН пробный запрос)
HALF-OPEN → [пробный успешен] → CLOSED
HALF-OPEN → [пробный неудачен] → OPEN (снова ждём timeout)
```

- **Closed** — обычная работа, запросы идут к сервису как есть; breaker считает ошибки/успехи в скользящем окне.
- **Open** — после того как доля ошибок превысила порог, breaker перестаёт **вообще** пытаться вызывать сервис — все запросы немедленно возвращают ошибку (или fallback) без похода по сети, экономя и время вызывающей стороны (не ждать таймаут на заведомо мёртвый сервис), и нагрузку на упавший сервис (не добавлять запросы в момент, когда он и так не справляется).
- **Half-Open** — по истечении таймаута breaker пропускает пробный запрос (или небольшое их число) — если он успешен, сервис считается восстановившимся, breaker закрывается; если нет — снова открывается на очередной таймаут.

```ts
class CircuitBreaker {
  private state: 'closed' | 'open' | 'half-open' = 'closed';
  private failures = 0;
  private openedAt = 0;

  async call<T>(fn: () => Promise<T>, fallback: () => T): Promise<T> {
    if (this.state === 'open') {
      if (Date.now() - this.openedAt < 30000) return fallback(); // ещё не время пробовать
      this.state = 'half-open';
    }
    try {
      const result = await fn();
      this.failures = 0; this.state = 'closed';
      return result;
    } catch (e) {
      this.failures++;
      if (this.failures >= 5) { this.state = 'open'; this.openedAt = Date.now(); }
      return fallback();
    }
  }
}
```

## Чем Circuit Breaker принципиально отличается от retry

Retry работает на уровне **одного вызова** — "эта попытка не удалась, попробуем снова, может, в этот раз получится". Circuit Breaker работает на уровне **истории вызовов** — "судя по последним N попыткам, сервис систематически недоступен, нет смысла даже пытаться прямо сейчас". Они комплементарны, не взаимозаменяемы: retry без circuit breaker при систематическом отказе сервиса просто умножает нагрузку на него ретраями от каждого клиента; circuit breaker без retry не даёт кода восстановления после единичного случайного сбоя. На практике их комбинируют: retry с backoff+jitter — для отдельных вызовов внутри closed-состояния, circuit breaker — как защита на уровне "стоит ли вообще пытаться" при систематических проблемах.

## Timeout budget — распределение времени по цепочке вызовов

```
Пользователь ждёт ответ API максимум 2000мс
  └─ Gateway → OrderService: timeout 1800мс (небольшой запас на сетевые издержки)
       └─ OrderService → PaymentService: timeout 800мс
       └─ OrderService → InventoryService: timeout 800мс (параллельно с PaymentService)
```

Если каждый сервис в цепочке ставит свой таймаут независимо (например, "у нас всегда таймаут 5 секунд" на каждом хопе), суммарное время ожидания по цепочке из нескольких последовательных вызовов может сильно превысить то, что реально готов ждать конечный пользователь — 5 сервисов по 5 секунд каждый теоретически дают 25 секунд, хотя пользователь давно закрыл вкладку. Timeout budget — общий бюджет времени на всю операцию, явно распределяемый по хопам цепочки (часто прокидывается как поле в запросе, аналогично deadline в gRPC, см. [05-api-communication/10-grpc.md](../05-api-communication/10-grpc.md)) — каждый следующий сервис в цепочке знает, сколько времени у него реально осталось, а не действует по независимому дефолтному таймауту.

## Что спрашивают на собеседовании

1. **Что такое Circuit Breaker, какие у него состояния, чем он отличается от retry?** — closed/open/half-open; retry работает на уровне одной попытки вызова, circuit breaker — на уровне истории вызовов, предотвращая бессмысленные попытки при систематическом отказе.
2. **Почему retry без backoff и jitter опасен?** — retry storm: синхронизированные волны ретраев от множества клиентов создают периодические пики нагрузки на и без того проблемный сервис, мешая ему восстановиться.
3. **Зачем нужен именно jitter, а не только экспоненциальный рост задержки?** — экспоненциальный backoff без jitter всё равно синхронизирует клиентов, упавших в одно время, — они ретраят одновременно на каждом шаге; jitter случайно размазывает их по времени.
4. **Что происходит в half-open состоянии circuit breaker?** — пропускается ограниченное число пробных запросов после таймаута open-состояния — успех переводит breaker обратно в closed, неудача — снова в open на новый таймаут.
5. **Что такое timeout budget и зачем он нужен в цепочке вызовов?** — общий бюджет времени на всю операцию, явно распределяемый между сервисами в цепочке вызовов, чтобы независимые таймауты на каждом хопе в сумме не превысили реальные ожидания конечного пользователя.
