# Слоистая архитектура: controller → service → repository

> **TL;DR:** Три слоя — не формальность ради структуры папок, а правило направления зависимостей: **контроллер знает про сервис, сервис знает про репозиторий, но не наоборот** — репозиторий ничего не знает о HTTP, сервис ничего не знает о том, что вызов пришёл именно из REST-контроллера (а не из очереди сообщений или CLI-команды). Нарушение этого направления — самый частый источник "спагетти" в growing Nest-приложении.

## Зоны ответственности

| Слой | Отвечает за | Не должен делать |
|---|---|---|
| **Controller** | разбор HTTP-запроса (DTO уже провалидирован пайпом), вызов сервиса, маппинг результата в HTTP-ответ | бизнес-логику, прямые обращения к БД, вычисления |
| **Service** | бизнес-логику, оркестрацию нескольких репозиториев/внешних вызовов, транзакционные границы | знание про `Request`/`Response`, HTTP-коды, формат конкретного транспорта |
| **Repository** | доступ к данным (запросы, маппинг строк в сущности) | бизнес-правила, валидацию бизнес-инвариантов |

```ts
@Controller('orders')
class OrdersController {
  constructor(private readonly orders: OrdersService) {}
  @Post()
  create(@Body() dto: CreateOrderDto) {
    return this.orders.create(dto); // контроллер не знает, ЧТО происходит внутри create
  }
}

class OrdersService {
  constructor(private readonly repo: OrdersRepository, private readonly pricing: PricingService) {}
  async create(dto: CreateOrderDto) {
    const total = this.pricing.calculate(dto.items); // бизнес-логика — здесь, не в контроллере и не в репозитории
    return this.repo.save({ ...dto, total });
  }
}

class OrdersRepository {
  constructor(@InjectRepository(Order) private readonly orm: Repository<Order>) {}
  save(data: Partial<Order>) { return this.orm.save(data); } // только доступ к данным, никакой логики
}
```

## Почему направление зависимостей важно, а не просто "три файла"

Если репозиторий начинает знать о HTTP (например, кидает `NotFoundException` из `@nestjs/common` вместо доменной ошибки) — его нельзя переиспользовать вне HTTP-контекста (CLI-скрипт миграции данных, консьюмер очереди) без протаскивания HTTP-специфичных зависимостей туда, где HTTP вообще нет. Если бизнес-логика "утекает" в контроллер (валидация бизнес-правил прямо в хендлере) — та же логика не может быть переиспользована, если тот же сценарий понадобится вызвать не из HTTP (например, из GraphQL-резолвера или scheduled job) — придётся дублировать код или городить костыль вызова контроллера напрямую.

## Частая ловушка — "толстый" сервис, ставший фасадом для всего

```ts
// антипаттерн: сервис на 500+ строк, делает вообще всё про заказы
class OrderService {
  createOrder() {}
  cancelOrder() {}
  refundOrder() {}
  generateInvoice() {}
  sendNotifications() {}
  calculateShipping() {}
  applyPromoCode() {}
  // ...
}
```

Три слоя не защищают от нарушения Single Responsibility внутри самого сервисного слоя (см. [SOLID с примерами из бэкенда](./01-solid.md)) — "service" — это архитектурная роль, а не гарантия того, что весь код внутри неё связан одной ответственностью. На практике growing-сервис делят дальше — по границам use case'ов (`CreateOrderUseCase`, `RefundOrderUseCase`) или по доменным сущностям (см. [DDD: entity, value object, агрегат, bounded context](./04-ddd.md) про bounded context) — трёхслойность и внутреннее деление сервисного слоя — ортогональные решения, оба нужны одновременно на определённом масштабе.

## Где репозиторий превращается в проблему — "анемичная" модель

Если вся бизнес-логика живёт в сервисе, а сущности (`Order`, `User`) — просто структуры данных с геттерами/сеттерами без поведения ("anemic domain model"), это работает нормально для CRUD-подобных сервисов, но плохо масштабируется, когда бизнес-правила становятся сложными (инварианты, которые обязаны соблюдаться при **любом** изменении сущности, а не только через один конкретный сервисный метод) — тогда правило "легко забыть повторить" в соседнем сервисе, который тоже трогает ту же сущность другим путём. DDD-подход (entity с собственными методами, защищающими инварианты) — один из ответов на этот рост сложности, но оправдан не для каждого сервиса — простая CRUD-сущность без сложных правил не выигрывает от переусложнения.

## Что спрашивают на собеседовании

1. **Почему репозиторий не должен знать про HTTP?** — иначе его нельзя переиспользовать вне HTTP-контекста (CLI, консьюмер очереди, другой транспорт) без протаскивания ненужных зависимостей.
2. **Что делать, если сервис разросся до сотен строк с десятком несвязанных методов?** — это нарушение SRP внутри сервисного слоя, а не проблема самой трёхслойности — делить дальше по use case'ам или доменным границам, а не по факту "все методы про Order".
3. **Чем "анемичная" доменная модель отличается от богатой (rich domain model)?** — анемичная — данные без поведения, вся логика в сервисах снаружи; богатая — сущность сама защищает свои инварианты через методы, не позволяя создать себя в невалидном состоянии.
4. **Где граница между тем, что делает контроллер, и тем, что делает сервис?** — контроллер — только транспортный маппинг (разбор запроса, HTTP-коды ответа), сервис — вся бизнес-логика и оркестрация; тест бизнес-логики не должен требовать поднятия HTTP-слоя.
5. **Почему нельзя просто разрешить сервису напрямую выполнять SQL вместо похода через репозиторий?** — смешение ответственности "что делать" и "как хранить" — репозиторий инкапсулирует детали хранения (конкретную ORM/СУБД), позволяя менять их, не трогая бизнес-логику сервиса.
