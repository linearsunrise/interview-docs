# Межсервисная коммуникация: sync vs async, оркестрация vs хореография

> **TL;DR:** Синхронный вызов (HTTP/gRPC) — простой ментально ("вызвал — получил ответ или ошибку сразу"), но временно **связывает** доступность вызывающего сервиса с доступностью вызываемого — если Б недоступен, А тоже не может продолжить. Асинхронная коммуникация (через очередь/брокер сообщений) разрывает эту связь по времени — А публикует событие и продолжает работу, не дожидаясь, пока Б его обработает — ценой того, что "получилось ли в итоге" больше не известно немедленно.

## Sync — простота ценой временной связанности

```ts
// A вызывает B напрямую и ждёт ответа
async function createOrder(dto: CreateOrderDto) {
  const order = await orderRepo.save(dto);
  await inventoryService.reserve(order.items); // HTTP/gRPC вызов к сервису B — блокирует до ответа
  return order;
}
```

Если сервис `inventory` недоступен или медленный — `createOrder` тоже недоступен/медленный, хотя формально проблема не в сервисе заказов. Это называется **temporal coupling** (временная связанность) — А и Б обязаны быть доступны **одновременно**, чтобы операция прошла целиком. Плюс синхронного подхода — простота рассуждения: результат известен сразу (успех/ошибка), не нужно проектировать под "а что если ответ не пришёл вообще".

## Async — развязка по времени ценой неопределённости

```ts
// A публикует событие и НЕ ждёт, пока inventory его обработает
async function createOrder(dto: CreateOrderDto) {
  const order = await orderRepo.save(dto);
  await eventBus.publish(new OrderCreatedEvent(order.id, order.items)); // не блокирует на ответ inventory
  return order; // возвращается сразу, резервирование склада произойдёт асинхронно
}
```

`inventory`-сервис может быть временно недоступен — событие просто подождёт в очереди, пока сервис не поднимется и не заберёт его (при durable-очереди/брокере). Цена — `createOrder` больше не знает синхронно, удалось ли зарезервировать склад: если резервирование в итоге провалится (товара не хватило), об этом нужно узнать отдельным путём — либо через компенсирующее событие обратно (см. [09-saga.md](./09-saga.md)), либо через отдельный статус, который клиент опрашивает/подписывается позже. Асинхронность не убирает сложность распределённой системы — переносит её из "таймаут HTTP-запроса" в "обработка ошибки, обнаруженной позже, в другом месте потока".

## Когда что выбрать

| Критерий | Sync | Async |
|---|---|---|
| Нужен ли результат немедленно, в рамках текущего запроса пользователя | да (например, "доступен ли товар прямо сейчас" для показа на странице) | нет (например, "отправить email после заказа" — не блокирует ответ пользователю) |
| Допустима ли временная связанность доступности сервисов | да, если Б — критичная зависимость с высоким SLA | нет, если Б может быть временно недоступен без потери всей операции |
| Нужна ли гарантированная доставка при недоступности получателя | нет (клиент сам решает, ретраить ли) | да (брокер хранит сообщение до обработки) |
| Природа операции | запрос-ответ (query, проверка) | факт, о котором нужно уведомить (event) — "что-то произошло", не "дай мне ответ" |

Практическое правило: команды/запросы, где вызывающей стороне действительно нужен ответ **сейчас**, чтобы продолжить — sync. Факты о случившемся, на которые могут (но не обязаны прямо сейчас) отреагировать другие части системы — async через события.

## Оркестрация — центральный координатор

```ts
// оркестратор явно вызывает каждый шаг и знает про весь процесс целиком
class OrderOrchestrator {
  async process(orderId: string) {
    await this.paymentService.charge(orderId);      // шаг 1
    await this.inventoryService.reserve(orderId);   // шаг 2
    await this.shippingService.schedule(orderId);   // шаг 3
    // при падении любого шага — оркестратор явно знает, что и в каком порядке компенсировать
  }
}
```

Один сервис (или явный saga-процесс) владеет всей последовательностью шагов, явно вызывает каждый сервис по очереди, знает текущее состояние всего процесса и что делать при падении на любом шаге. Плюс — весь флоу виден в одном месте (легче отлаживать, легче объяснить новому разработчику "как работает оформление заказа"). Минус — оркестратор становится точкой связанности со всеми участвующими сервисами (знает про их API), и потенциальной точкой отказа/бутылочным горлышком, если плохо спроектирован.

## Хореография — реакция на события, без центра

```ts
// OrderService просто публикует факт, ничего не знает про то, кто и как отреагирует
@EventsHandler(OrderCreatedEvent)
class ReserveInventoryHandler {
  handle(event: OrderCreatedEvent) { /* inventory сам решает реагировать на OrderCreated */ }
}
@EventsHandler(InventoryReservedEvent)
class ChargePaymentHandler {
  handle(event: InventoryReservedEvent) { /* payment сам решает реагировать на InventoryReserved */ }
}
```

Каждый сервис публикует события о том, что у него произошло, и реагирует на события, которые ему интересны — никто не знает про процесс целиком, только про свой кусок ("я реагирую на `OrderCreated`, публикую `InventoryReserved`"). Плюс — слабая связность: добавить нового участника процесса (например, отправку SMS-уведомления при резервировании) — просто подписать новый обработчик, ничего не трогая в существующих сервисах. Минус — сам процесс "оформление заказа" нигде не описан явно одним куском кода — чтобы понять полный флоу, нужно собирать его по крупицам из подписчиков в разных сервисах ("кто на что реагирует"), что заметно усложняет отладку и онбординг ("а что вообще происходит, когда создаётся заказ?").

## Что спрашивают на собеседовании

1. **В чём разница между sync и async межсервисной коммуникацией по сути, не по механике?** — sync создаёт временную связанность доступности (оба сервиса должны быть живы одновременно), async её разрывает ценой того, что результат операции больше не известен немедленно.
2. **Когда стоит выбрать синхронный вызов вместо события?** — когда вызывающей стороне нужен результат прямо сейчас, чтобы продолжить обработку текущего запроса пользователя (например, проверка доступности перед показом страницы).
3. **Оркестрация vs хореография — какие trade-offs?** — оркестрация даёт видимость всего процесса в одном месте ценой связанности координатора со всеми участниками; хореография даёт слабую связность и лёгкое добавление новых участников ценой того, что общий флоу не описан явно нигде целиком.
4. **Асинхронность решает проблему распределённой системы или просто откладывает её?** — откладывает и переносит: ошибка обнаруживается не сразу в текущем запросе, а позже, в другом месте потока — сложность распределённости никуда не девается, просто меняет форму.
5. **Как отлаживать хореографию, если процесс "размазан" по подписчикам в разных сервисах?** — distributed tracing с общим correlation/trace ID через всю цепочку событий — без этого действительно приходится вручную собирать флоу по логам каждого сервиса.
