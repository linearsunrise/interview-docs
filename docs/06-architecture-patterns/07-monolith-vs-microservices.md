# Монолит vs модульный монолит vs микросервисы: критерии перехода

> **TL;DR:** Микросервисы решают **организационную** проблему (независимые команды, независимый деплой, независимое масштабирование конкретных частей), а не техническую "монолит медленный/немасштабируемый" — хорошо спроектированный монолит масштабируется горизонтально не хуже (несколько инстансов за балансировщиком). Цена микросервисов — вся сложность распределённой системы (сеть между тем, что раньше было вызовом функции, eventual consistency, наблюдаемость через границы сервисов) появляется сразу и целиком, даже если организационная выгода ещё не нужна. Дефолт для новой системы — модульный монолит; выделение сервисов — по мере **доказанной** необходимости, не заранее "на будущее".

## Три точки на одной шкале, не бинарный выбор

| | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Деплой | один артефакт | один артефакт | независимые артефакты на модуль |
| Границы модулей | размыты, легко нарушить | явные (папки/пакеты + линтер границ), в рамках одного процесса | физические — отдельные процессы/сети |
| Вызов между модулями | прямой вызов функции | прямой вызов функции (в рамках правил границ) | сетевой запрос (HTTP/gRPC/сообщение) |
| Транзакции между модулями | обычная ACID-транзакция БД | обычная ACID-транзакция БД (если одна БД на монолит) | saga/eventual consistency (см. [Saga: choreography vs orchestration, компенсации](./09-saga.md)) |
| Независимое масштабирование частей | нет — только всего целиком | нет — только всего целиком | да — конкретный сервис под конкретную нагрузку |
| Независимый деплой командами | нет — общий релизный цикл | нет — общий релизный цикл | да |

**Модульный монолит** — средняя точка: код физически разделён на модули с явными границами (в Nest — отдельные `Module`, с дисциплиной "не импортировать внутренности чужого модуля напрямую, только через его публичный API/exports" — см. [Структура большого проекта](../03-nestjs/17-project-structure.md)), но всё ещё один процесс, один деплой, одна БД (или явно разделённые схемы в одной БД) — межмодульные вызовы остаются обычными вызовами функций, а не сетевыми запросами. Это даёт большую часть архитектурной дисциплины микросервисов (чёткие границы, невозможность тайком дотянуться до чужих внутренностей) без цены распределённости.

## Что микросервисы реально решают

- **Независимый деплой** — команда A может выкатывать свой сервис несколько раз в день, не координируясь и не блокируясь на релизный цикл команды B.
- **Независимое масштабирование** — сервис с высокой нагрузкой (например, обработка изображений) масштабируется отдельно от остальной системы, не заставляя реплицировать весь монолит целиком ради одной тяжёлой части.
- **Изоляция отказа** — падение одного сервиса (при правильно спроектированной устойчивости — таймауты, circuit breaker, см. [Circuit Breaker, retry с backoff+jitter, timeout budget](./11-circuit-breaker-retry.md)) не обязано валить всю систему целиком, как упавший процесс монолита.
- **Свобода технологического стека** — разные сервисы могут использовать разные языки/БД под свои задачи, если организационно это оправдано (редко реальная причина на старте, чаще — post-hoc обоснование).

## Что микросервисы создают

- **Сетевая ненадёжность на месте, где раньше был вызов функции** — таймауты, частичные отказы, retry-логика — то, о чём вызов метода в монолите вообще не должен был думать.
- **Распределённые транзакции** — операция, затрагивающая несколько сервисов, больше не может быть одной ACID-транзакцией (см. [Distributed transactions: почему 2PC избегают](./15-distributed-transactions-2pc.md)) — нужна saga с компенсациями и явное проектирование под eventual consistency.
- **Наблюдаемость становится обязательной инфраструктурой, не опцией** — без distributed tracing (trace ID, прокидываемый через все сервисы в цепочке запроса) отладка "почему запрос медленный" превращается в гадание по логам десятка сервисов по отдельности.
- **Версионирование контрактов между сервисами** — то, что в монолите решается компилятором (изменил сигнатуру функции — все вызывающие места не скомпилируются), в микросервисах требует явной дисциплины совместимости API (см. [Версионирование API](../05-api-communication/03-api-versioning.md)).
- **Организационные накладные расходы** — больше сервисов, больше пайплайнов CI/CD, больше поверхности для дежурства/мониторинга, больше когнитивной нагрузки "в каком сервисе искать эту логику".

## Критерии, когда реально пора выделять сервис

Не "у нас много кода" и не "модно" — конкретные, проверяемые сигналы:
1. **Организационный масштаб** — количество разработчиков/команд, работающих в одном монолите, начинает создавать реальные конфликты релизов/merge-конфликты, замедляющие всех (эмпирическое правило "команда из двух пицц" — не строгий закон, но ориентир на то, когда координация внутри одной кодовой базы становится узким местом).
2. **Явно разная профиль нагрузки** — конкретный кусок функциональности требует радикально другого масштабирования/ресурсов, чем остальная система (тяжёлая обработка видео vs лёгкие CRUD-эндпоинты).
3. **Явно разный жизненный цикл релиза** — часть системы должна деплоиться в разы чаще/реже остальной (например, ML-модель, обновляемая ежечасно, vs основной API, деплоящийся раз в неделю).
4. **Границы уже доказанно чистые в модульном монолите** — если модуль внутри монолита годами держит чёткие границы (не тянет чужие внутренности, общается только через свой публичный API) — это сильный сигнал, что выделение в отдельный сервис пройдёт безболезненно; если границы постоянно "текут" — выделение только физически зафиксирует существующий бардак в виде сетевых вызовов, не исправит его.

## Strangler Fig — как распиливать существующий монолит

```
1. Новая функциональность в этой предметной области -> сразу пишется в новом сервисе
2. Прокси/gateway перед монолитом постепенно перенаправляет трафик конкретных маршрутов в новый сервис
3. Старая логика в монолите остаётся нетронутой, пока не будет вытеснена полностью
4. Когда весь трафик идёт через новый сервис -> старый код в монолите удаляется
```

Паттерн назван по аналогии с растением-душителем: новая система "обрастает" вокруг старой постепенно, замещая её функцию за функцией, вместо big-bang переписывания с нуля (которое исторически проваливается чаще, чем успевает завершиться — legacy-система продолжает жить и меняться, пока идёт долгая параллельная разработка замены). Начинают обычно с наиболее изолированного по границам модуля (см. критерий 4 выше) — минимальный риск, максимальная валидация подхода на практике перед распилом более связанных частей.

## Что спрашивают на собеседовании

1. **Когда микросервисы — ошибка?** — когда организационная выгода (независимые команды/деплой) ещё не нужна, а система платит полной ценой распределённости (сеть, eventual consistency, наблюдаемость) без реальной пользы — типичная ошибка "микросервисы с первого дня" для команды из 5 человек.
2. **Чем модульный монолит отличается от обычного монолита и от микросервисов?** — явные границы модулей (как в микросервисах), но вызовы между ними остаются в процессе (как в монолите) — не платит за сеть/распределённые транзакции, но даёт архитектурную дисциплину.
3. **Какие проблемы монолита микросервисы реально решают?** — независимый деплой команд, независимое масштабирование конкретных частей под их нагрузку, изоляция отказа при правильном проектировании устойчивости.
4. **Какие проблемы микросервисы создают, которых не было в монолите?** — сетевая ненадёжность на месте бывшего вызова функции, распределённые транзакции вместо ACID, обязательная инфраструктура наблюдаемости, явное версионирование контрактов между сервисами.
5. **Как бы вы начали распиливать монолит?** — Strangler Fig: новая функциональность сразу в новом сервисе, постепенный перенос трафика конкретных маршрутов через прокси, начиная с модуля с самыми чистыми существующими границами.
