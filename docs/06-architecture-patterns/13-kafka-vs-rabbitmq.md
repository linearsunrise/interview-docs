# Kafka vs RabbitMQ: модель (log vs queue), ordering, consumer groups, гарантии доставки

> **TL;DR:** Разница не "что быстрее", а фундаментально разная модель хранения. RabbitMQ — **очередь**: сообщение живёт до тех пор, пока его не заберёт консьюмер, потом (обычно) удаляется. Kafka — **лог**: сообщения хранятся в порядке добавления фиксированное время (или до лимита размера) независимо от того, прочитал их кто-то или нет, и консьюмер сам отслеживает свою позицию (offset) в этом логе — можно перечитать историю заново, чего RabbitMQ в стандартной модели не предполагает.

## Модель хранения — очередь vs лог

```
RabbitMQ (queue): [msg1, msg2, msg3] → consumer забрал msg1 → [msg2, msg3]
                   сообщение исчезает из очереди после ack

Kafka (log):       partition: [msg1, msg2, msg3, msg4, msg5, ...]
                    consumer A: offset=2 (прочитал msg1, msg2, следующий — msg3)
                    consumer B: offset=4 (прочитал больше, независимая позиция)
                    сообщения остаются в логе (retention: время или размер), consumer может перечитать с начала
```

В Kafka чтение сообщения не удаляет его — консьюмер просто продвигает свою позицию (offset) в партиции; несколько независимых консьюмеров (или групп) могут читать один и тот же лог с разных позиций, включая "перечитать с начала", если нужно перестроить проекцию/state после бага в обработчике. В RabbitMQ (в классической модели очередей) сообщение адресовано конкретному потребителю очереди и удаляется после подтверждения — модель "получить и обработать один раз", не "хранилище истории, которое можно передумать и перечитать".

## Ordering — гарантии порядка

```
Kafka: порядок гарантирован ТОЛЬКО внутри одной партиции.
       Сообщения с одним key всегда попадают в одну партицию (hash(key) % partitions) — порядок для этого key гарантирован.
       Порядок МЕЖДУ разными партициями не гарантирован вообще.

RabbitMQ: порядок гарантирован в рамках одной очереди с одним консьюмером.
          Несколько консьюмеров на одну очередь (competing consumers) — порядок обработки уже не гарантирован,
          даже если сообщения отправлены по порядку.
```

Практическое следствие для Kafka: если важен порядок событий по конкретной сущности (все события заказа `order-123` должны обрабатываться строго по порядку), `order-123` используется как partition key — тогда все его события физически попадают в одну партицию и читаются последовательно одним консьюмером этой партиции. Пытаться гарантировать глобальный порядок по всему топику сразу — противоречит самой идее партиционирования (масштабирование за счёт параллельного чтения разных партиций разными консьюмерами).

## Consumer groups и rebalance (Kafka)

```
Topic "orders", 6 партиций
Consumer Group "billing-service": 3 инстанса
  → Kafka распределяет партиции: инстанс 1 читает партиции 0-1, инстанс 2 — партиции 2-3, инстанс 3 — партиции 4-5
```

Все консьюмеры в одной **группе** совместно читают топик — каждая партиция закреплена ровно за одним консьюмером группы в любой момент времени (это и даёт ordering внутри партиции — не два консьюмера читают её одновременно вразнобой). **Rebalance** — процесс переназначения партиций консьюмерам, происходит при изменении состава группы: новый инстанс присоединился (масштабирование), инстанс упал/не прислал heartbeat вовремя — Kafka перераспределяет партиции между оставшимися живыми консьюмерами. Во время rebalance обработка временно приостанавливается (весь consumer group "замирает", пока не завершится переназначение) — при частых передеплоях/автоскейлинге с настройками по умолчанию это может быть заметным источником задержки обработки, отдельная область тюнинга (`session.timeout.ms`, инкрементальный rebalancing вместо stop-the-world).

## RabbitMQ — exchange, routing, competing consumers

RabbitMQ строится вокруг **exchange** (маршрутизирует сообщение в одну или несколько очередей по правилам — direct/topic/fanout/headers) и **очередей**, из которых несколько **competing consumers** могут забирать сообщения — каждое конкретное сообщение достаётся ровно одному из них (round-robin по умолчанию), что даёт естественную балансировку нагрузки между воркерами без ручного партиционирования, как в Kafka. Это ближе к классической модели "очереди задач" (worker queue) — Kafka же по духу ближе к "шине событий с историей", на которую могут подписываться разные независимые системы, каждая со своим темпом чтения.

## Гарантии доставки

И Kafka, и RabbitMQ по умолчанию дают **at-least-once** при правильной настройке подтверждений (Kafka: `acks`, коммит offset после успешной обработки, не до; RabbitMQ: consumer ack после успешной обработки, не auto-ack сразу при получении) — сообщение может быть доставлено повторно (например, консьюмер обработал, но упал до коммита offset/ack — при рестарте получит то же сообщение снова). "Exactly-once" в обоих системах достижимо только при дополнительных усилиях: Kafka предоставляет транзакционный producer + idempotent producer API для exactly-once **внутри самой Kafka** (запись в несколько партиций атомарно), но это не распространяется автоматически на побочные эффекты потребителя (запись в БД, вызов внешнего API) — там всё равно нужен идемпотентный консьюмер (см. [At-least-once / at-most-once / effectively-once; идемпотентные консьюмеры](./14-delivery-guarantees-idempotent-consumers.md)). Утверждение "Kafka гарантирует exactly-once сама, из коробки" без этих оговорок — красный флаг на собеседовании.

## Когда что выбрать

| Критерий | Kafka | RabbitMQ |
|---|---|---|
| Нужна история/replay событий | да, естественно (retention) | нет, сообщение удаляется после обработки |
| Множество независимых консьюмеров одного потока | да, естественно (разные consumer groups читают независимо) | сложнее, нужны отдельные очереди на каждого потребителя (fanout exchange) |
| Сложная маршрутизация (по правилам, приоритеты, TTL на сообщение) | ограниченно | нативно (routing key, приоритеты очередей, per-message TTL) |
| Пропускная способность на большом объёме | очень высокая (оптимизирован под большой throughput) | высокая, но обычно ниже пикового throughput Kafka |
| Простая задача-очередь (worker pool разбирает джобы) | избыточно сложно для этой задачи | естественный fit |

## Что спрашивают на собеседовании

1. **Kafka vs RabbitMQ — как выберете для конкретной задачи?** — зависит от модели: нужна история/replay/множество независимых читателей одного потока — Kafka; нужна классическая очередь задач с гибкой маршрутизацией и без необходимости хранить историю — RabbitMQ.
2. **Как в Kafka гарантируется порядок и что такое consumer group rebalance?** — порядок гарантирован только внутри партиции (сообщения с одним key — в одну партицию); rebalance — переназначение партиций консьюмерам группы при изменении её состава, временно приостанавливающее обработку.
3. **Consumer получил сообщение дважды — как сделать обработку идемпотентной?** — общий паттерн независимо от брокера: таблица обработанных ID сообщений с unique constraint или естественно идемпотентная операция (UPSERT) — подробнее в [At-least-once / at-most-once / effectively-once; идемпотентные консьюмеры](./14-delivery-guarantees-idempotent-consumers.md).
4. **"Kafka гарантирует exactly-once из коробки" — согласны?** — нет без оговорок: транзакционный/idempotent producer даёт exactly-once только для записи внутри самой Kafka; побочные эффекты потребителя (БД, внешние вызовы) всё равно требуют идемпотентного консьюмера.
5. **Чем competing consumers в RabbitMQ отличаются от consumer group в Kafka?** — RabbitMQ распределяет отдельные сообщения между консьюмерами round-robin без привязки к порядку; Kafka закрепляет целые партиции за консьюмерами группы, что и даёт ordering внутри партиции, но требует ручного партиционирования по ключу для контроля порядка.
