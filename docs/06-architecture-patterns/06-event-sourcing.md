# Event Sourcing: суть, проекции, снапшоты — и почему это редко нужно

> **TL;DR:** Вместо хранения **текущего состояния** сущности (`orders.status = 'shipped'`) хранится полная **последовательность событий**, которые к этому состоянию привели (`OrderCreated`, `PaymentReceived`, `OrderShipped`) — текущее состояние всегда можно пересчитать, переиграв события с начала. Даёт бесплатный полный аудит-лог и возможность восстановить состояние на любой момент времени, но платит сложностью на каждом шагу: чтение требует проекций, эволюция схемы событий — версионирования, а "просто исправить одну строчку в БД" перестаёт быть возможным в принципе.

## Механика — состояние как функция от истории событий

```ts
interface DomainEvent { type: string; orderId: string; payload: unknown; occurredAt: Date; }

// текущее состояние — не хранится напрямую, а вычисляется сверткой (reduce) событий
function replay(events: DomainEvent[]): OrderState {
  return events.reduce((state, event) => {
    switch (event.type) {
      case 'OrderCreated': return { ...state, status: 'created', items: event.payload.items };
      case 'PaymentReceived': return { ...state, status: 'paid' };
      case 'OrderShipped': return { ...state, status: 'shipped', trackingId: event.payload.trackingId };
      default: return state;
    }
  }, initialState);
}
```

```sql
-- event store — по сути append-only лог, ничего не UPDATE/DELETE
CREATE TABLE order_events (
  id bigserial PRIMARY KEY,
  order_id uuid NOT NULL,
  type text NOT NULL,
  payload jsonb NOT NULL,
  version int NOT NULL,       -- порядковый номер события для этого order_id — оптимистичный concurrency control
  occurred_at timestamptz DEFAULT now(),
  UNIQUE (order_id, version)
);
```

Хранилище событий (event store) в принципе не поддерживает `UPDATE`/`DELETE` записей — только `INSERT` новых событий; "исправление" ошибки — это новое компенсирующее событие (`OrderCorrected`), а не правка истории. `UNIQUE (order_id, version)` — механизм защиты от конкурентной записи двух событий одновременно (аналог optimistic locking, см. [Блокировки: row-level, FOR UPDATE, advisory, optimistic vs pessimistic](../04-databases/07-locking.md)): если два процесса пытаются добавить событие с одинаковым `version`, второй получает конфликт и обязан перечитать состояние заново.

## Проекции — как читать без переигрывания всей истории на каждый запрос

```ts
// проекция — денормализованная read-модель, обновляемая по мере поступления событий
@EventsHandler(OrderShippedEvent)
class OrderShippedProjectionHandler {
  constructor(private readonly readDb: OrderSummaryReadRepository) {}
  handle(event: OrderShippedEvent) {
    this.readDb.update(event.orderId, { status: 'shipped', trackingId: event.trackingId });
  }
}
```

Переигрывать всю историю событий на каждый `SELECT` — неприемлемо для реальной нагрузки, особенно для сущностей с длинной историей. Проекция — материализованное представление, обновляемое инкрементально по мере появления новых событий (по сути то же самое, что read-модель в CQRS, см. [CQRS: когда оправдано, @nestjs/cqrs](./05-cqrs.md) — Event Sourcing и CQRS часто идут парой, хотя технически независимы друг от друга: можно делать CQRS без Event Sourcing и наоборот). Проекция может быть пересоздана с нуля в любой момент, переиграв весь event store заново — это то, что делает добавление **нового** способа чтения данных (новый отчёт, новая денормализация) дешёвым: не нужна миграция существующих данных, только новый обработчик событий + разовый replay истории.

## Снапшоты — оптимизация, не архитектурный принцип

```ts
// вместо переигрывания 100000 событий с начала — берём снапшот на версии 99000 + доигрываем последние 1000
async function loadOrder(orderId: string): Promise<OrderState> {
  const snapshot = await snapshotStore.getLatest(orderId); // { state, version: 99000 }
  const eventsSince = await eventStore.getEventsAfter(orderId, snapshot.version); // всего 1000 событий
  return replay(eventsSince, snapshot.state);
}
```

Для сущностей с очень длинной историей событий (тысячи+) переигрывание с нуля на каждую загрузку становится дорогим — снапшот периодически (например, каждые 1000 событий) сохраняет уже вычисленное состояние, дальше требуется доиграть только события после снапшота. Это чисто перформансная оптимизация — снапшот не источник истины (его всегда можно пересоздать из event store), просто кэш промежуточного результата свёртки.

## Почему это редко нужно

Полный аудит-лог, time-travel debugging (посмотреть состояние на любой момент прошлого), естественная поддержка сложных отчётов ("сколько заказов было в статусе X на конкретную дату") — реальные преимущества, но нужны далеко не каждому домену. Цена, которую платят всегда, независимо от того, нужны ли эти преимущества конкретному сервису:
- **чтение усложняется структурно** — нельзя просто `SELECT * FROM orders WHERE ...`, нужны проекции под каждый read-паттерн;
- **эволюция схемы событий** — старые события в сторе написаны по старой структуре, новый код должен уметь их прочитать (версионирование событий, upcasting старых версий к новым) — то, чего не существует при хранении текущего состояния (там миграция — одна `ALTER TABLE`, здесь — обязанность поддерживать чтение всех исторических форматов событий вечно);
- **"просто поправить данные руками" перестаёт работать** — в реляционной модели инцидент можно закрыть `UPDATE`; здесь любое исправление — новое событие, требующее продумывания, а не быстрый хотфикс;
- **команда должна думать событийно** — для многих доменов (простой CRUD-каталог, справочники) это чистые накладные расходы без реальной пользы, потому что "история изменений" никому не нужна и не incentivized бизнес-требованиями.

Практический ориентир: Event Sourcing оправдан там, где сама история изменений — часть бизнес-ценности (финансовые операции, где нужен полный аудит; складской учёт с движениями; юридически значимые процессы) — не как способ "сделать архитектуру круче".

## Что спрашивают на собеседовании

1. **В чём суть Event Sourcing?** — хранится последовательность событий, а не текущее состояние; состояние — производная величина, вычисляемая переигрыванием (сверткой) событий.
2. **Зачем нужны проекции, если можно просто переиграть события при чтении?** — переигрывание всей истории на каждый запрос неприемлемо по производительности — проекция инкрементально обновляемая денормализованная read-модель, актуальная без повторного replay.
3. **Что такое снапшот и это архитектурное решение или оптимизация?** — чисто оптимизация производительности загрузки: закэшированное промежуточное состояние на определённой версии, чтобы не переигрывать всю историю с нуля; всегда восстановим заново из event store.
4. **Почему Event Sourcing "редко нужен"?** — цена (сложность чтения через проекции, обязательное версионирование схемы событий, невозможность просто поправить данные руками) оплачивается всегда, а реальная польза (аудит, time-travel) нужна далеко не каждому домену.
5. **Как исправить ошибочно записанное событие в event store?** — никак не редактируя историю — добавляется новое компенсирующее событие, отражающее исправление как отдельный факт, а не переписывание прошлого.
