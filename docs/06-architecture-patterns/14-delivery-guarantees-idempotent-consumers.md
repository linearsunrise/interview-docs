# At-least-once / at-most-once / effectively-once; дедупликация и идемпотентные консьюмеры

> **TL;DR:** Три семантики доставки — это выбор, **что именно** может пойти не так при сбое, не "насколько надёжно" в абстрактном смысле. At-most-once — сообщение может потеряться, но никогда не задублируется. At-least-once — сообщение может задублироваться, но никогда не потеряется. Настоящего exactly-once **на сетевом уровне** между двумя независимыми системами не существует (см. ниже, почему) — то, что обычно называют "exactly-once" в продакшене, — это at-least-once доставка + идемпотентная обработка на стороне потребителя, что эквивалентно ровно однократному **эффекту**, даже если технически сообщение доставлено больше одного раза.

## Три семантики — откуда они берутся

```
At-most-once:  отправитель шлёт сообщение и НЕ ждёт подтверждения (fire-and-forget)
               -> если сообщение потерялось в сети — отправитель об этом не узнает и не повторит
               -> результат: 0 или 1 раз, никогда больше 1

At-least-once: отправитель ждёт подтверждения; если не получил — повторяет
               -> если подтверждение потерялось (сообщение ДОШЛО, но ACK — нет) — повтор задублирует
               -> результат: 1 или больше раз, никогда 0

Effectively-once ("exactly-once" в быту): at-least-once доставка + идемпотентная обработка
               -> сообщение может прийти несколько раз физически, но ЭФФЕКТ применяется один раз
```

Ключевая причина, почему "настоящий" exactly-once на транспортном уровне невозможен, — это частный случай **Two Generals' Problem**: отправитель не может одновременно (а) гарантированно доставить сообщение и (б) гарантированно узнать, что оно доставлено, за конечное число сообщений по ненадёжной сети — всегда остаётся последнее подтверждение, которое само может потеряться, и тогда отправитель не знает, повторять или нет. At-least-once — практический выход: смириться с возможным дублированием на транспорте и решить проблему дублирования уже на уровне бизнес-логики потребителя, где это структурно проще (там есть состояние, БД, возможность запомнить "это я уже обработал").

## Идемпотентный консьюмер — таблица processed_message_ids

```ts
async function handleOrderCreated(event: { id: string; orderId: string; items: Item[] }) {
  await db.transaction(async (tx) => {
    const inserted = await tx.query(
      `INSERT INTO processed_message_ids (message_id) VALUES ($1) ON CONFLICT DO NOTHING RETURNING message_id`,
      [event.id],
    );
    if (inserted.rowCount === 0) return; // уже обработали это сообщение раньше — no-op

    await reserveInventory(tx, event.orderId, event.items); // бизнес-эффект — В ТОЙ ЖЕ транзакции
  });
}
```

Критично, что запись в `processed_message_ids` и сам бизнес-эффект (`reserveInventory`) происходят **в одной транзакции** — если бы они были раздельными операциями, возникла бы та же dual-write проблема, что и в outbox (см. [10-transactional-outbox.md](./10-transactional-outbox.md)): можно записать "обработано", но не выполнить эффект (или наоборот) при падении между шагами. `message_id` берётся из самого события (Kafka: комбинация topic+partition+offset, или явный UUID в payload; RabbitMQ: явный UUID в payload, брокер сам такого ID не даёт) — важно, что это ID **сообщения**, не ID сущности внутри него (`orderId` может повторяться легитимно в разных сообщениях, например `OrderCreated` и `OrderShipped` для одного заказа — они не должны считаться дублями друг друга).

## Естественная идемпотентность — когда отдельная таблица не нужна

```sql
-- UPSERT: повторное применение того же события — no-op по эффекту
INSERT INTO order_status (order_id, status) VALUES ($1, 'shipped')
ON CONFLICT (order_id) DO UPDATE SET status = EXCLUDED.status;

-- атомарный set вместо инкремента: применить дважды — тот же результат
UPDATE inventory SET quantity = $2 WHERE sku = $1; -- не quantity = quantity - N (это НЕ идемпотентно)
```

Не каждая операция нуждается в явной таблице дедупликации — если бизнес-операция **сама по себе** идемпотентна (установка абсолютного значения вместо относительного изменения, `UPSERT` вместо `INSERT`), повторное применение того же события естественно не меняет результат. Правило разделения: команды вида "установи X в Y" — обычно идемпотентны сами по себе; команды вида "измени X на дельту" (`balance -= 10`, `quantity -= N`) — нет, и требуют либо явной дедупликации по ID сообщения, либо перепроектирования в терминах абсолютного состояния там, где это возможно.

## Окно дедупликации — сколько хранить processed_message_ids

Таблица дедупликации не может расти бесконечно — обычно ограничивают окно (например, храня только записи за последние 7 дней, с фоновой очисткой более старых) исходя из максимального реалистичного времени, в течение которого брокер/отправитель может повторно доставить сообщение (retry-политика outbox-relay, retention топика Kafka и т.п. — см. [10-transactional-outbox.md](./10-transactional-outbox.md)). Слишком короткое окно — риск обработать редкий поздний дубль как новое сообщение; бесконечное хранение — не нужная плата по объёму данных ради защиты от событий, которые физически не могут прийти так поздно при данной конфигурации системы.

## Что спрашивают на собеседовании

1. **В чём разница между at-most-once, at-least-once и exactly-once?** — at-most-once рискует потерей сообщения, никогда не дублирует; at-least-once рискует дублированием, никогда не теряет; "exactly-once" на практике — at-least-once доставка плюс идемпотентная обработка, дающая эффект ровно один раз.
2. **Почему настоящий exactly-once на транспортном уровне невозможен?** — частный случай Two Generals' Problem: отправитель не может одновременно гарантировать доставку и гарантированно узнать о ней за конечное число сообщений по ненадёжной сети — последнее подтверждение всегда может потеряться.
3. **Consumer получил одно и то же сообщение дважды — как сделать обработку идемпотентной?** — таблица `processed_message_ids` с unique constraint, запись в неё и бизнес-эффект — в одной транзакции; либо естественная идемпотентность операции (UPSERT, установка абсолютного значения).
4. **Почему запись в таблицу дедупликации и бизнес-эффект должны быть в одной транзакции?** — иначе возникает та же dual-write проблема, что и в outbox — можно зафиксировать "обработано" без реального эффекта или наоборот при падении между шагами.
5. **Почему `balance = balance - 10` не годится для идемпотентной обработки, а `balance = 100` годится?** — относительное изменение (дельта) при повторном применении меняет результат заново; установка абсолютного значения при повторном применении с теми же данными даёт тот же итоговый результат — естественная идемпотентность без явной дедупликации.
