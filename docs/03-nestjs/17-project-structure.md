# Структура большого проекта

> **TL;DR:** Модули по фичам (не по типам файлов), общая инфраструктура — в глобальные/shared модули, границы модулей = границы предметных областей. Открытый вопрос без единственного ответа — на собеседовании важнее аргументация, чем «правильная» схема.

## Базовая схема

```
src/
  main.ts
  app.module.ts
  common/            # то, что не знает о домене
    decorators/  filters/  guards/  interceptors/  pipes/
  config/            # registerAs-конфиги
  modules/
    orders/
      orders.module.ts
      orders.controller.ts
      orders.service.ts
      dto/  entities/
    payments/
      ...
```

Анти-паттерн: папки `controllers/`, `services/`, `dto/` на верхнем уровне («структура по типам») — изменение одной фичи размазывается по всему дереву.

## Ключевые решения, которые надо уметь защищать

- **Экспортировать минимум.** `exports` модуля — его публичный API. Если payments лезет в приватный репозиторий orders — граница нарушена.
- **Общение между фичами:** прямой вызов экспортированного сервиса (просто, но связность) vs события `@nestjs/event-emitter` (развязка, но неявность) vs CQRS (`@nestjs/cqrs`) для сложных доменов.
- **Баррел-экспорты (`index.ts`)** удобны, но регулярно порождают циклические зависимости — экспортировать точечно, только публичное.
- **Global-модули** (Config, Logger) — ок для инфраструктуры; глобальный доменный модуль — запах.
- **Монорепа:** несколько приложений + общие библиотеки — `nest g app` / `nest g library` (workspaces) или Nx. Отдельные пакеты заставляют держать границы честными.
- **Гексагональность по вкусу:** интерфейс репозитория в домене + реализация на ORM в infrastructure. В полный рост нужна не всегда — уровень церемоний должен соответствовать сложности домена.

## Что спрашивают на собеседовании

1. **Как организовать проект на 30+ модулей?** — фичёвые модули, common/ для инфраструктуры, явные exports, события между bounded contexts; показать, что понимаешь *почему*, а не только *как*.
2. **Какие проблемы у баррельных экспортов?** — циклы на уровне файлов (см. [циклические зависимости](./03-circular-dependencies.md)), утечка приватного API, ломается tree-shaking.
3. **Когда CQRS оправдан?** — сложный домен с разными моделями чтения/записи; для CRUD — оверинжиниринг (честность здесь плюс).
4. **Как расшарить код между несколькими Nest-приложениями?** — monorepo с библиотеками (nest workspaces / Nx), версионируемые пакеты — если команды независимые.
5. **Модуль = bounded context?** — хорошая цель: модуль владеет своими данными, наружу — API/события; это же дорожка к выделению микросервиса позже.
