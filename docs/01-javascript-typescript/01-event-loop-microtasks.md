# Event loop: микро- и макротаски

> **TL;DR:** После **каждой** макротаски (таймер, I/O, UI-событие) движок полностью дренирует очередь микротасков (Promise-колбэки, `queueMicrotask`) — и только потом берёт следующую макротаску или рендерит кадр. Это спецификация ECMA-262 + HTML spec, общая для браузера и Node. У Node сверху есть ещё `process.nextTick` — своя очередь с приоритетом выше промисов (детали и фазы event loop самого Node — в [Фазы event loop](../02-nodejs-core/02-event-loop-phases.md), здесь — только JS-движковая часть).

## Порядок на каждом тике

```
1. Взять одну макротаску из очереди (setTimeout, click, I/O-колбэк)
2. Выполнить её синхронный код
3. Дренировать ВСЮ очередь микротасков (включая те, что добавились во время дренирования)
4. (браузер) при необходимости — рендер кадра
5. → следующая макротаска
```

Микротаска, поставленная другой микротаской, выполнится **в этом же цикле дренирования** — не будет ждать следующую макротаску. Отсюда классическая опасность: рекурсивная постановка микротасков (`promise.then` внутри `then`) может надолго заблокировать рендер/следующий колбэк — «microtask starvation».

## Классическая задача

```js
console.log('sync 1');

setTimeout(() => console.log('timeout'), 0);

Promise.resolve()
  .then(() => console.log('promise 1'))
  .then(() => console.log('promise 2'));

queueMicrotask(() => console.log('microtask'));

console.log('sync 2');

// sync 1, sync 2, promise 1, microtask, promise 2, timeout
```

Синхронный код всегда первый (стек не пуст — микротаски не запускаются). Дальше — микротаски в порядке постановки в очередь (FIFO), включая те, что добавились по ходу дренирования. Таймер — только после того, как очередь микротасков опустела.

## `async/await` — это промисы

```js
async function f() {
  console.log('1');
  await null; // эквивалент Promise.resolve(null).then(...)
  console.log('2'); // выполнится как микротаска
}
f();
console.log('3');
// 1, 3, 2
```

Код до первого `await` выполняется синхронно в момент вызова функции. Каждый `await` — точка, где остаток функции превращается в колбэк `.then()`: он ставится в микротаск-очередь, даже если справа от `await` уже готовое значение (не промис — оно оборачивается в `Promise.resolve()`).

## `queueMicrotask` vs `process.nextTick` (Node)

`queueMicrotask` — стандартный API (есть и в браузере), встаёт в ту же очередь, что и `.then()` промисов. `process.nextTick` — специфичен для Node, отдельная очередь, которая дренируется **раньше** промис-микротасков и после каждой синхронной операции, а не только между колбэками цикла. Подробности и почему это может «заморить» I/O — в [node-core doc](../02-nodejs-core/02-event-loop-phases.md).

## Микротаски vs рендер (только браузер)

В браузере рендер кадра встаёт **между** макротасками, но не может произойти, пока не опустеет очередь микротасков — поэтому бесконечная цепочка `.then()` в теории способна заморозить рендер. На собеседовании это часто спрашивают как «почему нельзя злоупотреблять микротасками для длинных цепочек».

## Что спрашивают на собеседовании

1. **Дан сниппет с `setTimeout`, `Promise.then`, синхронным кодом — что выведет?** — разобрать по алгоритму выше: сначала весь sync, потом все микротаски по очереди постановки, потом макротаска.
2. **Чем микротаска отличается от макротаски?** — очередь микротасков дренируется полностью и сразу после текущей задачи/колбэка, до следующей макротаски; макротаски выполняются по одной за тик.
3. **Что если внутри `.then()` ставить новый `.then()` рекурсивно?** — микротаск-очередь никогда не опустеет — «голодание» следующей макротаски/рендера.
4. **Как `async/await` соотносится с промисами?** — синтаксический сахар: `await x` ≈ `x.then(v => остаток_функции)`, остаток всегда идёт через микротаск, даже для не-промис значений.
5. **Чем `queueMicrotask` отличается от `process.nextTick`?** — стандартный API vs Node-специфичный, разные очереди, `nextTick` приоритетнее и опаснее для starvation I/O.
