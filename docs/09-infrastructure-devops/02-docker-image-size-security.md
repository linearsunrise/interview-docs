# Образ: alpine/distroless, `npm ci --omit=dev`, размер и безопасность

> **TL;DR:** Размер образа — не эстетика, а конкретные последствия: дольше `docker pull` при каждом деплое/масштабировании (напрямую влияет на скорость rolling update и время реакции автоскейлинга), больше поверхность для CVE-сканеров находить уязвимости в неиспользуемых системных пакетах. `alpine` — компромисс (минимальный, но с shell и package manager для отладки), `distroless` — дальше по той же оси (совсем ничего лишнего, включая shell — сложнее отлаживать, но меньше что эксплуатировать).

## Базовые образы — сравнение

| Образ | Размер (примерно) | Shell/package manager | Компромисс |
|---|---|---|---|
| `node:20` (Debian-based) | ~1ГБ | полный набор утилит | максимум удобства отладки, минимум безопасности по умолчанию |
| `node:20-slim` | ~200МБ | минимальный Debian, есть shell | компромисс — меньше пакетов, ещё можно `docker exec` и разобраться |
| `node:20-alpine` | ~180МБ | есть (`ash`), `apk` package manager | значительно меньше, использует musl libc вместо glibc (изредка ломает нативные аддоны, скомпилированные под glibc) |
| `gcr.io/distroless/nodejs20` | ~120МБ | **нет shell вообще** | минимальная поверхность атаки, но `docker exec -it ... sh` физически невозможен для отладки |

`alpine` — самый частый практический выбор: заметно меньше Debian-based образов, при этом всё ещё позволяет зайти внутрь контейнера (`docker exec -it container sh`) для диагностики инцидента. Нюанс — musl libc (используемая в Alpine) не бинарно совместима с glibc, на которой обычно собираются нативные Node-аддоны (модули с C++/Rust-биндингами) — иногда это требует пересборки нативных зависимостей внутри alpine-образа или выбора альтернативного не-alpine базового образа для конкретного проблемного пакета.

## Distroless — крайняя точка минимизации

```dockerfile
FROM node:20-alpine AS builder
# ... сборка ...

FROM gcr.io/distroless/nodejs20-debian12
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["dist/main.js"]
```

Distroless-образы (проект Google) содержат только рантайм (в данном случае — сам исполняемый Node) и минимальные системные библиотеки, без shell, package manager, coreutils (`ls`, `cat`, `ps` и т.п.) — если в приложении есть RCE-уязвимость, атакующий, получивший исполнение кода, не может продолжить атаку стандартными Unix-инструментами (нет `sh` для запуска дальнейших команд, нет `wget`/`curl` для скачивания дополнительных инструментов) — это ощутимо сужает практическую эксплуатируемость даже успешной RCE. Цена — стандартная отладка через `docker exec -it ... sh` невозможна вообще, диагностика инцидента требует либо копирования бинарников для отладки в отдельный debug-образ (Google предоставляет `:debug`-теги distroless-образов именно для этого), либо полагаться исключительно на логи/метрики, собираемые снаружи контейнера.

## `npm ci --omit=dev` — воспроизводимая и минимальная установка

```dockerfile
RUN npm ci --omit=dev
```

`npm ci` (в отличие от `npm install`) устанавливает **строго** по `package-lock.json`, без пересчёта дерева зависимостей и без модификации самого lock-файла — детерминированная, воспроизводимая установка, которая либо полностью соответствует зафиксированному lock-файлу, либо явно падает с ошибкой (если `package.json` и `package-lock.json` рассинхронизированы) — то, что нужно именно в CI/CD, где непредсказуемое разрешение версий недопустимо (см. также обсуждение lock-файлов как защиты от supply chain атак в [OWASP Top 10 применительно к Node](../07-security/06-owasp-top10-node.md)). `--omit=dev` пропускает установку `devDependencies` — компилятор TypeScript, тестовые фреймворки, линтеры не нужны в финальном runtime-образе (они уже отработали в builder stage, см. [Docker: слои и кеш, multi-stage build](./01-docker-multistage.md)) — меньше пакетов, меньше потенциальных CVE в зависимостях, которые физически не исполняются в проде.

## Размер образа — конкретные практические последствия

- **Скорость деплоя** — `docker pull` большого образа на каждом узле кластера при rolling update или при добавлении нового узла под нагрузкой (HPA, см. [Kubernetes-базис: pod, deployment, service, ingress, configmap/secret, HPA](./04-kubernetes-basics.md)) — задержка масштабирования напрямую зависит от того, сколько мегабайт/гигабайт нужно скачать, прежде чем новый под сможет стартовать.
- **Поверхность CVE-сканирования** — инструменты типа Trivy/Snyk Container сканируют образ на известные уязвимости во всех установленных системных пакетах; лишние утилиты (компиляторы, отладчики, полный набор coreutils), не используемые приложением, всё равно добавляют потенциальные CVE в отчёт, требующие триажа, даже если реально не эксплуатируемы (не используются).
- **Кеш слоёв на узлах кластера** — Kubernetes-узлы кешируют уже скачанные слои образов; частая пересборка с изменяющимся базовым слоем (например, если базовый образ не запинен к конкретной версии и подтягивает новый `latest` при каждой сборке) снижает эффективность этого кеша между деплоями.

## Что спрашивают на собеседовании

1. **Чем `alpine` отличается от обычного `node` образа и от `distroless`?** — alpine значительно меньше стандартного Debian-based образа за счёт musl libc и минимального набора пакетов, но сохраняет shell для отладки; distroless идёт дальше — убирает shell и coreutils вообще, оставляя только рантайм, что сужает эксплуатируемость RCE, но полностью убирает возможность `docker exec` для диагностики.
2. **Почему `npm ci` предпочтительнее `npm install` в Docker-сборке/CI?** — детерминированная установка строго по lock-файлу без пересчёта дерева зависимостей — воспроизводимость между сборками и явная ошибка при рассинхроне манифеста и lock-файла, вместо тихого "разрешения по-своему".
3. **Зачем нужен `--omit=dev` в финальном образе, если сборка уже прошла на предыдущем stage?** — dev-зависимости (компилятор, тесты, линтер) физически не нужны для выполнения уже скомпилированного `dist/` — меньше пакетов в runtime-образе, меньше потенциальных CVE, которые не эксплуатируемы, потому что код не исполняется.
4. **Почему размер образа влияет не только на диск, но и на скорость деплоя/масштабирования?** — `docker pull` большого образа на каждый узел при rolling update или добавлении нового узла под HPA-масштабированием — задержка напрямую пропорциональна объёму данных для скачивания перед стартом пода.
5. **В чём практический риск distroless-образов и как с ним живут?** — невозможность зайти внутрь контейнера для отладки инцидента; решается через отдельные `:debug`-теги того же образа для локальной диагностики и полагание на внешние логи/метрики/трейсинг вместо интерактивной отладки в проде.
