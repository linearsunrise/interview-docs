# Деплой: rolling, blue-green, canary; feature flags

> **TL;DR:** Три стратегии решают один и тот же вопрос — как перевести трафик со старой версии на новую с минимальным риском — разными компромиссами между скоростью, стоимостью ресурсов и точностью обнаружения проблем. Rolling — постепенная замена подов, дёшево, но откат не мгновенный. Blue-green — два полных окружения, мгновенное переключение и откат, но двойные ресурсы на время деплоя. Canary — малая доля трафика на новую версию с метриками и постепенным наращиванием — лучше всего ловит проблемы до полного раската, но сложнее в реализации. Feature flags — отдельная ось: разделяют момент деплоя кода от момента его активации для пользователей.

## Rolling update — постепенная замена, дефолт в Kubernetes

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
```

```
3 пода v1 → создать 1 под v2 (surge) → дождаться Ready → убить 1 под v1 → повторить, пока все не станут v2
```

Постепенно заменяет старые поды новыми, поддерживая заданный уровень доступности на всём протяжении (`maxUnavailable: 0` — количество доступных подов никогда не падает ниже желаемого числа реплик). Не требует дополнительных ресурсов сверх `maxSurge` (обычно 1 лишний под временно) — самая ресурсно-дешёвая стратегия. Недостаток — на протяжении деплоя одновременно работают **обе** версии кода, что требует совместимости между ними (см. expand-contract для схемы БД в [Миграции БД в деплое: expand-contract](./14-db-migrations-deploy.md)), и откат не мгновенный — тот же постепенный процесс в обратную сторону, если новая версия оказалась проблемной уже после того, как её раскатили на часть подов.

## Blue-green — два полных окружения, мгновенное переключение

```
Blue (текущая, v1, принимает весь трафик)   Green (новая, v2, полностью развёрнута, трафика ещё нет)
                    ↓ переключение балансировщика/DNS одномоментно
Blue (простаивает, готова к мгновенному откату)   Green (v2, принимает весь трафик)
```

Новая версия разворачивается **полностью** параллельно со старой (оба окружения — с полным набором реплик, готовы принимать 100% нагрузки), но трафик всё ещё идёт на старую (blue). Переключение — одномоментное изменение точки входа (обновление Service selector'а, DNS, балансировщика) — весь трафик мгновенно переходит на green. Откат — так же мгновенен: переключить точку входа обратно на blue, которая всё ещё полностью развёрнута и не тронута. Цена — на время существования обоих окружений требуется **вдвое больше** вычислительных ресурсов, чем в норме — оправдано, когда мгновенность отката важнее экономии ресурсов (критичные сервисы, где даже несколько минут постепенного отката при rolling update неприемлемы).

## Canary — малая доля трафика, метрики, постепенное наращивание

```
95% трафика → v1 (stable)
 5% трафика → v2 (canary) — метрики error rate/latency v2 сравниваются со stable в реальном времени
   если метрики в норме → постепенно увеличить долю canary (5% → 25% → 50% → 100%)
   если метрики хуже    → автоматический откат canary до 0%, весь трафик обратно на stable
```

Новая версия получает **малую** контролируемую долю реального трафика, а не либо 0%, либо 100%, как в rolling/blue-green по отдельному поду — метрики этой малой доли (error rate, latency, бизнес-метрики) сравниваются со stable-версией автоматизированно, и решение о дальнейшем раскате (увеличить долю canary) или откате (вернуть 0%) принимается на основе этого сравнения, а не просто "задеплоилось без ошибок при старте". Это лучше всего ловит проблемы, проявляющиеся только под реальной пользовательской нагрузкой/данными (а не на этапе readiness-проверки при старте пода) — но требует дополнительной инфраструктуры: механизма гранулярного распределения трафика по процентам (service mesh типа Istio, или продвинутый Ingress-контроллер), системы метрик для автоматизированного сравнения (см. [Метрики: Prometheus, RED/USE, гистограммы](./10-metrics-prometheus.md)), и, в продвинутых реализациях, автоматизированного отката по порогам без участия человека.

## Сравнение

| | Rolling | Blue-green | Canary |
|---|---|---|---|
| Дополнительные ресурсы | минимальные (surge) | 2x на время деплоя | минимальные (малая доля) |
| Скорость отката | постепенная (обратный rolling) | мгновенная (переключение обратно) | быстрая (снизить долю до 0%) |
| Обнаружение проблем | по готовности подов (readiness) | по готовности + ручное решение после переключения | автоматизированное сравнение метрик под реальной нагрузкой |
| Сложность инфраструктуры | низкая (встроено в Kubernetes Deployment) | средняя (два полных окружения, механизм переключения) | высокая (гранулярный split трафика, автоматизированный анализ метрик) |
| Совместимость старой/новой версии | обязательна (обе работают одновременно) | не требуется (переключение атомарно для конкретного запроса) | обязательна (обе работают одновременно на реальном трафике) |

## Feature flags — отдельная ось, разделяющая деплой и релиз

```ts
if (featureFlags.isEnabled('new-checkout-flow', { userId })) {
  return newCheckoutFlow();
}
return legacyCheckoutFlow();
```

Стратегии выше — про то, **как** код физически попадает в прод. Feature flags — про то, **когда** этот код становится видимым/активным для пользователей, что структурно отдельный вопрос: код с новой функциональностью может быть задеплоен (физически присутствует и работает в проде) значительно раньше, чем flag включён для реальных пользователей — деплой перестаёт быть рискованным моментом сам по себе (код просто есть в бинарнике, но неактивен), а активация функциональности становится отдельным, гранулярным, обратимым **без нового деплоя** решением (включить flag для 1% пользователей, для конкретного tenant'а, мгновенно откатить простым изменением значения flag, а не редеплоем). Это то, что делает возможным "деплоить часто, релизить осторожно" — частота деплоев кода перестаёт быть связана с риском для пользователей.

## Что спрашивают на собеседовании

1. **Canary vs blue-green — trade-offs, что нужно для canary?** — blue-green проще (два полных окружения, атомарное переключение), но требует двойных ресурсов и решение об откате обычно принимает человек после переключения; canary экономнее по ресурсам и лучше ловит проблемы под реальной нагрузкой за счёт автоматизированного сравнения метрик, но требует инфраструктуры гранулярного split трафика и системы метрик.
2. **Почему rolling update — дефолт в Kubernetes, а не более "безопасный" blue-green?** — не требует дополнительных ресурсов сверх небольшого surge, встроен в стандартный механизм Deployment без дополнительной инфраструктуры — разумный компромисс по умолчанию, blue-green/canary добавляются поверх для сервисов, где их конкретные преимущества (мгновенный откат, метрики-driven раскат) оправдывают сложность.
3. **Что общего у rolling update и canary с точки зрения требований к коду?** — обе версии (старая и новая) работают одновременно и обслуживают реальный трафик параллельно — код и схема БД должны быть совместимы в обе стороны на всём протяжении деплоя (expand-contract).
4. **Зачем нужны feature flags, если уже есть canary-деплой?** — решают другую задачу: canary — про постепенный перевод трафика на новую версию кода; feature flags — про включение/выключение конкретной функциональности независимо от факта деплоя, гранулярно (по пользователю/tenant'у) и мгновенно обратимо без нового деплоя вообще.
5. **Как реализовать автоматический откат canary?** — непрерывное сравнение метрик error rate/latency (см. RED-метрики в [Метрики: Prometheus, RED/USE, гистограммы](./10-metrics-prometheus.md)) canary-версии со stable в реальном времени; при превышении заданных порогов — автоматическое снижение доли трафика canary до нуля без ожидания ручного решения.
