# 12-factor app — своими словами

> **TL;DR:** 12-factor — не список произвольных правил, а согласованный набор принципов вокруг одной идеи: приложение должно быть легко **разворачиваемым, масштабируемым и заменяемым** в облачной среде — большинство факторов прямо следуют из требования statelessness и строгого разделения кода/конфигурации/состояния. На собеседовании ценнее не пересказать список по памяти, а связать каждый пункт с уже разобранными темами (многие факторы — это просто другой ракурс на то, что уже обсуждалось отдельно).

## Двенадцать факторов — коротко и со ссылками на то, где уже разобрано подробнее

1. **Codebase** — одна кодовая база, отслеживаемая в системе контроля версий, множество деплоев (dev/staging/prod) из неё же — не форкать код под каждое окружение отдельно.

2. **Dependencies** — явно объявлять все зависимости (`package.json`/`package-lock.json`), не полагаться на то, что что-то "уже стоит" в окружении — тот же принцип, что даёт `npm ci` воспроизводимость сборки (см. [02-docker-image-size-security.md](./02-docker-image-size-security.md)).

3. **Config** — конфигурация (адреса БД, ключи API, feature-флаги) хранится в окружении (переменные окружения), не в коде — один и тот же артефакт (Docker-образ) переиспользуется между dev/staging/prod без пересборки, различаясь только конфигурацией снаружи (ConfigMap/Secret в Kubernetes, см. [04-kubernetes-basics.md](./04-kubernetes-basics.md)).

4. **Backing services** — база данных, очередь, кеш — трактуются как подключаемые ресурсы через URL/креды в конфигурации, взаимозаменяемые без изменения кода (локальный Postgres и managed Postgres в облаке — для приложения неотличимы, просто другая строка подключения).

5. **Build, release, run** — строго разделённые стадии: build (компиляция/сборка образа) → release (build + конкретная конфигурация конкретного окружения) → run (запуск конкретного release) — нельзя менять код на стадии run, откат — это переключение на предыдущий release, не правка кода на лету.

6. **Processes** — приложение выполняется как один или несколько **stateless** процессов, разделяемое состояние — только во внешних backing services (БД, Redis), не в памяти процесса — фундамент горизонтального масштабирования (см. [08-performance-reliability/04-scaling-load-balancing.md](../08-performance-reliability/04-scaling-load-balancing.md)).

7. **Port binding** — сервис самодостаточен и сам слушает свой порт (Node/Express/Nest сами поднимают HTTP-сервер), не полагаясь на внешний веб-сервер контейнера для обслуживания запросов — приложение экспортирует себя как сервис через порт, который дальше маршрутизируется Service/Ingress (см. [04-kubernetes-basics.md](./04-kubernetes-basics.md)).

8. **Concurrency** — масштабирование через запуск дополнительных процессов/подов (горизонтально), не через усложнение одного процесса потоками внутри себя — тот же аргумент "больше stateless-инстансов" против "один супер-процесс" из фактора Processes, применённый именно к вопросу роста нагрузки.

9. **Disposability** — быстрый старт и graceful shutdown — процесс можно запустить или остановить в любой момент без потери данных или деградации сервиса; корректная обработка `SIGTERM` — прямая реализация этого фактора (см. [03-container-signals-pid1.md](./03-container-signals-pid1.md) и [02-nodejs-core/10-graceful-shutdown.md](../02-nodejs-core/10-graceful-shutdown.md)).

10. **Dev/prod parity** — минимизировать разрыв между окружением разработки и продом (та же версия backing services, тот же способ деплоя, минимальный временной разрыв между написанием кода и его выкаткой) — Docker сам по себе — практический инструмент достижения этого фактора, один и тот же образ бежит везде.

11. **Logs** — трактовать логи как **поток событий**, а не управлять файлами логов внутри приложения (ротация, архивация — не забота самого приложения) — просто писать в `stdout`, окружение (Kubernetes + система сбора логов) само решает, куда это направить и как хранить (см. [09-structured-logging.md](./09-structured-logging.md)).

12. **Admin processes** — одноразовые административные задачи (миграции БД, скрипты очистки данных) запускаются как отдельные, короткоживущие процессы в том же окружении и с тем же кодом, что и основное приложение — не отдельным, рассинхронизированным набором ad-hoc скриптов.

## Где 12-factor не работает буквально — осознанные отступления

12-factor писался в контексте Heroku-подобных PaaS начала 2010-х — часть рекомендаций требует адаптации к реальной практике 2020-х, и на собеседовании честнее признать это, чем повторять список как догму:

- **Config строго через env-переменные** — на практике часто дополняется/заменяется структурированными ConfigMap/Secret-объектами Kubernetes или vault-системами (см. [07-security/14-secrets-management.md](../07-security/14-secrets-management.md)) — сам принцип (конфигурация отдельно от кода, единый артефакт на все окружения) сохраняется, конкретный механизм — эволюционировал.
- **Один процесс на "process type"** — worker threads и cluster mode (см. [02-nodejs-core/05-workers-cluster.md](../02-nodejs-core/05-workers-cluster.md)) внутри одного контейнера — распространённая практика, формально не совсем "один процесс = одна единица масштабирования", но прагматично оправданная для эффективного использования многоядерных узлов без раздувания числа отдельных подов.
- **Logs исключительно как stdout-поток** — иногда дополняется структурированной отправкой напрямую в систему трейсинга/APM (см. [11-distributed-tracing-otel.md](./11-distributed-tracing-otel.md)) для данных, которым нужна более богатая структура, чем плоский поток логов — не замена stdout-логированию, а дополнение для конкретного класса телеметрии.

## Что спрашивают на собеседовании

1. **Расскажите 12-factor и где вы отступали от него осознанно.** — не пересказ списка, а связка с практикой: конфигурация через ConfigMap/Secret вместо чистых env-переменных, worker threads/cluster внутри одного "process type", дополнение stdout-логов структурированным трейсингом — с объяснением, почему это прагматичная адаптация, а не нарушение духа принципа.
2. **Какой фактор из 12 напрямую связан с горизонтальным масштабированием?** — Processes (statelessness) и Concurrency (масштабирование через добавление процессов, не через усложнение одного) — оба формализуют то же требование, что разобрано отдельно для load balancing и HPA.
3. **Почему конфигурация должна храниться в окружении, а не в коде?** — один и тот же артефакт (образ) переиспользуется между всеми окружениями без пересборки — различие только в конфигурации снаружи, что упрощает и ускоряет процесс деплоя и снижает риск "работает у меня, не работает в проде" из-за случайно закоммиченной специфичной для конкретного окружения константы.
4. **Как фактор Disposability связан с обработкой сигналов в контейнере?** — быстрый старт и корректный graceful shutdown по `SIGTERM` — прямая реализация этого фактора; без правильной обработки сигналов (см. проблему PID 1) disposability нарушается — процесс не может быть остановлен без потери в процессе данных/соединений.
5. **Почему 12-factor рекомендует логи как поток stdout, а не файлы, управляемые самим приложением?** — приложение не должно заботиться о ротации/архивации/маршрутизации логов — это ответственность окружения выполнения (в контейнерах — сборщик логов платформы), приложение просто эмитит поток событий, оставаясь проще и не зависящим от конкретной инфраструктуры хранения логов.
