# Трейсинг: OpenTelemetry, распространение контекста между сервисами и через очереди

> **TL;DR:** Логи и метрики (см. [09-structured-logging.md](./09-structured-logging.md), [10-metrics-prometheus.md](./10-metrics-prometheus.md)) отвечают на "что происходило" и "сколько это стоило в среднем/по перцентилям" — трейсинг отвечает на "куда конкретно ушло время внутри **одного** запроса, прошедшего через несколько сервисов". Трейс — дерево **спанов** (span — одна временная операция с началом/концом), связанных родитель-потомок; propagation — механизм, которым это дерево остаётся единым, даже когда обработка запроса физически переходит из процесса в процесс через сеть.

## Trace, span, parent-child

```
Trace (весь запрос целиком, единый traceId)
├── Span: HTTP POST /orders (Gateway)          [0ms   -- 450ms]
│   ├── Span: OrderService.create              [10ms  -- 440ms]
│   │   ├── Span: PaymentService.charge (RPC)  [20ms  -- 280ms]
│   │   │   └── Span: DB query (внутри Payment)[30ms  -- 260ms]
│   │   └── Span: InventoryService.reserve     [285ms -- 430ms]
│   │       └── Span: DB query (внутри Inventory) [290ms -- 420ms]
```

Каждый span — конкретная операция с точным началом и концом (HTTP-вызов, SQL-запрос, обработка сообщения из очереди) — вложенность спанов (parent-child) отражает реальную структуру вызовов: `OrderService.create` породил вызов `PaymentService.charge`, который внутри себя сделал ещё и SQL-запрос. Визуализация этого дерева (waterfall-диаграмма в Jaeger/Grafana Tempo/Zipkin) сразу показывает, где именно из 450мс общей длительности запроса реально ушло время — в данном примере видно, что `PaymentService.charge` (260мс) — самая длинная часть, и внутри неё почти всё время съедает сам SQL-запрос (230мс из 260) — конкретная, actionable точка для оптимизации, которую невозможно так же прямо увидеть по агрегированным метрикам или разрозненным логам разных сервисов.

## OpenTelemetry — вендоронейтральный стандарт

```ts
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  instrumentations: [getNodeAutoInstrumentations()], // авто-инструментация HTTP, БД-клиентов, и т.п.
});
sdk.start();
```

OpenTelemetry (OTel) — открытый стандарт (объединивший ранее конкурировавшие OpenTracing и OpenCensus) для генерации, сбора и экспорта трейсов/метрик/логов, не привязанный к конкретному бэкенду хранения и визуализации — один и тот же инструментированный код может экспортировать данные в Jaeger, Grafana Tempo, Datadog, honeycomb.io или любую другую OTel-совместимую систему, просто сменив exporter в конфигурации, без переинструментирования самого приложения. Auto-instrumentation библиотеки (`@opentelemetry/auto-instrumentations-node`) автоматически оборачивают популярные модули (`http`, `express`, `pg`, клиенты БД) — базовые спаны на HTTP-запросы и SQL-запросы появляются без единой строчки ручного кода трейсинга в бизнес-логике; ручная инструментация (`tracer.startSpan()`) добавляется точечно для важных доменных операций, которые auto-instrumentation не видит (специфичная бизнес-логика внутри сервиса).

## Propagation — как контекст трейса переживает сетевой переход

```
Сервис A → HTTP-запрос к сервису B
Заголовок: traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                        │  └─ traceId (32 hex)  ─┘└─ spanId (16 hex)  ─┘└ flags
```

Без propagation каждый сервис, получив запрос, начал бы **новый** независимый трейс — трейсы разных сервисов, обрабатывающих один и тот же логический запрос пользователя, никак не связались бы друг с другом, и получилась бы россыпь несвязанных фрагментов вместо единого дерева. [W3C Trace Context](https://www.w3.org/TR/trace-context/) стандартизирует заголовок `traceparent`, который сервис A прикладывает к исходящему запросу к сервису B — B, получив этот заголовок, продолжает **тот же** `traceId`, создавая свои спаны как потомков переданного `spanId`, вместо генерации нового независимого трейса. OTel auto-instrumentation обычно делает это автоматически для HTTP-клиентов/серверов — разработчику не нужно вручную парсить и прокидывать заголовок в типичном REST/gRPC-взаимодействии.

## Propagation через очереди — не только HTTP-заголовки

```ts
// producer: инжектирует контекст трейса В САМО сообщение, не в HTTP-заголовок (которого здесь нет)
import { propagation, context } from '@opentelemetry/api';

const carrier: Record<string, string> = {};
propagation.inject(context.active(), carrier);
await queue.add('process-order', { orderId, traceContext: carrier });

// consumer: восстанавливает контекст из данных сообщения, продолжает ТОТ ЖЕ трейс
const extractedContext = propagation.extract(context.active(), job.data.traceContext);
context.with(extractedContext, () => {
  // спаны, созданные здесь, — потомки исходного трейса, а не начало нового
});
```

HTTP-заголовки — не единственный канал распространения — когда обработка запроса переходит через асинхронный брокер сообщений (Kafka, RabbitMQ, BullMQ, см. [06-architecture-patterns/13-kafka-vs-rabbitmq.md](../06-architecture-patterns/13-kafka-vs-rabbitmq.md)), заголовков в привычном HTTP-смысле нет — контекст трейса нужно явно **сериализовать в метаданные самого сообщения** на стороне producer'а и **десериализовать** на стороне consumer'а. Без этого шага трейс обрывается на границе очереди — та часть обработки, что происходит асинхронно после постановки в очередь (например, отправка email после создания заказа, см. [08-performance-reliability/09-queues-bullmq.md](../08-performance-reliability/09-queues-bullmq.md)), выпадает из общего дерева трейса исходного запроса пользователя, даже если логически является его прямым продолжением.

## Что спрашивают на собеседовании

1. **Как устроен трейсинг: что такое trace и span?** — trace — единый идентификатор всего логического запроса, span — конкретная операция с началом/концом внутри него; спаны образуют дерево parent-child, отражающее реальную структуру вложенных вызовов между сервисами и внутри них.
2. **Что такое OpenTelemetry и зачем нужен именно стандарт, а не проприетарная библиотека конкретного APM-вендора?** — вендоронейтральный стандарт генерации/сбора/экспорта телеметрии — один и тот же инструментированный код экспортирует данные в любую OTel-совместимую систему визуализации, без переинструментирования приложения при смене бэкенда.
3. **Как контекст трейса распространяется между HTTP-сервисами?** — заголовок `traceparent` (W3C Trace Context), содержащий `traceId` и `spanId` родительского спана — получающий сервис продолжает тот же trace, создавая свои спаны как потомков, вместо генерации нового независимого трейса.
4. **Как распространить трейс через очередь сообщений, где нет HTTP-заголовков?** — явная сериализация контекста трейса в метаданные самого сообщения на стороне producer'а (`propagation.inject`) и десериализация на стороне consumer'а (`propagation.extract`) — без этого шага трейс обрывается на границе очереди.
5. **Чем трейсинг дополняет логи и метрики, а не дублирует их?** — метрики дают агрегированную картину (сколько, как часто, какие перцентили), логи — дискретные события с деталями, трейсинг — точную временную структуру одного конкретного запроса через несколько сервисов, показывая, где именно внутри него ушло время, чего не даёт ни агрегат метрик, ни разрозненные лог-строки разных сервисов.
