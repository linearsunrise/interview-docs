# Requests/limits, OOMKilled и связь с `--max-old-space-size`

> **TL;DR:** `requests` — гарантированный минимум ресурсов, используемый планировщиком для решения "на какой узел поместить под" (сумма requests всех подов на узле не должна превышать ёмкость узла). `limits` — жёсткий потолок: превышение CPU-лимита приводит к throttling (под просто работает медленнее, не убивается), превышение memory-лимита приводит к мгновенному `SIGKILL` (OOMKilled) — асимметрия, которую часто не осознают. Node/V8 по умолчанию управляет размером heap исходя из памяти **хоста**, а не контейнера — без явной настройки `--max-old-space-size` V8 может пытаться вырастить heap до предела, недостижимого раньше, чем сработает OOMKilled от cgroup-лимита контейнера.

## Requests vs limits — разная роль, разное поведение при превышении

```yaml
resources:
  requests: { cpu: "250m", memory: "256Mi" }   # гарантированный минимум, для планировщика
  limits: { cpu: "500m", memory: "512Mi" }     # жёсткий потолок
```

- **CPU limit превышен** — процесс не убивается, а **throttling**: cgroup ограничивает долю процессорного времени, доступную контейнеру, за период — приложение просто работает медленнее (растёт latency, растёт event loop lag, см. [CPU-bound в Node: event loop lag, worker threads](../08-performance-reliability/06-cpu-bound-event-loop-lag.md)), но не падает.
- **Memory limit превышен** — мгновенный `SIGKILL` от ядра (через cgroup OOM killer) — память физически нельзя "троттлить" так же, как CPU-время (нельзя частично не выделить уже запрошенную память), поэтому единственная реакция ядра на превышение — немедленно убить процесс. Никакого graceful shutdown, никакого шанса завершить текущие запросы — это жёсткое, безусловное убийство в момент превышения.

Эта асимметрия — источник частой путаницы: разработчики интуитивно ожидают, что "превышение лимита" ведёт себя одинаково для CPU и памяти, хотя на деле это два принципиально разных механизма реакции ядра.

## OOMKilled — диагностика

```bash
kubectl describe pod myapp-xyz
# Last State: Terminated, Reason: OOMKilled, Exit Code: 137
```

`Exit Code: 137` = `128 + 9` (9 — номер сигнала `SIGKILL`) — стандартный признак OOMKilled в Kubernetes, отличимый от обычного краша приложения (который обычно имеет код 1 или специфичный код, заданный самим приложением). Диагностика — сопоставить момент убийства с графиком реального потребления памяти контейнером (`kubectl top pod`, метрики Prometheus по `container_memory_working_set_bytes`) — растущий тренд перед убийством указывает на утечку памяти (см. методику диагностики в [Поиск утечек памяти](../02-nodejs-core/08-memory-leaks.md)), резкий скачок — на разовую тяжёлую операцию (загрузка большого файла целиком в память, см. [Streams и backpressure](../02-nodejs-core/03-streams.md) про потоковую обработку вместо этого).

## Связь `--max-old-space-size` с memory limit контейнера

```dockerfile
CMD ["node", "--max-old-space-size=384", "dist/main.js"]
```

V8 исторически определяет дефолтный лимит old-space heap (см. поколения GC в [Память и GC в V8](../02-nodejs-core/07-memory-gc.md)) исходя из объёма памяти, доступной **хосту** (либо всей физической машине, либо — в новых версиях Node с частичной поддержкой cgroup — исходя из лимита cgroup, но это поведение исторически было ненадёжным и зависело от версии Node/способа деплоя). Если контейнер запущен с `memory limit: 512Mi`, а V8 внутри не знает об этом ограничении и пытается вырастить heap к дефолтному значению, ориентированному на память **всей ноды** (могут быть десятки ГБ) — суммарное потребление процесса (heap + стеки потоков + буферы + нативные аллокации) способно превысить 512Mi контейнера раньше, чем V8's собственный GC успеет сработать по внутреннему давлению памяти, потому что V8 просто не считает 512Mi своим реальным потолком.

**Практическое правило** — `--max-old-space-size` должен быть выставлен явно, заметно **ниже** memory limit контейнера (типичный ориентир — 75-80% от лимита), оставляя запас на всё, что не входит в V8 heap: стеки потоков (включая worker threads, если используются), `Buffer`/`ArrayBuffer` (внешняя память, не входящая в основной heap — см. рост RSS при стабильном heapUsed в [Поиск утечек памяти](../02-nodejs-core/08-memory-leaks.md)), память самого V8-движка (код, метаданные), нативные аддоны. Без этого запаса контейнер может быть убит OOMKilled раньше, чем V8 вообще посчитает нужным начать агрессивную сборку мусора — то есть GC не успевает "спасти" процесс, потому что не знает, что памяти реально мало.

## Requests и планировщик — почему это не просто рекомендация

```
Узел с capacity 4 vCPU / 8Gi:
Под A: requests { cpu: 1, memory: 2Gi }
Под B: requests { cpu: 1, memory: 2Gi }
Под C: requests { cpu: 2, memory: 4Gi }
→ Сумма requests = вся ёмкость узла — планировщик НЕ разместит здесь под D, даже если фактическое
   использование A/B/C сейчас намного ниже их requests (гарантия резервируется, не измеряется по факту)
```

`requests` — то, что планировщик **резервирует** при размещении пода на узел, независимо от того, использует ли под эти ресурсы фактически в моменте — заниженные `requests` относительно реального типичного потребления приводят к переуплотнению узла (много подов, реально конкурирующих за меньшую физическую ёмкость, чем формально "гарантировано" каждому), завышенные — к недоиспользованию кластера (узлы простаивают с зарезервированной, но не используемой ёмкостью). Подбор `requests`/`limits` — итеративная настройка по реальным метрикам потребления под нагрузкой (см. профилирование и нагрузочное тестирование в [08-performance-reliability](../08-performance-reliability/index.md)), не произвольные "круглые" числа наугад.

## Что спрашивают на собеседовании

1. **Под убивается OOMKilled — как диагностировать? Как связаны limits и heap size Node?** — `kubectl describe pod` → `Exit Code: 137`; сопоставить с графиком потребления памяти (тренд роста = утечка, скачок = разовая тяжёлая операция); V8 по умолчанию не знает про memory limit контейнера и может пытаться вырастить heap за пределы того, что реально доступно, — нужен явный `--max-old-space-size` ниже лимита с запасом.
2. **Чем отличается реакция на превышение CPU limit от превышения memory limit?** — CPU: throttling, процесс просто работает медленнее, не убивается; memory: мгновенный `SIGKILL` от cgroup OOM killer — память нельзя частично не выделить, поэтому единственная реакция ядра — убить процесс.
3. **Почему `--max-old-space-size` должен быть ниже memory limit контейнера, а не равен ему?** — heap — не единственное потребление памяти процесса: стеки потоков, внешние буферы (`Buffer`/`ArrayBuffer`), память самого V8-движка, нативные аддоны — всё это сверх heap, и если не оставить запас, контейнер убьётся раньше, чем V8 успеет отреагировать на давление памяти собственным GC.
4. **Зачем нужны `requests`, если есть `limits`?** — `requests` используется планировщиком для решения о размещении пода на узел — это гарантированный резерв, а не измеряемое фактическое потребление; заниженные requests ведут к переуплотнению узла, завышенные — к недоиспользованию кластера.
5. **Как отличить утечку памяти от разовой тяжёлой операции по графику потребления перед OOMKilled?** — устойчивый растущий тренд на протяжении времени — утечка (методичный разбор в отдельном документе про поиск утечек); резкий одномоментный скачок непосредственно перед убийством — разовая операция (например, загрузка большого файла целиком в память вместо потоковой обработки).
