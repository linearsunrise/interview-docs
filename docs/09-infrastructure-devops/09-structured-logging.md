# Логи: structured JSON (pino), уровни, correlation/request id, что нельзя логировать

> **TL;DR:** `console.log` в проде — красный флаг не из пуризма, а потому что неструктурированный текст нельзя эффективно фильтровать/агрегировать/алертить на масштабе (лог-система получает миллионы строк текста, а не queryable данные). Structured logging — каждая запись JSON-объект с предсказуемыми полями — то, что делает логи **данными**, по которым можно построить дашборд, а не просто текстом для чтения глазами. Correlation ID — единственный способ собрать цепочку событий одного запроса, размазанную по множеству лог-строк (и, в микросервисах, по множеству разных сервисов) в единую историю.

## Structured JSON logging — pino

```ts
import pino from 'pino';
const logger = pino();

logger.info({ userId: 42, orderId: 'abc123' }, 'order created');
// {"level":30,"time":1706000000000,"pid":1234,"userId":42,"orderId":"abc123","msg":"order created"}
```

```
console.log('order created for user 42, order abc123');
// "order created for user 42, order abc123" — текст, не данные: чтобы найти "все заказы userId=42",
// нужен regex/grep по неструктурированной строке, а не простой filter по полю
```

`pino` — один из самых быстрых JSON-логгеров для Node (минимальный оверхед сериализации, важно на горячем пути высоконагруженного сервиса) — каждый вызов `logger.info(fields, message)` производит одну строку JSON с явными полями. В отличие от текстовой строки, JSON-запись напрямую индексируется системой сбора логов (Elasticsearch/Loki/CloudWatch Logs Insights и подобные) — можно фильтровать `WHERE userId = 42 AND level = 'error'`, строить агрегации ("сколько ошибок по каждому `orderId` за час"), без парсинга текста регулярками на лету при каждом запросе к логам.

## Уровни логирования — не просто "важность", а фильтр по объёму

```ts
logger.trace(...); // максимально подробно — обычно выключен даже в dev
logger.debug(...); // детали для отладки конкретной проблемы
logger.info(...);  // штатные события бизнес-значимости ("order created", "user logged in")
logger.warn(...);  // не ошибка, но заслуживает внимания (retry сработал, deprecated API вызван)
logger.error(...); // операция не удалась, требует внимания
logger.fatal(...); // процесс не может продолжать работу
```

В проде обычно включён уровень `info` и выше (`trace`/`debug` — слишком высокий объём для постоянной работы, включаются точечно при расследовании конкретного инцидента через изменение уровня без передеплоя, если логгер это поддерживает динамически). Разделение уровней — практический механизм управления объёмом и стоимостью логирования (хранение и обработка логов в большом масштабе — не бесплатны), а не просто семантическая классификация "на будущее".

## Correlation / request ID — собрать историю одного запроса из множества строк

```ts
import { AsyncLocalStorage } from 'async_hooks';
const requestContext = new AsyncLocalStorage<{ requestId: string }>();

app.use((req, res, next) => {
  const requestId = req.headers['x-request-id'] || crypto.randomUUID();
  requestContext.run({ requestId }, next);
});

const logger = pino({
  mixin: () => ({ requestId: requestContext.getStore()?.requestId }), // добавляется АВТОМАТИЧЕСКИ в каждый лог
});
```

Один HTTP-запрос обычно порождает множество лог-строк (вход запроса, поход в БД, вызов внешнего сервиса, ответ) — без общего идентификатора эти строки в общем потоке логов сервиса (тем более при параллельной обработке множества запросов одновременно) невозможно достоверно сгруппировать в историю именно **этого** запроса. `AsyncLocalStorage` (см. подробный разбор в [AsyncLocalStorage](../02-nodejs-core/11-async-local-storage.md)) — стандартный способ в Node прокинуть `requestId` через всю асинхронную цепочку обработки запроса без явной передачи параметром через каждую функцию — логгер автоматически подмешивает текущий `requestId` в каждую запись, сделанную в рамках этого запроса, откуда бы в коде она ни происходила.

В микросервисной архитектуре тот же `requestId` (или полноценный `traceId` из distributed tracing, см. [Трейсинг: OpenTelemetry, propagation](./11-distributed-tracing-otel.md)) должен **распространяться** между сервисами — сервис A, вызывающий сервис B по HTTP, обязан прокинуть заголовок (`X-Request-Id`/`traceparent`) дальше, а сервис B — подхватить его в свой контекст логирования, а не сгенерировать новый ID с нуля — иначе цепочка обрывается на границе сервисов, и собрать полную историю запроса через несколько сервисов по логам становится невозможно.

## Что нельзя логировать

```ts
// НЕЛЬЗЯ:
logger.info({ password: dto.password }, 'login attempt');
logger.info({ creditCard: dto.cardNumber }, 'payment processed');
logger.info({ authHeader: req.headers.authorization }, 'request received'); // содержит Bearer-токен целиком

// pino redact — автоматическое вычищение чувствительных полей
const logger = pino({ redact: ['password', 'req.headers.authorization', '*.creditCard'] });
```

Пароли, полные номера карт, токены доступа, персональные данные без необходимости (PII) — логи обычно менее защищены и дольше хранятся, чем основная БД (реплицируются в системы агрегации, часто доступны более широкому кругу инженеров для отладки), и попадание туда чувствительных данных — реальный канал утечки (тот же класс риска, что и логирование секретов, см. [Секреты: env vs vault, ротация; helmet, валидация](../07-security/14-secrets-management.md)), плюс прямое нарушение GDPR/PCI DSS-требований, если применимо к юрисдикции/индустрии продукта. `pino` (и аналоги) поддерживают декларативное `redact` — автоматическое вычищение полей по указанным путям перед записью, снижающее риск случайного логирования чувствительных данных где-то в глубине кодовой базы, где разработчик мог забыть об этом явно подумать.

## Что спрашивают на собеседовании

1. **Почему `console.log` — красный флаг в проде, а не просто "не лучшая практика"?** — неструктурированный текст нельзя эффективно фильтровать/агрегировать в системе сбора логов на масштабе — нужен парсинг регулярками на лету при каждом запросе к логам вместо прямого запроса по полям, что и медленнее, и хрупче при малейшем изменении формата строки.
2. **Как собрать полную цепочку событий одного запроса в микросервисах?** — сквозной correlation/request ID (или полноценный traceId из distributed tracing), прокидываемый через заголовки между сервисами и подхватываемый в контекст логирования каждого — без него цепочка обрывается на границе сервисов.
3. **Как `AsyncLocalStorage` помогает с request-id в логах?** — прокидывает значение через всю асинхронную цепочку обработки запроса без явной передачи параметром в каждую функцию — логгер автоматически подмешивает текущий `requestId` в каждую запись, сделанную в контексте этого запроса.
4. **Что нельзя логировать и почему это не только про "хорошие практики"?** — пароли, токены, полные номера карт, PII без необходимости — логи обычно менее защищены и дольше хранятся, чем основная БД, что делает их реальным каналом утечки; для многих индустрий это ещё и прямое нарушение compliance-требований.
5. **Зачем нужны уровни логирования, если можно логировать всё на одном уровне `info`?** — управление объёмом и стоимостью: `debug`/`trace` дают детализацию для расследования конкретной проблемы, но неприемлемы для постоянной работы на масштабе — уровни позволяют включать детализацию точечно, не платя за неё постоянно.
