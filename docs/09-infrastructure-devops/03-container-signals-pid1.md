# Сигналы в контейнере: PID 1, почему `npm start` глотает SIGTERM

> **TL;DR:** Процесс с PID 1 в Linux — особый: ядро **не применяет** дефолтные обработчики сигналов к нему автоматически (в отличие от любого другого процесса), если сам процесс явно их не установил — это защита от случайного убийства init-системы. `npm start` запускает **дочерний** процесс (реальный `node`) — сам `npm`-процесс становится PID 1 в контейнере, и по умолчанию не пересылает полученный `SIGTERM` дочернему процессу — Node-приложение внутри просто никогда не узнаёт, что его просят завершиться, и графическое завершение (`app.enableShutdownHooks()`, см. [Graceful shutdown](../02-nodejs-core/10-graceful-shutdown.md)) не срабатывает вообще.

## Почему PID 1 особенный

В обычной Linux-системе PID 1 — это init-процесс (`systemd` и т.п.), отвечающий за запуск остальной системы и «усыновление» осиротевших процессов (reparenting) — ядро сознательно не убивает его дефолтными сигналами без явного обработчика, чтобы случайный `SIGTERM` не мог обрушить всю систему. В контейнере эта же логика ядра применяется буквально: какой бы процесс ни был назначен точкой входа контейнера (`CMD`/`ENTRYPOINT`), он получает PID 1 внутри изолированного PID-namespace контейнера — и наследует то же особое поведение ядра, даже если это не настоящая init-система, а просто `node` или `npm`.

## Как это ломает graceful shutdown

```dockerfile
CMD ["npm", "start"]   # ПРОБЛЕМА: npm — PID 1, node — дочерний процесс (PID 2+)
```

```
docker stop container → отправляет SIGTERM PID 1 (npm)
npm (PID 1) НЕ пересылает SIGTERM своему дочернему процессу node автоматически
node-процесс никогда не получает SIGTERM → app.enableShutdownHooks() никогда не срабатывает
docker stop ждёт grace period (по умолчанию 10 секунд) → не дождался → шлёт SIGKILL
Приложение убито ЖЁСТКО: незакрытые соединения к БД, недообработанные запросы обрываются
```

Это не гипотетическая проблема конкретной версии npm — исторически `npm` как обёртка над реальной командой не гарантированно и не всегда корректно пробрасывала сигналы дочернему процессу (поведение менялось между версиями npm, и полагаться на то, что "в этой версии вроде работает" — ненадёжная практика). Результат один и тот же вне зависимости от точной причины: Node-процесс, которому мы явно написали обработчик `SIGTERM` для graceful shutdown, никогда не получает шанс его выполнить, потому что сигнал застревает на процессе-обёртке.

## Решение 1 — запускать Node напрямую, без npm-обёртки

```dockerfile
CMD ["node", "dist/main.js"]   # node САМ становится PID 1, получает SIGTERM напрямую
```

Простейшее и обычно достаточное решение для типичного Node-приложения — сигнал доходит до процесса, который явно написал обработчик, без посредников. Ограничение — сам Node-процесс как PID 1 всё ещё не занимается **reaping зомби-процессов** (если приложение порождает дочерние процессы — `child_process.spawn`, см. [worker_threads / child_process / cluster](../02-nodejs-core/05-workers-cluster.md) — их завершённые, но не "собранные" процессы могут накапливаться как зомби) — для типичного HTTP API-сервиса без порождения дочерних процессов это не проблема, но становится ей, если приложение активно спавнит подпроцессы.

## Решение 2 — `tini` как минимальный init для контейнера

```dockerfile
FROM node:20-alpine
RUN apk add --no-cache tini
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "dist/main.js"]
```

`tini` — маленький (несколько КБ) init-процесс, спроектированный специально для контейнеров: становится PID 1 сам, корректно пробрасывает полученные сигналы (SIGTERM, SIGINT) дочернему процессу (`node`), и, что важно отдельно, занимается reaping зомби-процессов, которые Node сам по себе не собирает. Официальный образ `node:20` уже включает `tini` (доступен через флаг `docker run --init` или напрямую), Alpine-based образам обычно нужно установить явно (`apk add tini`, как в примере). На практике это защита "по умолчанию корректно", даже если приложение начнёт порождать дочерние процессы уже после того, как Dockerfile был написан и не пересматривался специально под этот случай.

## Почему health check и readiness завязаны на ту же проблему

Если graceful shutdown не срабатывает (сигнал не дошёл), под в Kubernetes при `SIGKILL` обрывает уже принятые, но не завершённые запросы жёстко — клиенты получают обрыв соединения вместо корректного `502`/ретрая от балансировщика, который у них был бы при штатном завершении с задержкой снятия с баланса (см. подробности координации readiness и graceful shutdown в [Probes: liveness vs readiness vs startup](./05-probes-liveness-readiness.md)). Проблема "приложение не завершает соединения при деплое, клиенты ловят 502" (частый практический вопрос на собеседовании) — почти всегда сводится либо к этой самой проблеме PID 1/сигналов, либо к отсутствию `preStop`-хука/правильной последовательности readiness перед остановкой.

## Что спрашивают на собеседовании

1. **Почему `npm start` в CMD Dockerfile — плохая практика?** — `npm` становится PID 1 и не гарантированно пробрасывает полученный `SIGTERM` дочернему `node`-процессу — graceful shutdown приложения никогда не срабатывает, контейнер убивается жёстко по истечении grace period.
2. **Что особенного в PID 1 с точки зрения обработки сигналов?** — ядро Linux не применяет дефолтные обработчики сигналов к процессу с PID 1 автоматически (защита init-системы от случайного убийства) — сигнал доходит только если процесс явно установил свой обработчик.
3. **Как правильно запускать Node-приложение в контейнере — двумя способами.** — либо `CMD ["node", "dist/main.js"]` напрямую (node сам PID 1, получает сигнал без посредников), либо через `tini` как минимальный init (`ENTRYPOINT ["tini", "--"]`), который корректно пробрасывает сигналы и дополнительно занимается reaping зомби-процессов.
4. **Когда одного прямого запуска `node` недостаточно и нужен именно `tini`?** — когда приложение порождает дочерние процессы (`child_process.spawn`) — сам Node как PID 1 не занимается сбором завершившихся зомби-процессов, это делает `tini`.
5. **Приложение в k8s не завершает соединения при деплое, клиенты ловят 502 — где искать?** — цепочка: `SIGTERM` от k8s → доходит ли до реального Node-процесса (проблема PID 1/npm-обёртки) → срабатывает ли обработчик graceful shutdown → согласован ли момент остановки приёма нового трафика (readiness) с моментом реального завершения процесса.
