# CI/CD: стадии (lint, test, build, scan), кеширование зависимостей

> **TL;DR:** Порядок стадий — не произвольный, а по возрастанию стоимости: дешёвые и быстрые проверки (lint) идут первыми, чтобы провалить пайплайн максимально рано и не тратить время на дорогие стадии (build, e2e-тесты) ради кода, который всё равно не пройдёт базовую проверку. Кеширование зависимостей — та же логика, что кеширование слоёв Docker (см. [Docker: слои и кеш, multi-stage build](./01-docker-multistage.md)): переиспользовать то, что не изменилось, вместо пересчёта на каждый запуск пайплайна с нуля.

## Типичные стадии и их порядок

```yaml
# упрощённый пример (GitHub Actions-подобный синтаксис)
jobs:
  lint:
    steps: [checkout, install, run: eslint .]
  test-unit:
    needs: lint
    steps: [checkout, install, run: npm run test]
  build:
    needs: test-unit
    steps: [checkout, install, run: npm run build]
  test-e2e:
    needs: build
    steps: [checkout, install, run: npm run test:e2e]
  scan:
    needs: build
    steps: [run: docker scan / trivy image myapp:latest]
  deploy:
    needs: [test-e2e, scan]
    steps: [run: kubectl apply -f ...]
```

**Lint** — самая дешёвая и быстрая проверка (секунды), ловит синтаксические и стилистические проблемы до того, как тратится время на что-либо ещё. **Unit-тесты** — быстрее интеграционных/e2e (не требуют поднятия БД/внешних зависимостей), запускаются следующими. **Build** — компиляция TypeScript, сборка Docker-образа — уже требует, чтобы код прошёл lint и unit-тесты, иначе тратить время на сборку заведомо проблемного кода бессмысленно. **E2E-тесты** — самые дорогие по времени (поднятие реальных зависимостей, полные сценарии) — запускаются после build, часто на уже собранном артефакте, а не пересобирая заново. **Scan** — сканирование Docker-образа на известные уязвимости (Trivy, Snyk Container, см. [OWASP Top 10 применительно к Node](../07-security/06-owasp-top10-node.md) про A06 Vulnerable Components) — обычно параллельно с e2e-тестами, оба независимо блокируют деплой. **Deploy** — последняя стадия, срабатывает только если всё предыдущее прошло успешно.

## Кеширование зависимостей — не пересчитывать то, что не изменилось

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}
    restore-keys: npm-
```

Ключ кеша, построенный на хэше `package-lock.json` — тот же принцип, что и порядок `COPY` в Dockerfile (см. [Docker: слои и кеш, multi-stage build](./01-docker-multistage.md)): пока файл зависимостей не менялся, кеш переиспользуется, и `npm ci` берёт пакеты из локального кеша вместо повторного скачивания из реестра — экономия минут на каждый запуск пайплайна, особенно заметная при частых коммитах/PR. `restore-keys` с частичным совпадением префикса — fallback: если точного совпадения по текущему lock-файлу нет (зависимости чуть изменились), взять ближайший похожий кеш как отправную точку — быстрее, чем качать вообще всё с нуля, даже если часть пакетов всё равно придётся обновить.

## Docker layer caching в CI — тот же принцип, применённый к сборке образа

```yaml
- uses: docker/build-push-action@v5
  with:
    cache-from: type=registry,ref=myapp:buildcache
    cache-to: type=registry,ref=myapp:buildcache,mode=max
```

CI-раннеры обычно эфемерны (новая чистая машина на каждый запуск) — локальный Docker layer cache, который работает на машине разработчика между локальными сборками, недоступен по умолчанию между запусками CI на разных раннерах. Explicit remote cache (registry-based, как в примере, или сервис типа BuildKit cache) сохраняет слои между запусками пайплайна во внешнем хранилище — следующий запуск может переиспользовать неизменившиеся слои (тот же слой `npm ci`, если `package-lock.json` не менялся) вместо полной пересборки образа с нуля на каждом CI-прогоне.

## Параллелизация независимых стадий

```
lint ─┐
      ├─→ build ─┬─→ test-e2e ─┐
test-unit ─┘      └─→ scan    ─┴─→ deploy
```

Стадии, не зависящие друг от друга по данным (например, `test-e2e` и `scan` — обе нужны только результат `build`, не зависят друг от друга) — запускаются параллельно, а не строго последовательно, сокращая общее время пайплайна до времени самой длинной цепочки зависимостей ("критического пути"), а не суммы всех стадий. `lint` и `test-unit` часто тоже можно запускать параллельно (оба независимы от результата друг друга, оба нужны только чистый checkout кода) — итоговое время пайплайна определяется не количеством стадий, а их графом зависимостей.

## Fail fast — почему порядок стадий имеет значение для стоимости

Если бы `build` (несколько минут на TypeScript-компиляцию + Docker build) шёл **до** `lint` (секунды), пайплайн тратил бы дорогие минуты на сборку кода, который в итоге всё равно будет отклонён из-за тривиальной ошибки стиля/синтаксиса, обнаружимой почти мгновенно. Fail fast — располагать проверки по возрастанию стоимости их выполнения, чтобы наиболее вероятные (и наиболее дешёвые для обнаружения) проблемы отклоняли пайплайн раньше, экономя суммарное время CI и, для облачных раннеров, реальные деньги (оплата по времени выполнения).

## Что спрашивают на собеседовании

1. **В каком порядке должны идти стадии CI/CD-пайплайна и почему именно так?** — по возрастанию стоимости выполнения (fail fast): lint (секунды) → unit-тесты (быстрее, не требуют внешних зависимостей) → build → e2e-тесты/security scan (самые дорогие) → deploy — чтобы дешёвые проверки отклоняли пайплайн раньше дорогих.
2. **Как кешировать зависимости в CI и зачем?** — ключ кеша на основе хэша lock-файла (`package-lock.json`) — пока зависимости не менялись, `npm ci` берёт пакеты из кеша вместо повторного скачивания из реестра на каждый запуск пайплайна.
3. **Почему Docker layer caching в CI требует отдельной настройки, а не работает "из коробки" как локально?** — CI-раннеры обычно эфемерны (чистая машина на каждый запуск), локальный кеш слоёв не переживает между запусками — нужен явный remote cache (registry-based или аналог), сохраняющий слои во внешнем хранилище между прогонами.
4. **Какие стадии пайплайна можно параллелить, а какие — нет?** — стадии, не зависящие друг от друга по данным (например, e2e-тесты и security scan, оба требующие только собранный артефакт), можно запускать параллельно; итоговое время пайплайна определяется самой длинной цепочкой зависимостей, а не суммой всех стадий.
5. **Что происходит на стадии `scan` и почему она важна?** — сканирование собранного образа на известные уязвимости (CVE) в системных пакетах и npm-зависимостях — защита от деплоя образа с известными уязвимостями, часть более широкой темы supply chain security (см. OWASP A06/A08).
