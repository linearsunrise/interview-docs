# Docker: слои и кеш, multi-stage build для Node, `.dockerignore`, non-root user

> **TL;DR:** Каждая инструкция Dockerfile создаёт неизменяемый слой; Docker кеширует слои и переиспользует их, пока не изменится сама инструкция или её вход — отсюда правило «сначала то, что меняется редко» (зависимости), «потом то, что меняется часто» (исходный код), иначе любое изменение кода инвалидирует кеш `npm install`. Multi-stage build решает отдельную задачу — не тащить в финальный образ инструменты сборки, dev-зависимости и исходники TypeScript, которые нужны только для получения `dist/`, а не для его выполнения.

## Слои и порядок инструкций — почему это не мелочь

```dockerfile
# ПЛОХО: любое изменение кода инвалидирует кеш npm install
COPY . .
RUN npm ci
RUN npm run build

# ХОРОШО: npm ci кешируется, пока не менялись package*.json
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build
```

Docker сравнивает инструкцию и её контекст (для `COPY` — контрольную сумму копируемых файлов) со слоем из кеша; если совпадает — слой переиспользуется без повторного выполнения. В первом варианте `COPY . .` включает весь исходный код — любое изменение хотя бы одной строки в любом файле проекта меняет контрольную сумму этого слоя, и Docker честно перевыполняет **все** последующие инструкции, включая `npm ci` (обычно самая долгая часть сборки) — при том что реально изменился только код, зависимости остались прежними. Второй вариант копирует только `package.json`/`package-lock.json` первым — `npm ci` кешируется отдельно и пересчитывается только когда реально поменялись зависимости, а не при каждом изменении кода.

## Multi-stage build — не тащить лишнее в финальный образ

```dockerfile
# ---- Stage 1: deps + build ----
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci                          # ВСЕ зависимости, включая dev (typescript, eslint, тесты)
COPY . .
RUN npm run build                   # tsc → dist/

# ---- Stage 2: runtime ----
FROM node:20-alpine AS runtime
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev               # ТОЛЬКО prod-зависимости
COPY --from=builder /app/dist ./dist   # берём только результат сборки из stage 1
USER node
CMD ["node", "dist/main.js"]
```

Первый stage (`builder`) содержит полный набор dev-зависимостей (TypeScript-компилятор, тестовый раннер, линтер) и весь исходный TypeScript-код — всё, что нужно, чтобы получить `dist/`, но не нужно, чтобы его **выполнить**. Второй stage (`runtime`) начинается с чистого базового образа и через `COPY --from=builder` забирает только скомпилированный результат — dev-зависимости, исходники, кеш сборки первого stage физически не попадают в финальный образ вообще (Docker отбрасывает промежуточные stage при финальной сборке, если на них нет ссылки в конечном stage). Итог — меньший размер образа (меньше поверхность для сканирования уязвимостей, быстрее `docker pull` при деплое) и отсутствие исходного кода/dev-инструментов в проде (меньше что можно случайно раскрыть при компрометации контейнера).

## `.dockerignore` — тот же принцип, что `.gitignore`

```
node_modules
dist
.git
.env
*.md
.dockerignore
Dockerfile
```

Без `.dockerignore` инструкция `COPY . .` тащит в build-контекст (и потенциально в образ) всё, что лежит в директории — включая уже собранный локально `node_modules` (может содержать нативные модули, скомпилированные под архитектуру разработчика, а не под архитектуру образа — рассинхрон, который проявится только в рантайме), `.git` (вся история репозитория, не нужна для выполнения приложения, раздувает контекст сборки), `.env` с локальными секретами (реальный риск утечки — см. [Секреты: env vs vault, ротация; helmet, валидация](../07-security/14-secrets-management.md)). `.dockerignore` также ускоряет саму отправку build-контекста демону Docker — меньше данных нужно передать перед началом сборки.

## Non-root user — не запускать процесс контейнера от root

```dockerfile
FROM node:20-alpine AS runtime
# ...
USER node   # официальный образ node уже содержит непривилегированного пользователя "node"
CMD ["node", "dist/main.js"]
```

По умолчанию процесс в контейнере запускается от `root`, если явно не указано иное — если в приложении (или в одной из зависимостей) есть уязвимость, позволяющая выполнение произвольного кода (например, через непропатченный path traversal или инъекцию, см. [SQL/NoSQL инъекции](../07-security/07-injections-sql-nosql.md)), атакующий получает эту уязвимость с правами `root` внутри контейнера — что расширяет потенциальный ущерб (запись в любые файлы контейнера, попытки эксплуатации container escape уязвимостей, которые чаще опаснее именно из-под root). `USER node` — принцип наименьших привилегий (тот же, что разобран для секретов и БД-аккаунтов приложения) применённый к самому процессу контейнера: даже при компрометации приложения атакующий ограничен правами непривилегированного пользователя.

## Что спрашивают на собеседовании

1. **Напишите (устно) Dockerfile для Nest-приложения production-уровня — что и почему.** — multi-stage (builder со всеми deps + сборкой, runtime только с `--omit=dev` и результатом сборки), правильный порядок `COPY` (сначала `package*.json`, потом код — для кеша слоёв), `.dockerignore`, non-root `USER`, прямой `CMD ["node", ...]` вместо `npm start` (см. [Сигналы в контейнере: PID 1, tini](./03-container-signals-pid1.md)).
2. **Почему порядок инструкций в Dockerfile влияет на скорость сборки?** — Docker кеширует слои по контрольной сумме инструкции и её входа; если файлы, часто меняющиеся (код), скопированы раньше файлов, редко меняющихся (манифест зависимостей), любое изменение кода инвалидирует и последующий дорогой `npm ci`, хотя зависимости не менялись.
3. **Зачем нужен multi-stage build, если можно собрать всё в одном stage?** — не тащить в финальный образ dev-зависимости, исходный TypeScript-код и промежуточные артефакты сборки — меньший размер образа, меньшая поверхность атаки, отсутствие исходников в проде.
4. **Что делает `.dockerignore` и почему его отсутствие — не просто неаккуратность?** — исключает ненужные/опасные файлы из build-контекста (`node_modules` локальной архитектуры, `.git`, `.env` с секретами) — без него возможна утечка секретов в образ и рассинхрон нативных зависимостей.
5. **Почему процесс в контейнере не должен работать от root?** — принцип наименьших привилегий: при компрометации приложения (RCE-уязвимость) атакующий получает права того пользователя, от которого работает процесс — root расширяет потенциальный ущерб внутри контейнера и повышает риск успешной container escape эксплуатации.
