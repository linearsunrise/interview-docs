# Миграции БД в деплое: expand-contract, совместимость версий

> **TL;DR:** Во время rolling update (см. [Деплой: rolling, blue-green, canary; feature flags](./07-deployment-strategies.md)) старая и новая версии приложения работают **одновременно**, обращаясь к **одной и той же** базе данных — миграция схемы, ломающая совместимость со старой версией кода хотя бы на несколько минут, гарантированно вызывает ошибки у части подов, всё ещё работающих на старом коде. Expand-contract для схемы БД — тот же принцип, что разобран для API-версионирования (см. [Версионирование API](../05-api-communication/03-api-versioning.md)), применённый к структуре таблиц: каждое изменение схемы проходит через фазу, где схема совместима **с обеими** версиями кода одновременно.

## Почему «переименовал колонку и задеплоил» — гарантированная авария

```sql
ALTER TABLE users RENAME COLUMN email TO email_address;
```

```
Момент деплоя: 3 пода со СТАРЫМ кодом (SELECT email FROM users) ещё работают
               1 под с НОВЫМ кодом (SELECT email_address FROM users) уже поднялся
→ Старые 3 пода получают ошибку "column email does not exist" на КАЖДЫЙ запрос к БД
→ Полный отказ большей части флота на всё время rolling update, не только момент переключения
```

Одна атомарная миграция (переименование, удаление колонки, смена типа несовместимым образом) применяется к схеме **мгновенно**, но код обновляется **постепенно** (rolling update по своей природе растянут во времени, обычно минуты) — в промежутке одновременно работают версии кода, ожидающие разной структуры одной и той же таблицы. Это не гипотетический edge case, а гарантированное состояние при любом rolling-деплое с одновременной несовместимой миграцией схемы.

## Expand-contract на конкретном примере — переименование колонки без даунтайма

```sql
-- Деплой 1 (expand): добавить НОВУЮ колонку, ничего не удалять
ALTER TABLE users ADD COLUMN email_address text;
```
```ts
// Код деплоя 1: писать в ОБЕ колонки, читать пока из старой (двойная запись)
async function updateEmail(userId: string, email: string) {
  await db.query('UPDATE users SET email = $1, email_address = $1 WHERE id = $2', [email, userId]);
}
```
```sql
-- Между деплоем 1 и 2: backfill — перенести исторические данные в новую колонку
UPDATE users SET email_address = email WHERE email_address IS NULL;
```
```ts
// Деплой 2: переключить ЧТЕНИЕ на новую колонку, запись всё ещё в обе (безопасный откат на деплой 1 при проблеме)
async function getUser(userId: string) {
  const user = await db.query('SELECT email_address AS email FROM users WHERE id = $1', [userId]);
}
```
```sql
-- Деплой 3 (contract): только теперь, когда ВСЕ поды точно на новом коде, убрать старую колонку
ALTER TABLE users DROP COLUMN email;
```

Пять отдельных шагов вместо одной операции — но каждый **отдельный** деплой в этой последовательности совместим сам по себе: во время rolling update деплоя 1 старый код (не знающий про `email_address`) продолжает работать как ни в чём не бывало (новая колонка просто существует, но не используется старым кодом), потому что `ADD COLUMN` — неразрушающая операция. То же верно для каждого следующего шага — ни один деплой в цепочке не требует, чтобы **все** поды одновременно перешли на новую схему мгновенно.

## Общее правило — что безопасно, что нет

| Операция | Безопасно для одновременной работы старой/новой версии? |
|---|---|
| `ADD COLUMN` (nullable или со значением по умолчанию) | да — старый код просто не знает о новой колонке |
| `ADD TABLE`/`ADD INDEX` | да — новые структуры не мешают существующим запросам |
| `RENAME COLUMN`/`RENAME TABLE` | нет — старый код ссылается на старое имя, которого больше нет |
| `DROP COLUMN` | нет, если хоть один под ещё читает/пишет эту колонку |
| Смена типа колонки (несовместимая) | нет — старый код может писать/ожидать значения старого типа |
| `NOT NULL` без значения по умолчанию на существующей колонке | нет, если старый код не всегда заполняет эту колонку |

Практический ориентир — любая операция, которую можно свести к "добавить новое, не трогая старое", безопасна для однократного деплоя; операция, которая одновременно "меняет форму существующего", требует разбивки на expand → миграция кода → contract, растянутую минимум на два отдельных деплоя (часто больше, если нужен backfill между ними, как в примере выше).

## Совместимость версий — не только схема, но и данные

```
Backfill: UPDATE users SET email_address = email WHERE email_address IS NULL;
```

Backfill исторических данных в новую колонку/таблицу — отдельный практический нюанс: если он выполняется одним большим `UPDATE` на таблице с миллионами строк, это создаёт длительную блокировку/нагрузку (см. [Deadlocks](../04-databases/06-deadlocks.md) про долгие транзакции и их влияние на конкурентные операции) — на практике backfill часто разбивают на батчи (`UPDATE ... WHERE id BETWEEN x AND y`, повторяемый небольшими порциями с паузами) вместо одной гигантской операции, чтобы не создавать заметную деградацию для реального пользовательского трафика, идущего к той же таблице параллельно.

## Миграции как часть CI/CD, а не отдельный ручной шаг

```yaml
jobs:
  migrate:
    steps: [run: npm run migration:run]   # ПЕРЕД деплоем нового кода, отдельная контролируемая стадия
  deploy:
    needs: migrate
```

Миграции (см. также обсуждение `synchronize` vs явные миграции в [ORM: N+1, транзакции, миграции (TypeORM/Prisma)](../04-databases/09-orm-typeorm-prisma.md) — `synchronize: true` категорически не для прода) должны запускаться как отдельная, явная, отслеживаемая стадия пайплайна — **до** раската новой версии кода (expand-миграция обязана применяться раньше кода, который на неё полагается) и, что важно для expand-contract, **после** того, как весь трафик гарантированно переведён на новый код при contract-миграции (удаление старой колонки — только когда точно не осталось ни одного пода со старым кодом). Ручное «зашёл на прод-сервер и выполнил ALTER TABLE» — источник рассинхрона между тем, что реально в схеме БД, и тем, что зафиксировано в истории миграций репозитория, а также риск забыть про необходимую последовательность expand → deploy → backfill → deploy → contract.

## Что спрашивают на собеседовании

1. **Как выкатить миграцию с переименованием колонки без даунтайма?** — expand-contract: добавить новую колонку (не трогая старую) → задеплоить код с двойной записью в обе колонки → перенести исторические данные батчами (backfill) → задеплоить код, переключивший чтение на новую колонку → только затем, когда весь трафик гарантированно на новом коде, удалить старую колонку отдельным деплоем.
2. **Почему нельзя просто выполнить `ALTER TABLE ... RENAME COLUMN` и сразу задеплоить новый код?** — во время rolling update старая и новая версии кода работают одновременно на одной БД — мгновенное переименование ломает старую версию, которая ещё обращается к старому имени, на всё время, пока не завершится rolling update.
3. **Какие операции со схемой безопасны для одновременной работы старой и новой версии кода, а какие нет?** — безопасны чисто аддитивные (`ADD COLUMN`, `ADD TABLE`, `ADD INDEX`); небезопасны переименования, удаления, несовместимая смена типа, добавление `NOT NULL` без дефолта на существующую колонку, читаемую/заполняемую старым кодом.
4. **Как безопасно перенести исторические данные в новую колонку на большой таблице?** — батчами с паузами между ними, а не одним большим `UPDATE` — избегает длительной блокировки/деградации для конкурентного пользовательского трафика к той же таблице.
5. **Почему миграции должны быть частью CI/CD-пайплайна, а не ручным шагом на сервере?** — гарантирует правильный порядок относительно деплоя кода (expand-миграция раньше кода, contract-миграция строго после полного раската), отслеживаемость истории изменений схемы, и устраняет риск рассинхрона между реальной схемой БД и зафиксированными в репозитории миграциями.
