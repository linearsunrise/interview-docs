# Probes: liveness vs readiness vs startup — что проверять и типовые ошибки

> **TL;DR:** Liveness отвечает на вопрос «жив ли процесс» — провал перезапускает под. Readiness отвечает на вопрос «готов ли принимать трафик прямо сейчас» — провал убирает под из балансировки без рестарта. Смешение этих двух вопросов — самая частая ошибка: проверка внешней зависимости (БД) в liveness превращает временную недоступность БД в **каскадный рестарт всего флота** приложения одновременно, что не решает проблему (БД всё ещё недоступна) и добавляет собственную (все поды одновременно перезапускаются и заново проходят startup, теряя всю ёмкость сразу).

## Liveness — «жив ли процесс», проверять только внутреннее состояние

```yaml
livenessProbe:
  httpGet: { path: /health/live, port: 3000 }
  initialDelaySeconds: 10
  periodSeconds: 10
  failureThreshold: 3
```

```ts
@Get('health/live')
liveness() {
  return { status: 'ok' }; // НЕ проверяет БД, Redis, внешние API — только "процесс отвечает"
}
```

Liveness должна отвечать только на вопрос "завис ли процесс изнутри" (deadlock, залипший event loop, неустранимая внутренняя ошибка) — событие, для лечения которого действительно нужен рестарт процесса. Проверка внешней зависимости в liveness — структурная ошибка: если БД временно недоступна (перегружена, идёт failover, сетевой blip), **liveness каждого пода** в кластере одновременно начнёт проваливаться (все поды одинаково не могут достучаться до одной и той же недоступной БД) — Kubernetes начнёт рестартовать **все** поды одновременно. Рестарт не чинит недоступность БД (проблема не в процессе приложения), зато на время рестарта и заново проходимого startup под теряет **всю** обслуживающую ёмкость сразу — вместо временной деградации получаем полный отказ.

## Readiness — «готов ли принимать трафик прямо сейчас», внешние зависимости уместны

```yaml
readinessProbe:
  httpGet: { path: /health/ready, port: 3000 }
  periodSeconds: 5
  failureThreshold: 2
```

```ts
@Get('health/ready')
async readiness() {
  await this.dataSource.query('SELECT 1'); // проверка БД ЗДЕСЬ уместна
  return { status: 'ok' };
}
```

Провал readiness убирает под из endpoint'ов Service (см. [04-kubernetes-basics.md](./04-kubernetes-basics.md)) — балансировщик просто перестаёт направлять на него новый трафик, **не перезапуская** сам процесс. Это правильная реакция на "не могу сейчас обработать запрос корректно" (БД недоступна, критичная зависимость не отвечает) — под остаётся живым и автоматически возвращается в ротацию, как только readiness снова проходит (зависимость восстановилась), без затрат на полный рестарт/повторный старт процесса. Проверка внешних зависимостей уместна именно здесь: readiness — ровно тот механизм, который спроектирован обрабатывать "временно не готов обслуживать", в отличие от liveness, спроектированного для "нужен рестарт".

## Startup probe — для медленно стартующих приложений

```yaml
startupProbe:
  httpGet: { path: /health/live, port: 3000 }
  failureThreshold: 30
  periodSeconds: 2   # до 60 секунд на полный старт, прежде чем включатся liveness/readiness
```

Пока startup probe не прошла успешно хотя бы раз, Kubernetes **не запускает** liveness/readiness проверки вообще — защита от преждевременного убийства контейнера, которому просто нужно больше времени на инициализацию (прогрев соединений к БД, загрузка большого конфига/модели), чем обычный `failureThreshold` liveness-проверки допускает. Без startup probe пришлось бы либо ставить неоправданно щедрый `initialDelaySeconds`/`failureThreshold` на саму liveness (что замедляет обнаружение реального зависания уже после старта), либо мириться с тем, что медленно стартующее приложение убивается собственной liveness-проверкой ещё до того, как успело подняться.

## Типовые ошибки

- **Проверка БД/внешнего API в liveness** — разобрано выше, самый частый и самый вредный вариант ошибки, прямо названный в чек-листе раздела красным флагом.
- **Слишком агрессивный `failureThreshold`/`periodSeconds`** — единичный медленный ответ (GC-пауза, кратковременный всплеск нагрузки) не должен мгновенно выбивать под из ротации/убивать его — нужен запас на кратковременный шум, но не настолько большой, чтобы реально зависший под держался в ротации минутами.
- **Один и тот же эндпоинт для liveness и readiness** — если оба указывают на один хендлер, который проверяет всё подряд (включая БД), это структурно воспроизводит проблему "БД в liveness" даже если разработчик формально завёл два разных probe-объекта в манифесте — они должны быть **разными** хендлерами с разной семантикой проверки.
- **Отсутствие координации между readiness и graceful shutdown** — под должен начать проваливать readiness (сигнализируя "не шлите мне новый трафик") **до** того, как реально начнёт закрывать соединения — иначе balancer продолжает слать новые запросы на под, который уже в процессе остановки (см. `preStop`-хук и порядок остановки в [02-nodejs-core/10-graceful-shutdown.md](../02-nodejs-core/10-graceful-shutdown.md)).

## Что будет, если проверять коннект к БД в liveness — развёрнутый ответ

```
БД временно недоступна (failover, перегрузка, сетевой blip) на 30 секунд
→ liveness ВСЕХ подов приложения начинает проваливаться ОДНОВРЕМЕННО (все бьются в одну и ту же недоступную БД)
→ Kubernetes рестартует ВСЕ поды одновременно
→ Пока поды перезапускаются и проходят startup — ВСЯ обслуживающая ёмкость сервиса = 0
→ БД, наконец, восстановилась, но сервис только начинает подниматься заново — период полного отказа
   длиннее, чем реальное время недоступности БД
```

Правильное поведение — эта же ситуация с БД в readiness: поды остаются живыми (не рестартуют), readiness каждого проваливается, они убираются из балансировки — сервис отдаёт `503`/не принимает новый трафик на время недоступности БД, но как только БД восстанавливается, readiness снова проходит **без рестарта** — под мгновенно возвращается в ротацию, без потраченного времени на повторный полный старт процесса.

## Что спрашивают на собеседовании

1. **Liveness vs readiness — что будет, если в liveness проверять коннект к БД?** — при недоступности БД liveness проваливается одновременно у всех подов, Kubernetes рестартует весь флот разом — рестарт не чинит недоступность БД, зато на время рестарта сервис теряет всю ёмкость целиком, вместо корректной временной деградации через readiness.
2. **В чём принципиальная разница реакции на провал liveness и провал readiness?** — провал liveness перезапускает процесс (для случаев, когда нужен именно рестарт — deadlock, залипание); провал readiness убирает под из балансировки без рестарта (для случаев временной неготовности — недоступная зависимость).
3. **Зачем нужна startup probe, если есть liveness с настраиваемым `initialDelaySeconds`?** — для приложений с непредсказуемо долгим/медленным стартом; пока startup probe не прошла, liveness/readiness вообще не запускаются — не нужно жертвовать чувствительностью liveness к реальным зависаниям ради щедрого допуска на старт.
4. **Как readiness должна координироваться с graceful shutdown?** — под должен начать проваливать readiness до фактического начала закрытия соединений, чтобы балансировщик успел перестать слать новый трафик прежде, чем процесс реально начнёт останавливаться.
5. **Достаточно ли просто завести два разных probe-объекта в манифесте, чтобы разделить liveness и readiness правильно?** — нет, если оба указывают на один и тот же хендлер, проверяющий всё подряд включая БД — нужны структурно разные обработчики с разной семантикой проверки, а не просто два разных URL с одинаковой логикой внутри.
